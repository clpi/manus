# GAP-058 — `temps` is one map for two register files, disambiguated by the reader

**Status:** OPEN · **Filed:** 2026-08-08 · **Severity:** latent SILENT WRONG ANSWER
**Owner file:** `src/native_backend.zig`
**Blocks:** raising `fp_value_reg_count` above 8, which blocks `examples/mandelbrot.duo`

This is the root cause under [[GAP-057]], found by reducing mandelbrot to
thirteen lines and reading the machine code. It is currently masked by a
refusal, so nothing miscompiles today — but the mask is a register-count
constant, and the next person to raise it gets an infinite loop.

## The minimal repro

Not reachable at `fp_value_reg_count = 8` (it refuses with DNB003). Set the
constant to 15 in `src/native_backend.zig` and it compiles and HANGS:

```duo
mandel(cx: f64, cy: f64): i64
    x: f64 = 0.0
    y: f64 = 0.0
    i: i64 = 0
    while i < 100
        x2: f64 = x * x
        y2: f64 = y * y
        if x2 + y2 > 4.0 return i end
        y = 2.0 * x * y + cy
        x = x2 - y2 + cx
        i += 1
    end
    100
end

main(): i64
    return mandel(0.5, 0.5)
end
```

`--backend=c` returns 5. `--backend=direct` never terminates. No print, no
nested loops, no records — this is a much smaller handle than mandelbrot.

## What the code actually says

`--emit asm`, and the loop condition is the giveaway. `i` is an i64 and lives in
**x10**:

```asm
    mov   x9, #100
    scvtf d18, x9        ; 100 converted to a DOUBLE
    fcmp  d10, d18       ; compares d10 — x10's NUMBER, read as an FP register
    cset  x9, lt
```

and the body does the same thing in reverse:

```asm
    fmul d19, d16, d16   ; x2 -> d19
    mov  x9, x19         ; a GP move of an FP value
    fmul d20, d17, d17   ; y2 -> d20
    mov  x11, x20
    fadd d21, d9, d11    ; reads d9/d11; should be d19/d20
```

## Two defects, and the second is the structural one

**1. An INTEGER comparison inside a float kernel is lowered as a FLOAT
comparison.** `i < 100` has integer operands. The `.binop` arm's
`else if (self.cur_func_float)` branch treats any comparison as FP because the
FUNCTION is a float kernel. This is the same confusion fixed on the return side
in 65b605c: `cur_func_float` is `is_float_kernel`, computed by
`f64AbiParamSlots` from PARAMETERS, and it keeps being read as a property of an
expression.

The arm cannot simply be deleted. Its comment records why it exists:
`zx*zx + zy*zy < 4.0` has FLOAT operands but is not typed `.f64` (the type is
the comparison's boolean result), so it reached the arm and was refused. So the
arm is right for float operands and wrong for integer ones, and `ins.ty` cannot
tell them apart.

**2. `temps` is a single `AutoHashMapUnmanaged(u32, u5)` shared by both register
files.** Nothing records whether a temp lives in a `d` or an `x`; the CONSUMER
decides by calling `evalDnirValue` or `evalDnirValueFp`. An existing comment
even defends this ("looks like a register-space confusion and is not... a
comparison's consumer reads an integer").

It worked only by numeric accident: GP values were allocated from x9-x28 and FP
values from d0-d7, so a register number implied its file. **a3ad3ec moved FP
values to d16-d30 to get them out of the argument-staging range, and d16-d30
overlaps x9-x28.** The accident is gone. Defect 1 was always a bug; defect 2 is
what makes it produce a plausible register number instead of an obvious crash.

## Why nothing is wrong today

`fp_value_reg_count = 8` keeps the pool small enough that these programs still
exhaust it and get an honest DNB003. That is the entire safety margin. The
constant is a mask over a miscompiler, not a capacity decision — the comment on
it says so.

## The fix

Give temps a register FILE, not just a number. Either a parallel
`fp_temps: AutoHashMapUnmanaged(u32, void)` marking FP-resident temps, or make
the map value a tagged `{ file, reg }`. Then:

- the `cur_func_float` comparison arm asks whether its OPERANDS are FP-resident
  instead of asking what kind of function it is in;
- `evalDnirValue` on an FP-resident temp becomes an assertion failure instead of
  a silent GP move of the wrong register.

Producers to mark: the two f64 `.binop` arms, `.fp_mov_arg`, f64 parameter
homing, f64 call results, and `load_local` of an f64 slot.

Only after that does raising `fp_value_reg_count` mean anything.

## Verification that must accompany the fix

The repro above returning **5** on both backends, plus `zig build abi-matrix`
still at 0 wrong, plus the corpus differential still at 86/2. And the constant
raised in the same commit — if it is not raised, the fix is untested, because at
8 registers none of these programs compile.
