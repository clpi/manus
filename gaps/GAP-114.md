# GAP-114 — an unannotated binding makes `s:len()` answer 0, and `s:sub(1, s:len() - 1)` silently returns the WHOLE string

**Status:** OPEN · **Filed:** 2026-08-09
**Law:** §3 MEASUREMENT HONESTY (*"Verify by VALUE, never by 'it compiled'"*) ·
§0.8 (`s:sub(i,j)` is the canonical form this defect attacks)
**Found by:** gaps/GAP-076.md, while trimming a captured path

## The defect

```
raw = std.proc.capture("printf %s /tmp/xyz")     -- NO annotation
raw:sub(1, raw:len() - 1)                        -- answers "/tmp/xyz", NOT "/tmp/xy"
```

Add the annotation and it is correct:

```
raw: str = std.proc.capture("printf %s /tmp/xyz")
raw:sub(1, raw:len() - 1)                        -- answers "/tmp/xy"
```

## Why it is silent, which is the whole problem

Codegen emits `lua_str_buf_len_i64(raw)` against a value that is still BOXED.
It answers **0**. So `raw:len() - 1` is `-1`, and `sub(1, -1)` is Lua for
*"the whole string"* — a perfectly ordinary, documented, non-error result.

There is:

- no compile error
- no runtime error
- no diagnostic
- no wrong TYPE — the answer is a string, of plausible length, differing from
  the correct answer by exactly one trailing character

The generated C is *visibly correct* — `lua_str_sub(__self, 1, len - 1)` with
the `VAL_STRING` fast path and a table-dispatch fallback, exactly as written.
Reading the C confirms the call and hides the defect, because the bug is in
what `lua_str_buf_len_i64` returns for a box, not in the shape of the call.

## Reproduction, both directions

```
-- CONTROL (works): the compiler knows it is a str
s = "hello\n"
s:len()                  -- 6
s:sub(1, s:len() - 1)    -- "hello"

-- DEFECT: the value arrives boxed from a call
raw = std.proc.capture("printf %s /tmp/xyz")
raw:len()                -- 0     <- the bug
raw:sub(1, raw:len()-1)  -- "/tmp/xyz"
```

The control is what makes this readable: the identical expression is correct
on a literal and wrong on a call result, so this is not "`:len` is broken" —
it is **boxed values do not reach the string-length intrinsic.**

## Where it was found and what it nearly shipped

`tools/mcp/shared.id`, trimming the trailing newline off
`std.proc.capture`'s answer to build the shared gap-reservation ledger path.
Untrimmed, the path became:

```
<repo>/.git
/idol-gapalloc
```

— one path with a newline in the MIDDLE. Every worktree would have agreed on
it, `mkdir` would have created a directory whose name ends in `\n`, and the
allocator **would have kept working and stayed wrong**. It was caught only by
dumping the bytes with `od -c`; a line-oriented `grep` over the gate's own
output hides it perfectly, and did, for two runs.

`str_trim` (`tools/mcp/shared.id:686`) survives the same hazard for the
same reason — its parameter is declared `s: str`, so `#s` and `string.byte`
see a real string. That is luck of style, not a guard.

## Why this is worse than an ordinary miscompile

Every other member of this class the repo has caught — gap[056] argument
classification, gap[058] register files, the f64-in-GP-register bug — produces
a wrong NUMBER or a crash. This one produces a **plausible string**, one
character longer than intended, from the canonical spelling §0.8 tells
everyone to use. `duo check` passes. The C reads correctly. Only a byte dump
convicts it.

## What closes this

1. `lua_str_buf_len_i64` (or the `:len()` lowering) must handle a boxed
   `VAL_STRING`, or the lowering must not select the buffer intrinsic for a
   value it cannot prove unboxed.
2. Failing that, **`sub` with a computed `j` must not silently reinterpret a
   negative `j` as Lua's from-the-end index** when the negative came from a
   length that answered 0. A `j` derived from a length is never meant to be a
   from-the-end index.
3. A fixture asserting `capture(...):len()` **by value**, not by shape — §3's
   rule, and the only thing that would have caught this.

## Trap for whoever takes it

Do not probe with `print`. `print` takes anything and renders a
newline-containing path across two lines that look like ordinary output.
Assert the LENGTH, or dump bytes.
