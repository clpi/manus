## The defect

```
raw = std.proc.capture("printf %s /tmp/xyz")     -- NO annotation
raw:sub(1, raw:len() - 1)                        -- answers "/tmp/xyz", NOT "/tmp/xy"
```

| # | directive |
|---|---|
| 1 | Add the annotation and it is correct: |

```
raw: str = std.proc.capture("printf %s /tmp/xyz")
raw:sub(1, raw:len() - 1)                        -- answers "/tmp/xy"
```

## Why it is silent, which is the whole problem

| # | directive |
|---|---|
| 1 | Codegen emits `lua_str_buf_len_i64(raw)` against a value that is still BOXED. |
| 2 | It answers **0**. |
| 3 | So `raw:len() - 1` is `-1`, and `sub(1, -1)` is Lua for *"the whole string"* — a perfectly ordinary, documented, non-error result. |

| # | directive |
|---|---|
| 1 | There is: |

- no compile error
- no runtime error
- no diagnostic
- no wrong TYPE — the answer is a string, of plausible length, differing from
  the correct answer by exactly one trailing character

| # | directive |
|---|---|
| 1 | The generated C is *visibly correct* — `lua_str_sub(__self, 1, len - 1)` with the `VAL_STRING` fast path and a table-dispatch fallback, exactly as written. |
| 2 | Reading the C confirms the call and hides the defect, because the bug is in what `lua_str_buf_len_i64` returns for a box, not in the shape of the call. |

## Reproduction, both directions

```
-- CONTROL (works): the compiler knows it is a str
s = "hello\n"
s:len()                  -- 6
s:sub(1, s:len() - 1)    -- "hello"

-- DEFECT: the value arrives boxed from a call
raw = std.proc.capture("printf %s /tmp/xyz")
raw:len()                -- 0     <- the bug
raw:sub(1, raw:len()-1)  -- "/tmp/xyz"
```

| # | directive |
|---|---|
| 1 | The control is what makes this readable: the identical expression is correct on a literal and wrong on a call result, so this is not "`:len` is broken" — it is **boxed values do not reach the string-length intrinsic.** |

## What closes this

1. `lua_str_buf_len_i64` (or the `:len()` lowering) must handle a boxed
   `VAL_STRING`, or the lowering must not select the buffer intrinsic for a
   value it cannot prove unboxed.
2. Failing that, **`sub` with a computed `j` must not silently reinterpret a
   negative `j` as Lua's from-the-end index** when the negative came from a
   length that answered 0. A `j` derived from a length is never meant to be a
   from-the-end index.
3. A fixture asserting `capture(...):len()` **by value**, not by shape — §3's
   rule, and the only thing that would have caught this.
