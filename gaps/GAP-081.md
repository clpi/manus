# GAP-081 — canonical orientation is 1647 to 1 against, and half of it cannot compile

**Status:** STEPS 1-3 CLOSED, STEP 4 OPEN · **Filed:** 2026-08-08 ·
**Repaired:** 2026-08-08
**Law:** Pass 121 Amendment §1 FACE-SUBJECT · §9 (`to` is the archetypal
orientation fixture) · §16 IDIOM-TOTAL · §17 (canonicalization performs the
repair) · §31 (canonical source is a fixed point)

## The measurement

Pass 121 §9 makes the orientation law concrete: `n:to(str)` is canonical,
`to(str)(n)` is not. Measured over tracked `.duo`:

| form | sites | files |
|---|---:|---:|
| `to(x)(y)` — operation-first immediate conversion | **1647** | 250 |
| `y:to(x)` — canonical subject-first | **1** | 1 |

The canonical form appears **once in the entire tree**. This is not drift at the
margin; the corpus is written in the noncanonical orientation essentially
without exception, and the one canonical site is the exception.

## Before rewriting anything: does the canonical form work?

Half of it does. Measured by VALUE, not by inspection — which is the whole point
of checking first, because a canonicalizer that rewrites 1647 sites into a form
the compiler cannot lower would take the tree down.

| conversion | operation-first | subject-first |
|---|---|---|
| `i64 -> str` | `42` | `42` |
| `f64 -> str` | — | `2.5` |
| `str -> i64` (typed `s: str`) | **FAIL** | **FAIL** |

`to(str)` canonicalizes cleanly in **both** faces. `to(i64)` fails in **both**
faces with `error: call to undeclared function 'lua_to_num'`, so it is NOT an
orientation defect — it is a missing conversion, and orientation is innocent.

One further asymmetry, worth recording because it will mislead someone:
`to(i64)(std.proc.capture(cmd))` — operation-first over an *untyped call result*
— compiles and runs, while the subject-first spelling of the same expression
boxes into `lua_invoke` and fails to build. So the two faces are not
interchangeable today even where one of them works.

## What this means for the canonicalizer

Pass 121 §17 says canonicalization performs the repair mechanically. It can, for
part of the corpus, and must decline the rest:

- **`to(str)` sites: REWRITE.** Both faces lower identically; the rewrite is
  semantics-preserving and provable by value.
- **`to(i64)` sites: DO NOT TOUCH** until `lua_to_num` exists. Rewriting them
  changes a program that fails to build into a different program that fails to
  build, which is churn that looks like progress.
- Every rewrite emits the §18 witness (relation, subject, level, graph identity
  unchanged) so the change is justified rather than trusted.

## The honest reading of 1647:1

It is tempting to read this as 250 files' worth of bad taste. It is at least
partly **capability**: the canonical spelling of the most common conversion
direction in this tree (`str -> i64`, every parse of a number) does not compile
in either face. Authors wrote what worked.

That is the sharper finding, and it inverts the repair order. **Fix the
conversion before enforcing the orientation** — otherwise the gate demands a
form the compiler cannot produce, and the first agent to hit it will conclude
the law is advisory.

## Cited site, left noncanonical on purpose

`scripts/bootstrap_scan.duo` keeps `to(i64)(std.proc.capture(cmd))` with a
comment naming this gap. It is the only spelling that builds. Converting it
would be the exact mistake this gap exists to prevent.

## Fix, in order

1. `lua_to_num` — make `str -> i64` build in both faces. Fixture asserts the
   VALUE (`"17":to(i64) == 17`), both backends, since a conversion that compiles
   and answers 0 is the failure mode `tonumber` already has in this tree.
2. A `convert` row in `audit100` counting operation-first immediate conversions,
   ratcheting DOWN from 1647.
3. The canonicalizer rewrite for `to(str)`, witnessed per §18.
4. Only then the `to(i64)` sites.

---

## What landed, 2026-08-08 — steps 1, 2 and 3

**STEP 1, `str -> i64` BUILDS AND ANSWERS.** The edge emitted `lua_to_num`,
which a full-native module never declares. It now emits `duo_str_to_i64`, a
plain-C parse in the prelude beside the `duo_str_from_*` family that already
handled the other direction. Measured, both faces, both lowerings:

| probe | before | after |
|---|---|---|
| `to(i64)(s)`, typed `s: str` | did not build | `17` |
| `s:to(i64)`, typed `s: str` | did not build | `17` |
| `to(i64)(std.proc.capture(…))` | `17` | `17` |
| `std.proc.capture(…):to(i64)` | did not build | `17` |
| `"abc":to(i64)` | did not build (boxed: `0`) | FAULTS, exit 134, names the input |
| `"12x":to(i64)` | did not build (boxed: `12`) | FAULTS on the trailing text |
| `"0":to(i64)` | did not build | `0` |
| `"9007199254740993":to(i64)` | did not build (boxed: `…992`) | `…993`, all 64 bits |

`zig build convert-proof` asserts every row above, and the exit codes, so the
refusal can never quietly become an answer again.

**THE ASYMMETRY IS CLOSED TOO.** `x:to(i64)` over an untyped receiver fell past
the receiver-first normalization — which was gated on a SCALAR receiver — into
ordinary member dispatch, and did not build. It now reaches the conversion edge
when the target names a primitive descriptor, the program has not bound `to`,
and the receiver carries no record alias declaring its own `to`. The two faces
now emit BYTE-IDENTICAL C for both the typed and the untyped receiver, which is
what makes step 3 provable rather than hopeful.

**A THIRD MEMBER OF THE SAME CLASS**, found while writing the canonicalizer and
fixed with it: `s:sub(a, b)` already returns `const char*`, but the string
comparison path did not know that for a `.method_call` and wrapped it in
`lua_to_str`. Same shape, same cause — the operation-first spelling of a fact
was taught to the emitter and the receiver spelling was not. When the two faces
disagree, authors write the one that builds, and the census reads as taste.

**STEP 2, the `convert` row.** `audit100` gained one row counting
operation-first immediate conversions, with controls that require it to SEE the
noncanonical form and DECLINE both `x:to(i64)` and the leveled `xs:to(seq)(e)`.
Its baseline is **949**, which is not 1647 and the difference is the gate rather
than the tree: this gap counted occurrences over every tracked `.duo`; the row
counts LINES over the canonical partition with comments and string bodies
stripped. Both numbers were measured at the same commit — 1640 occurrences
tree-wide by the row's own regex, 949 canonical lines through the gate.

**STEP 3, the rewrite.** `scripts/convert_canon.duo`, dry-run by default,
rewrote **720 `to(str)` sites across 118 files** and emitted a §18 witness for
each. The row fell **949 -> 325** and its budget was lowered by the same amount
in the same commit. It declines two things and says so: a subject richer than a
name or a field walk (`to(str)(a + b)` needs a paren, and adding one is a
judgement about precedence), and any line where a `to(str)(` hides inside a
STRING LITERAL — 6 of those, 4 in the otherwise-rewritable shape, i.e. a
substitution that did not look would have corrupted four literals and nothing
would have failed to build.

**STEP 4 IS STILL OPEN.** The `to(i64)`/`to(f64)` sites are not rewritten. The
conversion builds now and is fixtured, but the ordering in this gap was the
point: the fixture should hold across a release before 170 more sites are moved
onto it. `scripts/bootstrap_scan.duo` is converted and its gap comment deleted,
as are the two numerics fixtures that had been recording the defect as measured
behaviour — those four were the sites explicitly waiting on step 1.

**T-12 IS ONLY PARTLY REPAIRED and `docs/numerics_and_text.md` says so.** B-14
wants an unconsumed failure to DIAGNOSE and route; this FAULTS. Teardown is
admitted by the boring rulings and is categorically better than a silent `0`,
but it is not a routed `i64 | error` and will not be until a failure position
has somewhere to go at a conversion edge.
