# GAP-033 — `str + int` is pointer arithmetic, silently yielding a substring

**Status:** open · **Severity:** silent wrong values · **Filed:** 2026-08-07
**Violates:** STRATA-OP ("no registered edge ⇒ diagnostic, never coercion"),
B-5 (`..` is strict; no coercion), Pass 94 §1 ("bare positions never coerce")
**Sites:** `scripts/census/contract.duo` (P94-9)

## The defect

Adding an integer to a string produces **a substring**, with no diagnostic:

```duo
main(): void
    a = "42"
    c = "abcdef"
    print(a + 1)      -- 2
    print("7" + 1)    -- (empty)
    print(c + 1)      -- bcdef
    print(c + 3)      -- def
end
```

Strings lower to raw `const char *`, and `+` becomes **C pointer arithmetic**.
`a + 1` advances the pointer one byte and prints the tail. The sibling case
proves the lowering directly:

```duo
    print(a + a)
```
```
error: invalid operands to binary expression ('const char *' and 'const char *')
    printf("%s\n", (a + a));
```

## Why this is the worst class of failure

`"42" + 1` evaluates to **`"2"`** — a string that *looks like a number*. Feed it
anywhere numeric and the program continues with a plausible, wrong value. The
`"7" + 1` case is worse still: it yields the empty string, which converts to 0.

There is no diagnostic at any layer. The Duo front end accepts it, the C backend
emits valid pointer arithmetic, and the runtime prints a tail. A reader
reviewing `total = count + 1` cannot see the defect at the call site, because
the bug lives in the *type* of `count`, which may be several functions away.

Compare the failure modes already recorded here: LV-4 dropped an element,
STR-1 printed brace text, GAP-031 bound the wrong function. This one silently
rewrites arithmetic into string slicing.

## What the canon requires instead

STRATA-OP is explicit — *comma stratifies, operator selects*, and where no edge
is registered the result is **a diagnostic, never a coercion**. There is no
`add(str, i64)` edge, so `"42" + 1` must not compile. B-5 already settled the
adjacent case (`..` is strict, string operands only, repair = interpolation);
`+` needs the same strictness from the other side.

Pass 94 §1 states the guardrail as load-bearing while introducing
contract-directed realization: *bare positions never coerce — no declared shape,
no conversion, ever*. This site is a bare position and it converts, so the
guardrail is not merely unimplemented, it is contradicted.

## The fix

Reject `+` (and the other arithmetic roots) where either operand's shape is
`str`, with the repair named in the diagnostic:

- concatenation → `"{a}{b}"` (B-5's own repair)
- numeric intent → `to(i64)(a) + 1`, which works today and tolerates surrounding
  whitespace (measured, P94-5)
- substring intent → `s[i, j]`, the half-open view form (B-1)

All three destinations already exist, so this is a front-end rejection with no
new surface required.
