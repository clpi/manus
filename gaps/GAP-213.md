# GAP-213 — a literally false branch emits its comparison and its body

**Status:** CLOSED · **Filed:** !2026-08-22T02:40:00Z
**Priority:** P1 · **Kind:** perf_gap
**Filed by:** claude-gap145
**Files:** src/dnir_lower.zig,src/native_backend.zig

## Measured at `0ed88cfb`

```id
main: i64 = ()
    n: i64 = 0
    if 3 > 100
        n = n + 7
    n
```

Answers `0`, correctly. `_main` is **eleven instructions**:

```
mov  x9,  #0x0
mov  x10, x9
mov  x9,  #0x7
add  x11, x10, x9      <- the dead body's arithmetic
mov  x9,  #0x3
mov  x12, #0x64
cmp  x9,  x12          <- a comparison of two literals
csel x11, x11, x10, gt
mov  x10, x11
mov  x0,  x10
ret
```

The live twin `if 3 < 100` is **also eleven instructions** — the two differ only
in the condition code. The answer is `mov x0, #0`.

## What this is and is not

It is **not** an if-conversion gap: the `csel` shows if-conversion already
fires. It is a **constant-condition** gap — nothing folds a comparison whose
two operands are literals, so neither arm is ever proven dead.

It is also not the comptime folder's job here, and that is the interesting
part: `comptime.foldRelationBody` did not fold this body at all, even though
every value in it is a literal. Whichever of the two is meant to own it, **no
producer currently answers "this condition is constant"** where realization can
read it.

## The class

This is the same shape as the rest of the session's findings, in the
performance register rather than the correctness one: a fact that plainly
exists in the program (`3 > 100` is decidable at lift) has no producer, so the
backend emits both arms because nothing told it not to.

The demand census measured the sibling cases at the same time and they are all
open: unused record fields survive (`mul x11, x0, #7919` for an unread field is
emitted), an unread application result still runs (`k: i64 = work(300000000)`
with `k` never read costs 0.0900s against a 0.0035s baseline), and an unread
interpolation still emits `malloc` plus two `snprintf`.

## Landed

`constConditionTruth` in `dnir_lower.zig` answers the truth of a comparison
whose two operands are both literal, and the `.if_stmt` arm lowers only the arm
that runs. **Comparisons only** — an integer is not a truth value in this
language, and `null` means *"not known constant"*, never *"false"*, so an
undecided condition emits both arms exactly as before.

Bounded deliberately to a chainless `if`. An `elseif` chain whose first
condition is constant-false still has runtime conditions after it, so folding
it means re-forming the chain rather than choosing an arm — and re-forming is
where a rewrite starts moving statements the graph holds pointers into, the
cost the file-scope closure work already paid once. A chain is left whole and
measured byte-identical.

| control | HEAD | landed |
| --- | --- | --- |
| `if 3 > 100` | exit 0, **11** instructions | exit 0, **4** |
| `if 3 < 100` — live twin | exit 7, **11** | exit 7, **6** |
| `if 3 > 100 … else` | exit 5, **13** | exit 5, **6** |
| runtime condition `if k > 100` | exit 0 | exit 0, **byte-identical asm** |
| `elseif` chain — fold declines | exit 5 | exit 5, **byte-identical asm** |

`zig build unit-test`: **1673 pass, 8 fail, 0 crash / 1681** — identical to
baseline, same eight names.

538-example corpus differential on program output and exit status, compiled in
an isolated directory: **172 both compiled and ran, 0 genuine differences.**
One row flagged, `examples/shc/cwd.id`, which prints its working directory and
was run from two different ones; byte-identical from a single cwd. That
accidental catch is the sweep's positive control — it can move.

A first differential attempt hashed the compiler's own progress line, which
carries a per-run timing, and reported 213 of 538 differing. Recorded because
the failure mode is silent: it produces a false positive on every row and looks
like a catastrophic regression.

## Acceptance

`if <literal> <cmp> <literal>` emits neither the comparison nor the dead arm,
with a positive control that the live arm still emits and answers, and a
control that a **runtime** condition is unaffected.
