## The spec

Pass 100 **B-4**: *"division operand-selected: `i64/i64` truncates (overflow
regime); any float ⇒ float; `%` matches; no `//`."*

## What actually happens

```duo
a: i64 = 7
b: i64 = 2
q: i64 = a / b
```

```
error: type mismatch: variable 'q' declared as 'i64',
       but initializer has type 'f64'
```

**`i64 / i64` is typed `f64`.** Sema contradicts B-4 directly, and the error
message states it plainly. Everything below follows from that one fact.

## The consequences, measured

Each backend resolves the type mismatch its own way, so they disagree:

```
print(a / b)              --backend=c              --backend=direct
7 / 2                     4615063718147915776      3
100 / 7                   4624231760246491429      14
-7 / 2                    -4608308318706860032     -3
9007199254740993 / 1      4845873199050653696      9007199254740993
9007199254740993 / 3      4838367199671702869      3002399751580331
7 / 0                     9218868437227405312      (see gap[064])
```

`4615063718147915776` is `0x4008000000000000` — the IEEE double `3.0`. The C
backend computes the quotient as a double and then **prints its bit pattern** as
an integer. `9218868437227405312` is `0x7FF0000000000000`, `+inf`. This is the
same defect gap[064] recorded for `7/0`; the root cause is here.

**The direct backend is CORRECT on every row** — it truncates, which is what
B-4 says.

Modulus and shifts disagree too, and belong in the same family:

```
-7 % 2      c=1    direct=-1        C is FLOORED, direct is TRUNCATED
7 % -2      c=-1   direct=1
-8 >> 1     c=-4   direct=9223372036854775804    arithmetic vs logical
-1 >> 63    c=-1   direct=1
```

B-4 says `%` MATCHES division. Under `--backend=c` division truncates toward
zero (via double) while `lua_imod_i64` floors, so
**`(a/b)*b + (a%b) == a` is false for every negative operand** on the C path.

## Why this is worse than an ordinary miscompilation

Pass 103 §5 licenses foreign compilers as **CI ORACLES** — that is the entire
justification for keeping the C backend after NO FOREIGN WAIST. An oracle that
answers `4615063718147915776` for `7 / 2` is not an oracle for integer
arithmetic.

Every gate built on that comparison inherits the hole:

- the corpus differential (87 agree / 2 differ) — green, because no corpus
  program prints an `i64/i64` quotient;
- `abi-matrix` — its grid varies parameter signature, return type and
  comparison, and has **no arithmetic axis at all**;
- any "beats C" benchmark row involving integer division is measuring a C
  program the emitter got wrong.

This is the fourth green-differential-over-a-real-defect tonight, and the first
where **the reference side is the wrong one**.

## Why nobody hit it

`q: i64 = a / b` is a *type error*, so the natural spelling fails loudly and
gets rewritten. What compiles is `print(a / b)` and untyped bindings — which is
exactly where the bit pattern escapes silently. The loud failure hides the quiet
one.

## Fix direction

The fix is in **sema**, not in either backend: `i64 / i64` must have type `i64`.
Both backends are then consistent with B-4 and with each other, and the C
emitter stops needing a double at all.

**Blast radius is real: 439 tracked `.id` files contain a `/`.** Any file
currently relying on `/` yielding a float — `(a + b) / 2` used as a float, ratio
computations on integer inputs — changes meaning. That is a corpus migration
with a mechanical repair (`to(f64)(a) / to(f64)(b)`, or make one operand a float
literal), and it must be measured before it is done, not after.

Do NOT "fix" this by teaching the C backend to print the double as an integer.
That preserves the type error and makes the two backends agree on the wrong
answer, which is strictly worse than disagreeing.

## Verification for the fix

```
7 / 2 → 3 · 100 / 7 → 14 · -7 / 2 → -3        both backends
9007199254740993 / 1 → 9007199254740993       both backends
(a/b)*b + (a%b) == a for a,b ∈ {±7, ±2, ±100} both backends
q: i64 = a / b                                 compiles
```

Then add an **arithmetic axis to `abi-matrix`** — operand signs × widths ×
{div, mod, shift} × boundary values — so the class is covered rather than these
six rows. The lesson from gap[056] and gap[063] repeating a third time: a
generated grid only covers the axes someone thought to generate.
