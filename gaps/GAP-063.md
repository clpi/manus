# GAP-063 — dense table filled and summed in a loop: direct answers 1 for 6

**Status:** OPEN · **Filed:** 2026-08-08 · **Severity:** SILENT WRONG ANSWER
**Blocks:** the "better than C" claim on any table-summing workload

Not a bail. `ok compile`, runs, exits 0, prints the wrong number.

## Repro — nine lines, and an entirely ordinary shape

```duo
main(): i64
    t = { 0 }
    s: i64 = 0
    i: i64 = 1
    while i <= 3
        t[i] = i
        s = s + t[i]
        i = i + 1
    end
    print(s)
    return 0
end
```

```
--backend=c        prints 6      correct
--backend=direct   prints 1      WRONG
```

Scaled up (`t[i] = i * i`, n = 10): C prints **385**, direct prints **1**.

## Bisected

```
no table at all — `s = s + i * i` in the same loop     c 385   direct 385   OK
table filled, then read once outside the loop (t[3])   c 9     direct BAIL  honest
table filled AND summed inside the loop                c 6     direct 1     WRONG
```

So arithmetic is fine, and reading a table element outside the loop is honestly
refused. The defect is specific to **reading back an element written earlier in
the same loop iteration**. `1` is what the sum would be if `t[i]` read a
constant 1, or if only the first iteration contributed.

## Why no gate caught it

The corpus differential is at 87 agree / 2 differ and green. **No corpus program
fills a dense table and sums it in the same loop.** This is the third time
tonight that a green differential has covered a real miscompilation, after
gap[056] (f64 arguments in GP registers, the shape "f64 params + comparison +
non-f64 return") and the dead-code-after-non-tail-`if` defect.

`zig build abi-matrix` does not cover it either: that grid generates CALL
shapes — parameter signature x return type x comparison — and has no table axis.
**A generated grid only covers the axes someone thought to generate.** The
lesson from gap[056] is repeating one level over: extend the matrix with a table
axis (fill / read-back / sum, inside and outside the loop) rather than adding
one fixture for this one program.

## Adjacent defect, found on the way

`t = {}` — an EMPTY table literal — then `t[i] = i * 3` fails to compile under
the C backend:

```
error: incompatible integer to pointer conversion assigning to 'const char *'
       from 'int64_t'      t_items[t_len++] = (i * 3);
error: call to undeclared function 'lua_table_get_i64_num'
```

An empty table literal infers a STRING element type, so the first integer store
is a type error in the emitted C. `t = { 0 }` and `t: table = {}` both work.
That is a separate bug from the one above and it is in the C backend, not the
direct one — but it is why the first three probes for this gap reported "does
not compile" and nearly sent the investigation the wrong way.

Also: `t: {i64} = {}` reports no C errors and produces NO BINARY — a silent
failure where the compile claims success and emits nothing.

## Verification for the fix

The nine-line repro printing **6** on both backends, and the n=10 square version
printing **385** on both. Print the value; do NOT return it — exit codes are
8-bit and 385 wraps to 129, which looks like a plausible wrong answer and is
actually correct. That trap cost a probe here.

Then extend `scripts/abi_matrix.duo` with the table axis so the class is covered
rather than the instance.
