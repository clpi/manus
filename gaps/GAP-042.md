# GAP-042 — the compiler tokenized its ENTRY POINT with the Duo lexer and every `req`-ed module with the host one

**Status:** closed (both halves landed 2026-08-08) · **Filed:** 2026-08-08
**Cited at:** `src/codegen.zig` (`routeEmbedThroughDuoLexer`),
`src/duo_lexer_dispatch.zig` (`route`), `lib/std/compiler/lexer.duo:389`
(`_int_of`, hex branch).

(Took 042 after checking `gaps/` in this worktree and in every sibling under
`.claude/worktrees/`; 039, 040 and 041 were already filed by other sessions.)

## What was wrong

`duo_lexer_bridge.tokenizeAuthority()` has returned `.duo_native` since
2026-08-07, and the claim built on it — "the compiler tokenizes itself with the
Duo lexer" — was read as whole-program. It was not. Exactly one caller
consulted the authority: `main.zig`'s `routeThroughDuoLexer`, reached from
`parse_and_check` and `do_fmt`. Those see the **entry point only**.

Every module a program `req`s is re-read and re-scanned inside `codegen.zig`,
at five sites that built their own `Lexer` and never asked who the authority
was:

| site | function | role |
|---|---|---|
| `codegen.zig:3365` | `req_deps_are_native_direct` | native-embed eligibility probe |
| `codegen.zig:21072` | `emit_required_modules` | emits the module |
| `codegen.zig:21312` | `module_path_allows_full_native_embed` | eligibility probe |
| `codegen.zig:21363` | (embed dependency walk) | eligibility probe |
| `codegen.zig:22358` | `emit_embedded_module` | emits the module |

So one compilation ran **two scanners**: `lib/std/compiler/lexer.duo` on the
entry point and `src/lexer.zig` on its dependencies. That is the shape that
hides a divergence — the driver and the embed decision can disagree about the
same bytes and nothing reports it, because neither is compared to the other.

Measured, not assumed: with a probe printing `path` and `lex.isDuoBacked()`,
compiling `examples/pass16_lexer_embed_proof.duo` reached
`routeEmbedThroughDuoLexer` **93 times**. All 93 were host-scanned before.

## What it was hiding

Routing those 93 sites through the Duo lexer did not produce a divergence. It
produced an **abort**:

```
thread 780839 panic: signed integer overflow: 576460752303423488 * 16 cannot
be represented in type 'int64_t'
  src/duo_lexer_tokenize.c:6505  std_compiler_lexer___int_of
  src/duo_lexer_tokenize.c:6642  std_compiler_lexer__read_num
```

`_int_of` in `lib/std/compiler/lexer.duo` has two accumulators. GAP-024 found
the signed-overflow trap in the **decimal** one and changed it to `u64`. The
**hex** one, twelve lines above, was left as `i64`. So any hex literal at or
above 2^63 was undefined behaviour that the generated C traps on, and the Duo
lexer killed the process instead of returning a token.

The tree contains three such literals — none of them exotic:

- `lib/std/heap.duo:193` — `0xcbf29ce484222325`, the FNV-1a offset basis
- `lib/std/heap.duo:205` — `0xFFFFFFFFFFFFFFFF`
- `lib/std/encoding/varint.duo:49`, `lib/std/ml/gguf.duo:108` — `0x8000000000000000`

### Why nothing caught it

Because of the first half of this gap. A compile driver lexes the file the user
named; it never lexes `lib/std/heap.duo`. The only path that would have is the
one that was still on the host scanner. The two bugs concealed each other: the
routing gap kept the overflow unreachable, and the overflow is what the routing
gap was protecting.

Six differentials and a 256-case corpus were green throughout. None contained a
hex literal above 2^63 — the same blindness GAP-021 had for `float_val`, in a
different field. **A differential proves agreement on the cases it holds, and
nothing about the ones it does not.**

## The fix

Two parts, and the first is load-bearing for the second:

1. `lib/std/compiler/lexer.duo:389` — hex accumulator `i64` → `u64`. Unsigned
   multiplication wraps rather than trapping, and `src/lexer.zig` already
   treats a hex literal as a **bit pattern** (it retries `parseInt(u64)` and
   bitcasts), so this is what makes the two lexers agree rather than a new
   convention. `src/duo_lexer_tokenize.c` regenerated from
   `lib/std/compiler/host.duo` — editing the `.duo` alone changes nothing,
   the compiler links the generated artifact.

2. `duo_lexer_dispatch.route` — the routing body moved out of `main.zig`, where
   it was a private helper, so codegen's five embed sites call the same entry.
   A Duo-side rejection declines the embed; only host-side OOM/sizing falls
   back, because those say nothing about the source.

## Proof

- By value, not by agreement: `0xcbf29ce484222325` lexes to `int_val ==
  -3750763034362895579`, which is its bit pattern as i64. Pinned in
  `duo_lexer_dispatch.zig`.
- Field-for-field differential against `src/lexer.zig` over all three tree
  literals plus `0x7FFFFFFFFFFFFFFF` (the boundary below) and small hex.
- `unit-test` 1246/1304 → 1248/1306 at the same HEAD: two tests added, both
  pass, failure and crash counts unchanged (54 / 4, pre-existing).
- `pass16-m1-smoke`, `agent-smoke`, `repo-hygiene` all exit 0, including
  `pass16_lexer_text_differential` and `pass16_lexer_fingerprint_differential`.

## What this leaves open

`src/lexer.zig` still cannot be retired (RL-02) — see the ledger entry for the
real blocker. This gap closes only the claim about WHICH sources the Duo lexer
tokenizes, which is now: all of them, in the C-backend compile path.
