# GAP-060 — a one-statement body silently un-declares the function

**Status:** OPEN · **Filed:** 2026-08-08 · **Severity:** SILENT LOSS OF A DECLARATION
**Owner file:** `src/parser.zig` (GR-001 bare-declaration disambiguation)

A bare function declaration whose body is a SINGLE statement is not declared.
No error, no warning. Calls to it do nothing, and the program exits 0.

## Repro

```duo
global s = req "std.script"

pass(msg: str)
    s.echo("OK: " .. msg)
end

fail2(msg: str, out: str)
    s.echo("FAIL: " .. msg)
    if string.len(out) > 0
        s.echo(out)
    end
end

main(): i64
    pass("one-line body")
    fail2("multi-line body", "")
    0
end
```

Prints only `FAIL: multi-line body`. Exit status **0**.

The two functions differ in nothing but body length. Both are bare declarations
with typed parameters and no return type; both call the same `s.echo`.

## What fixes it, and what does not

```
pass(msg: str)          silent
pass(msg: str): void    works
pass(msg: str): i64     STILL SILENT
```

The presence of a return type is not sufficient — `: i64` on a body with no
`return` stays broken. Worth knowing before someone repairs one of these by
annotating it with the wrong type and concludes the annotation did not help.

## Why this one mattered

`scripts/run_compile_fail_tests.duo` — the `zig build test` gate — declares
`pass(msg: str)` with a one-line body and `fail(msg, out)` with a multi-line
one, six lines apart. So the suite printed `FAIL:` rows and NEVER an `OK:` row.
It could report what broke and never what it proved. 37 assertions were in that
state, and a fixture that silently stopped running was indistinguishable from
one that passed.

That is the general shape of the harm: this defect is invisible in any function
called for its side effect, and side-effect functions are exactly what test
harnesses, loggers and reporters are made of.

## The rule being violated

A declaration must either declare or be refused. `end` closes something, and if
the parser cannot decide what `name(args)` followed by a block IS, it must say
so rather than pick the reading that discards the body.

GR-001 is a known ambiguity (a bare `name(...)` is either a call or a
declaration), but the recorded workaround — "needs at least one type
annotation" — is INCOMPLETE. All three forms above carry a typed parameter. The
real discriminator in the current implementation appears to be the return type
together with something about the body, and whatever it is, it is not stated
anywhere.

## Fix direction

Decide by SHAPE, not by size: `name(params) <block> end` at statement position
with any typed parameter is a declaration, whatever the block contains. If some
ambiguity genuinely remains, emit a diagnostic naming both readings. Never
silently take the reading that throws the body away.
