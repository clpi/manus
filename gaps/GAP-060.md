# GAP-060 — a one-statement body silently un-declares the function

**Status:** OPEN — RE-DIAGNOSED · **Filed:** 2026-08-08 · **Re-measured:** 2026-08-09
**Severity:** SILENT LOSS OF A STATEMENT (not of a declaration — see below)
**Owner file:** `src/codegen.zig` — **NOT** `src/parser.zig`, and not GR-001

## RE-MEASURED 2026-08-09 — reproduces, but the filed cause is wrong twice

The repro still fails exactly as filed, on `--backend=direct` AND
`--backend=c`: only `FAIL: multi-line body` prints, exit 0. It is NOT stale.
Everything this file says about WHY is.

### It is not the body length

A one-statement body is fine on its own:

```duo
one(msg: i64)          -- prints 11
    print(msg)
two(msg: i64)          -- prints 22 twice
    print(msg)
    print(msg)
```

Both work. Bisected one change at a time from the filed repro:

| body's single statement | result |
|---|---|
| `print("A" .. msg)` | **works** |
| `sh("A" .. msg)` — a LOCAL callable declared `: void` | **works** |
| `s.echo("A" .. msg)` — a `req`-module member declared `: void` | **SILENT** |
| `os.getenv("HOME")` — a `req`-module member returning a VALUE | **works** |

So the discriminator is **a VOID call through a `req`-module binding**, and
body length is a red herring — it only decides whether anything else survives.
With TWO statements, `s.echo("A")` then `s.echo("B")`, the first prints and
**the second does not**: it is the statement in TAIL position that is lost, and
a one-statement body is simply the case where the tail is the whole body.

### The declaration is not lost either — the BODY is emptied

Read out of the emitted C, which is where this stops being a guess:

```c
static lua_Value one(const char* msg) {
    return lua_val_nil();
}
```

Declared, defined, called — and the `s.echo(msg)` is gone. "Silently
un-declares the function" is the symptom seen from the call site; the mechanism
is that a void module call in tail position lowers to `return nil` and the call
itself is discarded.

### And `: void` does NOT fix it

The file states `pass(msg: str): void` works. Measured: it does not.

```
one(msg: str)        silent
one(msg: str): void  SILENT — the filed workaround does not hold
one(msg: str): i64   C compiler error
```

Anyone repairing a site by annotating it `: void` will believe they fixed it.

### What closes it

Same family as gap[102], one step further along. Tail resolution hands the
lowerer a `.tail_call` because the callee is a call; the lowerer emits it as a
returned value; the callee returns void, so the value — and the call with it —
is dropped. gap[102] fixed the half where the callee's void-ness is knowable
without types (`print`, the built-in floor in
`tail_result_demand.isVoidShapedCall`) and left the hook for the rest:
`installVoidOracle`.

**The repair is to install that oracle from whoever holds the `req` module's
declared return types** — `lookup_req_module_func_type` in `src/codegen.zig`
already answers exactly this question for the call it is about to emit. A
module member declared `: void` must be transparent in tail position, which
routes it down the path `print` already takes: `blockTailResultWithDemand`
returns null, no tail return is emitted, and the call lowers as the statement
it is. Filed rather than done because `src/codegen.zig` is another agent's file.

Regression fixture must assert BY VALUE that the effect HAPPENED — a body that
compiles proves nothing here, since the defect compiles cleanly and exits 0.

**Original filing follows, retained for the record.**
**Owner file:** `src/parser.zig` (GR-001 bare-declaration disambiguation)

A bare function declaration whose body is a SINGLE statement is not declared.
No error, no warning. Calls to it do nothing, and the program exits 0.

## Repro

```duo
global s = req "std.script"

pass(msg: str)
    s.echo("OK: " .. msg)
end

fail2(msg: str, out: str)
    s.echo("FAIL: " .. msg)
    if string.len(out) > 0
        s.echo(out)
    end
end

main(): i64
    pass("one-line body")
    fail2("multi-line body", "")
    0
end
```

Prints only `FAIL: multi-line body`. Exit status **0**.

The two functions differ in nothing but body length. Both are bare declarations
with typed parameters and no return type; both call the same `s.echo`.

## What fixes it, and what does not

```
pass(msg: str)          silent
pass(msg: str): void    works
pass(msg: str): i64     STILL SILENT
```

The presence of a return type is not sufficient — `: i64` on a body with no
`return` stays broken. Worth knowing before someone repairs one of these by
annotating it with the wrong type and concludes the annotation did not help.

## Why this one mattered

`scripts/run_compile_fail_tests.duo` — the `zig build test` gate — declares
`pass(msg: str)` with a one-line body and `fail(msg, out)` with a multi-line
one, six lines apart. So the suite printed `FAIL:` rows and NEVER an `OK:` row.
It could report what broke and never what it proved. 37 assertions were in that
state, and a fixture that silently stopped running was indistinguishable from
one that passed.

That is the general shape of the harm: this defect is invisible in any function
called for its side effect, and side-effect functions are exactly what test
harnesses, loggers and reporters are made of.

## The rule being violated

A declaration must either declare or be refused. `end` closes something, and if
the parser cannot decide what `name(args)` followed by a block IS, it must say
so rather than pick the reading that discards the body.

GR-001 is a known ambiguity (a bare `name(...)` is either a call or a
declaration), but the recorded workaround — "needs at least one type
annotation" — is INCOMPLETE. All three forms above carry a typed parameter. The
real discriminator in the current implementation appears to be the return type
together with something about the body, and whatever it is, it is not stated
anywhere.

## Fix direction

Decide by SHAPE, not by size: `name(params) <block> end` at statement position
with any typed parameter is a declaration, whatever the block contains. If some
ambiguity genuinely remains, emit a diagnostic naming both readings. Never
silently take the reading that throws the body away.
