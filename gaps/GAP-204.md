# GAP-204 — a positional table of text is not lowerable, so the benchmark harness cannot run

**Status:** OPEN · **Filed:** !2026-08-21T18:20:00Z
**Priority:** P0 · **Kind:** expressiveness_gap
**Filed by:** claude-gap145
**Files:** src/dnir_lower.zig,src/codegen.zig,scripts/run_benchmark.id

Every performance claim about this project routes through `zig build bench`.
That step cannot run, and the reason is one shape.

## Minimal reproduction (measured 2026-08-21, subject a7c3d163)

```id
global names = { "alpha", "beta", "gamma" }

main: i64 = ()
    n = names[2]
    stdout:write("{n}\n")
    return 0
```

```
error: direct backend: DNB001 application: unknown missing: keyed-table-export
hint:  bail site: native-scalar precheck — keyed-table-export
```

Six lines reproduce what blocks the whole harness. `scripts/run_benchmark.id:472`
binds `global NAMES = { "Prime sieve", "Mandelbrot", … }` — 37 text literals,
positional, read only as `NAMES[i]` at `:543` and `:743`, with no keyed write
anywhere in the module. Located by instrumenting `module_materializes_table`,
which reported `binding='NAMES'` from its `global_decl` arm.

## The guard is CORRECT. Do not widen it.

`binding_materializes_table` exempts a positional blob whose entries are integer
literals, on the stated grounds that "a positional constant has no field symbols
to mismatch, and dnir_lower has had a memory-backed positional table
representation since SH-04 landed". That rationale reads as if it should cover
text as well, and `table_is_positional_int_blob` looks narrow by accident.

It is not an accident. Measured: admitting `.quoted` positional entries does not
produce a correct program. It produces a deeper refusal —

```
missing: graph-dnir-unsupported
bail site: lowerExprCons() at dnir_lower.zig:7225
```

— so the backend genuinely cannot represent a positional table of text. Widening
the precheck moves the failure later without enabling anything, and trades an
honest early refusal for a confusing one. The experiment was run and reverted;
it is recorded here so it is not repeated.

## The representation EXISTS. The module-level path does not reach it.

Measured matrix (2026-08-21, subject eca5b3f5), each row a runnable program:

| binding | elements | index | result |
| --- | --- | --- | --- |
| module level | int | runtime | **OK** — prints 20 |
| module level | text | runtime | FAIL `keyed-table-export` |
| module level | text | constant | FAIL `keyed-table-export` |
| `global` | int | constant | FAIL `graph-dnir-unsupported` |
| function local | text | runtime | **OK** — prints beta |
| function local | int | runtime | **OK** — prints 20 |

Two readings are ruled out by that table. It is not runtime-versus-constant
indexing: a module-level int table indexes at runtime and prints 20. It is not
global-versus-bare either: dropping `global` from a module-level text table
still refuses.

What remains is exact: **a positional TEXT table refuses at module level and
lowers correctly inside a function.** The same elements, the same runtime index,
the same read — only the binding scope differs.

That reframes the work. This is not "teach the backend to represent a pointer
table into constant data" — the backend already does it, today, for the
function-local case. It is "make the module-level binding path reach the
representation the local path already uses". A reference implementation is in
the tree and passing.

Whoever takes this should start by diffing the two lowering paths for an
identical table rather than designing a new representation.

## MEASURED HAZARD: the tempting fix produces a nondeterministic wrong answer

Recorded in full because the one-line change is inviting, sits right next to the
refusal, and its failure mode is the worst kind.

Admitting `.quoted` positional entries into `table_is_positional_int_blob` makes
the module-level text table COMPILE AND RUN. It does not produce the string:

```
$ cat m4.id
strs = { "alpha", "beta", "gamma" }
i = 2
stdout:write("{strs[i]}\n")

$ idol run m4.id          # expected: beta
4296852758
4338156822                # second run
4371236118                # third run
```

Three runs, three values, varying with ASLR: the program prints a POINTER as an
integer. It exits 0. Nothing signals failure.

That is strictly worse than the refusal it replaces — a compiler that refuses
honestly is incomplete, a compiler that emits a wrong answer is unusable, and
this one emits a DIFFERENT wrong answer on every run.

**It also corrects this gap's previous framing.** The entry above concluded from
the working function-local case that "the representation exists; the module-level
path does not reach it", and that the task was to connect the two. That is
wrong. Connecting them naively is exactly the experiment run here. The
function-local path works because a local carries a str slot; the module-level
path emits a pointer with no string materialization behind it, so the
representation does NOT transfer by routing alone.

Two experiments, two failure modes, same conclusion: **do not widen the
precheck.** With a constant index it refuses deeper (`graph-dnir-unsupported`,
`lowerExprCons`); with a runtime index it silently corrupts. Both were run and
reverted.

## String constant data EXISTS at module level. The aggregate does not.

Third and final narrowing, and it contradicts this gap's own closure statement
below, which asserted module-level string constant data was absent.

```id
a = "alpha"
b = "beta"
c = "gamma"
stdout:write("{a}\n")   # alpha
stdout:write("{b}\n")   # beta
stdout:write("{c}\n")   # gamma
```

Compiles and prints all three. `dnir_lower.zig:1253` states the mechanism: a
string-typed global with a literal initializer is skipped as a compile-time
constant word because the address is a link-time fact, and "the string is
materialized at the read site". That mechanism works, today, at module level.

So the missing piece is NOT string constant data. It is the AGGREGATE:

| shape | result |
| --- | --- |
| module-level scalar string | works — materialized at read site |
| module-level TABLE of strings | refused; silently corrupts if forced |

The elements of `{ "alpha", "beta", "gamma" }` are exactly the constants the
scalar path already materializes. What has no implementation is binding them as
one indexable aggregate and reading an element through a runtime index.

That is the smallest true statement of this gap, reached only after three
wrong ones: "text is unlowerable" (wrong — it lowers inside a function),
"the representation exists, connect the paths" (wrong — connecting corrupts),
and "module-level string constant data does not exist" (wrong — it does, for
scalars).

## Traced to the implementation boundary (2026-08-21)

The per-function mechanism exists and is complete. The module path does not have
it, and does not have a place to put it.

Working chain, function scope:

- `noteStrTable` (`dnir_lower.zig:5760`) records a table whose every positional
  element is text, taking the verdict AT THE BINDING and gating it on
  `tableUseInBlock` so a written, rebound, shadowed or passed-on table is
  `.opaque_use` and assumes nothing;
- `str_tables` carries that verdict;
- `lowerDynamicIndex` (`:6186`) builds a bounds-trapped select chain and marks
  the result slot as a string via
  `if (ctx.str_tables.contains(table_name)) try ctx.str_slots.put(…)`.

That last line's own comment names this gap's failure mode exactly: the marking
"has to agree with `exprIsStr`'s `.index` arm or the two classifiers disagree on
one read — which is the shape that printed a pointer."

Why it cannot simply be reused: `noteStrTable` opens `const body = ctx.body
orelse return`, and `ctx.body` is assigned at exactly ONE site
(`dnir_lower.zig:2482`, `.body = &fd.func.body`). A `LowerCtx` is constructed
per FUNCTION DECLARATION. There is no module-level `LowerCtx` to give a body to:
module-level bindings are handled by the separate `module_globals` /
`module_consts` collection passes, which carry no aggregate-string concept and
no `str_tables` equivalent.

All three `ctx.body` consumers fail closed when it is null, so nothing is
silently wrong today — the module path simply never reaches the machinery.

**So closure is: give the module-globals path the aggregate-string capability
the function path already has** — element materialization, the binding-time
str-table verdict with its `tableUseInBlock` safety, and a read that marks its
result slot as a string. It is a real feature in a subsystem that lacks the
concept, not a routing change, and the naive shortcut is the silent corruption
recorded above.

## Executable plan (four coordinated pieces, all located)

Written out because the mapping is done and the next agent should not re-derive it.

1. **`collectModuleConsts` (`dnir_lower.zig:492`) must collect POSITIONAL fields.**
   It handles `n = <int>`, `n = <quoted>` and `.named` table fields today; the
   field loop does `switch (fld) { .named => |x| x, else => continue }`, so
   `{ "a", "b", "c" }` is skipped entirely. Emit `n.1`, `n.2`, … into `strs`
   (or `ints`), keyed exactly as `lowerDynamicIndex` already spells them
   (`"{s}.{d}"`), and record `n.len`.

2. **`lowerDynamicIndex` (`:6186`) must fall back to module consts.**
   It resolves the length via `ctx.locals.get("{s}.len")` then
   `ctx.table_lens`, and each element via `ctx.locals.get("{s}.{d}")`. Both are
   locals-only, so a module-level table resolves nothing. It needs a
   module-const path for both.

3. **The result slot must be marked as text.**
   `:6205` does `if (ctx.str_tables.contains(table_name)) try
   ctx.str_slots.put(…)`, and `str_tables` is populated only by `noteStrTable`,
   which returns early without a `ctx.body`. A module-level table needs the same
   verdict reached another way — and it must keep `tableUseInBlock`'s safety, or
   a table that is written, rebound, shadowed or passed on will be assumed
   constant when it is not.

4. **The precheck must stop refusing.**
   `module_materializes_table` (`codegen.zig:3721`) refuses first, so pieces 1–3
   are unreachable until it admits the shape. It must admit ONLY what pieces 1–3
   actually implement — widening it ahead of them is the nondeterministic
   corruption recorded above.

The ordering matters: 4 before 1–3 corrupts; 1–3 before 4 is dead code that
changes nothing. They land together or not at all.

**Acceptance:** `strs = { "alpha", "beta", "gamma" }` with a runtime index must
print `beta`, deterministically, across repeated runs — and the same program
with a written or rebound table must still refuse.

## The plan was IMPLEMENTED and REVERTED — the safety does not hold (2026-08-21)

All four pieces were built and measured. The happy path works. The safety
controls do not, and that is the finding.

Built: `ModuleConsts` gained a `str_tables` set; `collectModuleConsts` collected
positional elements as `n.1`, `n.2`, … plus `n.len`, gated on
`tableUseInBlock(&mod.body, n, tbl) <= .dyn_read`; `lowerDynamicIndex` resolved
length and elements from module constants when locals lacked them; BOTH the
emit-side verdict and `exprIsStr`'s `.index` arm read the new fact, so the two
classifiers agree; and the precheck's `table_is_positional_int_blob` widened to
`table_is_positional_const_blob`.

**Acceptance passed.** `strs = { "alpha", "beta", "gamma" }` with a runtime index
printed `beta` on four consecutive runs, deterministically. A positional int
table still printed 30.

**Both negative controls failed.**

```
strs = { "alpha", "beta", "gamma" }
strs[1] = "changed"          # keyed write — MUST refuse
i = 2
stdout:write("{strs[i]}\n")  -> 4367123746

strs = { "alpha", "beta" }
strs = { "x", "y" }          # rebound — MUST refuse
i = 2
stdout:write("{strs[i]}\n")  -> 4309271825
```

Both RAN and printed pointers. So neither `module_has_keyed_write` in the
precheck nor `tableUseInBlock` at collection rejected a table that is written or
rebound, and the corruption reappeared through the safety gate rather than
around it.

Reverted in full; the tree refuses all three shapes again.

**What this teaches about closure.** The element and length plumbing is not the
hard part — that worked first try. The hard part is the VERDICT: deciding, at a
module-level binding, that a table is genuinely constant. `tableUseInBlock` over
`mod.body` is not sufficient as invoked, and `module_has_keyed_write` did not
see `strs[1] = "changed"` at module scope. Whoever closes this should start
there, with the two negative controls above as the first tests written, not the
last.

## One cause of the safety failure, located

`module_has_keyed_write` (`codegen.zig:3775`) only recognises a STRING-keyed
write. Its `.index` arm is:

```zig
.index => |ix| {
    if (ix.obj.* == .name and ix.key.* == .quoted and
        std.mem.eql(u8, ix.obj.name.ident, name)) return true;
},
```

`ix.key.* == .quoted` means `t["k"] = v` is caught and `t[1] = v` is not. The
function was written for the `M = {}` / `M.x = 1` keyed-table hazard, where the
key is always a name, so an integer-indexed write was never in its remit.

That is exactly how the first negative control walked through: `strs[1] =
"changed"` is an integer index, so the precheck saw no keyed write, admitted the
table, and the recorded elements were the ORIGINAL three.

Measured on the reverted tree, this is NOT a live wrong answer today: a
positional INT table with an index write prints the updated value (`nums = { 10,
20, 30 }; nums[1] = 99` prints 99 across runs). The int path handles the
mutation downstream. It is the text path — which does not exist — that would
have consumed a stale constant.

So closure needs the verdict to account for integer-indexed writes AND for the
marking to stay consistent when a table is mutated. Those are two defects, not
one, and only the first is a missing condition; the second is a design question
about what a mutated table's elements are allowed to be assumed to hold.

## The blunt tightening REGRESSES working programs (measured, reverted)

Third failed shortcut, recorded with the other two so the design space is mapped
rather than rediscovered.

Hypothesis: if the verdict correctly refuses a mutated table, then "marking must
stay consistent under mutation" is moot, and defect 1's fix subsumes defect 2.
So `module_has_keyed_write`'s `.index` arm was widened to treat ANY index as a
write, not only a `.quoted` key.

It does refuse the unsafe text case. It ALSO refuses a program that works today:

```id
nums = { 10, 20, 30 }
nums[1] = 99
i = 1
stdout:write("{nums[i]}\n")   # prints 99 before; REFUSES after
```

So the tightening trades silent corruption for lost capability, and the
hypothesis is wrong: fixing defect 1 bluntly does not subsume defect 2, it
breaks the int path that already handles mutation correctly downstream.

Reverted; `nums[1] = 99` prints 99 again.

**The real constraint, stated:** the write census cannot be tightened globally,
because two element kinds have different downstream contracts. An int table's
elements are NOT assumed constant after a write — the path re-reads them. A text
table's elements WOULD be, because the module-const record is the only storage
they have. So the verdict has to be per-binding and aware of what the consumer
will assume, not a single predicate over the module.

Three shortcuts have now failed, each in a different direction: widen the
precheck (silent corruption), connect the paths (same corruption, via the safety
gate), tighten the write census (regression). The verdict layer needs design.

## Why every shortcut failed: admission and capability are decided in different passes

The sharpest statement of this gap, and it explains all three dead ends at once.

`module_materializes_table` (`codegen.zig`) decides ADMISSION — may this module
take the native-scalar path. `collectModuleConsts` / `lowerDynamicIndex`
(`dnir_lower.zig`) decide CAPABILITY — can this exact binding actually be
lowered. They run in different passes over different state and share no fact.

So admission can say yes where capability says no, and the read falls through to
something that emits a pointer. That is the corruption, and it is why the FIRST
experiment reproduced it with the precheck widened ALONE, before any recording
existed to be wrong.

It also clears the safety machinery of blame. `targetWrites`
(`dnir_lower.zig:5547`) handles `.index` correctly — it recurses through
`ix.obj` to the name — so `tableUseInBlock` returns `.opaque_use` for
`strs[1] = "changed"` and the collection records NOTHING, exactly as intended.
The guard worked. The admission in the other file did not consult it.

That reframes closure. It is not "add the missing condition" and not "connect
the paths":

**the precheck must apply the same predicate the lowering will apply, or the two
must be derived from one shared fact.** Any admission rule maintained separately
from the capability rule can drift, and the drift is silent because the failure
is a pointer rather than a refusal.

Which is why:

- widening the precheck alone corrupts — admission moved, capability did not;
- adding the recording underneath did not help — admission still does not
  consult it, so the shapes the recording REFUSES are still admitted;
- tightening the shared write census regresses — it is the only fact both
  passes read, so tightening it moves both, including the int path that was
  already correct.

## RESOLVED for this gap's subject (2026-08-21). Harness blocker chain below.

Both table blockers are closed, on `main`, with controls.

```

  1. text-face parse error at `${ZIG:-zig}`   CLOSED  (byte face)
  2. keyed-table-export on `NAMES`            CLOSED  (this gap)
  3. runtime-global-call:tostring             OPEN — not a table problem
```

Closed by two changes, each verified against the same control matrix:

- **one shared verdict.** `moduleConstTableKind` is now the single fact both
  passes read, so the codegen precheck's ADMISSION and dnir_lower's CAPABILITY
  cannot drift apart. That is the fix for the architectural cause recorded
  above, and it is why three earlier shortcuts all failed.
- **`func_decl` is a block.** `tableUseInStmt` left it to
  `else => .opaque_use`; every real module declares a function, so one
  unmodeled declaration poisoned every name. An instrumented probe over the
  harness reported exactly one unmodeled kind, and it was this. The walk now
  descends, refusing when the declaration's own path takes the name and
  answering `.none` when a parameter or vararg shadows it.

Control matrix, held across both changes:

| --- | --- |
| text table, module scope, runtime index | `beta`, 6/6 deterministic |
| text table read inside a function | `alpha`/`beta`/`gamma`, 4/4 |

**Blocker 3 is not this gap's.** `tostring` needs int-to-string conversion in the

its JSON evidence builder, so it cannot run until one of those closes.

## Blocker 3 must NOT be closed the obvious way

Traced, because the obvious fix is a one-function runtime addition and it would
be wrong.

The string runtime (`src/idol_str_runtime.zig`) exports `duo_str_to_i64` and
`duo_str_to_f64` — str to number — and nothing in the other direction. Adding
`idol_i64_to_str` and wiring `tostring` to call it would make the harness run.

GAP-082 forbids exactly that. It measures **declared conversion edges: 0**, names
`to(str)(u32) = digits` as its own canonical example and records that the
spelling "appears nowhere in the tree", and states closure as `to` becoming a
RELATION with a declaration face. A host-minted `tostring` intrinsic is the
opposite move: it satisfies the harness while making the conversion algebra's
expansion ratio worse, which is the thing that gap exists to fix.

`src/conversion_law.zig` is the matching ruling — "no silent conversion" as a
law rather than a backend bail — and it documents the same asymmetry from the
other side.

So the remaining harness blocker is not a plumbing task. It is a declaration:
`to(str)` has to exist as a conversion relation before any backend may realize
it. That belongs to GAP-082 and its siblings, and taking it here by minting an
intrinsic would trade a measurable blocker for an unmeasurable law violation.

## Measured for GAP-082: the BODY is expressible today; only the FACE is missing

This narrows the blocker materially, and it was reached by testing the lawful
path rather than the intrinsic one.

GAP-082 names `to(str)(u32) = digits` as its canonical declared conversion. The
computation that declaration needs already lowers, in canonical Idol, on the
direct backend:

```id
digits: str = (n: i64)
    if n < 10
        return string.char(48 + n)
    return digits(n // 10) .. string.char(48 + n % 10)

main: i64 = ()
    stdout:write("{digits(40721)}\n")   # prints 40721
    return 0
```

`string.char` (byte to text) and concatenation are both admitted by the direct
path, so number-to-text needs NO new runtime primitive and no host intrinsic.

What does not exist is the DECLARATION FACE. Writing the same body as the
conversion edge itself refuses at the first token:

```
to(str)(n: i64) =
        ^  error: write `)` at this token edge
```

So GAP-082's "declared conversion edges: 0" is not blocked on the ability to
compute a conversion — that works. It is blocked on `to` having a declaration
face at all, which is a parser and semantic question about the conversion
algebra rather than a backend capability.

That is the whole distance between this gap's harness blocker and its closure:
one declaration form. And it must be built as that form, because minting
`idol_i64_to_str` instead is the move GAP-082 exists to prevent.

## What closure requires

A positional text table must become lowerable: the elements are constants with
known extent, so this is a representation question (pointer table into constant
data) and not a semantic one. `dnir_lower.zig:7225` `lowerExprCons` is the exact
consumer that refuses.

Then `binding_materializes_table`'s exemption widens to any positional constant
blob with no keyed write, and the narrowing to `int_lit` can be deleted with a
control proving a text blob round-trips.

`scripts/run_benchmark.id:50` built a shell command in the text face, so
`${ZIG:-zig}` opened an interpolation hole and the harness did not parse at all.
Fixed by moving the brace payload to the byte face; `idol check` now passes.
That was the first of two blockers. This gap is the second and last.
