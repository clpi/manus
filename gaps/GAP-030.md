# GAP-030 — the front end accepts overloads the C backend cannot emit

**Status:** open · **Filed:** 2026-08-07 · **Frequency:** blocks 25 renames
**Blocks:** Pass 88 §4 — the `is_*` predicate purge, wherever the bare noun is taken
**Sites:** `scripts/census/lawone.duo` (P88-16, P88-17)

## The defect

Duo's front end implements **overload resolution** — it accepts two top-level
bindings of the same name and reports an *ambiguous call* when it cannot choose:

```
error: ambiguous call to overloaded function 'ok': multiple overloads match the
       argument types
```

That message promises a feature: give the overloads distinct argument types and
the call will resolve. **It does not.** With distinct types the front end accepts
the program and the C backend emits two functions with the same symbol:

```
error: conflicting types for 'ok'
error: redefinition of 'ok__lua'
```

The `__lua` suffix is a fixed decoration, not a signature mangling, so no two
overloads can coexist regardless of their types. Overloading is half-implemented:
resolved in the front end, unrepresentable in the backend.

## Minimal repro

Same signatures — front-end diagnostic, correct and loud:

```duo
ok(v: i64): i64
    v
end
ok(r: i64): bool
    r > 0
end
main(): void
    print(ok(5))
end
```
```
dup.duo:8:11: error: ambiguous call to overloaded function 'ok'
```

Distinct signatures — front end accepts, backend collides:

```duo
ok(v: i64): i64
    v
end
ok(r: str): i64
    #r
end
main(): void
    print(ok(5))
end
```
```
/tmp/duo_dup2.c:5677:20: error: conflicting types for 'ok'
/tmp/duo_dup2.c:5691:18: error: redefinition of 'ok__lua'
```

## Why it blocks Pass 88

LAW-ONE §4 rules that predicate-hood is stated by use position, so `is_digit`
becomes `digit`. Measured, **25 of the 71 `is_*` bases in `lib/std` already name
a top-level binding**, and the collisions are not accidental. `lib/std/result.duo`
declares both halves of four pairs in one file:

| line | constructor | line | predicate |
| --- | --- | --- | --- |
| 9 | `ok(value: any)` | 22 | `is_ok(r: any)` |
| 14 | `err(message: any)` | 28 | `is_err(r: any)` |
| 114 | `some(value: any)` | 124 | `is_some(o: any)` |
| 119 | `none()` | 130 | `is_none(o: any)` |

Both take one `any`, so even a working overload could not separate them — and
`ok(v)` *builds* an ok while `ok(r)` *tests* one. Two genuinely different
concepts wearing one noun is precisely what LAW-ONE says a name may not do, so
the law convicts its own repair.

Typed overloads were the one mechanism that could have made the rename safe for
the other 21. This gap is why that path is closed.

## The fix

Mangle the emitted symbol per signature rather than with a fixed `__lua` suffix,
so the backend can represent what the front end already resolves. Until then the
front end should **refuse** a second declaration of a name instead of accepting
it and deferring to a C error — the current behavior turns a Duo-level naming
question into a backend diagnostic that names a C symbol.
