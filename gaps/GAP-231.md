# GAP-231 — vector element access is emitted as an application, and C refuses it

**Status:** OPEN (2 of 3 subjects closed) · **Filed:** !2026-08-25T04:40:00Z
**Priority:** P1 · **Kind:** realization_defect
**Filed by:** claude-reconcile
**Files:** src/codegen.zig,examples/simd_test.id,examples/simd_matmul.id,examples/simd_mandelbrot.id

## The measurement

`idol dump-c examples/simd_test.id`, then `cc -std=c11 -fsyntax-only` over the
result, on x86_64-linux-gnu with gcc 13.3.0 and clang 18.1.3. Eleven errors, one
class, both compilers, identical:

      6  called object 'v3' is not a function or function pointer
      4  called object 'picked' is not a function or function pointer
      1  called object 'v4' is not a function or function pointer

The emitted lines read

    lua_to_display_str(v3(lua_val_from_int((int64_t)(3))))

where `v3` is a `v4f64`. C needs `v3[3]`. Nothing about this is host-shaped: it
reproduces on clang, and it reproduced on clang before the `ext_vector_type` ->
`vector_size` repair in `b55ee675`, so it is not a consequence of that change.
That commit's own measurement is the control — gcc went 13 -> 11 and clang
stayed at 11, and these eleven are the residue both compilers agree on.

## Why it is a law defect and not a C bug

`docs/spec/law.md` §5: "`()` is ordinary application. It never means table
indexing." `CLAUDE.md` says the same from the source side — "Computed or indexed
aggregate access uses projection: `table[key]` and `row[1]`. Ordinary
`value(args)` remains application and never table indexing."

So the source wrote a projection, and the C realizer emitted an APPLICATION.
The two faces `law.paren.one` keeps separate were collapsed at the realization
boundary, and C — which also separates them — refused the result. The defect is
that the projection fact did not survive to the emitter, not that C is strict.

`42fd8de0` (landed here as part of the place-and-cache-contract lane) deleted the
mirror of this confusion on the READ side: a `placeFold` arm that folded `t(k)`
to the k-th element of `t`, against the same §5. This is the same question
answered wrongly in the other direction, at the other end of the pipeline.

## Why it was invisible

The `--backend=c --emit=c` route refuses these three programs earlier and for an
unrelated reason:

    error: C99 realizer: graph-to-DNIR refused (GraphFactsInvalid)
    hint: refused at: missing-application-id

so the only route that reaches this emission is `dump-c`, and nothing compiles
what `dump-c` writes for a SIMD subject. `gate/gap-141-runtime-temp.sh` compiles
an emitted unit but not one carrying vector element access. A gate that compiles
`dump-c` output for the three `examples/simd_*.id` subjects is the missing
instrument, and it should be written to FAIL now, at 11, rather than pinned to
the current count as an expected state — the shape `gate/lower/fallback.baseline`
and `gate/surface/reach.sh` §5 both had to be repaired for.

## CORRECTION: there was never a projection fact

This gap said "the source wrote a projection, and the C realizer emitted an
APPLICATION." Measured, it did not. `examples/simd_test.id:7` reads

    print("v3[0]:", v3(0))

and the graph agrees it is an application: node 13 is published as a
`call_shape` with `callee_kind: "direct"`, `applications: []`, `places: []`. So
the framing "the projection fact did not survive to the emitter" is wrong —
three example programs are written in a spelling the language RETIRED, and
`src/codegen.zig:23610-23619` already documents it as retired ("`a(i)` as an
index is RETIRED … nothing generates the spelling any more"). `42fd8de0`
deleted the read-side mirror of exactly this.

The emitter site is `src/codegen.zig:17934`, the terminal fallback of the
`.call` arm, reached because `ft == .v4f64` is neither `.func` nor `.any`. The
VECTOR fact is present and unread there — `types.is_vector`
(`src/types.zig:500`) and `indexed_element_type` (`src/codegen.zig:2824`, unit
tested at `:37324`) both already answer it, and the bracket road works end to
end (`src/sema.zig:4638`, `src/codegen.zig:17115`).

The precedent for a recognizer sits eighty lines above the defect:
`src/codegen.zig:17124-17133` opens the same `.call` arm with `str_byte_index`,
added for the identical failure ("called object type 'const char *' is not a
function in four corpus files"). A vector recognizer is that function with
`.str` replaced by `is_vector()`.

**But that is a type test in the emitter, which acceptance #1 below rules out**,
and no projection fact exists to replace it: `src/table_apply.zig` is pre-sema
and name-only (`BoundNames`, no types), so it structurally cannot mint one. The
cheapest correct answer is therefore the SOURCE REWRITE — `v3[0]` already works
with zero compiler change — and the recognizer is the compatibility answer.

`picked` is the SAME cause, not a different one as this gap hedged: the emitted
C declares `v4f64 picked` (`simd_test.id:19`), and clang names the subject type
`v4f64` on all eleven errors.

**Acceptance #2 spans two defects and cannot be closed by one repair.**
`examples/simd_mandelbrot.id` has no `()`-lane-read at all; its two errors are a
scalar `lua_to_num` C-cast to a vector type in the boxed-entry thunk for a
vector-parameter relation (`invalid conversion between vector type 'v4f64' and
scalar type 'double'`). That is the lua-ABI trampoline, not projection.

## The rewrite, measured

`v3(0)` -> `v3[0]` in `examples/simd_test.id` (11 sites) and `c(0)` -> `c[0]` in
`examples/simd_matmul.id` (2 sites). No compiler change.

    subject             check   gcc     clang
    simd_test           ok      11 -> 0  11 -> 0
    simd_matmul         ok       2 -> 0   2 -> 0
    simd_mandelbrot     ok       2        2      (the trampoline defect)

The emitted C did not merely become legal, it became BETTER. Before:

    lua_to_display_str(v3(lua_val_from_int((int64_t)(3))))

after:

    printf("%s\t%.17g\n", "v3[3]:", v3[3]);

The whole boxed round trip — `lua_val_from_int`, the call, `lua_to_display_str`
— collapsed to a native vector lane read, because the bracket road was already
wired end to end (`src/sema.zig:4638`, `src/codegen.zig:17115`) and the paren
road was falling through to the boxed fallback. The retired spelling was costing
a box, an unbox and a call per lane on every subject that used it.

The author's own labels already read `v3[0]` while the code read `v3(0)`, which
is the tell that these were stale spellings and not deliberate probes.

## Acceptance

1. A projection over a vector subject emits `v[i]`, and the fact that selects
   that face is the graph's projection fact rather than a name test in the
   emitter.
2. The three `examples/simd_*.id` subjects emit C that passes
   `cc -std=c11 -fsyntax-only` under BOTH gcc and clang, measured, with the
   two counts equal and zero.
3. `picked` — a boxed value in the same census — is covered by the same repair
   or is separated with its own measurement; it is grouped here only because
   the compiler reports it identically, which is not evidence that it is the
   same cause.
