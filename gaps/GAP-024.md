# GAP-024 — the host lexer overflows on a u64 literal above i64 max

**Status:** open (failing fixture committed) · **Filed:** 2026-08-07
**Found:** while probing GAP-023, and it is NOT that gap's cause

## The defect

`13636438360258349679` is a valid `u64` and Duo has `u64`. `src/lexer.zig`
parses integer literals as i64 and returns `error.Overflow`:

    error.Overflow
      std/fmt.zig parseIntWithSign
      src/lexer.zig read_number

The Duo lexer does not agree, so the two diverge on a construct the language
claims to support.

## Fixture

`src/duo_lexer_dispatch.zig`, test `GAP-024 — u64 literal above i64 max`,
committed **failing**. It is the only thing that makes the divergence visible;
deleting it to keep the failure count at baseline restores the blindness.

    try differential(a, "fingerprint = 13636438360258349679", "u64.duo");

## The question to settle

Which lexer is right? Duo has `u64`, so a literal in `[i64max+1, u64max]` should
plausibly lex as one — in which case the HOST is wrong and `Token.int_val: i64`
cannot represent it, making this a token-representation question, not a parsing
one. That is a language decision, not a bug fix, which is why this is filed
rather than patched.
