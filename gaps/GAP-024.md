# GAP-024 — the host lexer overflows on a u64 literal above i64 max

**Status:** CLOSED 2026-08-07 (failing fixture committed) · **Filed:** 2026-08-07
**Found:** while probing GAP-023, and it is NOT that gap's cause

## The defect

`13636438360258349679` is a valid `u64` and Duo has `u64`. `src/lexer.zig`
parses integer literals as i64 and returns `error.Overflow`:

    error.Overflow
      std/fmt.zig parseIntWithSign
      src/lexer.zig read_number

The Duo lexer does not agree, so the two diverge on a construct the language
claims to support.

## Fixture

`src/duo_lexer_dispatch.zig`, test `GAP-024 — u64 literal above i64 max`,
committed **failing**. It is the only thing that makes the divergence visible;
deleting it to keep the failure count at baseline restores the blindness.

    try differential(a, "fingerprint = 13636438360258349679", "u64.duo");

## ROOT CAUSE: int_val violates decomposition (2026-08-07)

`Tok` carries `int_val: i64` AND `float_val: f64` as sibling fields, with `kind`
deciding which is live. That is a **flattened tagged union** — the payload
belongs to the case:

    kind: { name, number(value), string(text), eof }

Pass 100 §20's golden `token` has `kind`, `span`, `text` and NO value fields at
all, which is the same conclusion from the other direction.

Everything about this gap is downstream of that. A u64 literal "does not fit
i64" only because the value was given one i64-shaped home for every numeric
case. With the payload on the case, a `number(u64)` case holds a u64 and no
cast, bitcast, or overflow question arises.

## What was done here, and honestly labelled INTERIM

**src/lexer.zig — landed.** Decimal literals now fall back to `parseInt(u64)`
and reinterpret, exactly as the HEX path beside them already did for
`0xcbf29ce484222325`. That asymmetry was the actual bug: two spellings of the
same value, one accepted and one rejected. Removing it is right independent of
the shape question.

**lib/std/compiler/lexer.duo — REVERTED.** `_int_of` accumulating in i64 traps
on signed overflow (the build checks it). Accumulating in `u64` and converting
with `to(i64)` does not compile in the native-direct lexer — `to` does not lower
there — and the attempt broke the checked-in artifact. Restored.

So the Duo and host lexers still disagree above 2^53, and the committed fixture
still fails. It stays failing: it is the only thing that makes this visible, and
the honest fix is the decomposition, not another cast.

## The question to settle

Which lexer is right? Duo has `u64`, so a literal in `[i64max+1, u64max]` should
plausibly lex as one — in which case the HOST is wrong and `Token.int_val: i64`
cannot represent it, making this a token-representation question, not a parsing
one. That is a language decision, not a bug fix, which is why this is filed
rather than patched.

## CLOSED 2026-08-07 — the accumulator was signed

`lib/std/compiler/lexer.duo`'s `_int_of` accumulated in `i64`, so `v * 10` on a
literal above i64 max was SIGNED OVERFLOW -- undefined behaviour the generated
C traps on. The compiler did not mis-lex the value, it ABORTED:

    panic: signed integer overflow: 1363643836025834967 * 10 cannot be
    represented in type 'int64_t'

reached from `print(tostring(13636438360258349679))` -- an ordinary literal.

The accumulator is now `u64`: unsigned multiplication wraps instead of
trapping, so it carries the full 64-bit range and lands the same bits the host
lexer's `parseInt(u64)` fallback produces.

    before  exit 134 (SIGABRT)
    after   exit 0, prints -4810305713451201937 (the u64 read as i64)

`src/duo_lexer_tokenize.c` regenerated from `lib/std/compiler/host.duo`, since
that generated artifact is what the compiler actually links. Both lexer
differentials and agent-smoke stay green.
