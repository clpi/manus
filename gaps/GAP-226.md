## `bootstrap` and `blocking` are not two causes

`FactCoverage` splits the unpublished remainder by whether a spelling roster
lowers the site anyway. That is an OUTCOME of the missing fact, not a cause of
it, and the table above cuts across the split in both directions: 71% of
`host-relation-no-entity` is bootstrap and 96% of `callee-is-a-value` is
blocking, but the repair inside each row is one repair. Ranking work off
`blocking` alone ranks the roster.

## The wall is one cause and it holds 74% of the population

`host-relation-no-entity` and `host-relation-name-declared-in-home` are the
same sentence: **the relation this application names has no relation entity in
the graph, because nothing declares it.** `print`, `s:len()`, `s:sub(a,b)`,
`b:byte()`, `x:floor()`, `s:gsub(a,b)`, `type(v)`, `assert(c)` are answered
from `subject_home`'s closed home enum and `native_bootstrap`'s face list. A
spelling roster is the producer, so there is no id for `publishApplication` to
point at, and every downstream fact — effect, demand, trap, completion,
witness, realization — has nowhere to attach. `gate/coverage.sh` names the same
thing from the other side: `relation.identity`, 514 sites, rival authority
`spelling comparison`, the largest rival in that table.

The split between the two rows is only whether a relation of that NAME happens
to be declared in a home `Sema.subjectFirstForeignRelation` searches. It is an
UPPER BOUND on what a resolution-order change could reach and nothing more:
`lib/table.id` declares `len`, and 1883 of the second row's sites are `s:len()`
on TEXT. Subject conformance decides that, and the classifier does not compute
it.

`Sema.methodCallResolved` short-circuits the foreign search — it returns true
for any roster hit and the `.method_call` arm then returns `.any` without ever
reaching `subjectFirstForeignRelation`. Reordering is NOT the repair on its
own: for the 257 sites where the declaration is real, the published target
would be a relation in another module, and a call whose target is never
compiled cannot be lowered at all.

## Cross-module reachability is 4.9%, not the wall

`cross-home-application` is 445 sites whose dotted home resolves to a module
file — `os` 150, `mem` 69, `math` 47, `bit` 46, `io` 43, `simd` 33. Those are
the sites that would need a call into another home's symbol, and a separate
concern owns them (`gate/lower/fallback.sh` ratchets the fallback). Adding
`home-unresolved` (114, of which 23 are the `std.` prefix `gaps/GAP-222.md`
forbids repairing) puts everything cross-home at 6.2%.

The prior worth retiring is that some large fraction of the application wall is
really cross-module reachability. It is not. Cross-home is a fourteenth of it.

## Two rows are the named traps, not work items

`callee-is-a-value` (1437) is application through a binding, a record field, or
a call result — `less(key, arr[j - 1])` where `less` is a parameter. That is
callable/application resolution, monomorphization, open-world function
semantics and boxed parameter realization, which is the chain a naive
whole-program `param-type:any` inference was measured to move by ZERO corpus
programs.

`comptime-directive` (353) is `@comp.*`, whose applications are compile-time
and whose relation entities are a separate owner's.

## What the classifier is, and is not

`gate/application.sh` reads the graph export's exact `unresolved_applications`
and `blocking_applications` node ids and then attributes each site by reading
SOURCE at the node's own line and column. The second half is a spelling
reading. It is admissible because nothing but a human consumes the output — no
compiler phase reads it and it publishes no fact — and `unattributed` is its
own row so an unparsed site is never folded into a neighbour. Two wrong
attributions were found and fixed by applying the repair they implied and
watching a fixture go green; the commit titled "gate: two shapes wear `()` on the left of `=` and are not
projection" records both.

## Acceptance

- a relation entity exists for every host relation an ordinary program applies,
  minted by a declaration rather than by a face list, and `subject_home`'s
  enum plus `native_bootstrap`'s roster shrink by exactly what it covers;
- `gate/application.sh` shows `host-relation-no-entity` and
  `host-relation-name-declared-in-home` falling together, since they are one
  cause;
- `gate/coverage.sh`'s `relation.identity` rival count falls with it;
- no scalar-specific or relation-specific registry appears beside the one
  application algebra (`gaps/GAP-202.md`); and
- the cross-home row does not move, because it is not this gap.

## What the wall costs PORTABILITY, measured 2026-08-25

The sections above count the wall at its own boundary — sites in
`gate/application.sh`, rivals in `gate/coverage.sh`. This measures its
consequence one layer out, on the only realization that is not
architecture-bound, and the number is worse than the site count suggests.

`idol compile <subject> --backend=c --emit=c`, over every subject in
`examples/`, on x86_64-linux-gnu:

    examples                                     253
    `idol check` refuses (not valid programs)     43
    `idol check` accepts                         210
      -> C backend realizes                       13
      -> refused missing-application-id           141
      -> refused for another reason                56

`missing-application-id` is `lowerModuleWithGraphObserved` refusing when
`OccurrenceBridge` leaves any application occurrence unresolved — "there is no
id for `publishApplication` to point at", observed by the consumer rather than
by a census.

**CORRECTION, AND IT NARROWS THIS GAP.** The first version of this section
read the 141 as this gap arriving at the realizer. It is not: 141 is FOUR
causes wearing one diagnostic identity. The refusal already binds the relation
face — `refuseApplication` sets `diagnostic.relation` from `applicationFace` —
and the C arm simply never printed it, so every one of the 141 reached a reader
as the same six words. Printed (`5f74ee27`+), they separate:

    63  compiler intrinsic (`__*`)      __emit, __comptimematch, __c_call,
                                        __static_assert, __comptimemap, …
    43  host relation with no entity    new, assert, setmetatable, type, cast
    20  no face bound at all            the invalidGraphFacts path, which binds
                                        no occurrence
    15  non-callable subject applied    tt, u, v4f64 — `T(i)` for `T[i]`

Only the second family, 43 of 141, is THIS gap. The largest is compile-time
intrinsics, which is a different question with a different owner, and the
fourth should not be reaching this identity at all — `examples/call_index_module.id`
is `tt: [4]i64 = {1,2,3,4}` then `tt(2)`, which `gate/application.sh` names as a
NEGATIVE probe and `law.md` §5 rules by one sentence. It passes `idol check` and
then refuses here as a missing id, so a correct refusal is wearing the wrong
cause. See GAP-233.

WHY THIS IS THE NUMBER THAT MATTERS FOR EVIDENCE. The direct backend emits
machine code for aarch64-darwin and refuses every other host (DNB004), so on any
other machine the C backend is the ONLY route from source to a running program.
At 13 of 253 it is not one, and the effect is not confined to examples: measured
on the same host, `tools/wasm/src/engine.id` refuses through both routes —
DNB004 on `--backend=direct` and `auto`, `GraphFactsInvalid /
missing-application-id` on `--backend=c`. Idol's WASM engine therefore cannot
execute at all on x86_64-linux.

That is why `GAP-130`'s six-runtime comparison is an aarch64 measurement and has
no x86_64 sibling, and why `benchmarks/wasm_baseline.txt` has not been refreshed
since 2026-06-08: there is nothing to run. Closing this gap is a precondition for
FTCFTW evidence on any host that is not a Mac, and no amount of realization work
on the JIT changes that, because the JIT is on the arm64 arm.

The four counts are not stored anywhere that can decay. This is the loop that
produced them; run it rather than citing them:

```sh
ok=0; missapp=0; other=0; n=0
for f in examples/*.id; do
    n=$((n + 1))
    if ./zig-out/bin/idol compile "$f" --backend=c --emit=c -o /tmp/x.c >/tmp/e.txt 2>&1; then
        ok=$((ok + 1))
    elif grep -q missing-application-id /tmp/e.txt; then
        missapp=$((missapp + 1))
    else
        other=$((other + 1))
    fi
done
printf 'examples=%s c-backend-ok=%s missing-application-id=%s other=%s\n' \
    "$n" "$ok" "$missapp" "$other"
```

The `elif` matters and the first draft of this loop got it wrong: written as
`cmd || grep -q … && hit=…`, shell precedence groups it `(cmd || grep) && hit`,
so the counter also increments on SUCCESS and the refusal count reads 154
instead of 141. A miscount in the direction that inflates the finding.
