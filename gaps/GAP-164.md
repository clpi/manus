# GAP-164 — graph-backed orthogonal C realization

## State

Open.

## Problem

The law permits an explicitly selected C physical realization over the same
graph-owned semantics used by direct native. No such graph-backed C realizer is
complete today. The reachable `dump-c` path still uses the legacy AST/Lua
emitter and cannot satisfy this capability.

Direct native remains the default, self-host, release, correctness, and
performance path. It never emits C, invokes a C compiler, depends on a C
artifact, or falls back to C. `auto` never selects C.

The admitted C feature must consume graph-observed DNIR and may not import or
revive the legacy AST/Lua code generator.

## Required first slice

- explicit `--emit c` selection;
- i64 constants, arithmetic, comparisons, branches, direct calls, and returns;
- portable C99 output from the same graph-observed DNIR consumed by other
  physical realizers;
- independent answer and damaged-DNIR controls;
- zero change to direct-native bytes when the C toolchain is absent or poisoned.

## Completion gate

The explicit C feature is complete only when every claimed operation is derived
from shared graph facts, the legacy C/Lua emitter has no consumer, and C evidence
is isolated from direct-native correctness and performance evidence.

## Rule

Implement C only as an orthogonal physical realizer. Never use it as semantic
authority, automatic selection, direct fallback, or proof for direct native.
The `c` foreign world remains a separate interop capability.
