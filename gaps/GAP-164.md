# GAP-164 — Conversion tripartition gate (satisfaction ≠ conversion ≠ realization)

**Status:** OPEN · **Filed:** 2026-08-12
**Priority:** P0 · **Kind:** architecture
**Owner:** Cursor (coordination / canonicality)

## Ruling

`law.conversion.tripart` must be adversarially enforced. Without it, `to` becomes
a garbage chute for every representation mismatch.

| Class | Graph | Source |
|---|---|---|
| **Satisfaction** | value already meets demand | no `to` |
| **Conversion** | semantic `to(T)` application | infer or spell when unique/necessary |
| **Realization** | same semantic value, different physical form | DNIR/machine only |

## Required controls

1. `n: i32 = 5` — exact integer specialization, not fake `i64 → to(i32)`.
2. ABI register width — realization fact, not semantic `to(i64)`.
3. Text → parsed integer — may be `parse` relation, not automatic `to(i64)`.
4. Redundant `value:to(T)` when binding already demands `T` — migration debt (INFER-ONE).
5. Physical cast in source for backend convenience — delete semantic `to`; move to realization.

## Acceptance

Graph-owned gate executes on staged diff when GAP-124 closes. Until then:

- `law.gate.infer` controls 5–6–14 cover text ratchet subset
- `scripts/infer_census.id` enumerates explicit conversion debt
- Agents classify per `law.repair.infer` A–L before rewrite

## Negative controls

- Inserting `to(i32)` for `n: i32 = 5` rejected.
- Modeling ABI width as source-level `to` rejected.
- Treating parse/validate/decode as ordinary `to` without relation audit rejected.
