| 4. The structural gap, which no feature list captures |

| # | directive |
|---|---|
| 1 | `src/parser.zig` builds an **AST** (`ast.zig` nodes) that `sema.zig` and `codegen.zig` consume. `lib/compiler/parser.id` builds an **s-expression string**. |
| 2 | They are not the same kind of artifact, and no amount of grammar coverage makes one substitutable for the other: `Parser.init(&lex, alloc)` cannot be handed a projector. |

| 1 | That is the honest content of RL-04's gate. |

| 5. Closed here: gap[046] proper — a face call in a statement-level argument |

| # | directive |
|---|---|
| 1 | `f(a:b(1))` as a **statement** was rejected. `x = f(a:b(1))` was accepted. |

| # | directive |
|---|---|
| 1 | `proj_stmt` dispatches NAME `(` through `params_have_colon`, which asks "is there a `NAME ':'` at a parameter slot inside these parens?" to tell a bare declaration (GR-001) from a call. |
| 2 | A face call in argument position spells the same three tokens, so `f(a:b(1))` was read as a declaration of `f` and failed. |

| # | directive |
|---|---|
| 1 | It never showed up as a wrong projection, only as a rejected file — and lib/std has no statement-level call carrying a face argument, so the 257/257 ratchet was blind to it. `ext/ward/src/nn/init.id`'s `assert(data:sub(1, 4) == "GGUF", ...)` was one of ward's three rejections. |

| # | directive |
|---|---|
| 1 | Fixed by looking one token further: a parameter's type is a type name (`a: i64`, `a: point`), a face call's method name is immediately applied (`a:b(`). |
| 2 | Only the applied form is skipped, and it is skipped by CONTINUING the scan rather than answering false, so a bare declaration whose first parameter type is applied still matches on its return colon. |

| # | directive |
|---|---|
| 1 | Measured after: lib/std 257/257 unchanged, `examples` 255 → 256, corpus proof exit 0. |
| 2 | Four rows added to `examples/pass16_parser_corpus_proof.id` — two calls that were wrong and two declarations the fix must not stop recognising, because without those two the fix would silently turn every bare declaration into a call. |
| 3 | Negative control: corrupting one row yields exit 97, restoring it yields 0. |

| 6. Cheapest remaining wins, in order |

| # | directive |
|---|---|
| 1 | `: T \| error` result types — Pass 100 §0.5, and currently unwritable in the self-hosted parser. |
| 2 | The two silent misparses in §3 (`nn { … }`, `as T`), which are worse than rejections because the ratchet reads them as passes. |
| 3 | Tuple return types (`fun f(…): (str, i64)`) — the next rejection in `ext/ward/src/nn/init.id` after this one was fixed. |
| 4 | `const` and `defer`, both trivially shaped and both zero-use in lib/std. |
| 5 | Make `parser_corpus_coverage` ratchet on a root that includes `ext/ward` and `tools`, so the denominator stops being the dialect the parser already handles. |

| 7. 2026-08-09 stash audit: offside over-indent is silently accepted |

| # | directive |
|---|---|
| 1 | The current Idol parser closes a body only when a later token is left of the first statement column. |
| 2 | It does not reject a later statement that is farther right even though no preceding source face opened a nested body: |

```duo
f: i64 = (n: i64)
    t = 0
        n = 1
    t
```

| # | directive |
|---|---|
| 1 | This is another accepted-but-wrong row that the 257/257 acceptance ratchet cannot see. `stash@{1}` contains an attempted offside implementation and the missing negative case, but it also modifies Lua benchmarks, preserves written `end`, and carries an older parser model. |
| 2 | Do not apply it wholesale. |
| 3 | Transplant the negative control, then implement the production rule in canonical Idol: each body has one established statement column, a deeper line is legal only when the preceding semantic face opened a nested body, and any other column is a structured diagnostic. |
| 4 | Differential the projected structure, not merely the accept/reject status. |
