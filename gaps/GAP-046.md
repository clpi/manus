# GAP-046 — RL-04: what the Duo parser at "256/256" does not do, itemised

**Status:** open (one item closed here) · **Filed:** 2026-08-08
**Cited at:** `lib/std/compiler/parser.duo` (`params_have_colon`),
`scripts/parser_corpus_coverage.duo`, `src/removal_ledger.zig` RL-04.

(Took 046 after checking `gaps/` here and in every sibling under
`.claude/worktrees/`; 039–045 were already filed by other sessions.)

RL-04's gate is "Duo-native parser kernel + syntax graph" and SH-04 is reported
at 256/256 corpus coverage. This is the measurement of what that number does
and does not say, so the gate stops being a vibe.

## 1. What the 256/256 actually measures

`scripts/parser_corpus_coverage.duo` walks `lib/std/**.duo` and counts files for
which `parse_status(src) == 0`. Two properties follow, and both matter:

- It is an **acceptance** measure, not a fidelity measure. A file that parses to
  the wrong tree counts as a pass.
- Its denominator is **lib/std**, which is one dialect of Duo, not the language.

Re-measured 2026-08-08 (the file count has since moved to 257):

| root | accepted / total | |
|---|---|---|
| `lib/std` | **257 / 257** | the ratcheted number |
| `ext/ward` | **21 / 24** | production Duo, downstream consumer |
| `tools` (LSP + MCP) | **35 / 48** | production Duo |
| `examples` | **256 / 354** | includes deliberate compile-fail fixtures |

So 100% on the corpus that was chosen and 73–88% on the Duo written elsewhere
in the same repository.

## 2. Why lib/std is 100%

Not because lib/std exercises the language. Because lib/std does not use the
constructs the Duo parser cannot parse. Counted:

| construct | uses in `lib/std` |
|---|---|
| `match` | 0 |
| `enum` | 0 |
| `const` | 0 |
| `defer` | 0 |
| `: T \| error` result type | **0** |

The last row is the sharp one. `: u64 \| error` is Pass 100 §0.5 — the result
discipline the language is built on — and neither lib/std nor the self-hosted
parser has it.

## 3. Construct-by-construct

40 constructs the host parser has a production for, probed against
`parse_status` and `proj_program`. **26 accepted, 14 rejected.**

**Rejected (14).** `match` · `enum` · macro definition · `async fun` · `defer` ·
`try` · `const` · applied type argument in a parameter (`x: list(i64)`) ·
table destructuring (`{ x, y } = p`) · `goto`/label · list comprehension ·
method reference (`f = obj:m`) · if-pack binding (`if v, e = g(x)`) ·
**result type (`: i64 | error`)**.

Four of those — `match`, `then`-form `if`, `-> T` return arrow, `enum` — are on
CLAUDE.md's §1 deny list. The parser rejecting them is arguably the parser being
right and the source being stale, and the three `tools/mcp` files and
`ext/ward/src/wasm/jit.duo` that reject on them should be read that way. The
other ten are real holes.

**Accepted but WRONG (2).** These are the dangerous ones, because acceptance is
what the ratchet counts:

- `m = nn { relu }` → `(program (assign m nn) (desc (item relu)))` — the block
  is torn off into a separate top-level statement.
- `y = x as i64` → `(program (assign y x) as i64)` — the cast falls out of the
  tree as raw text.

**Accepted (24).** lambda · `local` · `global` · `type` alias · `concept` ·
multiple assignment · `do` · attributes · string interpolation · `@comp.layout` ·
`@comp.c.include` · `req` · long-bracket string · method call · varargs ·
numeric `for` · generic `for` · `break` · `repeat` · descriptor · index ·
anchor (`x@rel`) · face call (`lx:read(number)(b)`) · guard chain.

## 4. The structural gap, which no feature list captures

`src/parser.zig` builds an **AST** (`ast.zig` nodes) that `sema.zig` and
`codegen.zig` consume. `lib/std/compiler/parser.duo` builds an **s-expression
string**. They are not the same kind of artifact, and no amount of grammar
coverage makes one substitutable for the other: `Parser.init(&lex, alloc)`
cannot be handed a projector.

That is the honest content of RL-04's gate. The syntax graph half is real work
in its own right, on top of the grammar half measured above.

Scale, for calibration: 132 functions in `src/parser.zig`, 66 in `parser.duo`.

## 5. Closed here: gap[046] proper — a face call in a statement-level argument

`f(a:b(1))` as a **statement** was rejected. `x = f(a:b(1))` was accepted.

`proj_stmt` dispatches NAME `(` through `params_have_colon`, which asks "is
there a `NAME ':'` at a parameter slot inside these parens?" to tell a bare
declaration (GR-001) from a call. A face call in argument position spells the
same three tokens, so `f(a:b(1))` was read as a declaration of `f` and failed.

It never showed up as a wrong projection, only as a rejected file — and lib/std
has no statement-level call carrying a face argument, so the 257/257 ratchet was
blind to it. `ext/ward/src/nn/init.duo`'s
`assert(data:sub(1, 4) == "GGUF", ...)` was one of ward's three rejections.

Fixed by looking one token further: a parameter's type is a type name
(`a: i64`, `a: point`), a face call's method name is immediately applied
(`a:b(`). Only the applied form is skipped, and it is skipped by CONTINUING the
scan rather than answering false, so a bare declaration whose first parameter
type is applied still matches on its return colon.

Measured after: lib/std 257/257 unchanged, `examples` 255 → 256, corpus proof
exit 0. Four rows added to `examples/pass16_parser_corpus_proof.duo` — two calls
that were wrong and two declarations the fix must not stop recognising, because
without those two the fix would silently turn every bare declaration into a
call. Negative control: corrupting one row yields exit 97, restoring it yields 0.

## 6. Cheapest remaining wins, in order

1. `: T | error` result types — Pass 100 §0.5, and currently unwritable in the
   self-hosted parser.
2. The two silent misparses in §3 (`nn { … }`, `as T`), which are worse than
   rejections because the ratchet reads them as passes.
3. Tuple return types (`fun f(…): (str, i64)`) — the next rejection in
   `ext/ward/src/nn/init.duo` after this one was fixed.
4. `const` and `defer`, both trivially shaped and both zero-use in lib/std.
5. Make `parser_corpus_coverage` ratchet on a root that includes `ext/ward` and
   `tools`, so the denominator stops being the dialect the parser already
   handles.

## 7. 2026-08-09 stash audit: offside over-indent is silently accepted

The current Duon parser closes a body only when a later token is left of the
first statement column. It does not reject a later statement that is farther
right even though no preceding source face opened a nested body:

```duo
f: i64 = (n: i64)
    t = 0
        n = 1
    t
```

Measured against both authorities in the same checkout:

```text
duo check probe.duo
  error: indentation matches no block
  exit 1

std.compiler.parser.parse_status(source, "probe.duo")
  0
```

This is another accepted-but-wrong row that the 257/257 acceptance ratchet
cannot see. `stash@{1}` contains an attempted offside implementation and the
missing negative case, but it also modifies Lua benchmarks, preserves written
`end`, and carries an older parser model. Do not apply it wholesale. Transplant
the negative control, then implement the production rule in canonical Duon:
each body has one established statement column, a deeper line is legal only
when the preceding semantic face opened a nested body, and any other column is
a structured diagnostic. Differential the projected structure, not merely the
accept/reject status.
