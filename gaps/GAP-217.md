# GAP-217 — transform provenance witnesses a call shape, not a transform

## Status
open — producer-hollow. The record exists, is emitted, and cannot support
the claim its schema makes.

## Claim under test
`transform-provenance-v0` (`src/transform_engine.zig:200`) emits, per
dispatch, `{transform, site, inputs_hash, output_hash, evidence}`. The two
hash fields assert that a transform took an input and produced an output.

## Measurement
Three probes, `idol explain`, compiler at 31453966.

Renaming the applied relation `add` -> `mul` changes the hash
(`6a61f67094faf019` -> `c7357f9ab9bd1d2b`), so the value is not a constant.
But changing the relation's entire BODY, `a * 10 + b` -> `a + b * 7`, with
names held fixed, yields a byte-identical record:

    6a61f67094faf019 6a61f67094faf019 51c667dc3a0d1830
    51c667dc3a0d1830 6a61f67094faf019 6a61f67094faf019

for both bodies. And on every entry `inputs_hash == output_hash`.

## Why
`inputs_hash` is `CallShape.identityHash()` -> `CallShape.fingerprint()`
(`src/types.zig:1968-1980`), a Wyhash over callee_kind, arg_count,
known_args_mask, typed_args_mask, has_varargs, return_consumption,
receiver_shape_known, callee_name, method_name. It is a hash of the CALL
SITE'S SHAPE. It contains nothing about the transform's input value, and
nothing about any output.

All four production call sites pass it twice:

    src/codegen.zig:4893   logProvenance(..., .emit_call, hash, hash)
    src/codegen.zig:4975   logProvenance(..., .emit_call, hash, hash)
    src/codegen.zig:4994   logProvenance(..., .emit_call, hash, hash)
    src/codegen.zig:5010   logProvenance(..., .emit_call, hash, hash)

So `output_hash` is definitionally equal to `inputs_hash`, and a record for
a transform that fired is indistinguishable from one that did not.

## The tree already ruled on this
`src/types.zig:1982-1983`:

    /// Physical bridge for the remaining codegen provenance consumer.
    /// Delete with its three `identityHash` call sites; this value never
    /// owns meaning.

The type declares itself a deletion target. The comment says three call
sites; there are four.

## Deletion witness
- Semantic entity? No. A call-site shape fingerprint is a physical index.
- Already in the graph? The application, its operands and its result have
  semantic identities. This hash is a fourth, weaker name for the same site.
- Survives renames / AST movement? No — `callee_name` is hashed, so a rename
  changes the "provenance" of an unchanged transform. Measured above.
- Deletion condition: stated in-tree. Delete with the `identityHash` call
  sites once provenance carries semantic value ids.
- Could two stores disagree? Yes, and they already do: this hash disagrees
  with semantic identity under rename in one direction and under total body
  replacement in the other.

## Related
`logProvenanceGraph` carries `{relation, application, subject, input_value,
output_value}` — the semantically correct shape — but has zero production
call sites, so every emitted record carries a null graph. The correct fix
is to route the four codegen sites through it and delete the shape hash,
not to add a fifth hash.

Consumer status of the record itself is unestablished. Do not treat the
JSON serializer as a consumer.
