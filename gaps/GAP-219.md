# GAP-219 — three PR-review findings that are real but not closed here

Raised by automated review on PR #70. A fourth finding from the same review
(the attribution gate scoring failed compiler runs as clean compiles) WAS a
live defect and is fixed in `aa46940c`. These three are real and open.

## 1. Field-write collection matches a shadowing binding by spelling

`registerTableFieldGlobals` -> `collectFieldWriteTypes` scans "every write
anywhere in the module, module scope and relation bodies alike" for
`name.field`. A relation that declares a parameter or local ALSO named
`name` writes its own binding, but the scan matches by SPELLING and counts
it as a write to the module table.

MEASURED, and it is milder than reported. A local shadow

    M = { x = 1 }
    bump: i64 = ()
        M = { x = 5 }
        M.x = 99
        M.x
    main: i64 = ()
        a = bump()
        M.x

REFUSES with `global-init-not-constant:M`. It does not emit a read or
mutation against the wrong binding, so this is not a live wrong-answer bug.
A parameter shadow refuses earlier still, at `param-type:inferred`, because
a relation taking a table parameter is outside the native scalar subset.

It remains a defect: the refusal is incidental rather than intended, and it
is identity-by-spelling in a project whose whole thesis is that spelling
never decides identity. The fix is to stop descending into scopes where the
base name is rebound, and apply the same scope handling to the sibling
scans (`moduleHasFieldWrite`, `moduleWritesNameBySubscript`).

ACCEPTANCE: a fixture where the shadow case COMPILES and answers the
module value, plus a negative control proving the non-shadowed write still
takes storage.

## 2. `lib/compiler/token.id` carries noncanonical identifiers

The executable grammar owner uses `KIND_TEXT_LIT`, `KIND_COMPAT_LONG_TEXT_LIT`,
`ROLESLOTCOUNT` and the mashed `rolebeginexpr`. Uppercase and underscores
are denied for canonical `.id`, and `rolebeginexpr` violates one-lowercase-word.

Partly inherited: 104 of the uppercase identifiers predate the transfer,
which added roughly 78 more. A sibling commit (`06feca94`) already
lowercased seven in the generated projection.

Not fixed inline because the names are load-bearing in two GENERATED
artifacts (`src/grammar_role_table.zig`, `lib/token/grammarrole.id`) and in
`src/parser.zig`'s consumers; renaming is a mechanical pass that must
regenerate both projections and prove byte-identity through
`gate/grammar-projection.sh`. It is a rename, not a redesign, and it should
happen before anything else generates from this owner.

## 3. Path names violate `law.path.name`, and its gate is broken

`AGENTS.md:550-561` forbids snake_case, kebab-case and mashed stems in
project-controlled path components. `src/grammar_role_table.zig`,
`gate/grammar-projection.sh`, `gate/module-zero-precheck.sh` and
`examples/keyed_table_*.id` all violate it.

Two facts decide how to treat this. The rule is essentially unenforced in
the trees involved — `src/` already carries `abi_resource.zig`,
`assumption_guard.zig`, `async_lower.zig`, `semantic_graph.zig`, and
`gate/` already carries `architecture-companion.sh`, `cache-home.sh` —
so renaming four new files while ~200 siblings keep the same forms buys
consistency with the law at the cost of consistency with the tree.

And the enforcer is broken: `gate/path.id` fails its own positive controls.

MEASURED SUBJECT, pinned. Compilers built from `idol/main` at `7483b1b4`
(and the identical `gate/path.id` at local `f5d87d40`, byte-identical
between the two). Instrumented arms and the contaminated worktree build are
named individually below. Relative `HEAD` labels are deliberately avoided:
once the branch advances they name nothing.

CORRECTED MEASUREMENT — the first reading of this named
`control FAIL: utils organizational home not rejected`, which was taken with
a binary built from the working tree while it carried another lane's
uncommitted changes. That binary fails TEN controls; a compiler built from
clean HEAD fails TWO, and `utils` is not among them. Verified across four
binaries (pre-projection-fold, `7483b1b4`, `7483b1b4`+one-producer, and a
build from the contaminated live worktree): the
first three all report exactly 2, the worktree build reports 10.

The two genuine failures at `7483b1b4` are:

    control FAIL: view(edges) curried binding rejected
    control FAIL: zerohistorycensus mashed census path not rejected

The conclusion is unchanged and the evidence for it is now correct: a gate
whose own positive controls fail cannot be trusted to reject anything, which
is why every commit in PR #70 passed it. `utils` in particular IS handled
correctly at `7483b1b4` — `known("utils")` is false (it is absent from the
`words` list) and `member(orghomes, "utils")` is true, so `orghome` fires as
designed.

A separate finding falls out of the same measurement: the uncommitted
working-tree changes cause EIGHT additional control failures on top of the
two, in the same tree whose changes also make `lib/compiler/token.id` emit
every token kind with an empty name. That is the higher-priority defect of the two: a law with a
non-functioning gate is decoration, and repairing the control must come
before any bulk rename, or the rename cannot be verified.

ACCEPTANCE: repair `gate/path.id`'s positive control first; then decide
tree-wide rename or explicit scoped exemption, and record which.
