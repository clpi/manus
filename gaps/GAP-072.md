## What was measured

1e9-iteration i32 multiply-add kernel (`benchmarks/wasm_rt/hot.c` with the bound
raised, `clang --target=wasm32-wasip1 -O1 -fno-unroll-loops`), positive-controlled
by halving the bound and confirming the time halves. **All five runtimes return
`3725993217`** — verified by value, not by exit status.

| runtime | best wall |
|---|---|
| wasmtime | 1.05 s |
| wasmer | 1.21 s |
| ward (`engine=jit-arm64`) | 1.32 s |
| wart (JIT — its default) | 1.36 s |
| ward (`WARD_ENGINE=interp`) | 43.04 s |

ward is 3% faster than wart, 26% slower than wasmtime, and last of the four
JIT-class runtimes. ward's own ARM64 JIT is worth **29×** over its interpreter,
in 820 lines of Duo.

## The three defects this exposed

**1. Two beliefs in the session notes were false.** wart was recorded as
un-buildable and SIGILL-ing on ARM64 macOS with no local baseline. It builds
clean (`BUILD_EXIT=0`) and its JIT runs and is correct. The documented command
`zig build -Doptimize=ReleaseFast` in `~/x/wart/CLAUDE.md` fails on current zig
master — wart's `build.zig:275` sets `preferred_optimize_mode`, so the flag is
`-Drelease=true`. A stale doc line, read as a broken runtime, and it removed the
oracle from the harness for an unknown period.

**2. wart JITs by default, so every "wart interpreter" column is mislabeled.**
`~/x/wart/src/config/types.zig:25` — `jit: bool = true`. There is no `--no-jit`,
and a cwd `wart.toml` with `jit = false` is not honoured (verified: `-V 1` still
prints `JIT: true`). `-j` is a no-op. `ext/ward/bench/run.id:87` still treats
exit 132 (`128+SIGILL`) as wart's expected failure — a dead arm guarding a
condition that does not occur.

**3. `ext/ward/README.md` fabricates both sides of its headline ratio.** It
claims wart is "~1.3M lines of Zig" and ward "~1,500 lines of Duo". Measured:
**121,283** and **11,350**. Both wrong by about an order of magnitude, both in
the flattering direction, and the comparison table beneath them (binary size,
startup time) carries no measurement at all. The true ratio is **10.7×**, which
is a strong result that does not need inflating. This is a §3 violation on the
runtime's front page.

## What ward would still lack after any of this

Grepped against `src/ward.id` (6,312 lines), **zero hits each**: component
model, threads, atomics, exceptions, GC, multi-memory, memory64, tail-call,
relaxed-SIMD. `src/wasm/aot.id` is 10 lines whose `compile()` returns `""`.
`wasi.id` is 285 lines of P1 against wart's P2+P3 worlds. No x86-64 JIT. A
dominance claim scoped to "the opcodes ward implements" is defensible; one
scoped to "WASM runtimes" is not, and the scope has to be written into the
table.
