**Owner files:** `src/lexer.zig`, `src/ast.zig`, `lib/std/compiler/parser.duo`

the report's only NO FIXTURE row and is `—` because of this

The current constitution gives `@` exactly two admitted roles: bare `@` names
the enclosing descriptor, and postfix `X@rel` selects relation `rel` anchored
at `X`. Prefix compiler directives do not exist. Leading-dot fields are a
separate retired source face and are not an anchor stance.

## The conflict, in three commands

**The self-hosted parser reads it as the anchor.** `lib/std/compiler/parser.duo`
declares the production at `:55` and builds the node at `:1386`:

```
--   anchor  := (anchor <expr> <name>)                postfix foo@bar
```

and `examples/pass16_parser_corpus_proof.duo` pins the projection:

```
{ "bar = foo@7", "(program (assign bar (anchor foo 7)))" },
```

**The Zig front end reads it as MATMUL.** `src/lexer.zig:752` produces a `.at`
token and the parser folds infix `@` into the `.matmul` binary operator
(`src/ast.zig:213`). `duo check` on

```duo
main = (): i64
    print(i64@to(str) != nil)
    0
end
```

says

```
warning: infix '@' matmul is non-canonical; prefer explicit tensor APIs or typed helpers
✓ checked — no errors
```

**Codegen then dies on the meaning nobody wanted.** `duo run` on the same file:

```
/tmp/duo_a1_postfix.c:5980:26: error: use of undeclared identifier 'to'
        lua_Value __fn = to;
error: C compiler failed (exit 1)
```

So the front end accepted a Pass 100 anchor as a tensor product, warned about
the tensor product, and handed the C compiler a program with a free variable.
`✓ checked — no errors` on a construct whose meaning the compiler does not have
is the part that makes this a gap and not a missing feature.

## The other two stances are also unimplemented, and they fail LOUDLY, which is fine

```
node: @{ value: i64, next: @ }
    -> error: expected 'name', got '}'                       (bare @ names it)

span: @{ start: i64, stop: i64, width = () .stop - .start }
    -> error: descriptor fields use 'name: Type' syntax, not '='   (GAP-025)
```

Those are honest refusals. They are not this gap; they are the reason the row
has no positive fixture to point at.

## And one form that should NOT exist does

`value.@name` is in Pass 48's graveyard (Part VI), alongside `point:@to` and
`Point.@to`. `scripts/spec_conformance.duo:139` carries a row asserting it is
ABSENT and expects that row to FAIL. It still parses and still checks clean:

```duo
main = (): i64
    p = {}
    print(p.@eq == nil)
    0
end
-- ✓ checked — no errors
```

## Why there is no fixture, and why that is the right answer for now

A fixture has to assert something. Written against the Zig front end it would
pin the matmul reading, which the spec denies; written against the self-hosted
parser it would pin a projection the compiler that ships does not implement.
Either one converts a disagreement into a claim. `zig build capability-rows`
therefore prints `—` across the `anchor semantics` row and names it under NO
FIXTURE, which is what an undecided capability is worth.

## What closing this looks like

1. Consume the constitution's postfix-relation anchor role in the production
   front end; do not rederive it from token adjacency or operator spelling.
2. If the anchor wins, infix `@` must stop being matmul — the deprecation
   warning is already there, so the warning becomes an error and the tensor
   spelling moves to a named operation.
3. Delete the `.@name` form or revisit the graveyard ruling, and make
   `spec_conformance.duo`'s `GRAVEYARD .@name absent` row mean what it says.
4. Then a fixture can exist, and the `anchor semantics` row can be measured
   instead of reported empty.

Until step 1, the useful invariant is the narrow one: **`duo check` must not
exit 0 on a construct it has no meaning for.** Refusing `i64@to(str)` outright
would be strictly better than accepting it as a tensor product.

## What landed, and why it landed in sema rather than the parser

The verdict is a TYPE question. `x @ y` over two `Tensor[..]` is a real,
shape-checked operation with three fixtures of its own
(`examples/compile_fail/tensor_matmul_*.duo`), and it is the only spelling that
operation has today; `p@x` over a record is the spec's anchor spelling with no
meaning here. The parser cannot tell those apart — it sees one token. Sema can,
and until now sema held no belief about `@` at all: 19 decision sites in
`parser.zig`, 0 in `sema.zig`, which is precisely how the two subsystems came
to disagree in the first place. So the parser's duo-mode `.matmul` warning was
deleted and `check_infix_at` replaced it: warn for tensor operands, error for
everything else, gated on `duo_mode`.

Measured, same file both ways:

```
examples/compile_fail/anchor_infix_at.duo
  c07bd7e            exit 0   ✓ checked — no errors        <-- the false green
  with this change   exit 1   error: infix '@' has no meaning in .duo …
                              hint: §2 gives the anchor two stances …
```

`duo check` over all 767 tracked `.duo` files, exit code diffed per file
against c07bd7e: **zero regressions** (60 files already failed, same 60). The
corpus contains no infix `@` over non-tensor operands — the positive control
for that zero is the row above, which the same sweep method catches.
