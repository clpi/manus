# GAP-023 — two lexer proofs regress when the compiler lexes itself with Duo

**Status:** CLOSED 2026-08-07 · **Filed:** 2026-08-07 · **Frequency:** 1
**Blocks:** nothing — SH-03 `tokenizeAuthority() == .id_native` ships.

## CLOSED — both halves

**Lexer half.** `_int_of` in `lib/std/compiler/lexer.id` accumulates decimal
and hex digits directly in i64, never through f64, so the Duo lexer and
`src/lexer.zig` now agree on integer literals above 2^53.

**Native half (269ec5b).** With the lexer correct, the text differential still
failed — first as exit 1, then, once a separate const-return fold bug was fixed
(533063d), as SIGSEGV. Cause: a native `main` never initialises the Lua runtime
it links against.

    main -> duo_lexer_text_fingerprint -> next_tok
         -> lua_require -> lua_table_get_raw_str_lit
         -> KERN_INVALID_ADDRESS at 0x68

The C backend's main opens `package = lua_package_init()`; the direct backend
emits no equivalent and cannot, since that function is `static inline`. The
direct path now declines when the executable must link Duo module objects, so
`auto` falls through to the C emit.

    pass16_lexer_text_differential          139 -> 0
    pass16_lexer_fingerprint_differential     0 -> 0

`to(i64)(str)` REMAINS LOSSY above 2^53 — that is the general primitive and is
not what the lexer uses. It stays open as its own row rather than being called
closed here.

## ROOT CAUSE FOUND (2026-08-07) — large integer literals lose precision

The hypothesis-free probe settled it in one step: diff the generated C for a
regressing proof under both authorities. 495132 bytes each, **four diff lines,
one constant**:

    host:  if ((corpus_text_fingerprint() != (-4810305713451201937)))
    duo:   if ((corpus_text_fingerprint() != (-4810305713451201536)))

That is the text fingerprint in its i64 spelling. (Earlier greps looked for the
u64 form `13636438360258349679`, which appears only in a comment — which is how
I twice concluded no such literal was lexed. It is lexed; it is spelled
negative.)

The delta is 401 and `…201536` is a multiple of 512: the signature of a value
round-tripping through an f64 mantissa. 4.8e18 needs 63 bits; f64 carries 53.

Measured directly:

    to(i64)("4810305713451201937")  ->  4810305713451201536   LOSSY
    tonumber("4810305713451201937") ->  4.8103057134512015e+18
    the literal 4810305713451201937 ->  4810305713451201536   LOSSY

So **Duo has no exact string-to-i64 conversion for values needing more than 53
bits**, and its own integer literal handling shares the defect. `src/lexer.zig`
parses exactly (`parseInt`), so the two lexers disagree on any integer literal
above 2^53 — which is exactly and only the two fingerprint proofs.

This subsumes GAP-024: the host overflowing on a u64 literal above i64 max and
the Duo side rounding an i64 literal above 2^53 are the same wound — integer
literals wider than the conversion path can carry.

**I introduced the specific regression** in 463a145, replacing
`tonumber(text) or 0` with `to(i64)(text)` on the INTEGER path while fixing
GAP-021 on the float path. The float fix is correct and stays; the integer path
needs an exact conversion that does not exist yet, which is the remaining work.

## What closing this needs

An exact decimal-to-integer conversion in Duo that never touches f64 — digit
accumulation in i64/u64 with an overflow rejection. That is a small, well-shaped
piece of Duo, and it closes GAP-023, GAP-024, and the recorded
u64-above-i64max-collapse together.

## The original hypothesis — DISPROVEN, kept as a record

Both proofs carry **lexer corpus data as string literals**. They are therefore
the programs most sensitive to how the compiler lexes string literals, which is
precisely what changes when the compiler lexes itself with the Duo lexer.

This has the same shape as a failure already recorded in this repo: a blanket
`~=` pass once rewrote a lexer's own corpus data, and `scripts/spec_conformance.id`
had its test PROGRAM interpolated as if it were the harness's own source
(GAP-016). Data that is itself source is the recurring trap here.

It is a strong hypothesis and nothing more. It has NOT been isolated, and the
two unit-test failures are unexplained by it.

## Where to start

1. Diff the two proofs' token streams under both authorities — the
   `differential()` in `src/duo_lexer_dispatch.zig` already does this for
   arbitrary source and currently passes on all 8 of its cases, so feed it the
   proof files themselves. If it stays green on them, the divergence is NOT in
   tokenization and the hypothesis above is wrong.
2. `c_sim_import` and `native_barrier_checks` touch neither strings nor the
