# GAP-228 — a shadowing relation-local declaration is given the module binding's word

**Status:** CLOSED · **Filed:** !2026-08-23T00:00:00Z · **Closed:** !2026-08-25T00:00:00Z
**Priority:** P1 · **Kind:** wrong_answer
**Filed by:** claude-mutation
**Files:** src/dnir_lower.zig,examples/place/mutate.id

## The defect

A relation that DECLARES a binding of the same spelling as a module-scope
`global` writes the module's `__DATA` word. The declaration is a new binding
with its own lifetime; the module's word is a different place, and the program
reads the shadow's value out of it.

Reduce it — the whole program, `--backend=direct`:

    global ring: i64 = 0

    shadow(): i64
      ring: i64 = 5
      ring

    print(shadow())
    print(ring)

    -> 5
    -> 5      and the answer is 0

## It is not the graph, and the graph says so

    zig-out/bin/idol graph <that file> | jq -c '.mutations, [.nodes[]|select(.name=="ring")|{id,scope}]'

    []
    [{"id":2,"scope":0},{"id":3,"scope":1}]

Two DISTINCT entities — the module binding at scope 0 and the relation's own at
scope 1 — and the mutation column (`gaps/GAP-225.md`) is EMPTY, because nothing
writes the module binding. The lift adjudicated the shadow correctly. The
storage decision in `dnir_lower.collectModuleGlobals` / the store path keys on
the NAME being registered as a module global, so it cannot see the adjudication
the graph already performed.

`place.zig`'s `BindOrigin` records the same class one level down: "Measured at
09b20611: a module table owning field storage and shadowed by a relation-local
declaration answered the shadow's write from the module's word, and no v9
export distinguished the shadow from a plain module write."

## Why it was found here and left open here

`examples/place/mutate.id` is GAP-225's regression fixture and carries
`shadow()` as its negative control: the lift must keep a genuine shadow
distinct while collapsing the shadow entities it used to mint for real writes.
Its GRAPH row is checked. Its STORAGE row is not, and the comment in that file
says so and names this gap, rather than pinning a passing assertion beside a
wrong answer.

## Acceptance

1. A relation-local declaration shadowing a module-scope binding gets its own
   storage, and the reduction above prints `5` then `0`.
2. The store decision reads the graph's binding entity rather than the
   spelling — `SemanticGraph.binding_mutations` already names the exact binding for a real
   write, and `resolveBindingInScope` already answers the shadow question.
3. A control in the other direction: a real write from a relation that does NOT
   declare the name keeps the module's word, which `examples/place/mutate.id`
   already checks by value.

## Closed — measured at fc48acea, in two halves

This host is x86_64: `--backend=direct` refuses with DNB004 by design, and the
C99 realizer refuses this program shape outright (`operation-not-in-c99-slice`
— the slice carries no `store_global`/`load_global` and no `print`), so the
exercised realization of the storage decision here is `--backend=wasm`, whose
backend consumes the same DNIR `store_global`/`load_global` rows the direct
backend does. Every value below is that path, plus the DNIR shape pinned
directly in unit tests.

### The declaration half was already repaired on main

Commit `92909911` (#151) made `lowerStmt`'s `.local_decl` arm publish the
declaration's own slot into the lowering's binding environment BEFORE its
initializer lowers, so the initializer's store and every later mention inside
the body resolve to the shadow's slot, never the module word. Measured at
fc48acea, the reduction above answers

    5
    0

and the interleaved control (shadow, then a module write from a relation that
declares nothing, then a module read) answers `5` then `7`. The DNIR shape is
pinned by `test "dnir_lower: same-spelled local shadows module storage by
binding"`: the shadowing body carries a `store_local` and no `store_global
ring`; `main` still reads the module word (`load_global`).

### The extent half was still live, same producer, opposite direction

The class the filing names — the storage decision keys on the SPELLING and
cannot see the graph's adjudication — was still answering wrongly one shape
over. `ctx.locals` had no block extent, so a declaration inside a nested block
stayed in the map after its block closed and a module write BELOW the block
was answered from the leaked shadow slot. Measured at fc48acea before the
repair, `--backend=wasm`:

    global ring: i64 = 0
    deep(): i64
      if ring > 100
        ring: i64 = 5
        return ring
      ring = 2
      3
    print(deep())
    print(ring)

    -> 3
    -> 0      and the answer is 2

with the graph RIGHT the whole time — `mutations` names exactly the module
binding, written by `deep`:

    [{"relation":1,"binding":2}]
    [{"id":2,"scope":0},{"id":3,"scope":1}]

The repair is `noteBlockDeclarations` / `restoreBlockDeclarations` around
`lowerBlockReturns` in `src/dnir_lower.zig`: every nested block records, for
each name its own statement level DECLARES, the mapping it is about to shadow,
and restores it at block exit — prior slot back, or the entry removed so the
next mention falls through to the storage the graph adjudicated. Only
`.local_decl` rows are recorded, because only a declaration is a new binding;
a bare assignment targets whatever binding is visible, and diverting it would
be the opposite defect (`bodyDeclaresBinding` documents that measured pair).
This is the same adjudication the lift performs — `liftBindingsInBlock`
shrinks its `declared` roster at block exit — consumed by the lowering instead
of re-derived from spelling. After the repair the program answers `3` then
`2`.

### Acceptance, row by row

1. The reduction prints `5` then `0` — measured above.
2. The store decision now agrees with the graph's binding adjudication at
   every site: the declaration publishes its own binding before its
   initializer, and the binding's extent is its block, exactly the roster rule
   `noteModuleWrite` used to publish `binding_mutations`. Verified against the
   graph per program (the `jq` rows above) and pinned at the DNIR layer by the
   two unit tests; disabling the restore fails exactly `test "dnir_lower: a
   module write below a closed shadow block reaches the module word"` and
   nothing else (positive control, 1 fail of 1828).
3. The control holds and is now CHECKED BY VALUE: `examples/place/mutate.id`
   reads `ring` back after `shadow()` (`!= 1` is return 6) and after `deep()`
   (`!= 6` is return 5, where 6 = the write above the block times the write
   below it), beside the graph rows it always checked. The fixture answers
   `place mutate: OK`, exit 0, on `--backend=wasm`.

Aggregate: `zig build` green; `zig build unit-test` green (1766 passed, 62
skipped, 0 failed); `gate/realize/census.sh` unmoved at 243 subjects, 54
check-refused, 13 realized, 176 realizer-refused — the C99 slice never carried
global storage, so the extent repair cannot move it.
