# GAP-039 — the dense-table bounds check is the last per-element cost, and no C compiler will remove it

**Status:** open · **Filed:** 2026-08-08 · **Frequency:** 1
**Cited at:** `examples/benchmark.duo` — `table_max_scan`, `prefix_sum`,
`dot_product`, `matmul`, `life`, `sparse_dot`. Every dense-table row that still
loses to reference C loses here.

(Took 039 after checking `gaps/` in this worktree AND in the sibling
worktrees: 038 was the highest, held by `.claude/worktrees/pass81-family-registry`.
`gaps/` is a shared numeric registry with no allocation protocol, so expect to
renumber.)

## What this is not

This is not the boxed loop bound. That was the other half of the same
investigation and it is **fixed** — see the `while_bound_hoist` commit. With
the bound hoisted, the remaining gap on these rows is entirely the accessor.

## The mechanism

`duo_dt_get_i64` is safe by construction: a wrong capacity guess cannot read
out of bounds, because every read is guarded.

```c
static inline ty duo_dt_get_##sfx(ty* p, int64_t cap, int64_t i) {
    return __builtin_expect((uint64_t)i < (uint64_t)cap, 1) ? p[i] : (ty)0;
}
```

That guard is one compare and one select **per element**. On a reduction it
lengthens the critical path; on a loop that would otherwise vectorise it is
fatal, because a speculative vector load past `cap` would be a real
out-of-bounds read, so LLVM cannot mask it — it simply does not vectorise.

## Measured ceiling

Method: `duo compile --pgo -O3 examples/benchmark.duo`, then the emitted
`/tmp/duo_benchmark.c` rebuilt three ways with the suite's own flags and PGO
(instrument → profile → use). Self-relative, same file, same flags; only the
accessor differs. Min of 3 runs.

| row | as emitted | bound hoisted | hoisted + **unchecked** | reference C |
|---|---|---|---|---|
| Table max   | 0.00101 | 0.00097 | **0.00051** | 0.000327 |
| Dot product | 0.00090 | 0.00099 | **0.00068** | 0.000712 |
| Prefix sum  | 0.00702 | 0.00701 | **0.00242** | 0.00233 |

Unchecked access alone is worth **2.0x** on Table max and **2.9x** on Prefix
sum, and it is what flips **Dot product** to a win. Prefix sum lands within 4%
of C. Note that Prefix sum is a serial dependence chain (`t[i] = t[i] +
t[i-1]`) and cannot vectorise at all — its 2.9x is the select on the critical
path, not lost SIMD. Both costs are real and they are separate.

## Why LLVM will not do this for us — tested, not assumed

The obvious hope is to hand the C compiler enough facts and let it fold the
guard itself. It does not. Tested: hoisting the loop bound to a native local
AND reserving the buffer from that same SSA value, so that `cap >= n+1` and
`i <= n` are both visible at the same point:

```c
int64_t __hoist_n = (int64_t)lua_to_num(n);
duo_dt_reserve_i64(&__dt_t, &__dtc_t, __hoist_n + 1);
while (i <= __hoist_n) { ... duo_dt_get_i64(__dt_t, __dtc_t, i) ... }
```

Result: **0.00101 → 0.00098 on Table max. No change.** LLVM will not carry the
monotonicity of `cap` across the growth path (`duo_dt_grow_*` can only
increase it, but proving that is an inductive argument over a `realloc` that
may fail). So the elimination has to be done by Duo, on Duo's own terms — the
C compiler is not going to rescue it.

## What a fix has to look like

Emitting raw `__dt_T[i]` unconditionally is not acceptable — that is exactly
the fixed-capacity overrun the grow-on-demand runtime exists to prevent, and a
use-after-free has already shipped in this area once. The fix has to *prove*
the index, not assume it. Two routes, in increasing order of honesty:

1. **Loop versioning.** For a loop with an affine induction variable and a
   loop-invariant bound, compute the min/max of each index expression from the
   loop extremes, emit one runtime guard before the loop (`__dtc_T > max_idx
   && min_idx >= 0`), and emit two bodies: unchecked on the fast arm, the
   current checked accessors on the slow arm. Sound at runtime with no static
   index proof, which is what makes it tractable. Cost: the loop body is
   emitted twice.

2. **Reserve to the proven high-water mark, then narrow the accessor.** The
   cap solver currently only ever considers the function's single parameter —
   see `detect_dense_table` in `src/sema.zig`, `param_is_bound`. It already
   guesses badly in both directions: `ring_buffer` reserves `n+1` = 5,000,001
   slots (40 MB) for a 1024-element buffer, and `life` reserves `steps+1` =
   501 for a grid that reaches 16,384. Neither is a correctness bug — the
   runtime grows — but a cap derived from the *fill loop's* bound rather than
   the parameter would be a prerequisite for any in-range proof.

Route 1 is the one that pays. It needs an index-range analyser over affine
expressions in the loop variable, which does not exist yet.

## Adjacent finding, same rows: element width

Not the same gap, but it caps what the above can win on one row. `life` loses
6.6x and the bounds check is **not** why. Reference C declares the grid
`int8_t` (16 KB, vectorises 16-wide, fits L1); Duo's dense tables are
`int64_t` only (128 KB per grid, 2-wide). Measured on a standalone reproduction
where both sides used raw unchecked indexing, `int64_t` was 0.0075s against C's
0.0028s — the whole remaining gap is the 8x data width. Closing it means
narrowing a dense table's element type when every value stored into it
provably fits (in `life`, every store is `(cond) ? 1 : 0`). That is a separate,
larger piece of work and should be its own gap when someone picks it up.
