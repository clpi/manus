# GAP-028 — the DUO parser rejects a receiver face inside parentheses (SH-04 gap)

**Status:** FIXED 2026-08-07 · **Filed:** 2026-08-07
**Blocks:** the `string.byte` → `x:byte(i)` sweep (gap[025]); any FACE-CALL
repair touching a compound condition

## FIXED — `is_lambda_head` read a receiver face as a parameter annotation

`lib/std/compiler/parser.duo`'s `is_lambda_head` scans a parenthesised group and
treats a depth-1 name followed by `:` as a parameter annotation, i.e. a
value-form function head. `(t:byte(2) == 120)` matched that: `t` then `:`. The
whole group became a lambda head and the expression never parsed.

The fix is the discrimination the HOST parser already makes in
`colon_is_method_call`: `: name (` is a call, not a shape. Applied in the Duo
parser, all four probes pass — including the two controls that must keep
working:

    x = (t:byte(2) == 120)                          0   was 1
    if (t:byte(2) == 120 or t:byte(2) == 88) ...    0   was 1
    g = (a: i64) a + 1        (lambda head)         0   control
    (a + b) * 2               (plain group)         0   control

Parser coverage 256/256, selfhost proofs 12/12.

## Historical: MISFILED as a host-parser bug

`parse_status` is `std.compiler.parser.parse_status` — the **Duo** parser
(SH-04). The host parser accepts the construct without complaint:

    duo check on  `x = (t:byte(2) == 120)`   ->  ✓ no errors

And the whole conversion compiles: `lib/std/compiler/lexer.duo` with all 16
`string.byte` sites converted builds its artifact with **0 errors**.

So the construct is valid Duo. Nothing is broken in the language or the host
compiler. What is missing is **coverage in the Duo parser**, which is exactly
what SH-04 is: a recursive-descent parser still short of the full grammar.

That also re-reads the original symptom. SH-09's `rewrite_proof` walks lib/std
through `P.parse_status` and reported "STOPPED PARSING after rewrite" — it was
reporting a Duo-parser limitation, not a defect in the rewritten source. Every
narrowing I did after that was chasing a host-parser bug that does not exist,
including a fix attempt on `scan_func_header_signal` that could never have
worked.

## The defect, precisely (as a Duo-parser coverage row)

A parenthesized group whose first tokens are `name:method(` does not parse,
anywhere:

```duo
x = (t:byte(2) == 120 or t:byte(2) == 88)    -- parse_status 1   ASSIGNMENT
if (t:byte(2) == 120) ...                    -- parse_status 1   no `or` needed
if (t == "a" or t == "b") ...                -- parse_status 0   no face
if t:byte(1) == 48 ...                       -- parse_status 0   no parens
```

So it is the pair — **parentheses + a leading receiver face** — not the
condition, not `or`, not nesting. My first framing said "condition"; three of
the four probes above disprove it.

**`scan_func_header_signal` is DISPROVEN as the site.** Making a depth-1 method
call `return false` outright (rather than merely declining to set
`typed_or_vararg`) changes nothing — both probes still fail. So the group is not
being misread as a parameter list, and the real site is elsewhere in expression
parsing. Reverted.

**Former suspect (wrong):** `scan_func_header_signal` (`src/parser.zig:1638`), the
lookahead that decides whether `(` opens a bare function-declaration parameter
list. `(t:byte(2) == 120)` survives its early guards — it does not open with
`(`, and `colon_is_method_call` correctly returns true for `t:byte(` so
`typed_or_vararg` stays false — and the group is then taken for a header.
`(t == "a" ...)` differs only in having no `:` at depth 1, which is consistent
with the observation.

## Historical framing: "inside a parenthesized condition"

`subject:method(args)` parses in an `if` condition, and stops parsing the moment
that condition is parenthesized:

```duo
if t:byte(1) == 48 return true end                          -- parse_status 0
if (t:byte(2) == 120 or t:byte(2) == 88) return true end    -- parse_status 1
if n > 2 and (t:byte(2) == 120 or t:byte(2) == 88) ...      -- parse_status 1
```

The same shape with the operation-first spelling is fine, which is what makes
this a FACE-CALL blocker rather than a general parenthesization bug:

```duo
if n > 2 and (string.byte(t, 2) == 120 or string.byte(t, 2) == 88) ...  -- 0
```

So: receiver face + parentheses + condition. Any two of the three are accepted.

## How it was found, and the two traps on the way

Converting `lib/std/compiler/lexer.duo`'s `string.byte` sites flipped
`parse_status` to 1. Bisection said "occurrence 9". I then spent four probes
disproving hypotheses about **line 393**, because `grep -n` had listed line 393
as the 9th MATCHING LINE while the regex counted the 9th OCCURRENCE — and
line 389 contains three of them.

Line 389 is the real site, and it is the only one in the file wrapped in
parentheses:

    if n > 2 and string.byte(text, 1) == 48 and (string.byte(text, 2) == 120 or ...)

**Trap 1: a line count is not an occurrence count.** Every probe was correct
about a construct that was never the one failing.
**Trap 2:** shape, nesting, accumulation and the `#`/face combination were each
disproven — all true, all irrelevant, because the target was wrong.

## The fix

The condition parser accepts `name:method(...)` at the top level of a clause but
not inside a parenthesized group within one. Likely the same clause
self-delimitation rule that forbids top-level parenless application in clause
position, applied one level too deep.

Fixtures: the three lines above, plus the operation-first control that must keep
passing.
