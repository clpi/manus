# GAP-028 — a `gmatch` nested inside a `gmatch` drops iterations

**Status:** open · **Filed:** 2026-08-07 · **Frequency:** 1
**Cited at:** `scripts/run_benchmark.duo` (`extract_times`)

## Repro

```
txt = "a Time \t1.5\tsec\nb Time \t2.5\tsec\nc Time \t3.5\tsec"

n = 0
for line in string.gmatch(txt, "([^\n]+)")
    n = n + 1
end
-- n == 3, correct

m = 0
for line in string.gmatch(txt, "([^\n]+)")
    for w in string.gmatch(line, "([^%s]+)")
        m = m + 1
    end
end
-- m == 4.  Expected 12 (3 lines x 4 words).
```

The outer loop alone is correct, so the inner `gmatch` corrupts the outer
iterator's state rather than the pattern being wrong.

## Why it mattered

`extract_times` in the benchmark harness used exactly this shape — iterate
lines, then iterate words to find the first numeric one. It returned **2**
timings for a 40-benchmark run. Every row printed `N/A`, so every winner
defaulted to C and the suite reported that Duo lost all 40 benchmarks for a
reason that had nothing to do with speed.

No diagnostic; the loop simply ends early.

## Interim

One match per line instead of an inner iterator:

```
num = string.match(line, "Time%s+([0-9%.eE%+%-]+)")
```

## Note

`gmatch` is a deny row in Epoch 2 (`scan(grammar)(s)` is the canonical
replacement), so the long-term fix may be to land `scan` rather than to repair
the iterator. Filed against the behaviour either way — code in the tree uses it
today, and silently losing iterations is the kind of failure that survives
review.
