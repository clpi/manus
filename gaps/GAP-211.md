# GAP-211 — a declared foreign export silently captures the compiler's own bootstrap extern

**Status:** OPEN · **Filed:** !2026-08-22T02:00:00Z
**Priority:** P0 · **Kind:** wrong_answer
**Filed by:** claude-gap145
**Files:** src/native_backend.zig,src/dnir_lower.zig

Exporting a relation under a name the direct backend also uses as a bootstrap
foreign call makes the program's own output disappear. Compile 0, run 0, no
diagnostic.

## Reproduction — verified at `4cce7c93`

```id
@c.export("puts")
mine: i64 = (s: i64)
    0
main: i64 = ()
    print("hello")
    0
```

| program | exit | stdout bytes | `nm` on `_puts` |
| --- | --- | --- | --- |
| `@c.export("puts")` | 0 | **0** | **`T`** — locally defined |
| `@c.export("notputs")` — positive control | 0 | **6** | undefined, external |

`print("hello")` lowers to a bootstrap `puts` call. The export defines `_puts`
in the same object. The program then calls its own relation, which answers `0`
and writes nothing.

## Mechanism

Linkage is decided **by name**, not by the opcode that was supposed to carry it.
`native_backend.patchCalls` never reads `ins.op`: it resolves
defined-here to a PC-relative `bl`, else registered-extern to a relocation, else
falls back to `c_signatures` and registers the extern itself. So a locally
defined symbol always wins, whatever the instruction says.

This is the same evidence that makes `call_direct` / `call_extern` a migration
census rather than a physical distinction: measured, `call_extern` is exactly
`application == null` and callee in the hard-coded 37-name
`isBootstrapForeignCall` list, and a lineage-carrying `call_extern` is already
refused as `unwitnessed-application-transform`.

## Why it is a wrong answer and not a name clash

The user's program is lawful. Nothing in the language reserves `puts`. The
compiler's own implementation detail — which relations it lowers through which
bootstrap C symbols — silently changes the meaning of a program that never
mentions `print`'s implementation.

## Required control

The bootstrap set is 37 names. Each needs the two-program control above:
export it, and check that the program's own output survives. `nm` alone is not
sufficient — `_puts` being `T` is the mechanism, but the wrong answer is the
zero bytes.

## The shape of a fix, and why a rename is not it

Renaming the bootstrap symbols to a reserved prefix would move the collision,
not remove it: any prefix is still a name a user may export. The lawful shape
is that a foreign call carries a **linkage fact on the application** — foreign
versus internal convention — rather than being recovered from a symbol string
at patch time. Measured today: `@ffi("llabs") absv: i64 = (n: i64)` publishes
an ordinary application with `effect: {card: unknown}` and
`authority: {card: unknown}` and **no foreign marker at all**, and the direct
backend then refuses it with `DNB011 missing-application-target`. The producer
that must publish it is the resolver, at the same point it resolves `@ffi` and
`@comp.c.export`; `Function.foreign_boundary` already carries the definer half
from AST attributes, and the caller half has no home.
