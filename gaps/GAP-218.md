# GAP-218 — the semantic graph has no columnar storage

## Status
open — measured, not yet a defect in correctness. It is a compile-time
performance ceiling, and it becomes one silently as fact families grow.

## Measured at HEAD

    node storage                    std.ArrayListUnmanaged(Node)
    side hash maps in
      semantic_graph.zig            16
    array/list decls                78
    MultiArrayList anywhere in src  0

The failure mode usually feared — millions of individually heap-allocated
polymorphic nodes behind a generic graph-database API — DOES NOT EXIST
here. Nodes live in one contiguous `ArrayListUnmanaged(Node)` and queries
are direct field access. That part is already right.

What is absent is the split between hot semantic columns and cold
provenance/evidence columns. `Node` is one struct carrying every field any
consumer might want, so a query that needs one discriminator drags
provenance, origin and quote fields through cache with it. Every fact
family added to `Node` widens the stride of every unrelated traversal.

## Why this is filed now rather than when it hurts

The cost is invisible in current measurements because the corpus is small
(78470 nodes over 809 modules). It is not invisible in a self-hosted
compiler: compiler B executes these traversals on every compile, and a
graph that is semantically rich but physically wide loses compile-time
performance to conventional compilers that carry less information.

The stated thesis is one semantic graph as authority with many specialized
physical views as disposable execution structures. Columnar storage is a
physical view of the same authority — it mints no second semantic store and
needs no deletion witness, because nothing reads it as truth.

## Deletion witness — not applicable, and that is the point
Nothing is being removed and no fact gains a second producer. A columnar
projection of `Node` is derived, rebuildable, and establishes nothing;
`law.derived.index` already admits exactly this shape.

## Acceptance
Not "adopt MultiArrayList". The acceptance is a MEASUREMENT: pick the
traversal that dominates `idol graph` on the corpus, record its cache
behaviour and wall time, split the fields it touches into their own
column, and re-measure. If the win is not visible on the current corpus,
record that too and state the corpus size at which it would be — a
projected win is not a win.

## Related
Four AST-pointer-keyed content maps were deleted in favour of one derived
reverse index (see the commit deleting `exact_i64_by_ast`), taking the side
hash maps from 20 to 16. That is movement in the same direction: fewer
independent stores, more derived views over one authority.
