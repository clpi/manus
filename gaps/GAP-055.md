# GAP-055 — three C-backend emit defects, found by nearly excluding them

**Status:** 1 of 3 FIXED 2026-08-08 (bd022b6) · **Filed:** 2026-08-08

## How this was found, because the method is the point

While clearing the direct-backend bail worklist I noticed that
`examples/pass5/c_point_smoke.duo` fails on the **C backend too**. That looked
like a denominator problem: the native census counts a program as "reachable,
not yet lowered" when the direct backend bails, and a program the reference
backend cannot build either is not evidence about native lowering. The obvious
move was to exclude every bailing program that C also refuses.

Measured first. Five of the 38 bailing programs also fail under `--backend=c`:

    pass27_proof_matrix.duo   error: call to undeclared library function 'sqrt'
    bench_simd_matmul.duo     error: call to undeclared function 'duo_retain'
    p09_closure.duo           error: call to undeclared function 'lua_val_from_closure'
    c_point_smoke.duo         fatal error: 'fixtures/point.h' file not found
    c_big_rect_smoke.duo      fatal error: 'fixtures/big_rect.h' file not found

They are not one kind. Only the last two are what the rule assumed — fixtures
that need an include path the `pass5_foreign_tests.zig` harness supplies. The
other **three are C emitter defects**: the backend writes a call it never
declares. The exclusion would have removed them from the denominator and
retired three real bugs as "not measurable", while the census number went UP.

That is the house pattern (CLAUDE.md §3): a plausible rule, applied without
checking each member, turning a defect into a green. The denominator was left
alone.

## The three defects

Each is the same shape — an emitted call with no declaration in scope — but
they are three different missing declarations, so they are probably three fixes.

1. **`sqrt` (`pass27_proof_matrix.duo`)** — the emitted C calls `sqrt` with no
   `#include <math.h>`. Under C99 an implicit declaration is an error, so the
   program never links. Whether `-lm` is also missing is unverified: the
   compile dies before the link.

2. **`duo_retain` (`bench_simd_matmul.duo`)** — an ARC runtime entry point is
   called without a declaration. The ARC pass runs before codegen, so this is
   the emitter failing to bring in the runtime header/prototype for a helper it
   chose to call.

3. **`lua_val_from_closure` (`p09_closure.duo`)** — closure construction emits a
   call to a boxed-value helper that is not declared. Note this program lives in
   `examples/native_differential/unsupported/`, so the direct backend refusing
   it is intended; the C backend refusing it is not.

## Why it matters beyond these three

The C backend is the ORACLE for every native differential in this repo — the
`agree=N mismatch=M` gate compares direct output against it. An oracle that
cannot compile a program is silently dropped from that comparison by the
harness's `|| continue`. So these programs are checked by nothing at all: not by
the native census (they bail), not by the differential (C cannot build them).

Worth checking whether other programs sit in that same blind spot for other
reasons. The differential's `continue` is load-bearing and unaudited.

## Verify

```sh
cd ~/x/duo
for f in examples/pass27_proof_matrix.duo \
         examples/bench_simd_matmul.duo \
         examples/native_differential/unsupported/p09_closure.duo; do
  ./zig-out/bin/duo compile --backend=c "$f" -o /tmp/x.bin 2>&1 | grep error | head -1
done
```

A fix is confirmed by the program COMPILING AND RUNNING, not by the error
changing — an undeclared-function error that becomes a link error is the same
bug one step later.

## Update 2026-08-08 — bd022b6 fixes one, and the other two are one bug

**`sqrt` — FIXED.** `<math.h>` and `<time.h>` were emitted only inside
`if (self.moduleNeedsLuaRuntime())`, though neither has anything to do with the
runtime: `sqrt` comes from typed numerics and `clock()`/`CLOCKS_PER_SEC` from
`os.clock`, and a native-scalar module reaches both. Now unconditional.
`pass27_proof_matrix.duo` goes from unbuildable-by-either-backend to `ok compile`
and runs rc=0. `zig build test` went OK 37 -> 43.

Deliberately NOT a ninth `native_scalar_needs_*_h` AST walk beside the existing
eight — that fixes `sqrt` and leaves the next libm function to be discovered the
same way, by a program failing to compile.

**`duo_retain` and `lua_val_from_closure` are the same bug, and a stub is the
wrong fix.** Both come from a predicate disagreement:

| decides to EMIT the call | decides to DEFINE the symbol |
|---|---|
| `codegen_needs_arc(rt)` — about a TYPE | `moduleNeedsLuaRuntime()` — about a MODULE |
| closure emission at codegen.zig:16744 | same, and `lua_val_from_closure` IS defined at :24389 |

Defining no-op `duo_retain`/`duo_release` stubs makes the C compile and BREAKS
`codegen: native scalar str compare uses strcmp not lua_neq`, which asserts
`duo_retain` is ABSENT from native-scalar output. **That test is right.** The
invariant is that a native-scalar module emits no ARC at all, so the defect is
the emitted CALL, not the missing definition. Suppressing the call inside
`emit_arc_retain` is also wrong — it would silently drop retains the day they
stop being no-ops, trading a compile error for a leak.

The real repair is to reconcile the two predicates: a module that emits ARC, or
emits a closure, is NOT fully-native-lowered and must take the runtime path.
That is `moduleUsesFullNativeLowering()`, which the native census and the
native-scalar precheck also key on, so it has a wide blast radius and wants its
own measured change rather than a fix smuggled in beside a header include.

Note `bench_simd_matmul.duo` ALSO fails on `duo_simd_matmul_f32`, a genuinely
unimplemented SIMD intrinsic, so it will not build even once ARC is reconciled.
`p09_closure.duo` is the cleaner test case for that work.
