# GAP-021 — a descriptor body accepts type slots only, so no family can be declared

**Status:** open · **Filed:** 2026-08-07 · **Frequency:** blocks ~12 census rows
**Blocks:** Pass 81 §2.1 `call`, §2.2 `place`, §2.3 `eq`/`cmp`/`len`/`hash`/`default`
**Sites:** `scripts/family_registry_census.duo` (CALL-2, PLACE-1, EQ-1, CMP-1, LEN-1, DEFAULT-1)

## The defect

Pass 81 rules that a descriptor customizes behavior by carrying the family as a
member of its own body:

```
handle: {
    fd: i32 & valid_fd
    call = (spec) @{ fd = os.open(spec.path, spec.mode) }
}
```

A descriptor body parses **type slots only**. Any `name = ...` member is a parse
error at the `=`. This is one rule, and it is the single highest-leverage
blocker in the registry: it gates the declaration form for `call`, `place`, `eq`,
`cmp`, `len`, `hash` and slot defaults simultaneously. Roughly twelve census rows
across five sections are downstream of it.

## Minimal repro

Three spellings, three distinct diagnostics, one cause.

```duo
-- A. any family member
p: {
    x: i64
    eq = (a, b) a.x == b.x
}
```
```
p.duo:3:5: error: expected '}', got 'name'
```

```duo
-- B. a slot default (§2.3 `default`)
p: { x: i64 = 42 }
```
```
p.duo:1:13: error: expected '}', got '='
```

```duo
-- C. a strata'd family member (§2.2 `place`)
s: {
    place(i64) = (self, i) i
}
```
```
s.duo:2:10: error: expected ':', got '('
```

Control — the type-slot body this is a superset of parses clean:

```duo
p: { x: i64, y: i64 }   -- ok
```

## Why this one first

The registry's value is that families are *declarable by the descriptor that
owns them*. Every other SPEC row in Pass 81 §2 needs a name to resolve; these
need a place to be written. Landing the member-binding form does not implement
any family, but it turns "no syntax exists" into "the edge is declarable and
unrealized", which is a different and much cheaper kind of missing.

Diagnostic C is worth separating from A and B: `place(i64) =` fails in the
*strata* position, before the `=`, so the fix must admit a parameterized member
name and not merely `name = expr`. §2.2 and §2.6 (`format(style)`) both depend on
that, and a fix that only handles bare names would land §2.3 and silently leave
the two parameterized families behind.

## Not to be confused with

The body form here is the **descriptor** `p: { ... }`. A **table literal**
`t = { eq = ... }` accepts member bindings today — that is ordinary data, and
`CALL-3` shows the members are stored but never dispatched to. Storing a family
member and honouring it are separate problems; this gap is only the first.
