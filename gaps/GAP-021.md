# GAP-021 — `and`/`or` return 0/1 on native numeric operands (B-3 violation)

**Status:** open (worked around at the one site that was corrupting data)
**Filed:** 2026-08-07 · **Frequency:** 1 · **Severity:** silent wrong values
**Sites:** `lib/std/compiler/lexer.duo` read_number (repaired, cites this gap)

## The defect

B-3 says `and`/`or` **return their operands** (short-circuit), and Pass 80 §6
re-justified that ruling on the grounds that operand-`or` *is* the nil-coalescing
operator. On the C backend, `and`/`or` whose operands are **native numerics**
lower straight to C `||` / `&&`, which are boolean operators returning `int` 0
or 1. The operand is destroyed.

## Minimal repro

```duo
a: f64 = 1.5
r: f64 = a or 0.0        -- r is 1.0, not 1.5
i: i64 = 7
j: i64 = i or 0          -- j is 1, not 7
s: f64 = 2.5
u: f64 = s and 3.5       -- u is 1.0, not 3.5
```

The generated C is the whole story:

```c
double  r = (a || 0e0);
int64_t j = (i || 0);
double  u = (s && 3.5e0);
```

Both types are affected. Note `x or default` is the canon's *recommended*
spelling for coalescing, so this is a defect in an idiom the spec actively
promotes.

**Boxed operands are fine.** `tonumber("42") or 0` yields 42, because that path
goes through the runtime's operand-returning helper. So the bug is exactly the
native-lowering path, which is why it survives in a codebase that mostly tests
boxed values.

Secondary symptom, same root: the result's static shape is corrupted too —
`to(str)(r)` where `r: f64 = a or 0.0` fails to compile with `call to undeclared
function 'lua_to_str' / 'tostring'`, while `to(str)(a)` on the same-shaped `a`
compiles and prints `1.5`.

## What it cost

Every float literal in the language lexed to its integer part. The Duo lexer's
`read_number` had

```duo
v = tonumber(text) or 0.0        -- "1.5" -> 1
```

so `float_val` was wrong for **every** float token. Nothing caught it across the
whole SH-03 proof set, because `float_val` is the one token field no differential
reads: `duo_lexer_kind_fingerprint` hashes kinds, `duo_lexer_text_fingerprint`
hashes text. The field that was wrong was the field nothing looked at.

It surfaced only when `duo_lexer_tokenize_full` was added to carry `float_val`
across the ABI for production dispatch, and a C host printed `float=1` for
`1.5`. Dispatch built on `tokenize_text` (which drops the field) would have
shipped it into the parser.

## Repair applied

The lexer now uses the relation surface instead of the deny-listed `tonumber`
plus a coalescing `or`:

```duo
if is_float
    return { …, float_val = to(f64)(text) }
else
    return { …, int_val = to(i64)(text) }
end
```

`to(f64)`/`to(i64)` cover every form `read_number` scans — verified on `1.5`,
`1e3`, `2.5e-2`, `42`, `0xFF`, `0`. The `or 0.0` fallback was dropped rather
than re-spelled: the branch is reached only after a well-formed literal has been
scanned, so it defended an unreachable case while corrupting the reachable one.

## The fix

Lower `and`/`or` on native operands to the operand-returning form (a conditional
expression selecting the operand, with the truthiness test on the left operand),
not to C's boolean `||`/`&&`. B-2 truthiness applies: only `false` and `nil` are
falsy, so `0` and `""` must select the LEFT operand — which C's `||` also gets
wrong independently.

Regression test: the repro above, asserting `1.5`, `7`, `3.5`.
