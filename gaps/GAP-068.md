# GAP-068 — `t:push(v)` is a SILENT NO-OP on an empty table

**Status:** CLOSED 2026-08-09 · **Filed:** 2026-08-08
**Severity:** SILENT WRONG ANSWER on a spelling the law mandates
**Blocks:** `primes`, `stackqueue` in the boring corpus (2 of the 10 failures)

## CLOSURE 2026-08-09 — and the sibling this file told us to look for was real

**`t:push(v)` appends.** By value, `--backend=c`, the exact program in this file:

```
before   0 nil nil        both appends vanished
after    2 10 29          the values this file demanded
```

`src/codegen.zig` had no arm for `push` in the table-method chain, so it fell to
the generic lookup, read the field `push` off the table, got NIL, and
`lua_invoke(nil, …)` did nothing at all. The repair routes it to
`lua_tbl_insert(t, v, nil)` — the append arm of the helper `table.insert`
already used, so no new runtime surface: the canonical spelling now reaches the
code that was always there. Alias and record methods resolve ABOVE that chain,
so a user-defined `push` still wins.

**The sibling check paid.** This file ends *"One no-op found by hand usually
means an untested receiver state, not a unique defect"* — and `t:pop()` had the
identical hole from the other side. `examples/boring/stackqueue.id` failed as
`want '3 1' got 'nil 1'`, and `nil` reads as "the stack was empty" rather than
"pop is not wired". `pop` now lowers to `lua_tbl_remove(t, nil)`.

**Both blocked corpus rows pass, by value, in a ratcheted gate:**

```
zig build boring-corpus
  pass  primes       10 29
  pass  stackqueue   3 1
  boring 14/20  (was 10/20 when this file was written; floor 10)
```

## STILL OPEN, and it is NOT this gap — a DENSE receiver has no length

`t = { 1 }` — a non-empty positional literal — is given the DENSE
representation (`int64_t* __dt_t` + a capacity, no length word), so `t:push(2)`
is a hard C error rather than an append. This file already recorded that case as
"a hard error instead", and it still is; what is new is the reason.

**It is not about `push`.** The same table fails identically with no push
anywhere in the program:

```duo
t = { 1 }
t[1] = 5
print(#t)     -->  error: passing 'int64_t *' to parameter of incompatible type 'lua_Value'
```

`#t` on a dense table does not compile at all. So the missing thing is a LENGTH
on the dense representation, not an append on the method chain, and the
qualification that hands a table that representation lives in `src/sema.zig`.
Filed as the residue here rather than reopened: the silent no-op — the reason
this gap was the worst row in the corpus — is gone, and what remains is loud.

`t:sort()` and `s:split(",")` were checked in the same sweep. `split` works;
`sort` on a dense receiver hits the same representation wall and nothing else.

## The spec

CLAUDE.md **§0.9** names it directly: *"operations live ON descriptors —
`s:split(",")`, **`t:push(v)`**, `t:sort(.key)`."* This is not one spelling among
several; §0.9 says `table.` DOES NOT EXIST, so `t:push(v)` is the only way to
append.

## What actually happens

```duo
main: i64 = ()
    t = { }
    t:push(10)
    t:push(29)
    print(#t)
    print(t[1])
    print(t[2])
    0
```

```
0
nil
nil
```

Exit 0. `ok compile`. No diagnostic, no warning.

**Both pushes vanished.** The canonical append is a no-op, and the program that
uses it reports a confident empty answer.

## The adjacent probe separates it

On a NON-empty literal the same call is a hard error instead:

```duo
t = { 1 }
t:push(2)
```
```
error: initializing 'lua_Value' … from 'int64_t *'
```

So it is not that `push` is unimplemented — it resolves to something. On `{ }`
that something silently does nothing; on `{ 1 }` it produces a type error. The
empty-table case is the dangerous one precisely because it is the one that
compiles.

## Why this is the worst row in the boring corpus

The other nine failures are LOUD — undeclared function, parse error, unknown
type name, exit 139. A developer hits them and stops. This one produces a
running program with a wrong answer, and the wrong answer is *empty*, which
reads as "no results found" rather than "the append did not happen".

`primes` and `stackqueue` both fail as `want '10 29' got '0 0'` — the shape of
every count that silently never accumulated.

## How it was found

The boring corpus (Pass 106 §4). Twenty programs any working language compiles
without ceremony; ten fail. Nothing was bent away from canonical spelling to
raise the score, which is why this surfaced instead of being written around with
a `table.insert` that §0.9 forbids anyway.

## Fix

`t:push(v)` must append and be observable through `#t` and `t[i]`, for `{ }` and
for a non-empty literal alike. Fixture asserts the VALUES `2`, `10`, `29` — not
that it compiled, since it already compiles.

Then check the siblings §0.9 names in the same breath — `t:sort(.key)`,
`s:split(",")` — for the same empty-receiver hole. One no-op found by hand
usually means an untested receiver state, not a unique defect.
