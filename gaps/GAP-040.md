# GAP-040 — the compiler cannot cross-compile to a non-POSIX host, because a macOS-generated C artifact is linked into every build

**Status:** CLOSED 2026-08-08 · **Filed:** 2026-08-08 · **Frequency:** 1
**Cited at:** `src/duo_lexer_tokenize.c` (tracked, generated),
`build.zig:linkProductionDuoLexer`, `src/codegen.zig:5066-5069`.

(Took 040 after checking `gaps/` here and in all eight sibling worktrees under
`.claude/worktrees/`: 039 was the highest, held by `perf-losing-rows` and
`shc-advance`. `gaps/` is a shared numeric registry with no allocation
protocol, so expect to renumber.)

`ucontext_t`, and `<setjmp.h>` (which on wasm-wasi-musl is a hard `#error`
until the exception-handling proposal lands).

## The mechanism

`build.zig` links a checked-in C artifact into the compiler binary for **every**
target:

```zig
fn linkProductionDuoLexer(b: *std.Build, mod: *std.Build.Module) void {
    mod.addCSourceFile(.{ .file = b.path("src/duo_lexer_tokenize.c"), … });
}
```

That file is generated by Duo itself from `lib/std/compiler/host.id`. Its
prelude is chosen at generation time by the target the generator was pointed
at — and it was generated on macOS. Line 2 of the file is `#define
_DARWIN_C_SOURCE`. The relevant emitter is `src/codegen.zig`:

```zig
} else if (!native_scalar_plain) {
    self.p("#include <setjmp.h>\n", .{});
    self.p("#include <ucontext.h>\n", .{});
}
```

The `if` arm immediately above it is the wasm arm, and it already does the
right thing — it `typedef`s a fake `ucontext_t`, `#define`s `makecontext` /
`swapcontext` to no-ops, and stubs `access`/`mkstemp`/`dlopen`/`R_OK`/`X_OK`.
So the compiler **knows how** to emit a portable prelude. The problem is that
the artifact in the tree was frozen with the POSIX arm taken, and cross-builds
get the frozen bytes.

This is a build-graph bug, not a codegen bug. Guarding the include alone does
not fix it: eight sites in the generated C use `ucontext_t` / `swapcontext` /
`makecontext` for the coroutine runtime (`src/codegen.zig:25864-25927`), so
suppressing the include just moves the failure to `unknown type name
'ucontext_t'` — which is precisely what the wasm log already shows.

## What a fix has to look like

1. **Generate per target.** `linkProductionDuoLexer` takes the resolved target
   and runs the generator (or selects a pre-generated variant) for it. This is
   a bootstrap problem: building duo for target T requires a duo that runs on
   the host, which is the ordinary two-stage arrangement, but the build graph
   does not express it today.
2. **Generate one artifact whose prelude is `#if`-portable**, so a single
   checked-in file compiles everywhere. Cheaper, and it makes the artifact
   honestly target-independent, which is what "checked in" already implies.
   Requires the codegen prelude to emit the union of the arms under
   preprocessor guards instead of picking one arm at generation time.

Route 2 is the smaller change and the one that matches what is already tracked.
Neither is a one-line fix, and both land in `src/codegen.zig` plus a full
regeneration of `src/duo_lexer_tokenize.c` — which is why this is filed rather
than fixed.

## What was fixed alongside, and is not this gap

Three genuine Zig-side portability bugs were found by the same matrix and are
repaired:

- `src/main.zig` — the REPL read stdin via `std.posix.read(std.posix.STDIN_FILENO, …)`.
  `STDIN_FILENO` is a `comptime_int` and Windows' `fd_t` is `*anyopaque`, so it
  did not coerce. Now `std.Io.File.stdin().readStreaming(io, …)`, which is
  already this file's idiom for stdout/stderr.
- `src/shell_session.zig` — `std.atomic.Value(u64).fetchAdd` on a session-id
  counter. wasm32 baseline has no 64-bit atomic RMW. Narrowed to `u32`.
- `src/shell_session.zig` — `std.process.getEnvVarOwned`, which no longer
  exists in Zig master. This sat inside `if (builtin.os.tag == .windows)`, so
  it had never been compiled by anything until the matrix ran; the file's only
  Windows branch was dead on arrival. Now `std.process.Environ.getAlloc`.

With those three fixed, x86_64-windows fails on **one** error and it is this
gap alone.

## Note on the direct ARM64 backend

`native_backend.unsupportedReason` restricts the direct Mach-O object writer to
macOS/aarch64 by design, and every other target falls back to the C backend.
That is not a portability defect and it is not what any row above failed on —
x86_64-macos, x86_64-linux-gnu and aarch64-linux-gnu all build green through
the C path.

## How it was closed

Route 2, the one this gap argued for. `src/codegen.zig` now emits the union of
the preludes under `#ifdef __wasm__` / `#elif defined(_WIN32)` / `#else`, so a
single tracked artifact compiles on every host and the arm is selected by the
consuming compiler rather than by the target the generator was aimed at. Route 1
would need a two-stage build graph that does not exist and would run for every
cross-build; dropping the artifact was never available, because
`tokenizeAuthority()` is `.id_native` and the compiler tokenizes itself with it.

Three things the gap had not seen, all found by building rather than reading:

- The `_WIN32` arm is small. mingw-w64 already carries `popen`, `pclose`,
  `access`, `R_OK`, `X_OK`, `mkstemp`, `close`, `unlink` and `L_tmpnam` — probed,
  not assumed — so only `ucontext` and `dlfcn` were actually missing. `dlopen`
  maps onto `LoadLibraryA`/`GetProcAddress`, so it is a working port rather than
  a stub. Of the nine POSIX headers the runtime included, mingw has three.
- `__argv` is not ours to use. mingw's `<stdlib.h>` defines it as
  `(*__p___argv())`, so every emitted `lua_Value __argv[N] = {…}` became a
  function-call initializer. Renamed to `duo_args`. A leading `__` is reserved
  for the implementation; the collision was the generator's fault, not the
  platform's.
- `system`, `tmpnam` and `tmpfile` are DECLARED by wasi-libc and never defined.
  They pass the compile and fail at `wasm-ld` with "undefined symbol", which is
  why the gap's error list did not contain them — the build never reached the
  link.

One Zig-side blocker remained after the C was portable:
`meta_codegen.comptimeProductHook` calls `std.Thread.spawn`, a hard
`@compileError` on a single-threaded target. It had to be excluded at comptime,
not skipped at runtime; the serial branch beside it computes the same product.

**Building is not running, and this gap only ever claimed building.** The
wasm32-wasi module does run: `duo check` under wasmtime answers "checked — no
errors" on a good file and a parse diagnostic on a bad one. It needs `--dir`
preopens — without them WASI answers errno 8 (EBADF) at startup, which is a
missing capability grant and not a defect. `duo run` still cannot compile there,
because compiling spawns a C compiler and WASI has no way to spawn anything.
That is a property of the target, not a gap in the compiler.
