# GAP-050 — `duo check` shares one semantic-cache file across concurrent runs

**Filed** 2026-08-08. **Status** open, and **partly unconfirmed — read §3.**

## The mechanism (verified)

`duo check` writes `.duo/cache/semantic/state.json` — a single file, resolved
relative to the CURRENT WORKING DIRECTORY. Confirmed present:

    $ ls .duo/cache/semantic/
    state.json

Every concurrent `duo check` in the same tree therefore writes the same path.
That is a real hazard independent of whether it has been observed to bite.

## The observation (from the capability-matrix sweep)

Two `xargs -P 8` sweeps minutes apart disagreed on six of 348 programs, and not
only at the backend rungs: `examples/native_differential/unsupported/p09_closure.duo`
read `0000000` in one sweep and `0110000` in the next, meaning `duo check`
itself flipped. Setting `DUO_SEMANTIC_CACHE=0` made two sweeps byte-identical
AND raised the totals — checked 282 -> 285, c path 240 -> 246 — i.e. the
contention was manufacturing FALSE FAILURES, the worst direction.

## §3 — I COULD NOT REPRODUCE THE NONDETERMINISM

Tried, and failed, before recording this as established:

    120 files, xargs -P 8, three runs      -> 97, 97, 97   (identical)
    same, DUO_SEMANTIC_CACHE=0, two runs   -> 97, 97       (identical)
    p09_closure.duo, checked six times
      each after a parallel 60-file load   -> 0 0 0 0 0 0  (identical)

So the mechanism is real and the observation is credible, but the failure did
not surface for me. Possible: it needs the full 348-file corpus, more workers,
a colder cache, or it was already fixed by a commit landing between the two
sessions. Do not cite the flip as a known behaviour until someone reproduces it.

## Why it still matters

A shared, CWD-relative cache file is a measurement hazard by construction, and
this repo's gates are increasingly sweeps. The existing ones are SEQUENTIAL
(`scripts/native_census.duo`, `scripts/audit100.duo`) and so are unaffected —
but the obvious optimization of any of them is `-P 8`, and that is the change
that would silently start producing false failures.

## Repair

Key the cache path by process or by input, not by CWD, so concurrency is safe
by construction rather than by nobody having parallelized yet. Until then, a
sweep that parallelizes should set `DUO_SEMANTIC_CACHE=0`.

A NOTE ON THE OTHER FIX THAT LOOKS RIGHT AND IS NOT: giving each worker its own
CWD is also deterministic and is WRONG — `req "std.compiler.token"` resolves
against CWD, so three `native_only` fixtures lose their module and native reads
86 where the census reads 89.
