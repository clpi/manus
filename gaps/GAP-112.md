# GAP-112 — DNIR measured against IR-ONE: 23 of 27 opcodes break LAW-ONE, and every instruction carries four string slices

**Status:** OPEN (measured) · **Filed:** 2026-08-09
**Law:** IR-ONE · VOCAB-SAME · IR-EXPLICIT · IR-COMPACT · IR-OMIT (owner ruling
2026-08-09) · LAW-ONE

## The ruling

> DNIR is not a second semantic language. It is the native-realization
> projection of Duon's semantic graph. It may add realization facts but may not
> rename semantic operations into a competing ontology.
>
> Readable DNIR is a projection. Hot DNIR is packed data.

## Measured, `src/duo_native_ir.zig`

```
Op enum variants                    27
  carrying an underscore            23      85%
Instr fields                        14
  of which []const u8 string slices  4      callee, req_alias, field, record
  of which Value                     3      lhs, rhs, third
```

The whole record:

```zig
op result lhs rhs callee req_alias field binop ty record third vals branch_target hw
```

**A `mul` uses six of fourteen** — `op`, `result`, `lhs`, `rhs`, `binop`, `ty`.
The other eight are storage it can never populate: a callee, a req alias, a field
name, a record name, a third operand, a value array, a branch target, a hardware
intrinsic.

### The four string slices are the sharper finding

Every instruction in the program carries **four `[]const u8`** — pointer plus
length each — for `callee`, `req_alias`, `field` and `record`. An integer
multiply pays for four name pointers it will never read.

That is not only cache density. It is the reason DNIR does string comparison
where it should do integer comparison, and it is what IR-COMPACT's "stable IDs
instead of names" deletes. It also blocks cheap serialization and makes
incremental invalidation compare bytes instead of IDs.

### The redundant dispatch level is real

`binop: BinOpTag` sits beside `op: Op`, so an add is `op = .binop` and then
`binop = .add`, and the backend reads

```zig
switch (ins.binop) { .add => …, .sub => …, .mul => …, .div => … }
```

inside a switch on `op`. **Two taxonomies for one relation**, which is exactly
VOCAB-SAME's prohibition: the semantic graph already knows `add`.

## The 23 underscore opcodes, and what each encodes

Every one fuses a relation with a qualifier that should be a level or a fact:

```
const_i64  const_f64  const_str      relation + descriptor
load_local load_field load_index     relation + PLACE
store_local store_field store_index  relation + PLACE
call_direct call_extern              relation + LINKAGE
mov_arg fp_mov_arg                   relation + ABI REGISTER FILE
br_if br_if_not                      relation + CONDITION SENSE
ret_record                           relation + REPRESENTATION
hw_fence hw_spin hw_unary            relation + INTRINSIC
str_len                              relation + DESCRIPTOR + AXIS
```

**The qualifier is never the same dimension twice**, which is why the fix is
levels and facts rather than shorter names. `calldirect` would satisfy a grep
and preserve the defect; `call` + `linkage = direct` deletes it.

Two of these should disappear entirely rather than become levels, and the ruling
says so:

- **`br_if_not`** is not a semantic operation. A negated condition is a
  canonicalization, not an opcode.
- **`mov_arg` / `fp_mov_arg`** are ABI placement leaking into a typed lowering
  IR. Argument register assignment belongs in machine realization, where it can
  be coalesced and precoloured — as virtual moves in DNIR it costs instructions
  and blocks the allocator.

## What this does NOT say

**Readable DNIR looking like Duon is not the goal and would not fix any of the
above.** The findings are structural: a wide record, four name slices per
instruction, and a two-level dispatch. A prettier text projection changes none of
them, and IR-COMPACT explicitly separates the two — *readable syntax never
dictates compiler memory layout*.

**And DNIR genuinely needs what source does not**: explicit value identity,
explicit blocks, explicit control edges. IR-EXPLICIT says so. The unification
claim is narrower and correct as stated — *DNIR adds explicit information; it
never invents a parallel semantic vocabulary.* The 23 underscore opcodes and
`BinOpTag` are that parallel vocabulary, measured.

## Order

1. **Delete `BinOpTag`'s authority** — point the instruction at the semantic
   relation identity. This removes a whole `switch` level in every consumer and
   is the smallest change with the widest blast radius.
2. **Move the four string slices out of line.** Names become interned IDs; rare
   payloads (call, record, hardware) live in side tables. This is IR-COMPACT and
   it is measurable: instruction size, and string comparisons per compile.
3. **Retire `br_if_not` and the `mov_arg` pair** — the two that should not exist
   rather than be renamed.
4. **Then levels for the remaining qualifiers**, and only then a readable
   projection.

Renaming first would satisfy LAW-ONE's grep across 23 opcodes and leave every
structural defect in place — the same trap gap[106] records for `std_string_*`.

## Falsifier

If in a month the Op enum has 27 underscore-free variants, `Instr` still has 14
fields with four string slices, and `BinOpTag` still exists, the rename happened
and the unification did not.

## The reconstruction surface in `dnir_lower`, measured — ten maps and six predicates

The audit names the recurring failure pattern: *"semantic fact exists somewhere
→ lowerer loses it → local tracking map re-discovers it → another consumer
misses the map → another special case is added."* Counted at the branch tip:

**Ten state structures that re-derive facts sema already knew:**

```
ints              module integer constants
strs              module string constants
const_ints        integer constants AGAIN, a second map
fp_params         floating ABI parameter slots   (StringHashMap([]bool))
str_slots         which slots hold a str
bool_slots        which slots hold a bool
ptr_slots         which slots hold a memory-backed table base
table_lens        table extents
locals            name -> slot
self_param_slots  receiver slots
```

**Six predicates that reconstruct by walking the AST:**

```
paramSlotIsFp   exprReturnsF64   exprIsBoolish   exprIsStr   (+2)
```

`ints` and `const_ints` are the pattern in miniature: **two maps for one fact**,
integer constants, in one file. Nothing about that is a design decision; it is
what happens when a consumer misses the first map.

And the predicates confirm the direction of the loss — `exprReturnsF64` and
`exprIsStr` are the lowerer asking, of an AST expression, a question the
descriptor already answers. Every one of them is a `descriptor(result(e))` query
wearing a hand-written walk.

### Why this ranks above the opcode rename

Each map is a place where a semantic fact was ESTABLISHED once and then
RECONSTRUCTED. The audit's target — *establish once, project many times,
reconstruct zero times* — makes this list the actual worklist, and it is
measurable without judgement: ten maps and six predicates, both of which should
fall toward zero.

**A renamed opcode set with these ten maps intact would satisfy LAW-ONE and
change nothing about the architecture.** That is the §26 trap stated in numbers.

### The smallest first target

`ints` + `const_ints` — one fact, two maps, one file. Collapsing them requires no
graph query at all; it only requires deciding which is authoritative. It is the
cheapest possible demonstration that the count can fall, and it makes the metric
real before the harder queries (`descriptor(result(callee))`, `abi(call,target)`)
are attempted.

### CORRECTION — `ints` + `const_ints` are NOT one fact, and the "smallest target" above is wrong

I claimed they were "two maps for one fact, integer constants, in one file" and
recommended collapsing them as the cheapest demonstration. **Reading them, that
is false on both counts.**

- **`module_consts.ints`** holds MODULE-level constants. Its sibling `strs`
  exists for module-level STRINGS, and the file documents why the split is
  deliberate rather than accidental: *"Two maps rather than a tagged union
  because every consumer knows which kind it wants: `exprIsStr` asks only
  `strs`, the numeric-for step asks only `ints`, and a union would make each of
  them re-check a tag they can't act on."*
- **`ctx.const_ints`** is a FUNCTION-LOCAL constant-propagation table, populated
  during lowering (`:1665`, `:1678`) when a local is assigned an integer literal.

Module scope versus function scope. Collapsing them would fuse two different
facts and lose the scope distinction — the opposite of convergence.

**I reached the claim from a grep of field names and did not read either
definition.** That is precisely the failure this file records elsewhere as the
session's most expensive habit, committed again while writing about it.

### What survives the correction

The **count** stands — ten state structures and six predicates — and so does the
direction: `exprReturnsF64` and `exprIsStr` really are `descriptor(result(e))`
queries done by hand. But the ten are not ten redundancies. **Some are genuine
scope distinctions and at least one split is documented as deliberate**, so the
worklist needs each entry adjudicated, not collapsed on sight.

A metric that counts maps without asking what each one KNOWS would push toward
fusing distinct facts to make a number fall — the same failure as renaming
opcodes to satisfy a grep, one level down.

**The right smallest target is therefore not a fusion but a QUERY**: pick one
predicate — `exprReturnsF64` is the clearest — and replace its AST walk with the
descriptor the graph already holds. That deletes a reconstruction without
deleting a distinction, and it is the shape every later removal takes.

### The maps exist because the lowerer HAS NO ACCESS to sema's facts

Tracing the corrected target — replace `exprReturnsF64`'s walk with a descriptor
query — the query turns out not to be available. That is the real finding.

**`LowerCtx` carries FOUR separate return classifiers**, each a hand-threaded
map answering one shape of "what does this callee return":

```
func_record_returns : *StringHashMapUnmanaged([]const u8)
str_returns         : *const StringHashMapUnmanaged(void)
bool_returns        : *const StringHashMapUnmanaged(void)
fp_params           : *const StringHashMapUnmanaged([]bool)
f64_kernels                                    (an ELEVENTH map, uncounted above)
```

**And the semantic graph is present but is not the authority:**

```zig
/// Pass 16 hook: OPTIONAL semantic graph for provenance/transform ordering.
graph: ?*const semantic_graph.SemanticGraph,
```

Optional, and scoped to provenance and ordering — not to type facts. So the
lowerer cannot ask `descriptor(result(callee))`; there is nobody to ask. The
maps are not laziness, they are the **only** source of the fact at this layer.

`exprReturnsF64` shows what that costs:

```zig
if (f.obj.* == .name and eql(f.obj.name.ident, "math") and args.len == 1)
    return true;
return ctx.f64_kernels.contains(expr.call.func.name.ident);
```

A hardcoded check on the NAME `math`, then a map lookup. A user relation named
`math` is misclassified; an f64-returning relation not spelled `math.…` and not
in `f64_kernels` is missed. Its own comment records the recurrence:

> *"Third time this exact lesson: a producer the type tracker does not know about
> breaks every consumer downstream. `exprIsStr` needed it for `string.char`, then
> again for concat; this is the f64 twin."*

**The file is documenting the failure loop from inside it, three iterations in.**

### What this changes about the worklist

"Eliminate one reconstruction map" is not a first step — it is a CONSEQUENCE.
Nothing can be eliminated until the lowerer has an authoritative fact source,
because each map is currently the only place the fact exists at that point.

So the true P0 ordering is the audit's §5 and not its §4:

1. **Make the graph non-optional and authoritative for type facts in
   `LowerCtx`** — the lowering boundary moves from `AST →  DNIR` toward
   `graph → realization`.
2. **Then** replace ONE classifier with a query. `exprReturnsF64` remains the
   right first one because it has only four callers and its failure mode is
   already documented three times.
3. **Then** the rest fall, and the count becomes a real ratchet rather than a
   number that could be gamed by fusing distinct facts.

Attempting step 2 before step 1 produces exactly what the last three iterations
produced: another map.
