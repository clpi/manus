# GAP-034 — the native precheck ratchets behind its own lowering

**Filed** 2026-08-07. **Status** open (structural). **Cost so far** four
separate bugs, ~17 programs.

## The pattern

`can_emit_native_scalar_module` / `expr_is_native_scalar` (src/codegen.zig) is a
*conservative approximation* of what `src/dnir_lower.zig` can lower. Nothing
keeps the two in sync. Every time the lowering grows a capability, the gate in
front of it keeps refusing programs that would now succeed — silently, because
the module falls back to the C backend and still compiles.

Four instances, all found and fixed 2026-08-07 by instrumenting the bail sites:

| construct | lowering had it | gate said |
|---|---|---|
| `string.byte(s, i)` | indexed load, added for tokenizer loops | `runtime-global:string` |
| `s:byte(1)` (FACE-CALL) | — (added with the fix) | `expr-unhandled:method_call` |
| `Kind = @{ eof = 0 }` | `collectModuleConsts`, doc names this exact form | `assign-value:compile` |
| `blob = { 0x00, 0x61 }` | memory-backed positional tables since SH-04 | `keyed-table-export` |

The third and fourth are the sharpest: in both, the lowering's own doc comment
names the construct it supports, and the gate rejected it anyway.

Worse, two of these were the **canonical** spelling. `s:byte(1)` (rule 6,
FACE-CALL) and `@{ … }` (the enum descriptor) both disqualified their module
while the deny-listed vestige either worked or failed identically — writing
canonical Duo bought no native coverage over the form the canon forbids.

## Why this is a gap and not four fixes

The fifth instance is already latent. The gate is hand-written prose about a
subset that is defined somewhere else, so it drifts by default and only
un-drifts when someone measures. The fix is to derive both from one description
of the subset — the lowering states what it accepts, the gate consumes that
statement — rather than re-deriving it by hand each time.

Interim, and cheap: when a program bails, **grep `dnir_lower.zig` for the
construct before writing any lowering code.** It is probably already there.

## The rows merge into three subsystems, not sixteen fixes

Re-measured over the REACHABLE set only (`zig build native-census`), and two
rows that look unrelated are the same missing capability:

  NATIVE STRING ALLOCATION -- 5 programs. RE-MEASURED 2026-08-08, and the
  blocker is NOT allocation. `mem.alloc` -> malloc already lowers (three mem
  primitives landed as plain libc calls). `string.char(n)` composes to
  malloc(2) + two byte stores + return, and the DNIR opcodes for all of it
  exist. What does not exist is the ARM64 ENCODING: `store_index` at byte width
  refuses at native_backend.zig:1751 -- only the `.i64` scaled 8-byte store is
  emitted. The READ side has been there all along (`string.byte` -> byte load),
  so this is a one-sided pair. `strb w, [base, idx]` is the missing
  instruction, and it unblocks string.char; `..` (concat) needs it too plus a
  length-driven copy loop.

  THE ENCODING, and the hazard. `emitLdrb` (native_backend.zig:3287) uses
  0x39400000 -- LDRB, immediate, unsigned offset. The counterpart is STRB with
  the same addressing form, 0x39000000, and `emitStrb` mirrors it field for
  field. That part is mechanical.

  What is NOT mechanical is the OFFSET CONVENTION, and it is why this was not
  landed blind. The existing byte READ is string.byte, which computes
  `base + (i - 1)` because Duo indexes strings from 1 and C pointers from 0.
  A raw buffer store (string.char writing the character at 0 and the NUL at 1)
  wants no such adjustment. So `store_index` at byte width serves two callers
  with different origins, and picking one silently corrupts the other -- a
  write to a wrong address, which the 68-program differential would NOT catch,
  because nothing else in the corpus performs a byte store. The verification
  would rest entirely on one hand-written probe.

  ATTEMPTED 2026-08-08, AND THE PROBE CAUGHT IT. The full chain was built:
  emitStrb (0x39000000, mirroring emitLdrb field for field), a byte-width
  store_index arm sharing the load's single `base + (i - 1)` origin,
  string.char lowering with 1-BASED indices so the raw buffer normalizes at the
  lowering instead of giving the backend a second convention, and exprIsStr
  taught that string.char PRODUCES a str (without which the local never enters
  str_slots and the very next string.byte does not recognize its own argument
  -- a producer the type tracker does not know about makes every consumer
  downstream fail).

  It compiles. It SIGSEGVs: `s: str = string.char(65); string.byte(s, 1)`
  returns 139, not 65. So the address computation or the register lifetime
  around the malloc result is wrong, and the corpus differential stayed green
  through all of it -- 89 programs, none of which perform a byte store.

  That is the predicted failure, observed. The reason this row was held back
  was that "it compiles and the gates are green" is not evidence here, and the
  one hand-written probe was the only thing that could fail. It did.

  Next session: keep the chain above (it is the right shape) and debug the
  segfault -- first suspect is the malloc result temp being clobbered before
  the two stores, since call_extern goes through emitSaveCallerRegs and the
  stores evaluate three operands afterward.

  CONCAT ATTEMPTED 2026-08-08 AND REVERTED — one layer past string.char.
  `a .. b` lowers cleanly as strlen, strlen, add, add 1, malloc, strcpy,
  strcat, and every piece exists: `mov_arg` marshals DNIR values into x0..x7,
  which is how every multi-argument call in dnir_lower already works. Also
  needed, and the same lesson string.char taught: exprIsStr must know that a
  concat PRODUCES a str, or `string.len` on its own result falls through to an
  undefined `string_len`.

  It compiles and is WRONG, not crashing: `"AB" .. "CD"` gives length 2, so
  strcpy ran and strcat did not append.

  FIRST SUSPECT WAS WRONG, and the correction matters more than the guess.
  I blamed `emitSaveCallerRegs` clobbering the staged x0/x1. It does not --
  measured, it saves x9..x28 only (native_backend.zig:3211), so mov_arg
  staging survives it untouched.

  What IS true and unverified: `Instr.lhs` defaults to `.void`
  (duo_native_ir.zig:127), so a call_extern emitted with no `lhs` correctly
  skips the move-to-x0 and leaves the mov_arg staging alone. That means the
  marshalling path is probably fine and the fault is elsewhere -- most likely
  in which register `evalDnirValue` hands back while x0 already holds the first
  argument, since `mov_arg` writes x0/x1 directly without any record that they
  are now live.

  The measurable fact, independent of cause: multi-argument extern calls have
  NO existing caller. Every current call_extern passes one argument through
  `ins.lhs`. So the path is untested.

  AND THE OBVIOUS DEBUGGING STEP IS BLOCKED. "Dump the assembly" is the right
  move and does not work: `duo compile --backend=direct --emit asm x.duo -o
  out.s` writes a MACH-O EXECUTABLE. Magic bytes cf fa ed fe, mode rwxr-xr-x,
  and it reports `ok compile` -- the wrong format is silent. Same class as
  gap[015] (`--emit obj`/`dylib` emit executables) and gap[019] (`--emit wasm`
  emits Mach-O), so this is the third member of that family and the first one
  that blocks an investigation rather than a deliverable.

  The capability exists internally: native_backend has `emitAssembly` and an
  `asm_text` buffer that every emitter already appends to (that is where the
  "strb w{d}, [x{d}]" listings go). Only the CLI route fails to select it.
  Fixing `--emit asm` is therefore small, and it is a PREREQUISITE for the
  concat work rather than a separate errand -- without it the next attempt is
  back to reasoning about the register allocator, which is exactly what
  produced the wrong suspect above.

  Resolve the convention first (either a distinct opcode/flag for raw vs
  string-indexed stores, or normalize at the lowering so the backend only ever
  sees 0-based), then emit. This is the one place in the remaining worklist
  where "it compiles and the differential is green" is not evidence.

    `lowerBinop` bail = `..` (concat), not a missing bitwise op as the site
    suggests; DNIR's BinOpTag genuinely lacks band/bor/bxor/lshift/rshift, but
    NEITHER blocked program uses them. Both use `..`. Add `string.char` (3) and
    the lever is one thing: a native string allocator (malloc + copy) in DNIR.

  MEM POINTER TYPES -- 5 programs.
    Not 17 extern calls. `mem.*` is a typed pointer family: `mem_pointer_to`,
    `.pointer` as a resolved type, type-argument strata (`mem.load(i64)(p)`).
    DNIR has no pointer type beyond a `ptr` parameter, so this extends the type
    system rather than adding call arms.

  CROSS-MODULE RECORD RETURNS -- 4 programs. SH-04 territory, already tracked.

Everything else is singletons or correct rejections (`any` params/returns at
codegen.zig:2946/2949 -- `any` IS boxed, refusing it is right).

So the honest shape of "the rest of native" is three subsystems worth roughly
14 of the 43 remaining reachable programs, and a long tail of ones.

## mandelbrot: a five-deep blocker chain, fully named

Worth recording as the worked example of what the instrumentation buys, and of
where it runs out. Each fix moved the bail one layer and revealed the next:

  1. precheck `runtime-global-call:print`   -> gap[033], fixed
  2. `lowerModule` function-count mismatch  -> `: void` ineligible, fixed
  3. `lowerExprCons — HEIGHT`               -> `const NAME: T = v` never
                                               collected, fixed
  4. `lowerModule — mandel`                 -> f64 params required an f64
                                               return, fixed
  5. `evalDnirValueFp:1791`                 -> integer immediate in a float
                                               position, fixed (scvtf)
  6. `compileDnirInstr:1343`                -> OPEN

Row 6 is a float binop the ARM64 emitter does not have. The comparison path
(fcmp + cset, producing a GP result) already exists and is selected on
`ins.ty == .f64`; the float-FUNCTION arm beside it emits only add/sub/mul/div
and refuses everything else.

TRIED AND REVERTED: typing the comparison from its operands in `lowerBinop`
(`exprTouchesF64` instead of `exprIsF64`, on the theory that `zx*zx + zy*zy >
4.0` is integer-VALUED so `exprIsF64` says false and the f64 path is never
selected). It builds and changes nothing measurable, so it was backed out
rather than kept as an unverified broad change to float typing.

The remaining suspect is the backend arm itself, and it carries a real hazard:
`temps` maps slots to u5 register numbers, and GP and FP registers share that
numbering. Routing a comparison inside a float function to a GP destination
puts a GP index into a map that `evalDnirValueFp` will later read as an FP
register. That is the same class as the three register-lifetime bugs the table
work hit, so it wants a session with room to differential it.

## The denominator is wrong

The 14 `global_decl` rows are all `global A = std.compiler.arm64`-style module
aliases inside compiler proof fixtures — programs whose PURPOSE is driving the
C emitter. They cannot compile to native ARM64, by construction. **The
reachable ceiling is ~126/140 (90%), not 140.** Any target stated as "100%
native" needs this denominator corrected first, or it is unsatisfiable for a
reason that has nothing to do with the compiler.
