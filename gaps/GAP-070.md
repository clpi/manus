# GAP-070 — the C backend turns a statement-position `if` block into an early RETURN

**Status:** OPEN — reproduces, and **MIS-SCOPED as filed.** The title below
("a trailing shell call at the end of `main` overwrites the exit status") names
one symptom of a general codegen defect that has nothing to do with shells,
with `main`, or with exit statuses.
· **Filed:** 2026-08-08 · **Root-caused:** 2026-08-09
**Owner:** the C backend — `duo_entry_main` emission
**Found by:** `scripts/foreign_census.id` printing FAIL and exiting 0

---

# ROOT CAUSE 2026-08-09 — INSTRUMENTED, and larger than the filing

Following gap[098]'s peel rule and gap[100]'s hard-won lesson: *do not implement
a mechanism you have not observed.* The emitted C answers it in one read.

```duo
main = (): i64
    code: i64 = 0
    work = "/tmp/x"
    if work != ""
        std.script.run("exit 7")
    code
```

```c
static inline int64_t duo_entry_main() {
    int64_t code = 0;
    const char* work = "/tmp/x";
    if ((strcmp(work, "") != 0)) {
        return std_script__run("exit 7");   /* <- the defect */
    }
    return code;                            /* <- unreachable */
}
```

**The `if` block is in STATEMENT position, and the C backend compiled its final
expression as a `return` from the enclosing function.** §0.7 says a body's value
is its final expression's, *and demand alone materializes* — the if-block's
value is not demanded here, so it must be discarded. It is not. Everything the
filing observed follows from this one line.

## It is not about shells, not about `main`, and not about exit status

| variant | correct | C backend | direct backend |
|---|---|---|---|
| `adds(2,3)` in an `if` before `main`'s tail | 0 | **5** | 0 |
| same shape in an ORDINARY function `pick(1)` | 99 | **5** | 99 |
| `std.script.run("exit 7")`, `code = 0` | 0 | **1** | *bails* |

The second row is the finding. A pure duon call, no world, no shell, no `main`:

```duo
pick = (n: i64): i64
    out: i64 = 99
    if n == 1
        adds(2, 3)
    out
```

`--backend=c` prints **5**, `--backend=direct` prints **99**. This is a
**silent wrong answer in any value-returning duon function**, and it is a
**backend divergence** — the two lowerings disagree on the same program.

## Why it looked like a shell defect

Because a world call is what forces the C backend to be used at all:

```
error: direct backend: DNB001: program construct is outside the direct backend subset
hint: bail site: lowerCall() at dnir_lower.zig:3055 — run
```

The direct backend gets this shape RIGHT. `std.script.run` bails it, the
compile falls back to C, and the C backend carries the defect. So the shell call
is not the cause, it is the thing that *selects the broken lowering*. Any bail
cause would do — which means the blast radius is "every program the direct
backend declines", not "every program that calls a shell".

## Corrections to the filing, point by point

* **"exits with THAT CALL'S status"** — no. It exits with the call's RETURN
  VALUE. `std.script.run("exit 7")` yields 1, not 7, because that is what the
  function returns.
* **"a bare call in statement position near the tail of `main`"** — the tail
  is irrelevant and `main` is irrelevant. A bare call inside a nested block in
  ANY value-returning function does it. Proven with `pick` above.
* **Binding still fixes it**, and the reason is now clear rather than empirical:
  a bound call is no longer the block's final expression, so nothing is
  returned. Verified: `code = 0` + a FAILING shell call exits 0 when bound and
  1 when bare.
* **The `if` (a nested block) is required** — the filing's repro contains one
  but never identifies it as the trigger. The same bare call at `main`'s top
  level does NOT leak. That is why the workaround "bind near the tail" happened
  to work and why it was never the real rule.

## Scope re-measured 2026-08-09, positive- AND negative-controlled

The filing's scope claim **HOLDS**. Swept 102 files (`scripts/`, `tools/lsp/`,
`tools/mcp/`) for a bare shell call in statement position in the last 10 lines.
Controls run before any row printed: the pattern matches a known-positive file
and rejects a bound call.

One hit — `tools/lsp/build.id:39`, `std.script.run("chmod +x duo-lsp")`. It is
**not affected**: it sits at `main`'s top level with a `print` after it, and
that exact shape was compiled and run — rc 0, correct. So no live gate in the
tree is broken by this today.

**But the sweep was looking for the wrong shape.** Now that the trigger is known
to be "a value-returning call as the final expression of a nested block in any
value-returning function", the true population is much larger than shell calls
in the last ten lines, and it has not been measured. That sweep is owed.

## Where the repair lives

`src/codegen.zig`, in the emission of a block in statement position: its final
expression's value must be discarded, not returned, unless the block is itself
in value position. The direct backend already does this correctly and is the
oracle for the fix.

The standing directive is **NO ZIG**, so this is **RECORDED AND NOT REPAIRED**.
The two-line repro is the gate, and it needs no harness:

```duo
adds = (a: i64, b: i64): i64
    a + b

pick = (n: i64): i64
    out: i64 = 99
    if n == 1
        adds(2, 3)
    out
```

When `--backend=c` and `--backend=direct` both print **99**, this is closed.

**`zig build semantic-harness` should have caught this** and did not — the
memory note that "native-differential compares exit status only" is the reason,
and here even the exit status differs, so the divergence is within reach of the
harness that exists.

## The defect

A `main` whose last *statement before the returned expression* is a
side-effecting call through `std.script.run` exits with THAT CALL'S status, not
with the value `main` returns. Reduced from the real case:

```
main(): i64
    code: i64 = 1
    …
    if work != ""
        sh("rm -rf {work}")      -- cleanup, status 0
    end
    code                          -- 1
end
```

`code` is 1 at that point — a `print` immediately above the `if` confirms it —
and the process exits **0**. Deleting the `if` block makes the same program
exit 1. Writing `return code` instead of the bare `code` does NOT help; the
status is lost either way. Binding the call's result does:

```
    if work != ""
        swept: i64 = sh("rm -rf {work}")
    end
    code
```

That exits 1. So the trigger is a bare call in statement position near the tail
of `main`, not the return form.

## Why this is worse than an ordinary bug

**It manufactures false greens in exactly the files that exist to prevent
them.** A gate that cleans up after itself — which is good practice, and which
every gate using `mktemp -d` must do — silently reports success no matter what
it printed. `scripts/foreign_census.id` printed

```
foreign_census: FAIL — 1 ledger rule(s) carry no `until:` termination condition.
```

and exited 0. Wired into `build.zig`, that step is green. CLAUDE.md §3's rule
is "positive-control every zero"; this is the shape where even a
positive-controlled gate lies, because the control passes and the *status* is
what is wrong.

## Scope, measured

`scripts/*.id` was swept for the shape (a bare `std.script.run` / `sh` call in
the last four lines of the file): **no other gate in `scripts/` is affected
today**. The two gates that were affected were both written in this session and
are fixed by binding, with a comment at each site pointing here. This is a trap
for the NEXT gate that does cleanup, not a backlog of broken ones.

## What must happen

1. Root-cause the return convention in codegen: a statement-position call must
   not be able to become the process status when `main` returns a value.
2. Until then, **bind the result of any side-effecting call that appears near
   the end of `main`**, and check both exit directions of every new gate before
   wiring it into `build.zig` — printing FAIL is not evidence that the step
   fails.
