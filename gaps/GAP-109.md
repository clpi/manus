# GAP-109 — interpolation silently passes through what it cannot resolve; a file-scope keyed table emits broken C

**Status:** OPEN · **Filed:** 2026-08-09
**Law:** §0.8 (interpolation is the canonical form) · H-8 OUTPUT TOTALITY ·
§3 MEASUREMENT HONESTY
**Answers** the audit's "interpolation crash / wrong-type path" P0 with two
measured defects, neither of which is a crash.

## 1. Interpolation silently emits its own source text

```duo
print("expr={1 + 2}")     ->  expr={1 + 2}
```

Not `3`. Not a diagnostic. **The braces and the expression are printed
literally**, so a program that asks for a value gets the source that asked for
it.

What resolves and what does not:

| hole | result |
|---|---|
| `"{a}"` a plain name | resolves |
| `"{p.x}"` a field walk | resolves |
| `"{1 + 2}"`, `"{a + 1}"` any expression | **passes through as text** |
| `"{t}"` a table | prints the word `table` |
| `"{n}"` nil | prints `nil` |

The name and field cases are the documented working forms, so this is a known
boundary — but the FAILURE MODE is the finding. §0.8 makes interpolation the
canonical spelling and bans concat chains, so a user reaching for `"{a + b}"` is
writing what the law tells them to write and getting source text back with no
diagnostic at all.

**H-8 makes this a finding twice over**: plain-string output is a finding, and an
unresolvable hole should DIAGNOSE with a repair edge, not degrade to its own
bytes. Degrading silently is the one behaviour that cannot be noticed.

`"{t}"` printing `table` is the same class one step down — an inspectable value
rendered as its type name carries no information and no way to ask for more.

## 2. A file-scope keyed table emits C that does not compile

```duo
p = { x = 7 }          -- FILE SCOPE
main(): i64
    print(p.x)
```

```
error: call to undeclared function 'lua_to_display_str'
error: call to undeclared function 'lua_table_set_raw_lit'
error: use of undeclared identifier 'tmp'
```

The identical table INSIDE a function works and prints `7`. So the defect is
scope, not shape: a keyed table at file scope emits calls to runtime helpers the
module never declared, plus a reference to an undeclared `tmp`.

This is loud, which is the good news, and it is the same family as gap[108] —
**file-scope bindings are handled by a path that has not kept up with the one
handling locals.** gap[108] is the silent half of that family (a file-scope
binding is per-function storage in the native backend); this is the noisy half.
Two symptoms, one under-maintained scope.

## Repair order

1. **The interpolation diagnostic first**, before any expression support. An
   unresolvable hole must diagnose — `"{a + b}"` should say so and name the
   repair. That converts a silent wrong output into a fixable one and costs
   nothing that works today.
2. **Then expression holes**, if they are wanted at all: §0.8's ban on concat
   chains means the alternatives are an expression hole or a bound local, and a
   language that forbids `..` while silently mangling `"{a + b}"` leaves no
   correct spelling for the common case.
3. **The file-scope keyed table** is independent and small — the emitter needs
   the declarations its local-scope sibling already gets.

## Do not

**Do not "fix" the pass-through by rendering the expression's text more
prettily.** The bytes are not the answer; the value is. A hole that cannot be
resolved is a diagnostic, and a hole that can be resolved is a value — there is
no third behaviour worth having.

## Related

gap[108] — the silent half of the file-scope family. Direct-backend
interpolation additionally bails at `lowerBinop()`, so the whole feature is
C-only today; that is a coverage gap, not a wrong answer, and is not counted
here.

## The diagnostic cannot be blanket — measured blast radius

`desugar_string_interpolation` (`parser.zig:5073`) walks the string, and for each
`{…}` calls `parseInterpolationPath`. When that returns null the loop does
`i += 1; continue;` — **the silent pass-through is that one line.** The obvious
repair is to diagnose there instead. Measured, that would be wrong:

```
brace holes in .id strings that are NOT a simple path
  46  {}
   7  { return a + b; }        C source inside a string
   4  {a = 1, b = 2, c = 3}    a duon table literal, quoted
   4  {1, 2}
   3  {print $1}               awk
   3  {out_buf, out_len}       C
   4  {files[i]}               <- SOMEONE ACTUALLY TRYING TO INTERPOLATE
```

Roughly eighty sites are legitimate literal braces — C in `@c.emit` payloads,
awk programs, JSON, prose. A diagnostic firing on those would be worse than the
defect: it would break working code to report a non-problem.

**And `{files[i]}` is the defect in the wild** — four sites where someone wrote
an index expecting interpolation and shipped the source text instead. So the
population contains both classes and the repair must separate them.

### The discriminator that would work

**Try to parse the hole as a duon expression.**

- parses AND is a path (`a`, `p.x`) -> resolve, as today
- parses BUT is not a path (`files[i]`, `a + 1`, `1 + 2`) -> **an interpolation
  attempt. DIAGNOSE**, naming the repair
- does not parse as an expression at all (`{}`, `{ return a + b; }`,
  `{print $1}`) -> literal braces, leave alone

That rule catches every real instance above and fires on none of the literals,
because C bodies, awk and empty braces are not duon expressions. It also
generalizes: the day expression holes are supported, the middle row becomes
"resolve" and the rule does not change shape.

**Not implemented here.** The rule is cheap but its false-positive rate must be
measured against the whole corpus before it ships, and this session has already
established that asserting a cost without measuring it is how the spiller
estimate came out wrong by 50%. Whoever takes it should print the middle row
across `lib/ tools/ scripts/ examples/` first and read every hit.
