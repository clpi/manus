The canon records this exact failure mode (GAP-014): applying a rule whose
surface does not exist replaces correct code with silently wrong code. 659
`.duo` files, two deleted gates, and every export site broken is not a repair.

1. Land `check` / `why` / `graph.*` / `add(…)` / `todo(gap[n])` as real bindings.

## CASE-SETS FIXED 2026-08-07 — the machinery existed behind a deleted sigil

`kind: { name, number, eof }` and `shape: { circle(r: f64), rect(w: f64) }` now
parse. Nothing was implemented to achieve it: `parse_descriptor_table` has
always handled bare cases AND payload variants. The declaration site gated it
on `@`:

```zig
if ((try self.pk()).kind == .at) { ... stmt_from_descriptor ... }
```

Pass 92 deleted prefix-`@`, which made the canonical spelling unreachable while
`kind: @{ … }` kept checking clean — the feature was live and unspellable.

Routed on LOOKAHEAD, not unconditionally: a case is a name followed by `,` or
`(`; a record field always has `:`. So `{ x: i64, y: i64 }` still goes to
`parse_type`, verified (`pt: { x: i64, y: i64 }` → `p.x + p.y` == 7).

This unblocks case payloads, which is the shape gap[024] needs — `Tok`'s
`int_val`/`float_val` siblings now have somewhere to go.

Still blocked: **method slots** (`bump = (self) …` inside a descriptor), which
FACE-CALL, BIND-1 and `:peek()` all need. Same file, likely the same shape of
fix — the descriptor entry parser accepts `name: type` and `name(payload)` but
not `name = callable`.

## The descriptor body accepted ONE slot form — measured (historical)

Everything epoch 2 asks of a descriptor lands on the same wall. A descriptor
body parses `name: shape` and nothing else:

```duo
tok: { kind: { name, number, eof } }
error: expected ':', got ','          -- case-set

tok: { kind: { name, number(value: i64), eof } }
error: expected ':', got ','          -- case-set with payload

r: { n: i64, bump = (self) self.n + 1 }
error: expected ':', got '='          -- method slot
```

So three separate rulings are blocked by one missing production:

- **case-sets** (Pass 100 §7, §0.3) — `kind: { name, number, eof }`, and with
  them `.eof` case inference, dispatch keys `@{ [.eof] = f }`, and the
  retirement of companion `*_kind` descriptors.
- **case payloads** — the decomposition that gap[024] needs. `Tok` carries
  `int_val` AND `float_val` as sibling fields because the payload has nowhere
  else to live; `kind: { number(value) }` is the fix and does not parse.
- **method slots** (Pass 95 FACE-CALL, BIND-1, `:peek()`) — `lx:read(number)(b)`
  needs `read` homed on the descriptor.

**Pass 100 §20's golden `token` and `lexer` do not compile.** Both are built
from these forms, and §3 instructs agents to pattern-match only from the golden
corpus — so following that instruction produces source the compiler rejects.
That is worth stating plainly because it inverts the usual failure: the corpus
is not aspirational decoration, it is the thing agents are told to copy.

**One production unblocks the largest batch of epoch-2 rules.** Ahead of the
stage surface (`check`/`why`/`graph`/`add`), ahead of the naming sweep: the
descriptor body is the bottleneck, and it is a parser change with a measurable
gate (the golden corpus compiling).

## FACE-CALL: the narrow blocker is the RECEIVER FACE, not method slots

Checked both spellings before concluding absence this time (the case-set fix
came from not doing that). Method slots are genuinely rejected either way:

```duo
r: { n: i64, bump = (self) self.n + 1 }    error: descriptor fields use
r: @{ n: i64, bump = (self) self.n + 1 }   'name: Type' syntax, not '='
```

`parse_descriptor_table` rejects `.assign` deliberately, and no AST node exists
for a callable slot — so unlike case-sets this is real machinery, not a route.

**But method slots are not what FACE-CALL needs.** `lib/std/compiler/lexer.duo`
declares free functions taking the subject first — `next(self: Lexer)`,
`peek_char(self: Lexer)` — which is exactly the shape a receiver face should
project. And that projection is broken:

```duo
r: { n: i64 }
bump(self: r): i64  self.n + 1  end
v: r = { n = 41 }
v:bump()
```

    error: call to undeclared function 'v__bump'

The face lowers to a mangled `<var>__<method>` symbol instead of resolving to
the free function `bump(v)`. So `v:bump()` is accepted by the checker and dies
in C — the same class as gap[026].

**This is the cheaper door to FACE-CALL.** If `subject:name(args)` fell back to
`name(subject, args)` when no member exists, every `L.next_tok(lex)` in the
corpus could become `lex:next()` with no descriptor change at all — which is
what Pass 95 actually asks for. Method slots would then be an ergonomic
addition rather than a prerequisite.

### The site, the precedent, and the safety condition

`src/codegen.zig:13927` — the `.method_call` emitter. The projection FACE-CALL
wants **already exists there** for scalars:

```zig
// a `:` invocation resolves ordinary members FIRST — data always wins the
// name — then a relation family with a receiver-bindable role, normalizing
// to the SAME edge: `p:to(str)` === `to(str)(p)`.
// Restricted to scalar receivers, where no user member can exist, so the
// data-wins rule is preserved by construction.
```

That comment states the whole problem. The restriction is not conservatism about
codegen; it is LAW-CALL's **data-wins** rule — a table carrying its own member
`bump` must beat a free function `bump`, and for an arbitrary table that cannot
be known statically.

CLAUDE.md's gap[014] note records the same wall from the other side: projecting
`t:push(v)` onto `table.insert` was tried and reverted because it hijacked a
table's own member, and "guarding with user_owns_name is NOT sufficient — that
sees free functions and locals, not table MEMBERS."

**A SEALED RECORD DESCRIPTOR closes exactly that hole.** `r: { n: i64 }` has a
statically known, complete member list, so "no member named `bump`" is provable
— which is precisely the "receiver-shape knowledge proving the member is absent"
gap[014] says a correct fix needs. The scalar restriction can widen to sealed
records without touching the dynamic-table case at all.

### THE SITE IS codegen.zig:14201 — and the projection is two lines from working

My earlier attribution to `table_module_type_for_expr` was WRONG: that function
guards every return with `is_table_module`, and `struct_type_for_mono_binding`
returns `.@"struct".name`, never an ident. Neither echoes the receiver.

The real site is the method-call FALLTHROUGH:

```zig
try self.emit_expr(mc.obj);        // renders "zebra"
self.p("__{s}(", .{mc.method});    // appends "__bump("
```

It builds a symbol out of the receiver's RENDERED TEXT. That is why renaming the
variable renames the symbol, and why no lookup table contains `zebra__bump` —
nothing ever declared it; it was concatenated.

## FACE-CALL FIXED 2026-08-07 — receiver faces over free functions work

    zebra: r = { n = 41 }
    zebra:bump()            ->  42        (was: undeclared 'zebra__bump')

Two changes, both in `src/codegen.zig`:

1. **The emission** (the method-call fallthrough). It built a symbol from the
   receiver's RENDERED TEXT — `emit_expr(obj)` then `"__{method}("` — so
   `zebra:bump()` produced `zebra__bump()`, a name nothing declares. Now, when a
   free function of that name exists (`func_decls`/`func_bodies`), it emits
   `bump(&zebra)`: the projection, with the receiver passed by pointer through
   `emit_arg_for_param` as records require.
2. **The type** (`expr_type`). A receiver face has the CALLEE's declared return
   type, read from `fd.func.ret_type`. Without it the call typed as `.any`, the
   caller wrapped it in `lua_to_num(...)`, and the native projection could not
   satisfy that. Note the branch immediately below resolves static-dispatch
   method types from a hardcoded list of method NAMES (`increment`, `greet`,
   `lang`, `to_string`, `eq`, default `.i64`) — the names-carry-semantics shape
   LAW-ONE denies, and worth retiring separately.

**Data-wins is preserved by construction, not by a guard.** The fallthrough runs
only after member, alias-method and table-module dispatch have all declined, so
a receiver carrying its own `bump` never reaches it. That is exactly the
receiver-shape knowledge gap[014] recorded as the prerequisite after projecting
`t:push(v)` onto `table.insert` hijacked a table's own member and was reverted.
Negative fixture verified at every step: a record owning `bump` returns its own.

This is the FACE-CALL surface Pass 95 asks for, available today with NO
descriptor change — `lex:next()` works against `next(self: Lexer)` as
`lib/std/compiler/lexer.duo` already declares it.

### Historical: DIAGNOSIS — the receiver's ident is echoed as a type name

Renaming the receiver renames the symbol:

```duo
zebra: r = { n = 41 }
zebra:bump()          ->  error: call to undeclared function 'zebra__bump'
```

So nothing is looking `bump` up on a type. `codegen.zig:14001` calls
`static_dispatch_type_for_expr(mc.obj, mc.method)`, which is itself correctly
guarded — every branch checks `type_has_static_method` before returning. The
failure is that one of its lookups returns the RECEIVER'S IDENT as a type name
and the guard agrees, because the **current module** does have a `bump`:

```zig
fn table_module_type_for_expr(self: *CodeGen, e: *const ast.Expr) ?[]const u8 {
    if (e.* != .name) return null;
    const ident = e.name.ident;      // <- the receiver's variable name
    ...
```

`type_has_static_method(ident, method)` then reaches
`table_module_has_method(ident, method)`, which finds the module-level `bump`
and answers true for *any* receiver name. The emitter duly writes
`{ident}__{method}`.

**The fix is a verification, not a fallback**: `table_module_type_for_expr` must
confirm the ident actually NAMES a table module before returning it. Once it
stops claiming every receiver, `v:bump()` falls through to the ordinary path and
FACE-CALL over free functions may work with no new projection at all — which is
worth re-measuring before writing one.

Fixtures: `zebra:bump()` → 42; a real table module's `mod:f()` must still
dispatch statically (that is what the current behaviour exists to serve).

**Descriptors are field-only today.** A `name: shape` slot parses; a
`name = (args) body` slot does not. So there is nowhere to home `read`,

`lexer: { peek = () …, next = () … }` shape from the context file's §3 does
not parse either.

This is the same shape as the rest of this gap: the denied spelling works, the
canonical one has no implementation. It also means the golden corpus's `lexer`

anyone tries to pattern-match from it.

before FACE-CALL, BIND-1, or the `:peek()` sibling-call form can be applied
anywhere.

## `x:byte(i)` IS NOT `string.byte(x, i)` — a semantic difference, not a spelling

Landed the 16 `byte` conversions once gap[028] unblocked `parse_status`, then
reverted: `examples/pass16_lexer_text_differential.duo` exits 3. The token TEXT
fingerprint changes, so the two spellings do not mean the same thing.

What makes this worth recording rather than retrying:

- **`parse_status` passed.** The Duo parser accepts it.
- **The artifact built, 0 errors.** The host compiler accepts it.
- **The field-for-field differential in `duo_lexer_dispatch.zig` passed** — kind,
  line, col, text, int_val, float_val all agreed.
- **The Duo-side TEXT fingerprint proof still caught it.**

Four gates said yes and the fifth said no. The `len` conversion in the same
sweep is fine (26 sites, landed, still green), so this is specific to `byte`.

**MEASURED — out-of-range behaviour differs:**

    s = "abc"
    i:      0      1     2     3     4
    string.byte(s, i)   0     97    98    99    0
    s:byte(i)          nil    97    98    99   nil

In range they are identical. Past the end `string.byte` returns **0** and the
receiver face returns **nil**. Every guarded site is unaffected — the lexer's
`peek_char` returns 0 explicitly before calling — but any site that relies on
the 0 sentinel changes meaning, and a comparison against a number silently
becomes a comparison against nil.

That is why kind/line/col stayed identical and only the token TEXT moved: the
divergence appears solely at boundary reads, which is exactly where a lexer
decides how far a token extends.

So the conversion is not a spelling change. It is a change of the absent-value
convention (B-8: absence over sentinels), and applying it requires auditing each
site for a 0-sentinel dependency rather than a regex.

Superseded guesses: a 1-based/0-based difference between the face and
the namespace function, or a different out-of-range behaviour. Both would leave
kind/line/col identical and change only the bytes read — which is exactly the
signature, and exactly what the text fingerprint exists to catch.

**Do not re-apply this conversion on the strength of parse_status plus a build.**
The next attempt should difference `x:byte(i)` against `string.byte(x, i)`
directly across the input domain, including index 0, index `#x`, and index
`#x + 1`, before touching the corpus.
