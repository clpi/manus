### THE RULING ON FRAGMENTS — a block is a FILE IN A PROJECT

Both red blocks ended on the same kind of diagnostic: `call to undeclared
function`. That is a statement about the CORPUS, not about the compiler, and
§20 answers it itself.

**§20 heads every block with a PATH, not with a program name.** `shc/lex.id`
and `shc/parse.id` are two files of ONE module: `parse.id` cites `lexer` and
`token` *because* `lex.id` declares them. Checking each path as a standalone
program was an artifact of the gate. Blocks sharing a path prefix are now
checked together, in the order §20 writes them.

**What is left over is three names, and §19 already rules on what they are** —
"**Descent**: four exits; stubs are `todo(gap[nn])` or bodiless declarations".
A fragment citing a helper it never declares is a fragment at a descent exit,
which the spec provides for. They are declared in
`examples/spec100/stubs/corpus.id`: `span` (cited by `lex.id`), `grow` and
`attach` (cited by `parse.id`). The alternative — declaring them in the §20
block — was rejected: that edits the corpus to match the compiler, and §20
exists to be evidence.

**The prelude is the one part of this gate that can turn a row green with no
compiler change**, so three controls stand behind it:

- a name may be added only after the compiler NAMED it in a diagnostic, and
  only with the shape §20's own use implies. Nothing is derived automatically;
  a prelude generated from error output could never fail;
- nothing in it carries BEHAVIOUR — `grow` and `attach` answer nil, so a block
  depending on what they RETURN fails rather than passing on a stub's
  arithmetic;
- `examples/spec100/stubs/control.id` cites a name the prelude does NOT
  carry, is checked with the prelude prepended exactly as a block is, and must
  still FAIL. If it stops failing the gate reports FAIL and no verdict. That
  control was itself positive-controlled: adding `nosuchhelper` to the prelude
  made the retired extracted-corpus check fail closed.

The stub file's line count is printed with the verdict, so it cannot grow
quietly.

`todo(gap[25])` — §19's own first stub spelling — **is not implemented**. It
reports `call to undeclared function 'todo'`. `nil` bodies stand in.

### CLOSED 2026-08-08 — six layout facts, and `shc/lex.id` parses end to end

One diagnostic (`13:42 expected expression, got 'else'`) hid six separate
parser decisions, each found by re-measuring after the previous one landed.
All six are the SAME defect wearing different clothes: a lookahead consuming
across a boundary §3 already draws, so the longer parse always won.

1. **The expression-if is ENDLESS** (§6 `kind = if tok.keyword keyword else
   name`). `end` was demanded. `then` now separates the dialects: written
   `then` still demands its closer, the endless form accepts an `end` only on
   the `if`'s own line (§3.4 "accepted and deleted"), so an `end` closing an
   ENCLOSING block is never swallowed. Fixture `ternary.id`, **10 20 3 2 1**.
2. **`.` is data access only when GLUED** (§4). `#.src .src[.pos]` parsed as
   `#((.src).src[.pos])` — both dot loops consumed a following `.` without
   consulting spacing. Adjacency was already a grammar fact here (`>>=` is
   `>>` with an `=` glued to it); this is the same test. Fixture `walk.id`,
   **12 3 12**.
3. **A one-line callable body may be a LOOP** (`skip = (p) while … .pos += 1`).
   The degenerate reading was not a parse error but a RUNNING PROGRAM:
   `(p)` scanned as a grouping paren, `skip = (p)` bound the parameter name as
   a value, and the loop became a file-scope sibling statement. `duo check`
   called that clean. Fixture `loopbody.id`, **0 3 9** — the leading 0 is the
   whole assertion, because a loop that ran at declaration time prints 3.
4. **The contract is written on the HEADER's line.** `parse_func_body` ate any
   following `:` as the return-type colon, so a body opening with a leading
   `:m()` sibling call began one statement late.
5. **…and so is a type constraint.** Same shape, second site:
   `parse_type_primary` read `T: Concept` across a newline, so in
   `token = (): token | error` the ALTERNATIVE swallowed the next line's
   sibling call. Only the union spelling was affected, which is what made it
   look unrelated to (4).
6. **Bare `@` NAMES the anchor** (§2, the @ DYAD) — `if r = read[b] return
   r(@)`. A slot body's anchor is its receiver, already bound as the first
   parameter, so naming it is the entire lowering. Fixture `anchorbare.id`,
   **5 9 5** — two receivers, because with one every degenerate reading agrees.

**(4) and (5) carry no fixture, deliberately.** Both need a statement opening
with a leading `:`, and a leading `:m()` still lowers to a closure in a
translation unit with no Lua runtime — rows 1b/1c of
`docs/anchor_stance_conflict.md`, owned elsewhere. Every value-level spelling
fails in the C backend for a reason that has nothing to do with these two
fixes, so asserting one would be asserting the defect. They are carried by the
`shc/lex.id` block row until those rows land. The same limit is why
`walk.id` asserts only the GLUED half of adjacency.

### CLOSED 2026-08-08 — the relation declaration, the result pack, the
### descriptor body

Four constructs, four fixtures, each verified BY VALUE. `blocks` did not move
— every one of them was behind a layout wall as well — but the walls they
owned are gone, which is what the `forms` number exists to record while a
block is still red.

- **Relation declaration with a LEVEL** — `decode(u64) = (cursor): u64 | error`.
  §9 declares at a trie place and the level is a descriptor-space key
  (LAW-STRATA), never a runtime parameter; the parser was reading the level
  group as the parameter list, so `u64` arrived where a parameter name was
  demanded. `parse_level_edge` recognises `name(key) = (` — unambiguous,
  because a function body cannot start with `=` — and mints the edge as
  `name__level`, the same `owner__member` symbol shape codegen already uses.
  The call site `decode(u64)(v)` resolves through the same mint, so the two
  cannot drift. Fixture `edge.id`, prints `42 141 1041`: **three edges that
  must disagree**, so a single-edge implementation that erased the level
  prints the same number three times and fails by value rather than by shape.
  LIMIT: the map is per-parse, so an edge declared in ANOTHER module does not
  resolve at a call site yet.
- **The RESULT PACK under a declared contract** — `: u64 | error` returning
  `nil, error.overflow`. `parse_type` parsed the union alternatives and threw
  them away, so the contract read as plain `u64` and nil was a type error. The
  alternatives still have no representation — `TypeExpr` has no union — but
  WHETHER one was written is now kept (`FuncBody.ret_fallible`), and that is
  the whole fact the check needs. `| nil` is excluded: B-12 makes it the
  SUCCESS-nil spelling, not a failure edge.
  Two halves, deliberately separate: sema keeps `current_ret` at the SUCCESS
  type so `return "x"` from `: i64 | error` still reports, while the signature
  a CALLER sees is dynamic, because a pack has no native scalar
  representation and `return nil, …` out of an `int64_t` C function is a hard
  clang error. One helper (`contract_ret`) in each of sema and codegen, and it
  is the IDENTITY for every contract without a failure alternative — which is
  all 753 tracked `.id` files — so no existing lowering can move.
  Fixture `pack.id`, prints `42 over trunc`: the success value, the detail of
  an early `return nil, err`, and the detail of the BARE TAIL pack
  `nil, "trunc"`. The bare tail needed nothing: `a, b` already parsed as a
  sequence and B-13 already made it the result.
- **Nested CASE-SET in a descriptor body** — `kind: { name, number, eof }` as a
  FIELD. This file's own correction was right: the 2026-08-07 fix reached the
  declaration site only, because a body's `name: …` runs through `parse_type`,
  which had no anonymous case-set production. It now has one, routed on the
  SAME lookahead as the declaration site (a case is a name followed by `,` or
  `(`; a record field always has `:`), so `{ x: i64, y: i64 }` in field
  position is still a record type — verified.
  It DECLARES rather than describes: the cases are hoisted as a real enum
  named for the field's HOME (§0.1 — `token.kind`), the field's type is that
  enum, and `token.kind.eof` reaches a case. A shape-only accept would have
  made the golden `token` parse while `.eof` still meant nothing.
  Fixture `caseset.id`, prints `9` — one inequality and one equality summed,
  so a case-set that parsed but declared nothing (every case equal, the
  degenerate zero) prints a different number.
- **RELATION SLOT in a descriptor body** — `format(sink) = (out) …`. A slot is
  an EDGE homed on the descriptor, so it is hoisted as a function whose first
  parameter IS the receiver, typed by that descriptor — the one shape both
  call spellings lower to. Fixture `slot.id`, prints `7 1 12`.

### A CODEGEN DEFECT the case-set work surfaced (pre-existing, fixed here)

A record field typed by an ENUM emitted the struct before the enum's typedef:

    kk: { name, number, eof }
    token: { kind: kk }        ->  error: unknown type name 'duo_kk'

Nothing to do with inline case-sets — the hand-written two-declaration form

### `>>= <<= |= &=` CLOSED — and they never needed a lexer token

This file had them filed as "missing at the TOKEN level … a two-lexer change
plus an artifact regeneration". That was the wrong diagnosis. `>>=` IS `>>`
immediately followed by `=`; the lexer already emits both. ADJACENCY is the
whole rule — the `=` must start in the column right after the operator ends,
on the same line — and `target >> = rhs` was a parse error before, so the
grammar rule is additive on its own terms. `src/lexer.zig` and
`lib/std/compiler/lexer.id` stay field-for-field identical and
`src/duo_lexer_tokenize.c` does not move.

This was the LAST wall in front of `ward/leb128.id`. Substituting
`v = v >> 7` for `v >>= 7` made the block check clean before the fix landed,
which is how the distance was measured rather than guessed. Fixture
`glued.id`, prints `8 16 13 8 5` — all four operators with operands that
separate them, plus a bare `e >> 1` negative control that must stay an
expression.

Closed 2026-08-08 and struck from this table: the result pack, the descriptor
RELATION slot, the nested case-set, and the relation declaration with a level.
The descriptor METHOD slot `here = () …` is closed as a PARSE (an unlevelled
relation slot is the same production) but its receiver-face dispatch is not —
see the open table above.

Two of those need correcting against what this file said before:

- **The case-set fix of 2026-08-07 only reaches the DECLARATION site.**
  `kind: { name, number, eof }` at top level checks clean; the same text as a
  FIELD of a descriptor body does not, because a body's `name: …` runs through
  `parse_type`, which has no anonymous case-set production. The claim
  "case-sets now parse" is true of one of the two positions §20 uses.
- **Compound assignment is missing at the TOKEN level.** `+= -= *= /= %= ^=`
  exist; `>>= <<= |= &=` are not lexed at all. Cheap in the Zig lexer, not
  cheap overall — `src/lexer.zig` and `lib/std/compiler/lexer.id` are held
  field-for-field identical by a differential, so a new token is a two-lexer
  change plus an artifact regeneration.

   **AMENDED 2026-08-08. The two lines are swapped: the shebang is line 1 and
   the label is line 2.** This is the one editorial change made to §20, and it
   is called out loudly here because the standing rule is that a §20 block is
   never edited to make it pass. It qualifies because *nothing about the
   program changed*: a comment moved down one line. The two conventions in
   collision — "every block carries a `-- path.id` header" and "an executable
   file starts with a shebang" — both demand line 1, and only one of them can
   have it. The shebang must, because "line 1" is a property of every POSIX

## CASE-SETS FIXED 2026-08-07 — the machinery existed behind a deleted sigil

`kind: { name, number, eof }` and `shape: { circle(r: f64), rect(w: f64) }` now
parse. Nothing was implemented to achieve it: `parse_descriptor_table` has
always handled bare cases AND payload variants. The declaration site gated it
on `@`:

```zig
if ((try self.pk()).kind == .at) { ... stmt_from_descriptor ... }
```

Pass 92 deleted prefix-`@`, which made the canonical spelling unreachable while
`kind: @{ … }` kept checking clean — the feature was live and unspellable.

Routed on LOOKAHEAD, not unconditionally: a case is a name followed by `,` or
`(`; a record field always has `:`. So `{ x: i64, y: i64 }` still goes to
`parse_type`, verified (`pt: { x: i64, y: i64 }` → `p.x + p.y` == 7).

This unblocks case payloads, which is the shape gap[024] needs — `Tok`'s
`int_val`/`float_val` siblings now have somewhere to go.

Still blocked: **method slots** (`bump = (self) …` inside a descriptor), which
FACE-CALL, BIND-1 and `:peek()` all need. Same file, likely the same shape of
fix — the descriptor entry parser accepts `name: type` and `name(payload)` but
not `name = callable`.

## The descriptor body accepted ONE slot form — measured (historical)

Everything epoch 2 asks of a descriptor lands on the same wall. A descriptor
body parses `name: shape` and nothing else:

```duo
tok: { kind: { name, number, eof } }
error: expected ':', got ','          -- case-set

tok: { kind: { name, number(value: i64), eof } }
error: expected ':', got ','          -- case-set with payload

r: { n: i64, bump = (self) self.n + 1 }
error: expected ':', got '='          -- method slot
```

So three separate rulings are blocked by one missing production:

- **case-sets** (Pass 100 §7, §0.3) — `kind: { name, number, eof }`, and with
  them `.eof` case inference, dispatch keys `@{ [.eof] = f }`, and the
  retirement of companion `*_kind` descriptors.
- **case payloads** — the decomposition that gap[024] needs. `Tok` carries
  `int_val` AND `float_val` as sibling fields because the payload has nowhere
  else to live; `kind: { number(value) }` is the fix and does not parse.
- **method slots** (Pass 95 FACE-CALL, BIND-1, `:peek()`) — `lx:read(number)(b)`
  needs `read` homed on the descriptor.

**Pass 100 §20's golden `token` and `lexer` do not compile.** Both are built
from these forms, and §3 instructs agents to pattern-match only from the golden
corpus — so following that instruction produces source the compiler rejects.
That is worth stating plainly because it inverts the usual failure: the corpus
is not aspirational decoration, it is the thing agents are told to copy.

**One production unblocks the largest batch of epoch-2 rules.** Ahead of the
stage surface (`check`/`why`/`graph`/`add`), ahead of the naming sweep: the
descriptor body is the bottleneck, and it is a parser change with a measurable
gate (the golden corpus compiling).

## FACE-CALL: the narrow blocker is the RECEIVER FACE, not method slots

Checked both spellings before concluding absence this time (the case-set fix
came from not doing that). Method slots are genuinely rejected either way:

```duo
r: { n: i64, bump = (self) self.n + 1 }    error: descriptor fields use
r: @{ n: i64, bump = (self) self.n + 1 }   'name: Type' syntax, not '='
```

`parse_descriptor_table` rejects `.assign` deliberately, and no AST node exists
for a callable slot — so unlike case-sets this is real machinery, not a route.

**But method slots are not what FACE-CALL needs.** `lib/std/compiler/lexer.id`
declares free functions taking the subject first — `next(self: Lexer)`,
`peek_char(self: Lexer)` — which is exactly the shape a receiver face should
project. And that projection is broken:

```duo
r: { n: i64 }
bump(self: r): i64  self.n + 1  end
v: r = { n = 41 }
v:bump()
```

    error: call to undeclared function 'v__bump'

The face lowers to a mangled `<var>__<method>` symbol instead of resolving to
the free function `bump(v)`. So `v:bump()` is accepted by the checker and dies
in C — the same class as gap[026].

**This is the cheaper door to FACE-CALL.** If `subject:name(args)` fell back to
`name(subject, args)` when no member exists, every `L.next_tok(lex)` in the
corpus could become `lex:next()` with no descriptor change at all — which is
what Pass 95 actually asks for. Method slots would then be an ergonomic
addition rather than a prerequisite.

### The site, the precedent, and the safety condition

`src/codegen.zig:13927` — the `.method_call` emitter. The projection FACE-CALL
wants **already exists there** for scalars:

```zig
// a `:` invocation resolves ordinary members FIRST — data always wins the
// name — then a relation family with a receiver-bindable role, normalizing
// to the SAME edge: `p:to(str)` === `to(str)(p)`.
```

That comment states the whole problem. The restriction is not conservatism about

## `x:byte(i)` IS NOT `string.byte(x, i)` — a semantic difference, not a spelling

Landed the 16 `byte` conversions once gap[028] unblocked `parse_status`, then
reverted: `examples/pass16_lexer_text_differential.id` exits 3. The token TEXT
fingerprint changes, so the two spellings do not mean the same thing.

What makes this worth recording rather than retrying:

- **`parse_status` passed.** The Duo parser accepts it.
- **The artifact built, 0 errors.** The host compiler accepts it.
- **The field-for-field differential in `duo_lexer_dispatch.zig` passed** — kind,
  line, col, text, int_val, float_val all agreed.
- **The Duo-side TEXT fingerprint proof still caught it.**

Four gates said yes and the fifth said no. The `len` conversion in the same
sweep is fine (26 sites, landed, still green), so this is specific to `byte`.

**MEASURED — out-of-range behaviour differs:**

    s = "abc"
    i:      0      1     2     3     4
    string.byte(s, i)   0     97    98    99    0
    s:byte(i)          nil    97    98    99   nil

In range they are identical. Past the end `string.byte` returns **0** and the
receiver face returns **nil**. Every guarded site is unaffected — the lexer's
`peek_char` returns 0 explicitly before calling — but any site that relies on
the 0 sentinel changes meaning, and a comparison against a number silently
becomes a comparison against nil.

That is why kind/line/col stayed identical and only the token TEXT moved: the
divergence appears solely at boundary reads, which is exactly where a lexer
decides how far a token extends.

So the conversion is not a spelling change. It is a change of the absent-value
convention (B-8: absence over sentinels), and applying it requires auditing each
site for a 0-sentinel dependency rather than a regex.

Superseded guesses: a 1-based/0-based difference between the face and
the namespace function, or a different out-of-range behaviour. Both would leave
kind/line/col identical and change only the bytes read — which is exactly the
signature, and exactly what the text fingerprint exists to catch.

**Do not re-apply this conversion on the strength of parse_status plus a build.**
The next attempt should difference `x:byte(i)` against `string.byte(x, i)`
directly across the input domain, including index 0, index `#x`, and index
`#x + 1`, before touching the corpus.

### CAUSE FOUND: string receiver faces do not lower on the NATIVE path

receiver faces, not on sentinels and not on the parser.** The `len` half landed

  turns SH-09 red. The Duo parser rejects something the sweep produces at scale
  that it accepts in isolation.

So `sub` is not blocked on capability the way `byte` was (native lowering) — it
is blocked on a Duo-parser coverage gap, like gap[028] was. The isolated form
parses; some spelling the 370 sites contain does not.
