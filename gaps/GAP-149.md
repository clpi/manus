Primitive-zero ruling supersedes docs/spec/numerics.md's irreducible scalar-descriptor table. Current ResolvedType tags encode i8..u64/f32/f64/vector faces as host enum cases; semantic_graph interns them as separate type_node identities. No admitted graph fact owner currently exposes numeric domain plus observable width/range/sign/format/overflow/rounding facts, and bare literal inference eagerly defaults to i64/f64 before all demand is applied. Session 1 will stop minting fixed-width primitive descriptor identities, retain ResolvedType only as migration fact on values/applications, publish descriptor identity unknown unless an exact declaration-owned descriptor exists, and keep source faces unchanged. Closure requires C0/numeric authority reconciliation plus a compact graph-owned numeric fact projection and contextual literal demand evidence; do not invent helper vocabulary locally.

into a place of another, the question a C RECORD MIGRATION asks per field — is
now derived from the same owner too. `type_diff.isWidening` carried a per-tag
lattice (`i8` → `i16,i32,i64,f64`; `u8` → `u16,u32,u64,i64,f64`; `f32` → `f64`;
…) that restated numeric containment a fourth time beside `numericFacts`,
`narrowFit` and `acceptsDescriptor`, and it was the ONE of the four whose wrong
answer silently loses field data: a migration that should CAST an old field into
a wider new one instead took the type-change arm and DEFAULTED the field to
zero.

It is now `ResolvedType.widensTo` → `NumericFacts.widensTo`, the containment
lattice read off `domain`, `width` and `signed`: a real widens to a strictly
wider real; a SUB-REGISTER integral (width < 64) widens into `f64`, whose 53-bit
mantissa represents it exactly, while `i64`/`u64` do NOT — a 64-bit integer
exceeds the double's exact-integer range, the exact precision loss the retired
lattice encoded by simply never listing `i64`/`u64` as sources — and no integral
widens into `f32`; a same-sign integral widens to a strictly wider one, and an
unsigned source additionally widens into the register-width signed integral that
dominates its whole range. A signed source never crosses into unsigned and a
real never narrows into an integral. `str` → `any` stays the caller's one
NON-NUMERIC widening (a managed reference into the top type): the numeric owner
has no facts for it, so `widensTo` returns null and `isWidening` owns that arm
exactly as `defaultInit` keeps `str`/`bool` explicit. A roster could not
compose: a scalar identity added to the numeric owner stayed unknown to the
hand-list, was silently declared non-widenable, and its migration defaulted to
zero — the wrong answer in the safe-looking direction, a field silently cleared
rather than cast.

A NOMINAL DESCRIPTOR DELEGATES its physical widening on purpose here, unlike
`numericAcceptsDescriptor` which withholds: a migration casts the physical
value, and the C cast is over the representation (`law.nominal` §46), the same
delegation `narrowFit` and `c_type` already make. The equal-descriptor case is
the caller's, ahead of the call, because two identical descriptors are a COPY,
not a widening.

Two controls pin it. In `types.zig`, `types: the widening face of the scalar
roster is derived from the same facts` iterates the union's own payload-free tags
over every ORDERED PAIR and pins `widensTo` equal to the retired numeric lattice
where both sides are numeric — the pairs it widened AND the `i64`/`u64`/`f64` and
vector sources it declined — and requires null on every non-numeric side, so a
scalar identity added to the union cannot be one the widening face silently does
not know. In `type_diff.zig`, `type_diff: isWidening composes the derived numeric
face with the non-numeric arm` pins the COMPOSED `isWidening` — equal-copy plus
derived numeric plus `str` → `any` — equal to the retired full switch bit for bit
over every ordered pair. Run

    zig build test

and read those two test names. Compare the failing-test NAME SET before and
after over the two trees that differ by exactly this slice — it is IDENTICAL, so
no consumer anywhere in the suite gained or lost an answer — while two new
controls pass. The pre-existing red aggregate (`GAP-134`/`GAP-145`
parser-fixture debt, ~482 fail / 2 crash) is unchanged. Planting the
`i64` → `f64` widening in `NumericFacts.widensTo` was checked to fail the numeric
control closed. The machine path still cannot be measured on a host where the

## The field-cell face of the scalar roster

The FIELD-CELL face — which of the three cells the native IR carries
(`native_ir.FieldKind = { i64, str, f64 }`) a scalar descriptor MATERIALISES IN
when it is a field of a natively-lowered record, table row, or parameter — is now
derived from the same owner too. It stood TWICE in `dnir_lower`, as
`graphFieldFact` (which also carries the sub-register store width) and
`tableFieldKind` (which drops it), each a per-tag switch mapping `str`→str,
`f64`→f64, and every integral spelling plus `bool`→i64. Two statements of one
fact that agree only until someone edits one of them, and the fact was not new:
a value in one cell has a domain (`numericFacts.domain`) and, if it carries no
numeric facts, is `bool` or `str` (`scalarRepr`).

It is now `types.scalarFieldCell` — `scalarRepr` gates the roster, `str` answers
the reference cell, an integral or `bool` answers the register-integer cell, and
a real answers the double cell ONLY at width 64. The two exclusions the retired
switches encoded by OMISSION are preserved as facts rather than widened: `f32`
has no native field cell (the switches listed only `f64`, so `domain == .real`
is not the test — `width == 64` is), and a NOMINAL DESCRIPTOR is withheld, not
delegated — the switches listed only bare scalar tags, so a nominal-over-`i32`
(a `.struct` tag) fell to `else`, and `scalarRepr` withholds it identically
(`nominalReprOf != null`). This is the one physical field face where the nominal
takes the caller's boxed row rather than its representation's cell. A roster
could not compose: a scalar identity added to the union gained numeric facts but
stayed unknown to the hand-lists, took their `else` arm, and was silently
declared NOT A NATIVE FIELD — a record that should lower natively fell back to a
boxed row, the wrong answer in the safe-looking direction. The sub-register store
width `graphFieldFact` carries is exactly the descriptor when `narrowFit` gives
it one and null otherwise, so that face too reads the owner rather than a second
list of which widths are narrow.

The two enums are the same three identities; the one consumer renames
`types.ScalarFieldCell` to `dnir.FieldKind` by NAME at the seam (`fieldKindOf`),
not by shared integer tag (`law.magic.code.zero`), because `types.zig` is IR and
`native_ir.zig` is a codegen carrier below it and must not gain a reverse import.

## The boxing face of the scalar roster

The BOXING face — which `lua_Value` CONSTRUCTOR a scalar descriptor boxes
through when a native value crosses into the dynamic runtime — is now derived
from the same owner too. It stood in `codegen` as two per-tag SWITCHES that
hand-listed all eight integral tags (`.i8,.i16,.i32,.i64,.u8,.u16,.u32,.u64 =>
"lua_val_from_int((int64_t)"`, reals → `lua_val_from_num((double)`, then
`bool`/`str`, else a box-less tail) — one at a native module-call RETURN
boundary and one at a native scalar-GLOBAL export. Two statements of one fact
that agree only until someone edits one, and the fact was not new: an integral
scalar boxes as an integer, a real scalar as a number — that is
`numericFacts.domain` — and the two arithmetic-free scalars box as themselves
(`bool`, `str`), the same two `scalarRepr` names explicitly.

It is now `types.luaBoxClass` → `types.LuaBoxClass.ctor`, where `LuaBoxClass` is
the four box classes `{ int, num, bool, str }` and `ctor` is the ONE place the
constructor string is stated. `luaBoxClass` reads `scalarRepr` to gate the
roster, answers `str`/`bool` for the two arithmetic-free scalars, and reads
`numericFacts.domain` for the numeric owners — an integral boxes as an integer
so a value above 2^53 is not ROUNDED through the number box, the exact defect
`emit_native_scalar_to_lua_value`'s own comment records where `crc64.final`
returned `0x2B9C7EE4E2780C8A` and the double box handed back its low 9 bits
cleared. A switch could not compose: a scalar identity added to the union gained
numeric facts but stayed unknown to the two switch sites, took their box-less
tail, and lost its integer box — the wrong answer in the safe-looking direction.
Every non-scalar identity is declined by the `numericFacts`/`scalarRepr` fact
rather than by absence: the vectors span several cells (`lanes != 1`) and were
absent from the retired bare-tag lists exactly so; `any` is already boxed; and
`void`/`nil`/`never`/composed identities are not scalars the runtime boxes with
a bare constructor. A NOMINAL DESCRIPTOR is WITHHELD here as an identity,
exactly as `scalarRepr` withholds it and exactly as the retired switches' bare
scalar tags let a nominal-over-`i32` (a `.struct` tag) fall to their box-less
tail; the global export site's `luaBoxClass(grt) orelse .str` maps it to a null
wrap the same way.

Both switch sites are converted BYTE-FOR-BYTE: the return-boundary open/close
pair reproduces the extra paren the int/number boxes wrap the call in
(`lua_val_from_int((int64_t)(` … `))`) and the single paren `str`/`bool` and the
non-scalar identity path use, and the global export site keeps its
`emit_as_lua_value` fallback for the null wrap. The two remaining `codegen`
predicate chains (`emit_native_scalar_to_lua_value`, `emit_lua_value_from_native`)
already read `is_integer`/`is_float` and are LEFT UNCHANGED, because those
predicates delegate through `numericFacts` and answer true for a vector, so
converting them would change a latent vector edge the switch sites never had —
a behaviour change this equivalence slice does not make.

A control pins the derived face equal to the retired switch partition on every

the union's own tags rather than a list, so a scalar identity added to the union

planted `real → int` widening is refused by the `domain` fact. Run
