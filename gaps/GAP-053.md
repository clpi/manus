# GAP-053 — a `str` function ending in if/else reads its own condition wrong

**Filed** 2026-08-08. **Status** open. **Class** SILENTLY WRONG — no
diagnostic, no crash, a plausible answer.

Found while writing `scripts/spec_corpus.duo`: the gate reported "no diagnostic
captured" for all five Pass 100 §20 golden blocks while the compiler was in
fact producing a diagnostic for each of them.

## Minimal repro

```duo
f(): str
    line = std.script.chomp(std.script.capture("echo hello"))
    if line == ""
        "EMPTY"
    else
        line
    end
end
main = (): i64
    io.write("<" .. f() .. ">\n")
    0
end
```

    <EMPTY>          -- wrong; `line` holds "hello"

`line` demonstrably holds the right value at that point: inserting
`io.write("INNER<" .. line .. ">\n")` immediately above the `if` prints
`INNER<hello>`, and the very next line takes the then-branch anyway.

## What the boundary is, measured rather than guessed

Each of these is CORRECT, so none of the obvious single causes is it:

    f(a: str): str  if a == "" "EMPTY" else a end          -- param, correct
    f(): str        line = "hello"  if line == "" …        -- literal, correct
    f(): bool       line = capture(…)  line == ""          -- bool fn, correct
    f(): str        line = capture(…)  if line == "" line = "EMPTY" end  line
                                                           -- assign form, correct

So it needs all three at once: a **`str`-returning** function, a **local bound
from a call**, and the comparison in the **if/else TAIL** position — i.e. the
demand-return path (§5 CDR) rather than an ordinary statement `if`. The
assign-then-fall-through spelling of the same logic is correct in both
directions, which is the workaround the gate uses and comments.

## Not this session's change

Reproduced on the compiler built from `HEAD` with every parser change of the
session stashed. The bug predates them.

## Second symptom, probably the same machinery

```duo
label(path: str): str
    head = std.script.chomp(std.script.capture("head -1 " .. path))
    if head == ""
        std.script.path_stem(path)
    else
        head
    end
end
```

SIGSEGV (rc 139) in the compiled binary, before any output. Both halves work
alone: `path_stem` called on its own returns `pass100`, and the same if/else
tail with a string literal in the then-arm returns the wrong branch (above)
rather than crashing. Same shape, worse failure — a call in the then-arm of a
`str` demand-return tail.

## Why it matters more than its size

The whole class of thing this repository keeps being burned by is a
measurement that answers confidently from evidence it never had. This bug
produces exactly that: a gate that reads a subprocess, compares its output to
`""`, and takes the empty branch. `scripts/spec_corpus.duo` would have shipped
reporting "no diagnostic captured" for every block — a plausible-looking row,
five times, with the real diagnostics sitting in a buffer three lines up.

Any gate in `scripts/` shaped `x = capture(…)` then an if/else tail on `x` is
suspect and should be re-read.

## Where to look

The `str` demand-return path — the edge §5 says realizes the last expression —
where the last expression is an `if_stmt`/`if_expr`. `at()` in the same gate
has the identical shape returning `i64` and is CORRECT, so the divergence is in
how the `str` result of the branch is materialized, not in the branch itself.
