# GAP-035 — a `gmatch` nested inside a `gmatch` drops iterations

**Status:** FIXED 2026-08-08 · **Filed:** 2026-08-07 · **Frequency:** 1
**Cited at:** `scripts/run_benchmark.id` (`extract_times`)

(Third number for this record. Filed as 028, overwritten by a parallel session;
refiled as 030, overwritten again. `gaps/` is a shared numeric registry with no
allocation protocol — see the recorded collision hazard.)

## Repro

```duo
txt = "a Time \t1.5\tsec\nb Time \t2.5\tsec\nc Time \t3.5\tsec"

n = 0
for line in string.gmatch(txt, "([^\n]+)")
    n += 1
-- n == 3, correct

m = 0
for line in string.gmatch(txt, "([^\n]+)")
    for w in string.gmatch(line, "([^%s]+)")
        m += 1
-- m == 4.  Expected 12 (3 lines x 4 words).
```

The outer loop alone is correct, so the inner `gmatch` corrupts the outer
iterator's state. No diagnostic; the loop just ends early.

## Why it mattered

`extract_times` in the benchmark harness used exactly this shape and returned
**2** timings for a 40-benchmark run. Every row printed `N/A`, every winner
defaulted to C, and the suite reported Duo losing all 40 benchmarks for a
reason that had nothing to do with speed.

## FIXED 2026-08-08 — there was ONE cursor for the whole program

`src/codegen.zig`'s runtime string held `static GmatchState gmatch_state` — a
single file-static struct — and `lua_str_gmatch` reset it on every call while
`lua_str_gmatch_iter` read it through a bare function pointer that carried no
identity. So an inner `gmatch` did not merely share the outer's cursor, it
RESET it; when the inner iteration ended it set `active = 0`, and the outer
loop read that same flag on its next step and stopped. The outer loop was
correct alone because nothing else touched the flag.

The cursor now lives inside the iterator VALUE, so iterator identity is cursor
identity and nesting depth is unbounded:

- `GmatchState` moved into `DuoGmatchIter`, whose prefix (`duo_ObjHeader
  header; int id; int nup;`) is layout-compatible with `lua_Closure` exactly as
  the generated `duo_closure_N` structs are.
- `lua_str_gmatch` allocates one per call and returns it as a `VAL_CLOSURE`
  carrying the reserved id `DUO_GMATCH_CLOSURE_ID` (-9001; generated ids are
  assigned from 0 up, so they cannot collide).
- `lua_invoke` — the single dispatch point for both `VAL_FUNC` and
  `VAL_CLOSURE`, and therefore the only thing the generic-for protocol and a
  manual `f()` both go through — recognises that id and steps that cursor.
- The source and pattern copies are freed the moment an iteration ends.

### Measured, the gap's own repro

| | before | after | want |
| --- | --- | --- | --- |
| outer alone, 3 lines | 3 | 3 | 3 |
| inner nested in outer, words | **4** | **12** | 12 |

and the words are right, not just the count:
`a|Time|1.5|sec|b|Time|2.5|sec|c|Time|3.5|sec|`.

Nine further shapes, all correct after: a manually-called iterator (`xyz`, then
nil, then nil again), two independent iterators interleaved (`172839`), three
levels deep (2x2x2 = 8), the receiver face `("one two three"):gmatch("%a+")`
(3), a ragged inner string per outer step (6), and a `break` out of the inner
loop leaving the outer intact (3).

### Adjacent, measured, NOT introduced here

Two `gmatch` defects are unchanged by this fix — identical values before and
after, so they are separate rows, not regressions:

- captures are not projected: `for k, v in gmatch(s, "(%a+)=(%d+)")` binds both
  `k` and `v` to the whole match (`a=1`), because `duo_lp_find_at` returns only
  the match span.
- the empty pattern yields 3 matches on `"abc"`, where Lua yields 4.

## Regression test

`src/codegen.zig`, `test "runtime: each gmatch owns its cursor"` — asserts the
program-wide `GmatchState` is gone, that the step reads its cursor through the
closure, and that `lua_invoke` dispatches the reserved id.


## Interim (historical — the gap is closed)

One match per line instead of an inner iterator:

```duo
num = string.match(line, "Time%s+([0-9%.eE%+%-]+)")
```

## Note

`gmatch` is a deny row in Epoch 2 (`scan(grammar)(s)` is canonical), so the
long-term fix may be to land `scan` rather than repair the iterator. Filed
against the behaviour either way: code in the tree uses it today, and silently
losing iterations is the failure mode that survives review.
