# GAP-187 — relation directional modes and solution cardinality lattice

**Status:** OPEN · **Filed:** !2026-08-18T16:15:00Z
**Priority:** P1 · **Kind:** research_gap
**Filed by:** devin-semantic-20260818
**Files:** docs/spec/constitution.md, docs/spec/law.md, src/relation.id, src/demand.id

Expand relation semantics beyond rigid `call(inputs) -> output pack` to first-class
directional modes (which slots are input vs output) and solution cardinality
(`det`, `semidet`, `nondet`, `multi`, `erroneous`, `failure`). Icon demonstrates
how expressions naturally producing 0, 1, or many values drive goal-directed
evaluation; Mercury demonstrates that relation modes and determinism allow
reordering and specialization while preserving declarative semantics.

## Current measured boundary

Relations assume fixed forward application `(subject, operands) -> result_pack`.
Directional inversion and solution multiplicity are not represented in the graph.

**Crossed:**

- Relation identities and pack structures exist in C0.
- `gate/subject.id` proves subject/edge decomposition.

**Still missing:**

- Relation definition owning slot roles + admissible directional modes.
- Solution cardinality lattice: `0` (failure), `1` (exactly one), `0..1` (optional),
  `1..n` (at least one), `0..n` (generator/iterator/stream), `divergent` (never returns).
- Demand-driven execution: `:first` (stop after 1), `:has` (stop after existence proven),
  `:count` (cardinality only), `:all` (materialize full pack), `:any` (nondeterministic pick).
- Unification of predicates, optionals, iterators, generators, search, and logic relations
  under one solution lattice.

## Required order

1. Add directional mode and solution cardinality descriptors to `Relation` in C0.
2. Formalize the solution lattice and mode lattice.
3. Wire observer demand (`:first`, `:has`, `:count`, `:all`) to solution cardinality.
4. Implement goal reordering based on producer/consumer mode analysis.
5. Prove algorithmic reduction on queries and generator chains under restricted demand.

## Closure acceptance

Close when a single relation declaration can execute across multiple directional modes
and when solution demand changes the realized algorithm (e.g. `find` + `:first` stopping
at first witness without full scan).
