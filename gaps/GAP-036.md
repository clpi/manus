# GAP-036 — a table declared inside a loop cannot use the native array path

**Status:** open · **Filed:** 2026-08-08 · **Frequency:** 1
**Cited at:** `examples/benchmark.duo` (`leven`), the last heavy loser in the
`.duo`-vs-C mirror after the dense-table work (0.283s vs 0.0237s reference C).

(Took 036 after checking `gaps/` — 035 was the highest. `gaps/` is a shared
numeric registry with no allocation protocol, so expect to renumber.)

## What works, and what does not

The dense (native array) lowering now covers ordinary indexed table code,
including the two-buffer swap (`tmp = a; a = b; b = tmp`). It is still limited
to tables bound at the **top level of a function body**:
`detect_dense_table` (src/sema.zig) scans `fb.body.stmts` only.

## Repro

```duo
-- densifies: `t = {}` is a top-level statement of the body
top(n: i64)
    t = {}
    i = 1
    while i <= n do
        t[i] = i * 2
        i += 1
    end
    return t[n]
end

-- does NOT densify: `t = {}` is inside the loop
nested(n: i64)
    total = 0
    rep = 0
    while rep < n do
        t = {}
        i = 1
        while i <= 12 do
            t[i] = i * 2
            i += 1
        end
        total += t[12]
        rep += 1
    end
    return total
end
```

Check with `duo compile x.duo --backend=c` and grep the emitted C for
`duo_dt_set_i64`: present for `top`, absent for `nested`.

## Why it was not just widened

Two things break if the scan simply walks nested blocks.

1. **Scope.** The dense declaration is emitted at the binding site, and the
   `free` is emitted at the function's return. A declaration inside a loop is
   not in scope there — the emitted C does not compile. This is the same class
   of bug that alias locals hit (`__dt_tmp` declared inside the swap loop,
   freed after it); aliases were fixed by never freeing them, which is not
   available here because a loop-local table *does* own a buffer.

2. **One allocation per iteration.** `t = {}` inside a loop means a fresh empty
   table each iteration. With the frees at the return, that is an unbounded
   leak — for `leven(100000)` roughly 200k allocations.

## The shape of a fix

Hoist the `(pointer, capacity)` declaration to the function prologue and lower
an in-loop `t = {}` to a **reset** — keep the buffer, zero the reserved region
— rather than a declaration. That is semantically equivalent, because the dense
accessors already read an unwritten slot as 0, and it costs the same O(cap) the
original allocation did. The frees then stay at the return, where the names are
in scope, and there is exactly one buffer per name for the whole call.

The obstacle is that the prologue is emitted before the body's locals, and a
cap expression may name one of them. `detect_dense_table` already works around
this in one narrow case by inlining an integer-literal local's value into the
cap string; a hoisted declaration needs that generalised, or needs the
reservation to move to the reset site while the declaration stays in the
prologue.

## Adjacent, same file, different cause

`cond_swap` in the same benchmark stays boxed for an unrelated reason: it holds
an element in a local across the swap.

```duo
tmp = t[i]
t[i] = t[i + 1]
t[i + 1] = tmp
```

`expr_is_numeric_valued` has no `.index` arm, so `tmp` is not proven numeric
and the store of `tmp` disqualifies `t`. Note that `dense_check_non_numeric`
*does* treat a bare `.index` read as numeric (it falls through to `else`), so
the direct form `t[i + 1] = t[i]` is accepted and only the form that goes
through a local is rejected — the two paths disagree. Aligning them is a
one-line change, but it is not obviously sound on its own: it would also accept
`x = t["k"]; u[i] = x` where `t` holds strings, silently storing 0. A sound
version needs the fixpoint — an `.index` read is numeric when the table read
from has itself qualified — which means running the qualification twice.
