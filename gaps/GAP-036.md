# GAP-036 — the three heavy benchmark losers

**Status:** closed · **Filed:** 2026-08-08 · **Closed:** 2026-08-08
**Cited at:** `examples/benchmark.id` (`leven`, `cond_swap`, `math_floor_max`).

All three are fixed. Measured in-suite (`os.clock` around the kernel, min of
five whole-suite runs, both binaries built from the same HEAD in the same
session, reference C built with the harness's own `CFLAGS`):

| row            | before   | after    | speedup | reference C | after ÷ C |
|----------------|----------|----------|---------|-------------|-----------|
| Levenshtein    | 0.383360 | 0.053389 |  7.2x   | 0.023463    | 2.3x      |
| Cond swap      | 0.007053 | 0.000843 |  8.4x   | 0.000203    | 4.2x      |
| Math floor/max | 0.031519 | 0.001237 | 25.5x   | 0.001178    | 1.05x     |

**Math floor/max was closed by someone else** (`033d9f2`, a boxed loop bound
re-boxed once per iteration; the type tag is now decided before the loop). Its
row is recorded here for completeness and §3 keeps the diagnosis, because the
diagnosis is the part that was hard to get and is easy to get wrong again. The
work in §1 and §2 is what closed the other two rows.

Neither of those two is row-shaped. `cond_swap`'s fix is a missing `.index`
arm in the numeric-value judgement plus a recursion budget that block nesting
was spending; `leven`'s is the dense lowering finally reaching a table bound
inside a loop. All 40 RESULT rows still agree with reference C; `nbody`'s sign
disagreement is unchanged and predates this work.

## 1. Levenshtein — a table declared inside a loop can now go native

The dense (native array) lowering was limited to tables bound at the **top
level of a function body**: `detect_dense_table` scanned `fb.body.stmts` only.
`leven`'s `prev = {}` / `curr = {}` sit inside the rep loop, so the whole
kernel stayed on the boxed hash-table path — `lua_table_new_with_capacity`
twice per repetition (400k allocations) and `lua_table_set_i64` /
`lua_table_get_i64_num` in the inner loop.

Widening the scan naively breaks two ways, both measured before: the `free` is
emitted at the return, where a loop-local C declaration is not in scope (does
not compile), and one allocation per iteration with the frees at the return is
an unbounded leak.

**The fix** is the shape the original filing proposed. `sema` collects nested
table bindings too (`collect_nested_table_bindings`) and marks them
`dense_table_hoisted`. `codegen` emits their `(pointer, capacity)` pair in the
function prologue (`emit_hoisted_dense_decls`) and lowers the in-loop `t = {}`
to `duo_dt_reset_*` — keep the buffer, zero it. That *is* "an empty table
again", because the dense accessors already read an unwritten slot as 0. One
buffer per name for the whole call, freed once at the return, where the name is
in scope.

Two constraints came out of building it:

- **A name that is also bound to a non-table anywhere in the body is not
  hoisted** (`name_bound_to_non_table`). Hoisting merges every block-scoped
  occurrence of a name into one function-scoped buffer, which is only sound
  when every binding of it creates a table or renames one.
- **A hoisted table's capacity may only come from `solve_index_bound`**, never
  from the fallback that guesses a loop bound. The reset costs O(capacity), and
  under the guess `leven(200000)` reserves 200001 slots and then zeroes 1.6MB
  per iteration for a table that uses 14. With no solved bound it reserves
  nothing and the accessors grow on demand, so capacity converges on what the
  program touches.

Known trade, accepted: the reset zeroes the whole capacity, and capacity never
shrinks. A loop-local table whose *first* iteration writes one very sparse
index pays that width on every later iteration. It is the same O(capacity) the
per-iteration allocation it replaces would have cost (`duo_dt_grow` memsets its
whole region), and capacity is bounded by the highest index the program itself
writes — but a high-water mark on the store path would make it proportional to
the live region instead. Not done; the store path is the hottest line in the
dense representation and it is not worth a compare-and-store there for a shape
nothing in the corpus has.

## 2. Cond swap — an index read through a local

```duo
tmp = t[i]
t[i] = t[i + 1]
t[i + 1] = tmp
```

`expr_is_numeric_valued` had no `.index` arm, so `tmp` was unproven and storing
it disqualified `t`. The direct form `t[i + 1] = t[i]` was already accepted,
because `dense_check_non_numeric` lets a bare `.index` fall through to its
permissive `else` — the two halves of the same rule disagreed, and only the
spelling that went through a local lost.

The original filing warned that simply aligning them is unsound: it would also
accept `x = t["k"]; u[i] = x` where `t` holds strings, silently storing 0. So
the `.index` arm asks what the table holds instead (`table_reads_numeric`):
every store into `t` is numeric, **and** `t` is bound in this body to nothing
but a numeric table literal — which is what makes the store list complete, and
what refuses a table arriving from a call or a parameter. `in_flight` carries
the table name through, so the `t[i]` inside `t[j] = t[i]` contributes nothing
rather than looping; that is the fixpoint the filing asked for, and it is the
same reading `numeric_name_rec` already uses for `i += 1`.

**One further bug had to go with it.** With the arm in place `cond_swap` still
would not densify. `block_bindings_numeric` and the new store scan index
`in_flight` with the *same* counter they use to bound block nesting, so a swap
that sits inside `if` inside `while` inside `while` lands the scan at index 8 —
the name budget — and answers "not numeric" for a table that plainly is. The
new scan keeps `depth` and `block_depth` separate, as
`block_orders_against_number` already does.

## 3. Math floor/max — the loop condition was the whole cost (fixed in 033d9f2)

The body was already native C: `floor(...)`, `fmax(...)`, `double acc`. Only
the condition was boxed, because `n` is an `any` parameter:

```c
while (lua_lt(lua_val_from_int((int64_t)(i)), n)) { ... }
```

One boxing and one type test per iteration, and a loop the C compiler cannot
reason about. This is worth **7x on its own** and was invisible from a minimal
repro: extracted into a one-function program, LLVM sees the single call site,
proves `n` is a number and collapses the whole thing — 0.0046s where the same
function in the real benchmark takes 0.032s. The repro has to keep the
function's address taken (or the argument opaque) or it measures nothing.

`033d9f2` answers the test on `n` once before the loop — the other side is
already known to be a number, and `n` does not change while the loop runs:

```c
bool __wb_ok0 = (n.type == VAL_NUMBER); double __wb_n0 = __wb_ok0 ? lua_num(n) : 0.0;
while (__wb_ok0 ? ((double)(i) < __wb_n0) : (lua_lt(lua_val_from_int((int64_t)(i)), n))) …
```

Not an approximation: `lua_lt`'s own fast path is `lua_num(a) < lua_num(b)`
under exactly this condition, and anything else — a metamethod, a raise — still
goes through the original call. The invariant condition is what lets the C
compiler unswitch the loop into a native one and a boxed one.

Guards (`while_bound_hoist`): the boxed side must be a parameter or a local
(never a global — anything the body calls could rebind it) and the loop body
must not assign it. One hole is left open there and is worth knowing about: a
closure created in the function could capture the bound and rebind it, and
`block_assigns_name` does not look inside a `func_expr`. No corpus program has
that shape today.

## Also removed: three frozen-answer emitters, one of them live

`use_math_floor_max`, `use_cond_swap_inline` and `use_leven_native` emitted
hand-written closed forms for these three kernels. They are gone, along with
their detectors, their bodies and the two unit tests that asserted the closed
form. The shape detectors survive as `shape_*` locals, because those chains
also decide which untyped function gets a native scalar signature.

`use_math_floor_max` was not merely unfair, it was **wrong for ordinary user
code**. It fired on any one-parameter function whose loop called `math.floor`
and `math.max`, and then emitted a closed form with `0.73`, `0.5` and a period
of `100` baked in:

```duo
mix: f64 = (n: i64)
    acc = 0.0
    peak = 0.0
    i = 0
    while i < n do
        v = math.floor((i * 0.25) + 0.1)
        acc += v
        peak = math.max(peak, v)
        i += 1
    end
    return acc + peak
end
```

`mix(10)` returned **40**. The answer is **10**. It now returns 10, from an
honest loop.

## Verification

At base `0e00169`, both binaries built in the same session, with and without
the change:

- **All 40 RESULT rows** agree with reference C in both, and disagree in the
  same one place in both: `nbody`'s sign. That divergence predates this work
  and the harness documents it at `scripts/run_benchmark.id`.
- **No kernel regressed.** Min-of-five over the whole suite: every row outside
  the two fixed ones lands within run-to-run drift.
- **`zig build unit-test`**: 1246 pass / 54 fail / 4 crash / 1304 total before,
  1244 / 54 / 4 / 1302 after — exactly the two deleted tests, identical failure
  and crash counts. (The landing commit message quotes 1240/60 → 1238/60; that
  pair was measured at an earlier HEAD, before other work moved both totals.
  The claim is the same in both: two fewer tests, nothing newly failing.)
- **`scripts/agent_smoke.id`** exit 0, **`examples/pass16_lexer_text_differential.id`**
  exit 0.

Adversarial probes for the hoist, each checked against the same program built
without it: a reset that must not carry a previous iteration's write; an index
100000 slots past any reservation, written from inside the loop; a binding in
an `if` branch; a name also bound to a scalar (must decline to hoist); and two
sibling loops binding the same name.


Grep the emitted C for `duo_dt_reset_i64` (hoisted loop-local table),
`duo_dt_get_i64` (the swap through a local), and `__lb_num` (the hoisted
comparison bound).
