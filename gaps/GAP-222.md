# GAP-222 — `unresolved-application-facts` is not one cause, and its largest named sub-population must not be "fixed"

**Priority:** P2 · **Kind:** evidence_gap

## Status
open — a refutation, filed so the wrong repair is not attempted again.

## The premise that was wrong

It was believed that cross-home FUNCTION application publishes no
`ApplicationFact` while cross-home METHOD application does, and that this
single missing producer blocked two `zig build test` steps.

**Refuted.** `Sema.moduleLevelRelationNamed` (`src/sema.zig:975`) accepts
both spellings, and its own doc comment says so — commit `cf2473e0` added
the method arm ALONGSIDE a plain-function arm that was always there. A
four-way `idol graph` probe on a clean mirror:

    helper.plainfn(1)   cross-home FUNCTION   published 1, blocking 0
    helper.methfn(1)    cross-home METHOD     published 1, blocking 0
    script.chomp(...)   bare home             published 1, blocking 0
    std.script.chomp    std-prefixed          published 0, blocking 1

There is no missing producer. Nothing to add beside `cf2473e0`.

## The real cause, and why resolving it is forbidden

It is the `std.` prefix, not function-versus-method. `std.script.chomp`
makes `home_resolve.resolve` seek `lib/std/script.id`. There is no
`lib/std/` — the file is `lib/script.id`. Only `vendor.` and `std.core.` are
prefix-stripped (`src/home_resolve.zig:195-199`), so the home never
resolves and the site is never a candidate.

That is deliberate, and making it resolve is explicitly forbidden.
`lib/std.id` is a seven-line tombstone: "NO std namespace. NO std table. NO
`std.*` spellings in Idol source." GAP-157 is P0 and OPEN: "No `std`
anywhere. Not in source spellings, not as a runtime table, NOT AS A
MIGRATION ALIAS", with acceptance that `std_dot` ratchets monotonically down
and added lines carry zero new `std.`.

So the compiler is correct and the SOURCES are wrong. The repair is
`std.script.` -> `script.` in the corpus, which belongs to the GAP-157
migration, not to a DNB011 fix.

## And the correct repair unblocks neither step

Applied to both named files (10 and 13 sites, both `idol check` clean
after):

    scripts/run_gpu_benchmark.id   DNB011 chomp  ->  DNB001 `run` / unspecified
    scripts/luahost.id             DNB011 chomp  ->  DNB011 `shout` /
                                                     application-realization-count

`luahost`'s next blocker is `shout`, a LOCAL relation at
`scripts/luahost.id:37` with no return type — nothing to do with cross-home.
And `scripts/agent_smoke.id` already compiles on direct today; it is not
blocked at compile time at all, it shells out at line 28 and fails at
RUNTIME.

## Denominator, which is the durable part

Over all 1923 tracked `.id` under `idol compile --backend=direct`:

    unresolved-application-facts   87 files   (largest DNB011 family — confirmed)
      of which contain any `std.`  18 files   (~21%)
      of which do not              69 files
      with `chomp` as head           6 files

So the `std.` cause explains about a fifth of the family. Attributing the
whole family to one producer — as this lane's premise did — is exactly the
error `gate/attribution.sh` warns about: a diagnostic string is not a cause.

## A contradiction worth resolving separately
`scripts/run_gpu_benchmark.id`'s own header declares it "OPT-IN — not part
of the CI gate", while `build.zig:391` wires it into `test_step`. One of the
two is wrong, and it should be settled before that step is counted as a gate.

## Correction to a cited denominator
The figures "`idol check` 75/81, `idol compile --backend=direct` 10/81" are
over `build.zig`'s PATH LITERALS, not the corpus. Measured over
`examples/*.id` the direct figure is 43/250. Quoting the two together
without naming the population is the same verb-and-denominator error the
capability frontier work already documented.
