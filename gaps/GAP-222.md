## The real cause, and why resolving it is forbidden

| # | directive |
|---|---|
| 1 | It is the `std.` prefix, not function-versus-method. `std.script.chomp` makes `home_resolve.resolve` seek `lib/std/script.id`. |
| 2 | There is no `lib/std/` — the file is `lib/script.id`. |
| 3 | Only `vendor.` and `std.core.` are prefix-stripped (`src/home_resolve.zig:195-199`), so the home never resolves and the site is never a candidate. |

| # | directive |
|---|---|
| 1 | That is deliberate, and making it resolve is explicitly forbidden. `lib/std.id` is a seven-line tombstone: "NO std namespace. |
| 2 | NO std table. |
| 3 | NO `std.*` spellings in Idol source." GAP-157 is P0 and OPEN: "No `std` anywhere. |
| 4 | Not in source spellings, not as a runtime table, NOT AS A MIGRATION ALIAS", with acceptance that `std_dot` ratchets monotonically down and added lines carry zero new `std.`. |

| # | directive |
|---|---|
| 1 | So the compiler is correct and the SOURCES are wrong. |
| 2 | The repair is `std.script.` -> `script.` in the corpus, which belongs to the GAP-157 migration, not to a DNB011 fix. |
