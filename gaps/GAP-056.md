# GAP-056 — f64 arguments are passed to a float kernel in GP registers

**Status:** OPEN · **Filed:** 2026-08-08 · **Severity:** SILENT WRONG ANSWER
**Owner file:** `src/dnir_lower.zig` (`emitScalarCallArgs`)

Not a bail. The program compiles, runs, exits cleanly, and reports the wrong
number. That is the worst class of defect this repo recognises, and it is in the
backend that CLAUDE.md calls canonical.

## Repro

```duo
p(x: f64, y: f64): i64
    if x > y return 9 end
    return 1
end

main(): i64
    return p(3.5, 1.5)
end
```

```
--backend=c        9      correct
--backend=direct   1      wrong
```

Before commit 57e4d12 the direct answer was **0** — also wrong, differently
wrong. The defect predates that commit; only the flavour of wrongness changed.

## Cause, read off the generated code

`--emit asm` settles it. The callee is flawless:

```asm
_p:
    fcmp d0, d1
    cset x9, gt
    cmp  x9, #0
    b.eq .Lduo_0
    mov  x9, #9
    mov  x0, x9
    ret
```

The caller is not:

```asm
_main:
    mov  x9, #0
    movk x9, #16396, lsl #48    ; 3.5
    mov  x0, x9                 ; <-- GP. Should be fmov d0, x9
    mov  x9, #0
    movk x9, #16376, lsl #48    ; 1.5
    mov  x1, x9                 ; <-- GP. Should be fmov d1, x9
    bl   _p
```

Both arguments are materialised correctly and then placed in the WRONG REGISTER
FILE. `_p` compares whatever d0 and d1 happened to hold, so the branch is
decided by leftover state and the function usually falls through to its else.

`emitScalarCallArgs` (dnir_lower.zig ~1933) ends with:

```zig
var i: u32 = 0;
while (i < count) : (i += 1) {
    try ctx.emit(.{ .op = .mov_arg, .result = i, .lhs = values[i] });
}
```

Unconditional `.mov_arg` — no argument type is consulted. DNIR has carried a
`fp_mov_arg` op the whole time (`duo_native_ir.zig` Op enum), and the f64-kernel
path at 2407/2414/2420 already uses it. The generic multi-argument path never
learned to.

## The fix needs the CALLEE's signature

`emitScalarCallArgs` does not currently receive the callee. `lowerFunction`
already takes an `f64_kernels` set, which is the set of functions whose params
arrive in d0-d7 — that is exactly the predicate, so the information is in the
context already; it has to reach the marshalling site.

AAPCS64 assigns FP and GP argument registers from SEPARATE counters, so this is
not a matter of swapping `mov_arg` for `fp_mov_arg` at the same index. A mixed
signature `f(a: i64, b: f64, c: i64)` puts a in x0, b in d0, c in x1. A fix that
keeps one shared counter will be right only for all-float and all-integer
signatures and quietly wrong for every mixture — which is the same failure mode
as the current bug, just rarer.

## Why no gate caught it

The native differential is at `81 agree / 2 differ` and has been green
throughout. It is green because **no corpus program has the shape "f64 params +
comparison + non-f64 return"**. The gate is not broken; it is uncovered.

That is the finding worth keeping. A differential only tests the shapes someone
thought to write down, and 81/2 reads like a proof of correctness when it is a
statement about corpus coverage. This shape was found by construction while
chasing an unrelated bail, not by any gate.

## Fixture to add with the fix

Must cover a MIXED signature, not just all-float — an all-float fixture passes
under the shared-counter mistake described above:

```duo
mix(a: i64, b: f64, c: i64, d: f64): i64
    if b > d return a + c end
    return 0
end
```

And assert by VALUE against `--backend=c`, with a control under 256 (exit codes
are 8-bit; 12345 and 57 are the same exit status).
