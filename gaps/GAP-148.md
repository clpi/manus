# GAP-148 — value locations and fixed-frame register spilling

**Status:** OPEN · **Filed:** !2026-08-10T13:08:38Z
**Priority:** P0 · **Kind:** native_lowering_gap
**Filed by:** codex-root-continuation-20260810
**Files:** src/native_backend.zig, build.zig, docs/performance.md
**Migration fixtures to replace/delete:** examples/pass11_spill_proof.id, scripts/pass11_spill_smoke.id (deleted with the retired catalog apparatus)

The GP spiller keys state by physical register while DNIR values and local homes still point at that register. Reusing a spilled register therefore creates two owners and has a proven silent-miscompile history; the current guard correctly fails closed. Dynamic inline stack growth is also unsafe because existing record/table slots use fixed SP-relative offsets, and compiler spill state is not an authoritative value realization. WP-03 is false evidence: v1..v20 are unread, so its required STR/LDR canonizes storage that semantic demand does not require. Current bounded backend repair omits only unlineaged unread i64 immediate stores, proves exact assembly/object equality to the equivalent two-binding program, and retains a genuine 20-live-value RegisterExhausted control. Closure requires Idol to assign authoritative graph values to `register` or `frame` realization facts before emission, with CFG/backedge-aware liveness, a prologue-reserved frame, materialization returning the actual register, per-function state reset, value differentials under calls/branches/records, and replacement of the stale spill proof projections. Zig may project that assignment only as a bounded bootstrap bridge with an explicit deletion gate.

## The reclaim arm returned a destination as if it were the value

Measured on `0c753bd4d` plus this change, in
`~/src/idol/.worktrees/named-gap148-20260901`.

been spilled — `evalDnirValue` hands its result straight back as THE register
holding that value. Its gate-transport exhaustion arm returned
`reclaimSpilledReg()` directly, above the single `ldr` that is the only
instruction moving the value out of the frame, and so also above the
`spilled_regs` removal, the slot release, and the temp remap. The caller

`spilled_regs` because something else needed it, so when the reclaim returns the
same register it holds that something else. A wrong value with no diagnostic, on
the one path whose whole job is to make a spilled value readable again.

value, which is the condition that puts `allocRegExcluding` into the reclaim in
the first place: `spillReg` refuses once `gate_spill_cursor + 16 >

it. The arm now supplies the reload destination and the rest of the function runs
as written.

transport: it drops the `spilled_regs` entry that would have reloaded the
register it hands back, abandoning that register's previous owner. Remapping this
value's owner onto the same register adds a reader to an owner already abandoned
by that drop, so no owner is broken that the reclaim had not already broken, and

## The reclaim abandoned an owner and kept its records

Measured on `0365b107` plus this change, in
`~/src/idol/.worktrees/named-gap148-20260901`.

Dropping the `spilled_regs` entry is what makes a register allocatable again and
is also what abandons its owner: that entry was the only thing that would have
reloaded the value. That hazard is this gap's and is unchanged here. What the
drop did NOT do was clear the two OTHER records the abandoned owner held, and
each is a defect in the opposite direction — against the live value the reclaim
just handed the register to:

- `gp_reg_owner[reg]` still named the abandoned owner. That owner is normally
  absent from `value_free_at`, its reads being behind emission, which
  `sweepGpLive` reads as dead at every index. The next sweep therefore cleared
  `used_regs[reg]` for a register a live value had just been given, and
  `allocRegExcluding` handed the same register out a second time.
- the frame slot stayed reserved permanently. `ensureRegLive` and
  `ensureRegLiveRemap` are its only readers and both key on the entry just
  removed, so nothing can read it again; holding it kept `spillReg` stepping
  `gate_spill_cursor` toward `gate_spill_end` and refusing spills the
  pre-reserved area still had room for.

Releasing the slot in the reclaim exposed a second, latent defect on the one
path that already reached it. `ensureRegLiveRemap` appended `off` to
`free_spill_slots` unconditionally after its own `spilled_regs.remove(reg)`,
which is a no-op when the reclaim returned `reg` ITSELF — the case the reload
repair above turns on. One frame slot then entered the free pool twice, and two
later spills store two live values at the same offset. The release now belongs to
whichever removal actually took the entry out: the removal is idempotent, a
release is not.

## The reload put the value back and left the register free

Measured on `33f2f82e` plus this change, in
`~/src/idol/.worktrees/named-gap148-20260901`.

`spillReg` performs two halves of one act: it moves the value out of the register
— `str`, then `spilled_regs.put` — and it stops the register standing for that
value, `used_regs[victim] = false`. `ensureRegLive` is the exact inverse, the
`ldr` back into THAT SAME register, and it undid only the first half.

So the value returned to a register that read as free. Worse, the one fact that
had been substituting for the claim left in the same breath: both free scans in
`allocRegExcluding` skip a register `spilled_regs` contains, which is the
fail-closed guard that made a spilled register unallocatable, and the reload's
own `spilled_regs.remove` is what ends that. Between the reload and the next
`sweepGpLive` the register is in neither set, so the next allocation of any kind
returns a register holding a live value whose owner still names it, and the
second owner's first write is a silent wrong answer for the first.

Restoring the claim returns the register to the state it held before the spill,
and cannot leak for the same reason: `spillReg` never cleared
`gp_reg_owner[victim]`, so `sweepGpLive` releases this claim on the same owner
record, at the same index, as it would have had the register never spilled.

Bounded to gate transport with the rest of this gap. `spillReg` is reached only
from `allocRegExcluding`, which refuses above its spill loops unless
`gate_transport`, so `spilled_regs` is empty elsewhere and `ensureRegLive` is a
no-op there. Distinct from both reclaim facts above: those are
`reclaimSpilledReg` and `ensureRegLiveRemap`, the paths that move a value to a
DIFFERENT register; this is the path that puts it back in the same one.

## The remap relocated the value and left its owner record behind

Measured on `aa936dfa` plus this change, in
`~/src/idol/.worktrees/named-gap148-20260901`.

`ensureRegLiveRemap` moves a spilled value from `reg` into a different register:
it emits the `ldr` into `fresh`, drops the `spilled_regs` entry, releases the
frame slot, and rewrites every `temps` entry that named `reg`. `gp_reg_owner` is
the fifth record naming the same value and was the only one not moved. This is
the identical relocation `preserveArgReg` performs, which finishes by writing
`gp_reg_owner[fresh]` for exactly this reason; the missing write is wrong in
both directions at once.

`reg` keeps an owner it no longer holds. `spillReg` cleared `used_regs[reg]` and
never cleared `gp_reg_owner[reg]` — deliberately, so the sweep would release the
claim on the same owner record had the value come back to that register. Here
the value does not come back: the removal above takes `reg` out of
`spilled_regs`, so both free scans in `allocRegExcluding` stop skipping it and
hand it out. Then `sweepGpLive`, reading the stale owner against a
`value_free_at` that has no entry for a value whose reads are behind emission,
clears `used_regs[reg]` for the register a live value was just given, and the
pool hands the same register out a second time. Two owners, one register, no
diagnostic — this gap's shape, reached through the remap rather than through
`reclaimSpilledReg`.

`fresh` holds a live value under a null owner, because `claimReg` records only
`used_regs` and the callee-save touch set. `sweepGpLive` skips an unowned
register, so nothing reclaims `fresh` for the rest of the function and the pool
shrinks by one — on the one path whose whole job is to relieve register
pressure, and whose exhaustion arm is the reclaim hazard above.
`preserveArgReg` names this same failure from the other side: owner null there
ran `tree.id` out of registers on the spot.

The repair moves the owner record with the value and clears the vacated end.
When the exhaustion arm reclaimed `reg` itself, `fresh == reg` and there is
nothing to move; a home register is excluded from receiving the owner for the
same reason `sweepGpLive` skips one. This is not the closure — closure is still
authoritative `register`/`frame` assignment before emission, per the record
above — and the `reclaimSpilledReg` two-owner hazard remains open and bounded to

into, and it asked `reclaimSpilledReg` for one. A reclaim frees a register by
dropping the `spilled_regs` entry that would have reloaded it — the only thing
that could still move that value out of the frame — so a READ of one spilled
value destroyed another, and which other was hash order.

It never had to buy anything. `reg` is itself spilled, and its entry is the one
this function drops a few lines down anyway, because its value is the value
being loaded out. Reloading into `reg` frees exactly the one register the

## The reclaim ignored the one register the allocation excluded

`allocRegExcluding(exclude)` makes exactly one promise, and every path in it
kept that promise but the last. Both free scans skip `exclude`; all three spill
passes skip `exclude`, which is also why this call can never be what puts
`exclude` into `spilled_regs`. Then the bottom handed the whole decision to
`reclaimSpilledReg`, which took no `exclude` at all and walked the map in hash

could be handed back the register it had just named as holding a value it was
still using.

The exclusion is not a preference. `emitBinopFlooredConstDivisor` states the
reason at its own call: `dst` is claimed by the caller and a plain `allocReg`
could spill it, leaving `dst` mapped to a slot holding the value it had BEFORE
the sequence. The reclaim is worse than that spill, because it drops the
`spilled_regs` entry as well — the caller's value is abandoned in the frame with
nothing able to read it back, the caller writes its second value into the same
register, and both reads are wrong with no diagnostic.

The excluded register has to have been spilled BEFORE the call, and those
windows are ordinary. `emitIfConverted` reads the binding into `old`, then
evaluates both operands — each of which allocates, and can therefore spill `old`

the then-arm's `rt` across the whole else arm and then asks for

filled with every allocatable register; when it is genuinely the last one, the

## The release dropped the entry and kept the slot

Measured on `359fa064` plus this change, in
`~/src/idol/.worktrees/named-gap148-20260901`.

Four paths take a register out of `spilled_regs`, and taking the entry out is
what makes the frame slot behind it unreadable: `ensureRegLive` and
`ensureRegLiveRemap` are that slot's only readers and both key on the entry.
The removal is therefore the moment the slot becomes dead, and three of the four
hand it straight back to `free_spill_slots` on exactly that removal —
`sweepGpLive` and `reclaimSpilledReg` for a register they take from its owner,
both reloads for a value they move out of the frame. `releaseReg` was the fourth
and kept it.

A slot nothing can ever read again then stayed reserved for the rest of the
function. `spillReg` takes `free_spill_slots` first and otherwise steps
`gate_spill_cursor`, so every leaked slot moves the cursor one step closer to
`gate_spill_end` and the refusal there is a spill the pre-reserved area still had
room for. That refusal is not inert: it is the exact condition that propagates
out of the `allocRegExcluding` cascade into `ensureRegLiveRemap`'s exhaustion arm
and into the `reclaimSpilledReg` at the cascade's bottom — the two paths this
gap's open hazard lives on. The leak spends the reserved area on dead storage and
then hands the allocator the state where it has to abandon an owner.

Reached by ordinary scratch, not by a corner. `releaseReg` returns above every
record an owner holds, so only an UNOWNED register gets past that guard — which
is the ordinary state of a register `allocReg` handed out for one instruction's
operands, and it is exactly what the spill passes take first, since they require
`used_regs[victim]` and skip homes. `emitFlooredDivRem` holds `q` across two more
`allocRegExcluding(dst)` calls, either of which can spill it, and releases it at
the end of the sequence.

Releasing it is safe because the storage is dead in both directions at once: no
owner record names the register, or this body is not reached at all, and the
entry that was the slot's only reader is gone on the line above. This is the
argument `reclaimSpilledReg` already makes for the slot of the owner it abandons,
where the owner at least still exists.

The append belongs to the removal that actually took the entry, because the
removal is idempotent and a release is not. The emit paths release one register
more than once — `releaseReg(addr)` beside `releaseReg(base)` where both resolved
to the same register — and one offset in `free_spill_slots` twice is two later
spills storing two live values at one offset. `sweepGpLive` already spells it
this way; this makes the third path agree with it.

## The spill area was reserved at one end of the frame and handed out from the other

`spillReg` and `ensureRegLive` both reach a slot as
`stack_frame_bytes - off - 8`, so `off` counts DOWN FROM THE TOP of the frame.
That is what the last-resort branch means when it takes

that instant `off` IS the distance from the top, and it stays correct as the
frame grows underneath it. The prologue named the band at the OTHER END. It
subtracts `gp_stack_bytes + spill_reserve` in one `sub sp` and puts the spill
area at `[sp, gp_stack_bytes .. gp_stack_bytes + spill_reserve)`, directly above
the GP stack locals at `[sp, 0 .. gp_stack_bytes)` — "locals sit at [sp,#0]…;
spill temps sit above them" — and then set `gate_spill_base = gp_stack_bytes`,
which is that area's address measured UP from `sp`.

Mixing the two does not shift the area, it overlaps it: `off = gp_stack_bytes`
addresses the TOP of the reservation and the cursor then walks DOWNWARD through
the frame, out of the reserved area, across the locals, and into whatever the
frame already held.

reservation. The twelfth is 72 and the last is 8, and those are the homes of
locals 9 and 1: the spill store is a wrong answer for the local, and the local's
next store is a wrong answer for the spilled value, in both directions, with no
diagnostic. It is this gap's two-owner shape reached through the frame instead of
through a map, and the pressure that reaches it is the same pressure the
reservation exists for — twelve simultaneous spills in one function, which is why
the eleven correct slots hid it. With a table or record already in the frame the
same walk runs off the reservation the other way instead, over the region the
prologue rebased above it.

The band is therefore measured from the top, like the offsets that read it: it
starts at whatever the frame held BEFORE this prologue's `sub` and runs for
`spill_reserve` bytes, which maps exactly onto
`[sp, gp_stack_bytes + 8 .. gp_stack_bytes + spill_reserve)` and touches nothing
else. No slot is lost — the count is `spill_reserve / 16` either way — and
`spillReg` still refuses with `RegisterExhausted` at the end of the area, which
is the refusal the reserve's own sizing comment relies on when it says a bound

## The argument register was preserved into itself

Measured on `1fd3ff84` plus this change, in
`~/src/idol/.worktrees/named-gap148-20260901`. `1fd3ff84` is the
call-result section above rebased onto `cd2e0f40`; the arm below is unrelated to
it and was not part of that measurement.

Every face recorded above is bounded to gate transport, because `spillReg` is
reached only from `allocRegExcluding`, which refuses above its spill passes
otherwise. This one is not. It is the same two-owner shape reached through the
allocator's ordinary x0..x7 fallback with `spilled_regs` empty, and the only
bound it carries is register pressure.

`preserveArgReg` exists for one act: move a live value OUT of an x0..x7 slot
before the caller stages an argument into it. Its own comment records what it
was written for — `fib(n-1) + fib(n-2)` collapsing to `(n-2) + f(n-2)` and
returning wrong values for `fib(n) >= 7`, because the second call's marshaling
overwrote the first call's result before `emitSaveCallerRegs` could preserve it.

It asked for the destination with `allocReg`, which is `allocRegExcluding(null)`
— and null is the whole defect. The first scan walks x9..x28; when all nineteen
are busy the second scan walks x0..x7 from x0 up and returns the first register
whose `used_regs` is clear. `slot` is exactly such a register: `used_regs[slot]`
is false while `temps` still names it, which is the released-but-still-named
state `releaseDnirTemp` documents at the `call_direct` operand and is the state
that makes a victim findable here at all. So the allocator hands back the very
register whose contents were to be moved.

The old arm read that as nothing to do:

```zig
const fresh = try self.allocReg();
if (fresh == slot) {
    self.releaseReg(fresh);
    return;
}
```

It is the opposite of nothing to do. A victim was already found three lines
earlier — `const t = victim orelse return` — so `temps` names `slot`, and the
caller's next instruction writes the staged argument into it: `emitMovImm(slot,
n)`, `emitAdrpAdd(slot, sym)`, `emitMovReg(slot, reg)`, in the three marshaling
arms. Every id that named `slot` then reads the argument in place of its own
value, with no diagnostic. `releaseReg(fresh)` makes it worse in the same
breath by clearing the claim, so `emitSaveCallerRegs` will not preserve the
register either.

Under gate transport `reclaimSpilledReg` reaches `slot` a second way: the
cascade spills it, the reclaim drops the `spilled_regs` entry that was the only
thing able to reload it, and returns `slot` with its value abandoned in the
frame — and the arm above then frees it for the argument, so nothing holds the
value at all. `reclaimSpilledReg` states the rule this violates in its own
documentation: `exclude` IS THE CALLER'S, AND HASH ORDER MUST NOT REACH IT.
`emitIfConverted` and `emitIfConvertedTwoSided` each hold a register across an
allocation and exclude it; `preserveArgReg` opens the identical window and did
not.

The repair is that exclusion — `allocRegExcluding(slot)` — and the removal of
the arm, which the exclusion makes unreachable.

### The cost, stated

When the pool has nothing but `slot`, the exclusion refuses where the old arm
returned. That is the trade this file makes everywhere else, a refusal being a
bail while the alternative is a wrong answer, and it is under test.

It has a real cost and this record does not hide it. Nothing removes a `temps`
entry when its value dies — `sweepGpLive` clears `gp_reg_owner` and `used_regs`
and leaves `temps` alone — so a stale id naming `slot` can be the victim found
here, and relocating or refusing for a dead value is work or a bail nobody
needed. The exclusion cannot tell a stale name from a live one, because
`preserveArgReg` receives no instruction index and so cannot read `value_free_at`
the way `sweepGpLive` does. Threading that index through `compileDnirInstr` is a
separate change and is NOT made here; this one is the two-owner face. No test
moved either way in the measurement below, so the refusal is not reached on the
current corpus, and that is the whole of what is known about its frequency.

A second limit is untouched and pre-existing: the owner record is written only
for a destination in x9..x28 (`if (fresh >= 9 and fresh < 29 …)`), so a value
relocated into another ABI register lives under a null owner that `sweepGpLive`
skips. That leaks a register for the rest of the function; it does not
miscompile, and it is the same asymmetry `ensureRegLiveRemap` names from the
other side.

Not the closure. Closure is authoritative `register`/`frame` assignment before
emission, per this record's head, under which the value in an ABI slot has a
location the assignment names and is not one the scratch allocator can bid for.

## A pack result took the ABI register the spill map was still describing

It is the same question asked in the pack's own words. `pack_conflict` decides
whether the callee's answers are parked in the frame across the call or claimed
where the callee left them, and it decided by reading `used_regs[i]`. That is
clear in two states, not one: x_i is idle — or `spillReg` took it, and the store
that moved the value to the frame is exactly what cleared `used_regs[i]`, leaving
`spilled_regs` naming x_i and `gp_reg_owner[i]` naming an owner whose reads are
still ahead.

Read as "no conflict", the arm claims that register for the pack answer with
`claimReg(i)` and publishes `temps[temp] = i`. One register, two owners, and both
directions fail at once, exactly as the call result did. The spilled owner's id
also names x_i, so the next read of EITHER reaches `ensureRegLive` or
`ensureRegLiveRemap`: the reload puts the frame copy over the callee's answer, or
the remap rewrites every `temps` entry naming x_i and carries the answer's id
away with the owner. In the other direction `gp_reg_owner[i]`, which `spillReg`
deliberately preserved across the store, still names the spilled owner;
`sweepGpLive` reads it dead at this index and clears `used_regs[i]` for the
register the pack answer was just given, and the pool hands it out again. No
diagnostic on any of them.

different destination — and the record above said this arm has none, because the
callee wrote x_i and no other register can answer for x_i. That is true of the
register and not of the repair. The entry may not be retired to make room
either: its value is not the pack's, and dropping the only thing that reloads it
is the abandonment `reclaimSpilledReg` documents. What is left is the answer the
arm already had for the ordinary busy-register case, which is `pack_conflict`
itself. The pack is stored to the frame across the call and reloaded into
registers `allocReg` proves free, and both of its free scans skip anything
`spilled_regs` contains. So the repair is one term in the conflict test — not a
relocation, not a new path, and not a widening.

Nothing reloads inside the window. Between `sub sp` and `add sp` the save, the
`bl`, the park stores and the restore all address `sp` directly and emit no
reload; a spill-slot offset is measured from the frame base, so a reload landing
in that window would read the wrong slot and land over a callee answer besides.
The test asserts that absence directly, by scanning the emitted words for the
exact `ldr` encoding.

above its spill passes otherwise, so `spilled_regs` is empty elsewhere, the added

gap's record, under which a pack result is assigned a location rather than

## A pinned parameter moved and the pin that names it was not a home

Measured on `fb7d6b67` plus this change, in
`~/src/idol/.worktrees/named-claude-gap148-20260903T1013PT`.

The section "A spilled home moved and the pin that names it did not" above
repaired the pin/remap face and asked `gp_home_regs` to decide it. That flag is
the same set as "pinned" at five of the six `pinned.put` sites, each of which
calls `markGpHome` first. The sixth is not, and it is the one a LEAF's parameter
takes: `compileDnirFunction` keeps an incoming argument in its own x0..x7
register — `self.claimReg(arg_reg)`, `temps.put(slot, arg_reg)`,
`pinned.put(slot, arg_reg)` — and marks no home, because there is none to mark.
The bit stays clear until a store to that slot sets it at the `.store` arm, so a
parameter that is only ever READ is pinned and is not a home for its whole life.

That register is a spill victim. The third pass in `allocRegExcluding` walks
x7..x0 and takes any `used_regs` register that is neither `exclude` nor a staged
argument, and a parameter at rest is neither: `pending_arg_regs` is zero outside
argument marshaling, and the first two passes never reach x0..x7 at all. So the
parameter goes to the frame with `spilled_regs` naming its register and
`used_regs` cleared, which is the ordinary state this gap is open on.

The next read of that parameter is `evalDnirValue` on a `.local`, which consults
`pinned` FIRST and `temps` second, and both name the same register. It reached
`ensureRegLiveRemap`, the home branch was false, and the remap relocated the
value: `ldr` into a fresh register, the entry dropped, the slot released, and
every `temps` entry naming the old register rewritten. `pinned` is the map this
function cannot reach — it is not handed it — so the pin went on naming the
register the value LEFT, and that register is vacant, because `spillReg` cleared
`used_regs` and the remap removed the `spilled_regs` entry that had been standing
in for the claim. Both free scans in `allocRegExcluding` hand it out, and the
read after that answers with whatever the pool put there. A wrong answer, no
diagnostic — the same failure `gp_call_home_regs` measured for a home (`sha.id`

already carries because `evalDnirValue` reads it before `temps`. Reloading into

of them mention the home flag: a register in `spilled_regs` holds nothing,
because both free scans in `allocRegExcluding` skip that map and all three of its

## The exclusion refused for a value nothing would read again

Measured on `3668dada` plus this change, in
`~/src/idol/.worktrees/named-claude-gap148-20260903T1210PT`.

This is the cost the argument-preserve section above stated and declined to pay,
paid. That section excluded `slot` from the allocation that finds
`preserveArgReg` a destination, which stopped the allocator handing back the
very register whose contents were to be moved; and it recorded, in its own "The
cost, stated" subsection, that the exclusion then refuses where a liveness fact
would relocate — "the exclusion cannot tell a stale name from a live one,
because `preserveArgReg` receives no instruction index and so cannot read
`value_free_at` the way `sweepGpLive` does. Threading that index through
`compileDnirInstr` is a separate change and is NOT made here."

That is this change and it is nothing else. Nothing removes a `temps` entry when
its value dies — `sweepGpLive` clears `gp_reg_owner` and `used_regs` and leaves
`temps` alone — so an id whose last read is already behind emission goes on
naming an ABI register for the rest of the function. The victim scan found that
name, could not tell it from a live one, and asked for somewhere to put a value
nobody would read again: a move and a register where the pool had one, and
`error.RegisterExhausted` — a REFUSED PROGRAM — where it did not, at exactly the
pressure the scan is reached under, since the x0..x7 fallback is entered only
once x9..x28 are all busy.

The fact that separates them is not a new one. `value_free_at` is what
`sweepGpLive` reads one line later in the same driver iteration, and what the
victim scan was already reading to pick the LONGEST-LIVED of the ids naming the
register. What was missing was the index to read it against, so `compileDnirInstr`
now carries `at` — the flat instruction index the driver already computes and
already hands `sweepGpLive` and `immHoistExit` — down to this function, along
with `emitTailCallDirect`, `emitIfConverted`, `emitIfConvertedTwoSided` and
`emitIfConvArm`, which are the paths between the driver and the two marshaling
arms that call it.

The boundary is `last < at`, not the sweep's `last <= idx`. The sweep runs AFTER
the instruction at `idx` and may retire an id that instruction read; this runs
BEFORE the marshaling it guards completes, so an id whose last read IS the call
being marshaled is still owed its value and stays a victim. An id ABSENT from
the map stays a victim too, which is what the scan's own `orelse maxInt(u32)`
already spelled: absence is "no read this compiler attributed to the id", not
"no read" — `sweepGpLive` reads it as dead at every index and the register it
hands back for it is the abandonment `reclaimSpilledReg` documents, so on a path
whose act is to MOVE a live value the safe reading of the same silence is the
opposite one.

Victim SELECTION is unchanged wherever a live id exists, which is why this is
one term and not a new policy: a dead id has `last < at` and a live one has
`last >= at` or no entry at all, so the maximum over the live ids is the maximum
over all of them. The only state that moves is the one where EVERY id naming the
slot is dead, and there the function now returns without a move, without a
register, and without a bail. The trade the exclusion makes for a live value is
untouched, and is asserted alongside the repair.

Not gate transport, like the argument-preserve face it completes: `spilled_regs`
is empty on the free-scan path and the bound this one carries is register
pressure alone. Not the closure — closure is authoritative `register`/`frame`
assignment before emission, per this gap's record, under which a value's
liveness is a fact the assignment carries rather than one recovered from a map
that outlives it.

## The reclaim bid for a register the variadic tail had already been given

Measured on `5cf2da4f` plus this change, in
`~/src/idol/.worktrees/named-claude-gap148-20260903T1418PT`.

`pending_arg_regs` is eight bits describing x0..x7, and the section above taught
`reclaimSpilledReg` to honour it. Apple's ARM64 ABI passes every argument past a
variadic function's last named parameter in MEMORY, so a tail argument never
reaches those eight registers and those eight bits cannot state its reservation.
`materializePendingVarargs` evaluates each one into whatever the pool gives —
normally x9..x28 — records it in `pending_varargs[i].reg`, and `emitPushVarargs`
stores the lot to `[sp, #i*8]` after `emitSaveCallerRegs`. Between those two the
register holds an argument for the `bl` being built, which is the identical
statement `markStagedArgReg` makes about x_k, and nothing had ever made it to
the allocator.

The window is the materialization's own loop: slot 0's register is staged while
slot 1's operand is evaluated, and that evaluation allocates. Both free scans in
`allocRegExcluding` do pass over a staged tail register — but for the wrong
reason, `used_regs`, which is precisely what the cascade's spill passes take.
After `spillReg` the claim is gone, the value is in the frame, the entry is in
`spilled_regs`, and the reclaim took it: entry dropped, `gp_reg_owner` nulled,
`claimReg`, and the staged tail argument handed back as scratch. The caller's
first write lands on it, `emitPushVarargs` stores that write into the callee's
memory-argument slot, and the variadic call is made with it. A wrong argument
with no diagnostic, on the tail every `printf`/`snprintf` in this compiler goes
through.

A spill ALONE does not clobber it. Both free scans skip anything `spilled_regs`
contains, so the bytes survive in the register and the push happens to store the
right ones — accidentally correct, and correct only until hash order offers that
entry. This arm is the one that makes it wrong, and it is the one arm no
reservation had ever been stated to.

The fact is derived rather than restated: `pending_varargs[i].reg` already
records the register, and a `staged` bit records that the slot's operand has
been written into it. `operand == null` alone could not say it — a slot inside
`pending_vararg_count` that no `mov_arg` ever wrote is `.{}`, whose operand is
null and whose `reg` is 0, so reading the cleared operand as "materialized"
would reserve x0 for a hole. The bit is set where `reg` is assigned and cleared
by the whole-struct `.{}` writes `mov_arg` and `emitPopVarargs` already perform,
so there is no second mask for the two to disagree about.

genuinely the last entry the refusal the function already answers with is the

before emission, per this gap's record, under which a tail argument's location
is a fact the assignment carries rather than a register the marshaling holds
across an allocation that may bid for it.

`pending_varargs[i].reg` is a FOURTH map naming a register, beside `pinned`,

## A parameter begins before an entry-header loop

## A read before an in-loop definition is loop-carried

The pre-emission liveness producer classified a value as beginning inside a
loop whenever its first definition was inside that loop. That is insufficient
for a carried value: the loop header can read the value delivered by the prior
iteration before a later instruction replaces it. In that shape the definition
does not dominate the read. The old range stopped at the header read, so
emission could reuse its register in the remainder of the body before the
backedge returned to the header.

The producer now retains instruction-indexed reads and asks whether any loop
read precedes the first definition. Such a value enters the loop and widens to
the backedge. A definition that precedes every loop read remains the negative
control and does not widen. A pre-loop read of the same value is also present in
the control, proving the producer asks about the loop interval rather than a
function-global first-read shortcut.

Semantic diff: before, definition position alone erased the carried-in value
when a loop read preceded its in-loop replacement; after, definition and read
order jointly produce the conservative CFG liveness fact before emission, and
register release consumes that fact unchanged. No parser, type, DNIR lowering,
spill-reclaim, ABI, frame, or instruction-selection surface changes.
