# GAP-148 — value locations and fixed-frame register spilling

**Status:** OPEN · **Filed:** !2026-08-10T13:08:38Z
**Priority:** P0 · **Kind:** native_lowering_gap
**Filed by:** codex-root-continuation-20260810
**Files:** src/native_backend.zig, build.zig, docs/performance.md
**Migration fixtures to replace/delete:** examples/pass11_spill_proof.id, scripts/pass11_spill_smoke.id (deleted with the retired catalog apparatus)

The GP spiller keys state by physical register while DNIR values and local homes still point at that register. Reusing a spilled register therefore creates two owners and has a proven silent-miscompile history; the current guard correctly fails closed. Dynamic inline stack growth is also unsafe because existing record/table slots use fixed SP-relative offsets, and compiler spill state is not an authoritative value realization. WP-03 is false evidence: v1..v20 are unread, so its required STR/LDR canonizes storage that semantic demand does not require. Current bounded backend repair omits only unlineaged unread i64 immediate stores, proves exact assembly/object equality to the equivalent two-binding program, and retains a genuine 20-live-value RegisterExhausted control. Closure requires Idol to assign authoritative graph values to `register` or `frame` realization facts before emission, with CFG/backedge-aware liveness, a prologue-reserved frame, materialization returning the actual register, per-function state reset, value differentials under calls/branches/records, and replacement of the stale spill proof projections. Zig may project that assignment only as a bounded bootstrap bridge with an explicit deletion gate.

## The reclaim arm returned a destination as if it were the value

Measured on `0c753bd4d` plus this change, in
`/home/clp/src/idol/.worktrees/named-gap148-20260901`.

`ensureRegLiveRemap` is the read path for a `.local`/`.temp` whose register has
been spilled — `evalDnirValue` hands its result straight back as THE register
holding that value. Its gate-transport exhaustion arm returned
`reclaimSpilledReg()` directly, above the single `ldr` that is the only
instruction moving the value out of the frame, and so also above the
`spilled_regs` removal, the slot release, and the temp remap. The caller
therefore received a register nothing had loaded; a register reaches
`spilled_regs` because something else needed it, so when the reclaim returns the
same register it holds that something else. A wrong value with no diagnostic, on
the one path whose whole job is to make a spilled value readable again.

Reached whenever the pre-reserved gate spill area is full at a read of a spilled
value, which is the condition that puts `allocRegExcluding` into the reclaim in
the first place: `spillReg` refuses once `gate_spill_cursor + 16 >
gate_spill_end`, that refusal propagates out of the cascade, and this arm catches
it. The arm now supplies the reload destination and the rest of the function runs
as written.

`reclaimSpilledReg`'s own hazard is unchanged and still bounded to gate
transport: it drops the `spilled_regs` entry that would have reloaded the
register it hands back, abandoning that register's previous owner. Remapping this
value's owner onto the same register adds a reader to an owner already abandoned
by that drop, so no owner is broken that the reclaim had not already broken, and
one guaranteed wrong read is removed. This is not the closure — closure is still
authoritative `register`/`frame` assignment before emission, per the record
above.

## The reclaim abandoned an owner and kept its records

Measured on `0365b107` plus this change, in
`/home/clp/src/idol/.worktrees/named-gap148-20260901`.

Dropping the `spilled_regs` entry is what makes a register allocatable again and
is also what abandons its owner: that entry was the only thing that would have
reloaded the value. That hazard is this gap's and is unchanged here. What the
drop did NOT do was clear the two OTHER records the abandoned owner held, and
each is a defect in the opposite direction — against the live value the reclaim
just handed the register to:

- `gp_reg_owner[reg]` still named the abandoned owner. That owner is normally
  absent from `value_free_at`, its reads being behind emission, which
  `sweepGpLive` reads as dead at every index. The next sweep therefore cleared
  `used_regs[reg]` for a register a live value had just been given, and
  `allocRegExcluding` handed the same register out a second time.
- the frame slot stayed reserved permanently. `ensureRegLive` and
  `ensureRegLiveRemap` are its only readers and both key on the entry just
  removed, so nothing can read it again; holding it kept `spillReg` stepping
  `gate_spill_cursor` toward `gate_spill_end` and refusing spills the
  pre-reserved area still had room for.

Releasing the slot in the reclaim exposed a second, latent defect on the one
path that already reached it. `ensureRegLiveRemap` appended `off` to
`free_spill_slots` unconditionally after its own `spilled_regs.remove(reg)`,
which is a no-op when the reclaim returned `reg` ITSELF — the case the reload
repair above turns on. One frame slot then entered the free pool twice, and two
later spills store two live values at the same offset. The release now belongs to
whichever removal actually took the entry out: the removal is idempotent, a
release is not.

## The reload put the value back and left the register free

Measured on `33f2f82e` plus this change, in
`/home/clp/src/idol/.worktrees/named-gap148-20260901`.

`spillReg` performs two halves of one act: it moves the value out of the register
— `str`, then `spilled_regs.put` — and it stops the register standing for that
value, `used_regs[victim] = false`. `ensureRegLive` is the exact inverse, the
`ldr` back into THAT SAME register, and it undid only the first half.

So the value returned to a register that read as free. Worse, the one fact that
had been substituting for the claim left in the same breath: both free scans in
`allocRegExcluding` skip a register `spilled_regs` contains, which is the
fail-closed guard that made a spilled register unallocatable, and the reload's
own `spilled_regs.remove` is what ends that. Between the reload and the next
`sweepGpLive` the register is in neither set, so the next allocation of any kind
returns a register holding a live value whose owner still names it, and the
second owner's first write is a silent wrong answer for the first.

Restoring the claim returns the register to the state it held before the spill,
and cannot leak for the same reason: `spillReg` never cleared
`gp_reg_owner[victim]`, so `sweepGpLive` releases this claim on the same owner
record, at the same index, as it would have had the register never spilled.

Bounded to gate transport with the rest of this gap. `spillReg` is reached only
from `allocRegExcluding`, which refuses above its spill loops unless
`gate_transport`, so `spilled_regs` is empty elsewhere and `ensureRegLive` is a
no-op there. Distinct from both reclaim facts above: those are
`reclaimSpilledReg` and `ensureRegLiveRemap`, the paths that move a value to a
DIFFERENT register; this is the path that puts it back in the same one.

  fails at `expect(compiler.used_regs[spilled])` — the register the `ldr` had
  just filled reading as free;
- with the reload repaired: 1755 of 1986 pass, 62 skipped, 166 failed, 3

The two failing sets differ by exactly one entry, the new test, so nothing else

The test builds an `Arm64Compiler` directly, like the two reclaim tests: the

Like both reclaim repairs, this removes a wrong state and is not the closure.
Closure remains authoritative `register`/`frame` assignment before emission, per
this gap's record.

## The remap relocated the value and left its owner record behind

Measured on `aa936dfa` plus this change, in
`/home/clp/src/idol/.worktrees/named-gap148-20260901`.

`ensureRegLiveRemap` moves a spilled value from `reg` into a different register:
it emits the `ldr` into `fresh`, drops the `spilled_regs` entry, releases the
frame slot, and rewrites every `temps` entry that named `reg`. `gp_reg_owner` is
the fifth record naming the same value and was the only one not moved. This is
the identical relocation `preserveArgReg` performs, which finishes by writing
`gp_reg_owner[fresh]` for exactly this reason; the missing write is wrong in
both directions at once.

`reg` keeps an owner it no longer holds. `spillReg` cleared `used_regs[reg]` and
never cleared `gp_reg_owner[reg]` — deliberately, so the sweep would release the
claim on the same owner record had the value come back to that register. Here
the value does not come back: the removal above takes `reg` out of
`spilled_regs`, so both free scans in `allocRegExcluding` stop skipping it and
hand it out. Then `sweepGpLive`, reading the stale owner against a
`value_free_at` that has no entry for a value whose reads are behind emission,
clears `used_regs[reg]` for the register a live value was just given, and the
pool hands the same register out a second time. Two owners, one register, no
diagnostic — this gap's shape, reached through the remap rather than through
`reclaimSpilledReg`.

`fresh` holds a live value under a null owner, because `claimReg` records only
`used_regs` and the callee-save touch set. `sweepGpLive` skips an unowned
register, so nothing reclaims `fresh` for the rest of the function and the pool
shrinks by one — on the one path whose whole job is to relieve register
pressure, and whose exhaustion arm is the reclaim hazard above.
`preserveArgReg` names this same failure from the other side: owner null there
ran `tree.id` out of registers on the spot.

The repair moves the owner record with the value and clears the vacated end.
When the exhaustion arm reclaimed `reg` itself, `fresh == reg` and there is
nothing to move; a home register is excluded from receiving the owner for the
same reason `sweepGpLive` skips one. This is not the closure — closure is still
authoritative `register`/`frame` assignment before emission, per the record
above — and the `reclaimSpilledReg` two-owner hazard remains open and bounded to
gate transport.
