## The defect

A idol function whose name is a C keyword emits an unmangled C declaration and
fails to build:

```duo
double: i64 = (x: i64)
    x + x
```

```c
static inline int64_t double(int64_t x);
```

```
error: cannot combine with previous 'type-name' declaration specifier
error: 'inline' can only appear on functions
```

Measured — **every one of these 19 fails**:

```
double int char float long short void const static struct
union enum switch case default sizeof register auto inline
```

Not a sample. Nineteen of nineteen probed.

## Why this is worse than an ordinary name collision

**Several of these are idol's own vocabulary**, and the language cannot compile
a function named after its own concepts:

| word | where idol uses it |
|---|---|
| `case` | §0.3 INFERRED CASES — "case-sets INLINE at the field" |
| `union` | §0.5 / §5 — `id: u8 \| u16 \| u32` is the union edge |
| `register` | §0b — "registers are PLACES" |
| `enum` | on the §1 deny list, but still a word a user may want |
| `default` | `get(.y, default)` — Pass 119's own `?.` repair |
| `int`, `char`, `float`, `short`, `long`, `void` | ordinary nouns in any systems program |

`get(.y, default)` is written in the law as the canonical repair for optional
chaining. A parameter named `default` is fine; a *function* named `default` is
not buildable.

## The rule this breaks

§0.1 promises identifiers are one lowercase word and names carry ZERO semantics.
A reserved set of ~40 English words that fail at the C stage is a semantic
property of names — imposed by the bootstrap host, invisible in the language,
and discovered only at link time.

`law.host.projection` grants un-idol-like behaviour ONLY where the host requires
it. C requires that ITS keywords not be redeclared; it does not require that
DUON's identifiers pass through unmangled. **Mangling is the repair and the host
does not forbid it.**

## Related, same root

`duo-identifiers-collide-with-libc` records `read`, `write` and `open` as
unbuildable for the neighbouring reason — unmangled static symbols colliding
with POSIX, which can silently bind the libc function instead of diagnosing.
That one is worse than this one: **this fails loudly, that one can succeed
wrongly.** One mangling scheme closes both.

## Fix

Mangle every user identifier on the C path — the direct backend does not have
this problem, which is itself evidence that the C emitter is the outlier.
Fixture asserts by VALUE that a function named `case`, `union`, `register` and
`default` each compiles and returns the right answer on **both** backends.

Include the libc set (`read`, `write`, `open`, `close`, `time`, `index`) in the
same fixture, and assert the idol function's answer rather than merely that it
built — a silent bind to libc `read` compiles fine and returns the wrong number.

## How it was found

Probing the Realized Specialization Ratio (gap[084]). The probe function was
named `double` and produced ten C errors that had nothing to do with
specialization. The probe name was the bug — which is the finding.

The repair is complete, green on 14 gates, positive-controlled against a

- I argued the directive means "stop reaching for Zig", not "leave a finished

- The directive was restated. **A directive restated is not an argument to

## What this costs, stated so it is not discovered later

Until this merges or is rebuilt in idol:

- a idol function named `read`, `write`, `open`, `abs` or any future libc symbol
  can bind the C function instead of its own body, **compiling cleanly and
  returning the wrong number**;
- 19 ordinary English words remain unusable as function names, four of them
  idol's own vocabulary (`case`, `union`, `register`, `default`).

## What would unblock it without Zig

Same shape as gap[088]: the repair is only expressible in the excluded
language because **no idol-native owner of C emission exists**. The unblock is
not a smaller patch — it is a idol lowering path that owns symbol emission, at
which point mangling is a idol repair and the bootstrap copy is
`law.host.projection` debt with this gap as its deletion gate.

Second gap in one session that terminates at the same missing capability. That
convergence is the finding: **the self-hosted compiler's missing code generator
is now the single blocker for three separate canonical repairs** (gap[083],
