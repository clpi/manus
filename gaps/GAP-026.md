# GAP-026 — `duo check` green-lights calls to undefined functions

**Status:** open · **Filed:** 2026-08-07 · **Severity:** the gate lies
**Found:** measuring GAP-025 step 1 (does `check` exist as a binding?)

## The defect

`duo check` is the fast gate — what agents run before committing, what CI runs
per file, what `scripts/*.duo` walks the corpus with. It reports success on a
program that cannot compile.

```duo
main(): i64
    totallynotafunction(42)
    0
end
```

```
$ duo check undef.duo
✓ checked — no errors                      rc=0

$ duo run undef.duo
error: call to undeclared function 'totallynotafunction'
error: C compiler failed (exit 1)          rc=1
```

The call is never resolved; the C compiler is the first thing that objects.

## Why it matters more than a missing diagnostic

Every corpus walk in `scripts/` and every `duo check` in a gate inherits this.
A file can pass the checker and be uncompilable, so a green corpus number does
not mean what it appears to mean — the same class as the recorded
"a resolving ambient path is not a working one", where `std.string.byte` was a
missing member returning nil at 431 sites.

It also means the checker cannot be used to answer "does this binding exist?",
which is exactly the question GAP-025's step 1 needs answered for `check`,
`why`, `graph.*`, `add(…)` and `todo(…)`. Measuring those required running
codegen, not checking.

## Discovery path (worth keeping)

`check(1 + 1 == 2)` passed `duo check`, which briefly looked like evidence that
`check` already existed as a binding. It does not — `duo run` emits
`call to undeclared function 'check'`. A checker that accepts undefined calls
turns "it checks clean" into no evidence at all.

## MECHANISM LOCATED (2026-08-07) — and one wrong fix, recorded

`src/sema.zig:2206`. In `duo_mode`, ANY unresolved name is silently defined:

```zig
if (self.duo_mode and !self.is_builtin_global(n.ident)) {
    // Implicit local: bare bindings and forward references are module/file locals.
    try self.scope.define(n.ident, .{ .typ = .any, .is_const = false });
    return .any;
}
```

The comment justifies it with forward references — but `check_module` already
has a **pre-registration pass** ("Pre-register top-level bindings so forward
references work", ~line 1341) that runs before `check_block`. So top-level
forward refs are covered, and a name reaching 2206 is genuinely unbound.

**The fix I tried, and why it does not work.** Flagging the symbol
(`implicit_unresolved`) and reporting survivors at end of `check_module` fails
because the auto-define lands in the scope where the name was USED — a function
body — and that scope is popped long before the end-of-module check. `lookup`
finds nothing and the report is silently empty. Reverted.

A working fix has to either report at each scope pop, or record enough context
at 2206 to re-decide later (was this name ever bound in the scope chain it was
used in?). The narrow version is easier and is what this gap actually asks for:
**a CALL whose callee resolves to nothing is an error**, which needs only the
call handler (`sema.zig:2303`), not general name resolution.

## The fix

Resolve call targets during checking: a call to a name with no binding — no
local, no parameter, no module member, no ambient root, no builtin — is a
diagnostic, not a deferral to the C compiler.

Regression fixture: the four-line program above must fail `duo check`.

## Blast radius: ZERO gates — corrected TWICE, both times by grep

First I wrote that every gate using `duo check` "is weaker than it reads".
Then I grepped and scoped it to two. Both were wrong, and the second was wrong
the same way as the first: **I grepped for the word `check`, not for the
command.**

    build.zig:782,791          `duo catalog audit check` — a subcommand of
                               `catalog audit`. Not `duo check <file>` at all.
    stdlib_embed_gate.duo      only MENTIONS `duo check` in prose, documenting
                               that it is weak. Its gate is the embed path,
                               which is the strong signal it exists to provide
                               (measured: self-check fails on 1 of 246 modules,
                               the embed path on 38).
    setup-nvim.duo             editor setup, not a gate.

Verified unaffected: `parser_corpus_coverage.duo` calls `P.parse_status` (the
Duo parser), `selfhost_proofs.duo` runs binaries and reads exit codes, the
pass16 proofs differential against oracles.

**No gate in this repo depends on `duo check`.** The bug is real and the fix is
still worth making — `duo check` is what a human runs, and what an agent reaches
for first — but it is a developer-experience defect, not a hole in the gate
suite, and nothing green today is green because of it.

The lesson is the finding: a string match is not a behaviour measurement.
Scoping this by grep produced a wrong answer twice in a row, in both directions.
