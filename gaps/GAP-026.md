# GAP-026 — `duo check` green-lights calls to undefined functions

**Status:** open · **Filed:** 2026-08-07 · **Severity:** the gate lies
**Found:** measuring GAP-025 step 1 (does `check` exist as a binding?)

## The defect

`duo check` is the fast gate — what agents run before committing, what CI runs
per file, what `scripts/*.duo` walks the corpus with. It reports success on a
program that cannot compile.

```duo
main(): i64
    totallynotafunction(42)
    0
end
```

```
$ duo check undef.duo
✓ checked — no errors                      rc=0

$ duo run undef.duo
error: call to undeclared function 'totallynotafunction'
error: C compiler failed (exit 1)          rc=1
```

The call is never resolved; the C compiler is the first thing that objects.

## Why it matters more than a missing diagnostic

Every corpus walk in `scripts/` and every `duo check` in a gate inherits this.
A file can pass the checker and be uncompilable, so a green corpus number does
not mean what it appears to mean — the same class as the recorded
"a resolving ambient path is not a working one", where `std.string.byte` was a
missing member returning nil at 431 sites.

It also means the checker cannot be used to answer "does this binding exist?",
which is exactly the question GAP-025's step 1 needs answered for `check`,
`why`, `graph.*`, `add(…)` and `todo(…)`. Measuring those required running
codegen, not checking.

## Discovery path (worth keeping)

`check(1 + 1 == 2)` passed `duo check`, which briefly looked like evidence that
`check` already existed as a binding. It does not — `duo run` emits
`call to undeclared function 'check'`. A checker that accepts undefined calls
turns "it checks clean" into no evidence at all.

## The fix

Resolve call targets during checking: a call to a name with no binding — no
local, no parameter, no module member, no ambient root, no builtin — is a
diagnostic, not a deferral to the C compiler.

Regression fixture: the four-line program above must fail `duo check`.
