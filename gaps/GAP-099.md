# GAP-099 — the `any` handicap is one int-to-double compare, and the guard to remove it already exists

**Status:** OPEN — the ANALYSIS is confirmed and the NUMBER is far too small
**Filed:** 2026-08-09

## 2026-08-09, second re-measurement — "14%" understates this by orders of magnitude

The emitted C is confirmed character-for-character: the hoisted `__wb_ok0` guard
and the `__wb_ok0 ? ((double)(i) <= __wb_n0) : (lua_leq(...))` condition are
exactly as this file describes, and there is no frozen constant or recognizer
anywhere in either program (checked, per §3, before any timing was believed).

But the handicap is not 14%. Value first, both forms answering **2601333333330000**:

```
scan(n: any): i64    6.23s   (five runs, all 6.23)
scan(n: i64): i64    0.00s   (five runs, all 0.00 — below timer resolution)
```

Same kernel, one word different, 20000 x ~500000 with a VARYING argument.

The varying argument is load-bearing and is why this reads differently from the
first measurement. With a constant argument (`scan(500000)`) **both** forms time
0.00s: `scan` is `static inline`, clang closes the form, and the benchmark
measures nothing. That is the minimal-repro trap, and the honest version of this
file's earlier `0.21 / 0.19` is that it was taken close enough to that edge that
both columns were partly folded.

**The mechanism, which is the actionable half.** The typed form is a clean i64
induction, so LLVM's scalar evolution closes it to arithmetic — O(1). The `any`
form's loop condition is a ternary over a guard flag, and that is opaque to the
same analysis, so it runs every iteration — O(n). The handicap is therefore not a
constant factor to be shaved; it is the difference between the loop existing and
not existing, and it grows with the trip count without bound.

This makes item 1 of the fix list below **more** valuable, not less, and for a
reason the list does not state: emitting the integer arm under the guard that
already dominates the loop does not merely remove a widening compare — it hands
LLVM back a loop it can recognize. The 14% was the visible tip of that.

Value first, per §3: **both forms answer `25000050000000`.** Only then the time,
same kernel, 200 x 500000, one word different:

```

scan(n: i64): i64    0.19s
```

The emitted C is character-for-character the shape this file describes — the
guard is still hoisted and still nothing specialises under it:

```c
bool __wb_ok0 = (n.type == VAL_NUMBER); double __wb_n0 = __wb_ok0 ? lua_num(n) : 0.0;
while (__wb_ok0 ? ((double)(i) <= __wb_n0) : (lua_leq(lua_val_from_int((int64_t)(i)), n))) {
        s = (s + i);
        i = (i + 1);
}
```

Emitters: `src/codegen.zig:13288` writes the hoisted guard, `:12123` writes the
`__wb_ok{d} ? ((double)(…) <= __wb_n{d}) : (…)` condition. Item 1 of the fix
list — emit the integer arm under the guard that already dominates the loop — is
a change at those two sites and remains the whole of the observed→guarded rung.
**Law:** `law.perf.dominance` (§47) · §38 the specialization ladder ·
`law.canon.performance`
**Answers:** "is there a path to high performance on inferred types?" — **yes,
and most of it is already built.**

## The measurement

Identical kernel, identical answer (`100002`), one word different:

```
scan(n: any): i64    0.001183
scan(n: i64): i64    0.001022      14% faster
```

Across the benchmark suite that handicap is systemic: **C declares `int64_t n`
on 39 kernels; duon declared `n: any` on 30.**

## What the 14% actually is — not boxing

The emitted C for `scan(n: any)` with a single `i64` call site:

```c
static inline int64_t scanany(lua_Value n) {
    int64_t s = 0;
    int64_t i = 1;
    bool   __wb_ok0 = (n.type == VAL_NUMBER);
    double __wb_n0  = __wb_ok0 ? lua_num(n) : 0.0;
    while (__wb_ok0 ? ((double)(i) <= __wb_n0)
                    : (lua_leq(lua_val_from_int(i), n))) {
        s = (s + i);
        i = (i + 1);
    }
    return s;
}
```

**The body is already native.** `s` and `i` are `int64_t`; `s = s + i` is an
integer add. Nothing is boxed per iteration.

The entire cost is in the LOOP CONDITION:

1. a branch on `__wb_ok0` — predictable, nearly free;
2. **`(double)(i) <= __wb_n0`** — an int-to-double conversion and a FLOAT
   compare, every iteration, where the typed version emits an integer compare.

That is the 14%. It is one instruction pair in the hot loop, not a
representation problem.

## The compiler already proved the fact it then fails to use

Look at what it did: it HOISTED a type guard out of the loop —
`__wb_ok0 = (n.type == VAL_NUMBER)` — and computed `__wb_n0` once. So the
compiler already knows, before the first iteration, that `n` is a number and
what its value is.

Having proven that, it emits **one loop that re-tests the guard and converts to
double each iteration**, instead of **two loops** selected once:

```c
if (__wb_ok0) {
    int64_t bound = (int64_t)__wb_n0;        // or lua_int(n)
    while (i <= bound) { s += i; i += 1; }   // integer compare
} else {
    while (lua_leq(...)) { ... }             // the existing slow path
}
```

Same guard, same descent, one specialization. **The observed→guarded rung of
§38's ladder is half-built: the guard exists and nothing specializes under it.**

## And the guard should not be needed here at all

`n` is a parameter whose every call site is visible — `scan(500000)`, a literal.
That is the `sealed` rung, one further up. With whole-program visibility the
type is not observed-and-guarded, it is KNOWN, and the slow arm is dead code.

So there are two independent wins available, and the smaller one is nearly free:

| rung | what it buys | state |
|---|---|---|
| observed → **guarded** | integer compare under the existing guard | guard built, specialization missing |
| guarded → **sealed** | guard erased entirely on known call sites | not built |

## Why this matters beyond 14%

`law.perf.dominance` says adding semantic facts may never REDUCE the realization
set. The dual should also hold and currently does not: **omitting an annotation
whose fact is derivable should not reduce it either.** Today writing `any`
costs 14% even when the compiler has already derived the exact fact the
annotation would have supplied — and it derived it *in the emitted code, on the
line above*.

That makes the handicap an implementation gap rather than a language property,
which is the difference between "duon punishes inference" and "duon has not yet
cashed an inference it already performs".

## Fix, in order

1. **Specialize under the existing guard.** The hoisted `__wb_ok0` already
   dominates the loop; emit the integer arm under it. Smallest possible change,
   and it is the observed→guarded rung by definition.
2. **Fixture asserts by VALUE and by TIME**: same answer, and the `any` form
   within noise of the typed form on the same kernel. A speed fixture is only
   honest with the value fixture beside it.
3. **Then the sealed rung**: when every call site is visible and passes one
   descriptor, drop the guard and the slow arm.
4. Re-measure the 13 benchmark losses afterward — several are table-shaped and
   will not move, but the loop-bound ones should.

## Do not

Do not close this by retyping the benchmark and calling it fixed. Retyping makes
the COMPARISON fair — C declares `int64_t`, so duon writing `any` was a
handicap, not a language result — but it leaves the underlying gap in place for
every user who writes what the language advertises as idiomatic.
