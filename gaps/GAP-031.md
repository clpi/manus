# GAP-031 — Duo identifiers collide with libc; `read` is unbuildable

**Status:** open · **Filed:** 2026-08-07 · **Frequency:** 1 per colliding name
**Blocks:** Pass 91's own repair spelling — the canon writes `read(number)`
**Sites:** `scripts/census/names.duo` (P91-6), `scripts/census/epoch.duo` (E2-8 note)

## The defect

The C backend emits Duo top-level functions as `static` C functions **under
their Duo names, unmangled**. Any Duo binding whose name matches a libc symbol
fails to build.

```duo
read(n: i64): i64
    n + 1
end
main(): void
    print(read(1))
end
```
```
/tmp/duo_readname.c:5675:23: error: static declaration of 'read' follows
                                    non-static declaration
/tmp/duo_readname.c:5681:22: error: too few arguments to function call,
                                    expected 3, have 1
```

The second error is the dangerous one: the call site bound to **POSIX
`read(2)`**, not to the user's function. Where the arities happened to match,
this would be a silent miscompile rather than an error.

## Why it matters more than it looks

Pass 91 rules that every interior `_` decomposes, and the canon's §4 repair
table gives the spelling directly:

```
read_number → read(number)
```

**The canonical repair name is unbuildable.** The same hazard covers every
common libc verb a decomposed Duo name would land on — `read write open close
time index link free exit stat send recv kill wait` — which is exactly the
vocabulary LEVEL repairs produce, because LEVEL turns `verb_noun` into
`verb(noun)` and the surviving bare verb is a short common word.

## How it was found, and the measurement lesson

This gap was found while auditing a **wrong measurement of my own**. Two census
rows probed Pass 91's LEVEL destination using `read` as the family name — taken
verbatim from the canon's repair table — and both scored MISSING. That was
recorded as "the LEVEL destination does not compile", and from it the much
larger claim that Pass 86, Pass 88 and Pass 91 all queue behind one absent
operand-selection mechanism.

**All of that was false.** Spelled with any non-libc name the LEVEL form works:

```duo
number: { v: i64 }
scan(k: any): any
    (x: i64): i64
        x + 1
    end
end
main(): void
    print(scan(number)(1))   -- 2
end
```

All three Pass 91 destinations (LEVEL, HOME, CONTEXT) are live. The repair is
far more reachable than the first measurement said.

The lesson is narrow and worth keeping: **a probe that fails for a reason
outside the thing being probed reads exactly like the thing being missing.** The
control rows in these censuses catch a dead harness; they do not catch a probe
whose *identifier* is the defect. When a row fails, vary the name before
concluding the form is absent.

## The fix

Mangle emitted C symbols for user bindings (a module-qualified prefix is enough),
or maintain a reserved-name list and diagnose at the Duo level — "`read` collides
with a C runtime symbol" is a fixable Duo diagnostic; `static declaration of
'read' follows non-static declaration` is not.

Same family as `GAP-030`: the backend has no name-mangling scheme, so Duo's
namespace and C's are one namespace.
