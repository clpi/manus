## Isolation

The working tree carries two uncommitted lines. **Only the `exprIsStr` one
causes this**, applied alone:

```zig
-        .quoted => true,
+        .quoted => |lit| !ast.quotedLiteralIsByteSequence(lit.quote),
```

The companion line in `concatOperandOk` — `if (expr.* == .quoted) return true;`
— is a partial mitigation. It covers a **literal** operand and does not cover a
**name bound to** a byte literal, which is the shape above.

## Mechanism

At `HEAD`, `exprIsStr` answers `.quoted => true`, so `s` enters `str_slots` and
`planConcat` emits `%s`. Correcting `exprIsStr` to the quote face takes `s` out
of `str_slots`; `concatOperandOk(s)` then falls through to `exprIsIntegral`,
which admits it, and `planConcat` emits `%lld` on a `const char*`.

The correction is right and the fall-through is what is wrong. `exprIsStr`
returning false must not mean "integral".

## The class

This is APPLICATION-CONSUMER-ZERO's failure mode in the shape GAP-204 already
measured: an admission rule (`concatOperandOk`) and a capability rule
(`exprIsStr` -> `str_slots` -> `planConcat`) decided in different places, so
narrowing one silently widens the other. The narrowing is correct; it needs the
third arm — a byte-sequence operand is neither text nor integral, and the
lowering has no member to carry it (`native_ir.Value` has
`void/i64/f64/str/local/temp/record` and no byte-sequence face).

Until that member exists, the lawful shape is a named refusal, not a
fall-through.
