|---|---|
| title | GAP-044 — a function cannot be attached to a table, in any spelling |

| # | directive |
|---|---|
| 1 | **Filed** 2026-08-08. **Status** open. **Cited at** `src/parser.zig` (`scan_func_header_signal`), commit "parser: a one-parameter `X:m = (a) …` degraded to a local_decl, silently". |

| section |
|---|---|
| What happens |

| # | directive |
|---|---|
| 1 | Every spelling that puts a function on a table produces `nil`, or fails to reach a binary at all. |
| 2 | Measured on one build, one run each: |

| source | result |
|---|---|
| `fun P.greet(other) … end` then `type(P.greet)` | **`nil`** |
| `fun P:greet(other) … end` then `P:greet("you")` | **`nil`** |
| `P:greet = (other) …` then `P:greet("you")` | **`nil`** |
| `P.greet = (a, b) a + b` then `P.greet(1,2)` | **`nil`** |
| `P.greet = function(other) … end` | **C compiler failed (exit 1)** |

| # | directive |
|---|---|
| 1 | `type(P.greet)` reporting `nil` is the important row: the function is never installed on the table at all. |
| 2 | The call is not what is broken, so this is not a dispatch bug. |

| # | directive |
|---|---|
| 1 | Nothing warns. `duo check` reports "no errors" for all but the last row. |

| section |
|---|---|
| What is NOT the cause |

| # | directive |
|---|---|
| 1 | The parse. `X:m = (a) …` was ALSO degrading to a `local_decl` because a guard in `scan_func_header_signal` meant for the bare-declaration path fired in expression position; that is fixed, and the AST is now a proper `func_decl` with `method = true`, a two-element path and an implicit `self`. |
| 2 | The runtime result did not change. |
| 3 | Whatever consumes `func_decl` with `path.len > 1` is where this lives -- sema or codegen, not the parser. |

| # | directive |
|---|---|
| 1 | The classic `fun P.greet(x) … end` form never had the parse problem at all and behaves identically, which is the cleanest evidence that the parse fix and this gap are independent. |

| section |
|---|---|
| Why it matters more than it looks |

| # | directive |
|---|---|
| 1 | Duo advertises as a Lua superset. |
| 2 | A table of functions is the primary way Lua programs are organized, and `M.f = function(...)` is the single most common shape in the language. |
| 3 | The in-tree corpus does not catch this because Duo modules export via a trailing table literal (`{ name = name, … }`) whose values are already-declared top-level functions -- a different path, and one that GAP-043 shows is itself only half working (a second key for the same function yields nil). |

| # | directive |
|---|---|
| 1 | So the two gaps meet: the export-table path drops aliases, and the assign-to-table path drops everything. |
| 2 | Between them, a function value cannot be placed in a table under a name of the author's choosing. |

| section |
|---|---|
| Reproducing |

```
P = {}
fun P.greet(other)
  return "Hey " .. other
end
print(type(P.greet))   -- nil, expected "function"
print(P.greet("you"))  -- nil, expected "Hey you"
```

| section |
|---|---|
| Positive control for any fix |

| # | directive |
|---|---|
| 1 | Assert by VALUE, both rows: `type(P.greet)` must be `"function"` AND `P.greet("you")` must be `"Hey you"`. |
| 2 | A fix that makes only the first row pass has installed something that is not callable. |
| 3 | Do not accept "it compiled" -- every row above compiles today except the last. |
