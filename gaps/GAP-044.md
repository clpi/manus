# GAP-044 — a function cannot be attached to a table, in any spelling

**Filed** 2026-08-08. **Status** open. **Cited at** `src/parser.zig`
(`scan_func_header_signal`), commit "parser: a one-parameter `X:m = (a) …`
degraded to a local_decl, silently".

## What happens

Every spelling that puts a function on a table produces `nil`, or fails to reach
a binary at all. Measured on one build, one run each:

| source | result |
|---|---|
| `fun P.greet(other) … end` then `type(P.greet)` | **`nil`** |
| `fun P:greet(other) … end` then `P:greet("you")` | **`nil`** |
| `P:greet = (other) …` then `P:greet("you")` | **`nil`** |
| `P.greet = (a, b) a + b` then `P.greet(1,2)` | **`nil`** |
| `P.greet = function(other) … end` | **C compiler failed (exit 1)** |

`type(P.greet)` reporting `nil` is the important row: the function is never
installed on the table at all. The call is not what is broken, so this is not a
dispatch bug.

Nothing warns. `duo check` reports "no errors" for all but the last row.

## What is NOT the cause

The parse. `X:m = (a) …` was ALSO degrading to a `local_decl` because a guard in
`scan_func_header_signal` meant for the bare-declaration path fired in
expression position; that is fixed, and the AST is now a proper `func_decl` with
`method = true`, a two-element path and an implicit `self`. The runtime result
did not change. Whatever consumes `func_decl` with `path.len > 1` is where this
lives -- sema or codegen, not the parser.

The classic `fun P.greet(x) … end` form never had the parse problem at all and
behaves identically, which is the cleanest evidence that the parse fix and this
gap are independent.

## Why it matters more than it looks

Duo advertises as a Lua superset. A table of functions is the primary way Lua
programs are organized, and `M.f = function(...)` is the single most common
shape in the language. The in-tree corpus does not catch this because Duo modules
export via a trailing table literal (`{ name = name, … }`) whose values are
already-declared top-level functions -- a different path, and one that GAP-043
shows is itself only half working (a second key for the same function yields
nil).

So the two gaps meet: the export-table path drops aliases, and the
assign-to-table path drops everything. Between them, a function value cannot be
placed in a table under a name of the author's choosing.

## Reproducing

```
P = {}
fun P.greet(other)
  return "Hey " .. other
end
print(type(P.greet))   -- nil, expected "function"
print(P.greet("you"))  -- nil, expected "Hey you"
```

## Positive control for any fix

Assert by VALUE, both rows: `type(P.greet)` must be `"function"` AND
`P.greet("you")` must be `"Hey you"`. A fix that makes only the first row pass
has installed something that is not callable. Do not accept "it compiled" --
every row above compiles today except the last.
