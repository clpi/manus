# GAP-240 — the settled parser faces disagree with the tokens they name, so `main` cannot parse Idol

**Status:** OPEN · **Filed:** !2026-09-03T01:00:00Z
**Priority:** P0 · **Kind:** correctness_gap
**Filed by:** named-claude-gap204-20260903T0013PT
**Files:** src/parser.zig, src/parser/projection.c, lib/compiler/parser.id, lib/compiler/token.id, tools/node/dev/parser/artifact

The compiler built from `main` rejects almost every Idol program at its first
statement. This is not a corner: `x: i64 = 1` does not check.

## Defect 1 — the brace face and the declaration face share bit 12 (REPAIRED HERE)

`lib/compiler/parser.id:945` packs the decision word as

```id
out[count + index] = … | (declaration << 9) | (braceface << 12) | (delimiter << 13)
```

`declaration` is four bits wide and starts at bit 9, so it OWNS bit 12.
`src/parser.zig` read the fact as the whole nibble:

```zig
fn currentParserTable(self: *Parser) ParseError!bool {
    return (((try self.currentParserDecision()) >> 9) & 0xF) == 8;
}
```

Two different tokens present nibble 8:

| token | `declaration` | `braceface` | nibble |
| --- | --- | --- | --- |
| `{` | 0 | 1 | 8 |
| a NAME that heads a declaration, or is followed by `:` | 8 | 0 | 8 |

`lib/compiler/parser.id` sets `declaration = 8` for exactly that name
(`kind == token.kindname` and `head == 1 or following == token.kindcolon`), so
every typed binding, every callable declaration and every `subject:relation()`
receiver answered "this token is a brace". `parse_simple_expr` then took
`parse_table`, and `parse_pack_body` demanded a `{` nobody wrote. Located by
stack trace, not by reading:

```
parser.zig:1191  expect
parser.zig:8141  parse_pack_body
parser.zig:8132  parse_pack
parser.zig:8128  parse_table
parser.zig:6269  parse_simple_expr      <- currentParserTable() said yes for `x`
parser.zig:7625  parse_suffixed_expr
```

The bit-12 test alone is the separately retracted unsound form (`243d0356`,
"retract unsound table primary projection") because the `@` face sets bit 12
too; widening to the nibble traded one collision for another and nothing
measured a program afterwards.

**Repaired at the consumer**, because this collision is recoverable: `declaration
= 8` is emitted for a NAME and for nothing else, and the name face is its own
bit, so the brace fact is the settled nibble WITHOUT the name face. Both readers
(`currentParserTable`, `currentParserTypeRecord`) now conjoin
`!currentParserName()`. Control, same command, same 40 files:

```
ok=0 bad=40   ->   ok=12 bad=28
x: i64 = 1        ✓
main: i64 = ()    ✓
b = a:len()       ✓
```

Re-measured after rebasing the repair onto `origin/main` `2954038e` (four
intervening lands, including the `gap134` expression-prefix transfer): fresh
`zig build`, same command, same 40 files — `ok=12 bad=28`, and `x: i64 = 1`
still checks. The repair is not sensitive to those four.

`gate/gap-145-consumer.sh`'s brace section passes across the change (its
`brace_consumers` count of 2 is preserved; the seven violations it does report
are its own owner-shift probes returning `shifted_len=0`, which is this same
breakage seen from the other side — the probe compiles Idol and gets nothing).

`zig build unit-test`, the same 2028 tests, built either side of the two-line
predicate and nothing else:

```
without the repair   1420 pass  544 fail  2 crash  62 skip
with the repair      1649 pass  316 fail  1 crash  62 skip
```

228 tests and one crash recovered, none lost. The 316 that remain are defects
2, 3 and 4 below; they fail on parse errors of their own shapes.

## Defect 2 — the pack-entry face is ORed over the primary face

`lib/compiler/parser.id:952` marks the first token inside `{ … }`:

```id
if entry
    out[count + index] = out[count + index] | (23 << 13)
```

Bits 13+ are the primary-face field, which is already occupied for exactly the
kinds `entry` admits:

| first entry | its primary face | `| 23` | outcome |
| --- | --- | --- | --- |
| `{ 1 }` | 2 (integer) | 23 | `expected expression, got 'integer'` |
| `{ "s" }` | 6 (text) | 23 | `expected expression, got 'text'` |
| `{ [k] = v }` | 19 (bracket) | 23 | index face lost |
| `{ a = 1 }` | 0 | 23 | intended, and the only case that works |

The comment above it checks the collision against the `(` matching-delimiter
coordinate and concludes "does not collide"; the collision is with the primary
faces it ORs over, which are in the same field. This one is NOT recoverable at
the consumer — the face is destroyed, not made ambiguous.

## Defect 3 — the generated artifact names the wrong tokens for `true` and `false`

`src/parser/projection.c` is generated from `lib/compiler/parser.id`
("Generated by duo compiler — do not edit"). Comparing every `kind ==
token.kindX -> delimiter N` arm in the producer against `lib/compiler/token.id`
and the generated C, 23 arms, two disagree:

| producer name | face | `token.id` value | emitted in `projection.c` |
| --- | --- | --- | --- |
| `kindtrue` | 9 | 26 | **18** (`kindin`) |
| `kindfalse` | 10 | 11 | **19** (`kindlocal`) |

Every other arm agrees exactly. So the boolean primary face is attached to `in`
and `local`, and `true`/`false` carry no face at all — which is the whole of
`x = true` failing at top level, and 10 of the 28 remaining corpus failures.
Both wrong values were emitted by the same commit that added the arms
(`185a7dc8`, "parser: transfer boolean primary faces"), so this is a
mis-generation and not staleness: `token.id` has carried 26 and 11 unchanged
since `5ddcd3b1` (2026-08-22). The mechanism is not identified here. Not
recoverable at the consumer either — the artifact tests the wrong kinds.

## Defect 4 — nothing parses after a callable declaration

Any top-level statement following a function declaration fails at its `=`:

```
f: i64 = ()
    0

y = 2          error: expected expression, got '=' (line 4, col 3)
```

It does not depend on the result descriptor, the parameter list, the blank line
or the following statement's shape; `x = 1` then `y = 2` is fine, and a comment
after the declaration is fine.

**Narrowed (2026-09-03, base `8a1a9a7c`, fresh build).** It is not "after a
callable declaration". It is after a callable whose body's LAST statement is a
BARE VALUE — the implicit-return form. The declaration is incidental; the
trailing value is the trigger, and it consumes the head of whatever follows:

```
f: i64 = (c: i64)          f: i64 = (c: i64)          f: i64 = (c: i64)
    if c >= 48                 if c >= 48                 if c >= 48
        return 1                   return 1                   return 1
    0                          return 0                   0

g: i64 = (p: i64)          g: i64 = (p: i64)          # nothing follows
    return p                   return p
REFUSED at g's `=`         OK                         OK
```

and the same with `y = 2` following refuses at `y`'s `=` (col 3), so the
following statement need not be a declaration either. `f: i64 = ()` with a
`return 0` body and `y = 2` after it now CHECKS at 12 statement offsets — the
shape this section opened with was fixed by defect 1's repair, and what remains
is only the bare-value tail. That is the whole of what blocks the artifact gate:
`lib/compiler/parser.id:69` closes `is_digit` with a bare `0`, so line 71 is the
next statement's `=`.

Not diagnosed past the shape. The suspect is the value-continuation walk over
the dedent rather than any face: the trailing expression parse does not stop at
the block edge, so it takes the next statement's first token and then meets `=`.

## Defect 5 — the `(` matching-delimiter COORDINATE is read as a primary face (REPAIRED HERE)

The fifth instance of this gap's own class, and it was already in the tree when
the class was written down.

`lib/compiler/parser.id:983` packs the primary face into bits 13.. of the
decision word. For a `(` it packs something else into the same field
(`:927`) — the index of the token after the matching `)`:

```id
elseif kind == token.kindlparen
    depth = 1
    probe = index + 1
    while probe < count and depth > 0
        …
    if depth == 0
        delimiter = probe
```

So for a `(` that field is a COORDINATE, and a coordinate ranges over every face
value. `currentParserAttributeBoundary` reads it as the coordinate it is. Every
face reader in `src/parser.zig` read it as a face.

**Measured** (base `8a1a9a7c`, fresh `zig build`, `idol check`). The identical
statement at twenty statement offsets, padded with `p0 = 0` lines that shift the
coordinate by three:

| file | coordinate | face it collided with | diagnostic |
| --- | --- | --- | --- |
| `x = (1 + 2)` | 7 | `bytes` | write `` `<eof>` `` at this token edge |
| `x = (1 + 2)` | 10 | `false` | write `` `<eof>` `` at this token edge |
| `x = (1 + 2)` | 13 | `if` | write `` `if` `` at this token edge |
| `x = (1 + 2)` | 16 | `method` | write `` `name` `` at this token edge |
| `x = (1 + 2)` | 28 | `comptime` | 'comptime' is not valid in .id files |

Accepted at the other fifteen offsets. One statement, decided by where it sat in
the FILE. `x = print(1)` is the same defect through `currentParserSuffix`: over
30 offsets (padding lines plus extra arguments, so every residue is covered) it
was refused at exactly the five whose coordinate hit a suffix face — 15 answered
"field access" and demanded a name, 19 answered "index" and demanded a `]`, 26
answered "no suffix" and the call was never taken at all.

**Repaired at the consumer**, like defect 1 and for the same reason: whether a
token is a `(` is its own settled bit (event bit 63, `callface`, set for a `(`
and nothing else), so the answer does not need the colliding field.
`currentParserFace` answers 0 for a `(` and the ~26 face readers ask it instead
of the raw word. Strictly additive: every `(` whose coordinate already missed
all face values reached these same answers through these same readers.
`currentParserExpressionGroup` and `currentParserAttributeBoundary` keep reading
the raw field — they are the coordinate's consumers, not face readers — and that
distinction is now stated at the accessor rather than implied.

The seven gained corpus files are `fib.id`, `compound_metamethods.id`,
`nested_test.id`, `test_sql.id`, `native_shift_smoke.id`,
`embed_json_data_smoke.id`, `embed_json_schema_smoke.id`. The failing-name sets
are nested: **nothing that passed at the baseline fails with the repair**, and 62

The one extra crash is inside a test that was already failing. `sema.test.sema:
GAP-060 void return cascades to a caller in tail position` asserts
`mod.body.stmts[0].func_decl.func.ret_type.named` with no tag check; the program

`gate/gap-145-consumer.sh` reports the same 7 violations with the baseline

side (the probe compiles Idol and gets nothing back).

The class again, since this instance predates its statement: a field that holds a
coordinate for one token kind and a face for the others is not settled, and a
reader that does not know which is which is guessing. This one WAS recoverable at
the consumer because the kind is carried by its own bit; defects 2 and 3 are not.

## Why this went unseen: the gate that would catch defect 3 cannot run

`zig build parser-artifact` proves `src/parser/projection.c` regenerates
byte-identically from `lib/compiler/parser.id`. It regenerates by running the
compiler on `lib/compiler/parser.id` — which is Idol source, and defect 4 stops
it at line 71:

```
$ IDOL=./zig-out/bin/idol ./tools/node/dev/parser/artifact
lib/compiler/parser.id:71:18: error: expected expression, got '='
parser artifact: FAIL — canonical dump-c recipe failed
```

So the artifact a broken parser produced is verified by a gate that the same
broken parser cannot run. The failure seals itself, and every transfer since has
landed on an artifact nothing re-derived.

## What closure requires

Defects 2 and 3 are destructive and must be repaired at the producer and the
artifact regenerated, which needs defect 4 fixed first so the compiler can
compile `lib/compiler/parser.id` at all. The ordering is forced:

```
defect 1 (repaired)  ->  defect 5 (repaired)  ->  defect 4  ->
regenerate projection.c  ->  defects 2, 3
```

Defects 1 and 5 were both recoverable at the consumer and are both landed, so
the frontier is defect 4 and it is now narrowed to one shape: a callable body
whose last statement is a bare value takes the head of the next statement.

The class, stated once so the next transfer does not add a fifth instance: a
settled face is a claim that one field names one fact. Two facts packed into
overlapping bits are not settled, and `|`-ing a face into a field that already
holds one destroys it. Every transfer in this series must run a program, not
only a shape check — `x: i64 = 1` would have failed the moment defect 1 landed.
