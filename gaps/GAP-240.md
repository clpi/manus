## Defect 1 — the brace face and the declaration face share bit 12 (REPAIRED HERE)

`lib/compiler/parser.id:945` packs the decision word as

```id
out[count + index] = … | (declaration << 9) | (braceface << 12) | (delimiter << 13)
```

`declaration` is four bits wide and starts at bit 9, so it OWNS bit 12.
`src/parser.zig` read the fact as the whole nibble:

```zig
fn currentParserTable(self: *Parser) ParseError!bool {
    return (((try self.currentParserDecision()) >> 9) & 0xF) == 8;
}
```

Two different tokens present nibble 8:

| token | `declaration` | `braceface` | nibble |
| --- | --- | --- | --- |
| `{` | 0 | 1 | 8 |
| a NAME that heads a declaration, or is followed by `:` | 8 | 0 | 8 |

`lib/compiler/parser.id` sets `declaration = 8` for exactly that name
(`kind == token.kindname` and `head == 1 or following == token.kindcolon`), so
every typed binding, every callable declaration and every `subject:relation()`
receiver answered "this token is a brace". `parse_simple_expr` then took
`parse_table`, and `parse_pack_body` demanded a `{` nobody wrote. Located by
stack trace, not by reading:

```
parser.zig:1191  expect
parser.zig:8141  parse_pack_body
parser.zig:8132  parse_pack
parser.zig:8128  parse_table
parser.zig:6269  parse_simple_expr      <- currentParserTable() said yes for `x`
parser.zig:7625  parse_suffixed_expr
```

The bit-12 test alone is the separately retracted unsound form (`243d0356`,
"retract unsound table primary projection") because the `@` face sets bit 12
too; widening to the nibble traded one collision for another and nothing
measured a program afterwards.

**Repaired at the consumer**, because this collision is recoverable: `declaration
= 8` is emitted for a NAME and for nothing else, and the name face is its own
bit, so the brace fact is the settled nibble WITHOUT the name face. Both readers
(`currentParserTable`, `currentParserTypeRecord`) now conjoin
`!currentParserName()`. Control, same command, same 40 files:

```
ok=0 bad=40   ->   ok=12 bad=28
x: i64 = 1        ✓
main: i64 = ()    ✓
b = a:len()       ✓
```

Re-measured after rebasing the repair onto `origin/main` `2954038e` (four
intervening lands, including the `gap134` expression-prefix transfer): fresh
`zig build`, same command, same 40 files — `ok=12 bad=28`, and `x: i64 = 1`
still checks. The repair is not sensitive to those four.

`gate/gap-145-consumer.sh`'s brace section passes across the change (its
`brace_consumers` count of 2 is preserved; the seven violations it does report
are its own owner-shift probes returning `shifted_len=0`, which is this same
breakage seen from the other side — the probe compiles Idol and gets nothing).

`zig build unit-test`, the same 2028 tests, built either side of the two-line

```

```

228 tests and one crash recovered, none lost. The 316 that remain are defects
2, 3 and 4 below; they fail on parse errors of their own shapes.

## Defect 2 — the pack-entry face is ORed over the primary face

`lib/compiler/parser.id:952` marks the first token inside `{ … }`:

```id
if entry
    out[count + index] = out[count + index] | (23 << 13)
```

Bits 13+ are the primary-face field, which is already occupied for exactly the
kinds `entry` admits:

| first entry | its primary face | `| 23` | outcome |
| --- | --- | --- | --- |
| `{ 1 }` | 2 (integer) | 23 | `expected expression, got 'integer'` |
| `{ "s" }` | 6 (text) | 23 | `expected expression, got 'text'` |
| `{ [k] = v }` | 19 (bracket) | 23 | index face lost |
| `{ a = 1 }` | 0 | 23 | intended, and the only case that works |

The comment above it checks the collision against the `(` matching-delimiter
coordinate and concludes "does not collide"; the collision is with the primary
faces it ORs over, which are in the same field. This one is NOT recoverable at
the consumer — the face is destroyed, not made ambiguous.

| --- | --- | --- | --- |
| `kindtrue` | 9 | 26 | **18** (`kindin`) |

## Defect 4 — the compound-update field is read one bit too wide (REPAIRED HERE)

Any top-level statement following a function declaration fails at its `=`:

```
f: i64 = ()
    0

y = 2          error: expected expression, got '=' (line 4, col 3)
```

It does not depend on the result descriptor, the parameter list, the blank line
or the following statement's shape; `x = 1` then `y = 2` is fine, and a comment
after the declaration is fine.

**Narrowed (2026-09-03, base `8a1a9a7c`, fresh build).** It is not "after a
callable declaration". It is after a callable whose body's LAST statement is a
BARE VALUE — the implicit-return form. The declaration is incidental; the
trailing value is the trigger, and it consumes the head of whatever follows:

```
f: i64 = (c: i64)          f: i64 = (c: i64)          f: i64 = (c: i64)
    if c >= 48                 if c >= 48                 if c >= 48
        return 1                   return 1                   return 1
    0                          return 0                   0

g: i64 = (p: i64)          g: i64 = (p: i64)          # nothing follows
    return p                   return p
REFUSED at g's `=`         OK                         OK
```

and the same with `y = 2` following refuses at `y`'s `=` (col 3), so the
following statement need not be a declaration either. `f: i64 = ()` with a
`return 0` body and `y = 2` after it now CHECKS at 12 statement offsets — the
shape this section opened with was fixed by defect 1's repair, and what remains
is only the bare-value tail. That is the whole of what blocks the artifact gate:
`lib/compiler/parser.id:69` closes `is_digit` with a bare `0`, so line 71 is the
next statement's `=`.

It is not the value-continuation walk over the dedent, and it is not a layout
question at all. It is this gap's own class again, in the third form: a field
READ one bit too wide.

`lib/compiler/parser.id:990` packs the decision word's top end as

```id
… | (updateface << 57) | (primary << 61) | (layouttype << 62) | (callface << 63)
```

so the compound-update field is bits 57..60 and bit 61 is the PRIMARY face. Four
bits is the whole field and it is not tight: `updateface` is `relation + 1` over
the six `_roleupdate` identities `+= -= *= /= %= ^=`, whose relations are
`add sub mul div mod pow` — ordinals 0..6, so the field is 7 at its widest.
`src/parser.zig` read FIVE:

```zig
fn compound_assign_op(self: *Parser) ParseError!?ast.BinOp {
    const code = ((try self.currentParserEvent()) >> 57) & 0x1F;
    return relation_from_ordinal(code - 1);
}
```

The fifth bit is `primary`, which the owner sets for `name`, `intlit`,
`floatlit`, `star`, `question`, `lparen` and `lt`. Each of those presented
`code = 0 | (1 << 4) = 16`, and `relation_from_ordinal(15)` is `.lt` — a real
`ast.BinOp`, so the answer was never null. `parse_expr_stmt` asks this question
about the token FOLLOWING a parsed expression:

```zig
const compound = try self.compound_assign_op();
if (nxt.kind == .assign or compound != null or glued != null) {
```

so an expression statement whose next token was any of the seven parsed as a
compound assignment: that token was consumed AS THE OPERATOR and an expression
was demanded at whatever followed it. `y` became `<=` and its `=` was the
reported error. The bare-value tail is the trigger only because a tail value is
the one statement form that ends without consuming what follows it — the
declaration, the dedent and the blank line are all incidental, and the same
refusal reproduces with no declaration anywhere:

```
a = 1        a = 1        a = 1
a            a            a
b = 2        2            # nothing follows
3:3 `=`      4:1 `<eof>`  OK — eof is the one following token with no primary bit
```

**Repaired at the consumer** by masking the field the owner packs, `0xF`.
`currentParserTypePointer` already read `(event >> 57) & 0xF`, so this reader was
the only one disagreeing with the producer, and the two sibling readers are right
for the reason this one was wrong — `unary 47..51` and `glue 52..56` each stop
exactly where the next field starts, and this one ran one past it.

Controls across that one mask and nothing else, base `d10eb674` (so defect 5 is
already repaired underneath), fresh `zig build` either side:

| --- | --- | --- |
| first 40 `examples/*.id` `idol check` | ok=12 bad=28 | **ok=19 bad=21** |
| `zig build unit-test` (2037) | 1706 pass / 265 fail / 4 crash / 62 skip | **1841 pass / 131 fail / 3 crash** / 62 skip |

## What closure requires

Defects 2 and 3 are destructive and must be repaired at the producer and the
artifact regenerated. Defects 1, 5 and 4 were all recoverable at the consumer and
are all landed, and measuring the artifact gate after defect 4 corrects the
ordering this record first wrote: defect 3 is not downstream of the regeneration
waiting on it, defect 3 is what now BLOCKS it, because `lib/compiler/parser.id`
is itself a program containing `true` and `false`.

```
defect 1 (repaired)  ->  defect 5 (repaired)  ->  defect 4 (repaired)  ->
defect 3  ->  regenerate projection.c  ->  defect 2
```

So the seal is now exactly one defect wide, and it is a closed loop: defect 3 is
a MIS-GENERATION in `src/parser/projection.c`, so repairing it means editing a
generated artifact whose regeneration gate cannot run until it is repaired. Two
exact values close it (`kindtrue` 26 for the emitted 18, `kindfalse` 11 for the
emitted 19), but the mechanism that emitted the wrong pair is still
unidentified, and a hand edit that does not also explain the mechanism will be
re-emitted by the first successful regeneration. `src/parser/projection.c` is
claimed by the GAP-145 seat and is not touched here.

The class, stated once so the next transfer does not add a fifth instance: a
settled face is a claim that one field names one fact. Two facts packed into
overlapping bits are not settled, and `|`-ing a face into a field that already
holds one destroys it. Every transfer in this series must run a program, not
only a shape check — `x: i64 = 1` would have failed the moment defect 1 landed.

Defect 4 widens the class by one form, and it is the form a shape check is worst
at. Defects 1, 2 and 5 are all "two facts sharing bits". Defect 4 is one fact
packed correctly and READ one bit too wide — the consumer disagreeing with the
producer about where a field ENDS. Nothing about that is visible in a shape
check, because a field read too wide still returns a well-typed answer: `.lt` is
a real relation, and `ast.BinOp` was happy to hold it. The rule is that a reader
masks the width the OWNER packs, and the owner's packing line is the only
authority for that width — not the reader's sibling, and not a gate ratchet,
which in this case had the wrong width written into its failure message.

## Measured transfer at tip dad3d374 — the pack-entry OR destroys the `[` entry face (2026-09-09)

Defects 1, 5, 4 and 3 are repaired at that tip and the artifact gate is open:
`IDOL=./zig-out/bin/idol ./tools/node/dev/parser/artifact` runs to
`parser artifact: PASS` with `generated bytes match tracked artifact` — the

`./zig-out/bin/idol check`:

```

t = { "a", "b" }          ✓
```

`1:11` is the consumed `=` edge — the exact symptom the defect-2 table
predicted when the index face is lost. The mechanism is this gap's class once
more: the `[` entry field holds face 19 (`parser.id:944`), the entry OR fires
unconditionally (`parser.id:1057`), and `19 | 23 = 23` replaces the only face
the consumer's indexed-entry branch switches on. Destroyed, not made
ambiguous — so this instance is repaired at the producer, where the
destruction happens, not at the consumer.

Two prior facts fall out of the same measurement. The `[` matching-delimiter
walk added at `0dc492a8` (`parser.id:956`) is unreachable: the earlier
`kindlbracket -> 19` arm owns the kind, so the walk never executes — and the
artifact census (`event-cases=228`, every lane count) is byte-identical when
the walk is deleted, which is the proof it decided nothing. It is deleted
here. And `parse_pack_body`'s older `face == 19` arm was dead for the same
reason defect 5 recorded: a face-19 word arriving at a coordinate-read was
refused long before the pack body. No case loses a parse.

Repair: face 33 is the indexed-entry face at the shared `[` identity. Inside
a pack, a `[` after `{` or `,` is always an indexed entry — type position and
patterns carry their own faces — so the settled answer needs neither an OR
nor the destroyed field:

```id
if entry
    if kind == token.kindlbracket
        out[count + index] = (out[count + index] & 8191) | (33 << 13)
    else
        out[count + index] = out[count + index] | (23 << 13)
```

The mask is the owner's field boundary: bits 13.. are the whole face field,
so `& 8191` clears only that field and keeps every other face. Face 33 is
local to the non-parenthesis delimiter space and above the closure band
(`closure - 13 = 20 > 14`), so a subsequent `}` still closes the pack. The
consumer reads the settled face and drops the residual token-identity replay:
`currentParserTableEntry` admits 33, and `parse_pack_body`'s indexed branch
reads `face == 19 or face == 33` (19 remains for defense; 33 is the settled
fact). The tracked artifact is regenerated by the canonical recipe, never
hand-edited; it carries
`out[(count + index)] = ((int64_t)((((int64_t)((out[(count + index)]) & (8191)))) | (270336)));`.
