# GAP-020 — `--lib` never initializes the primary module

**Status:** FIXED 2026-08-08 (the workaround is now a convenience, not a
requirement)
**Filed:** 2026-08-07 · **Frequency:** 1 · **Blocks:** SH-03 production dispatch
**Sites:** `lib/std/compiler/host.duo` (the workaround, and the only citation)

## The defect

`--lib` emits an `__attribute__((constructor))` that runs the runtime
initializers and `duo_register_modules()`. That registration initializes every
**required** module. It does not initialize the module **being compiled**.

A primary module's file-scope bindings are emitted as statements inside `main`,
and `--lib` returns before emitting `main` at all. So the top module of a
library artifact is the one module in the link unit that is never initialized.

## Minimal repro

```duo
_seed = (): i64
    77
end

global g_state: i64 = _seed()

@c.export("duo_read_state")
duo_read_state(): i64
    g_state
end
```

```
duo compile prim.duo --backend=c --lib --emit obj -o prim.dylib
cc -o h host.c prim.dylib && ./h
primary-module global -> 0 (want 77)
```

The emitted C is the whole story: `duo_g_g_state` is **declared** and **read**,
and assigned nowhere.

```c
static int64_t duo_g_g_state;          /* declaration */
    return duo_g_g_state;              /* read */
```

## Why it was expensive to find

The failure wears two masks and neither names the cause.

- When the uninitialized global is a **pointer** (a module table, e.g.
  `lexer.duo`'s `global strm`), the export dereferences NULL: SIGSEGV, or a
  hang. Loud, but it points at the callee, not at initialization.
- When it is a **scalar**, the export returns **0** with no diagnostic. That is
  the dangerous half: a host reading a plausible number cannot tell a real
  answer from an uninitialized one, and every "does the boundary work" smoke
  test passes.

This is why `examples/pass16_lexer_host_proof.duo` runs a live-boundary control
*before* comparing anything, and differentials against the in-process lexer
rather than asserting a hard-coded expectation.

Two earlier diagnoses of this same seam were wrong and are recorded so the
bisection is not repeated: "every `@c.export` symbol has internal linkage"
(false — they are `T` under both the bare and mangled names) and "there is no
standalone init entry" (closer, wrong mechanism — the constructor exists and
runs; it just skips one module).

## FIXED 2026-08-08 — the constructor runs the primary module's file-scope body

The gap's own prescription, and it was one call once the emitter existed. The
module's file-scope body — table-const initialisers, alias metatables, every
top-level statement, the tail expression — was written inline inside `main`,
and `--lib` returns before `main` is emitted. It is now
`CodeGen.emit_file_scope_body`, with two callers: `main`, unchanged, and the
lib constructor, which previously stopped after `duo_register_modules()`.

The constructor is also no longer gated on `moduleNeedsLuaRuntime()` — only its
runtime-globals half is. A full-native library used to get no constructor at
all, so it had the same hole for a different reason.

### Measured, the gap's own four-line repro

    duo compile prim.duo --backend=c --lib -o prim.dylib
    cc -o h host.c prim.dylib && ./h

| | result |
| --- | --- |
| before | `primary-module global -> 0 (want 77)` |
| after  | `primary-module global -> 77 (want 77)` |

And the artifact built DIRECTLY from `lib/std/compiler/lexer.duo` — the case the
table below records as "no answer (139 SIGSEGV, or 124 hang)" — answers a C host
that knows only the ABI:

    n=15 first_kind=14        (14 is KIND_FUN for "fun add")

`examples/pass16_lexer_host_proof.duo` is green: 20 cases, a C host agreeing
with the in-process lexer on kinds, text, int_val and float_val.

### Note on the build spelling

That proof was already red at HEAD before this work, for an unrelated reason:
it built the artifact with `--backend=c --lib --emit obj`, and `obj`/`dylib`
became machine targets that refuse the C backend ("C emit is bootstrap-only").
It reported 91 — "artifact did not build" — without ever reaching the seam.
`--lib` alone already produces the linkable dylib, and the proof now says so.
This is GAP-015 territory, not this gap's.

## Disposition of the workaround

`lib/std/compiler/host.duo` **stays**, demoted from load-bearing to convenience.
Nothing about the lexer requires it any more — the measurement above compiles
`lexer.duo` directly and it works. What it still supplies is the two things a
foreign caller cannot otherwise ask for: `duo_lexer_host_stride`, so a host
asserts the record layout instead of hard-coding 4, and `duo_lexer_host_probe`,
the live-boundary control that distinguishes "linked and live" from "linked and
reading zeros". Those are worth keeping on their own terms; the anchor trick is
not.


## Workaround (historical — how it was worked around before the fix)

Compile an **anchor** module that references the real module ambiently, and let
the real module be a dependency:

```duo
-- lib/std/compiler/host.duo
@c.export("duo_lexer_host_probe")
duo_lexer_host_probe(out: i64, cap: i64): i64
    std.compiler.lexer.duo_lexer_tokenize_all("fun add(a: i64): i64 = a + 1 end",
        "probe.duo", out, cap)
end
```

The dependency path is the one that already works, so the real module's flat
exports (`duo_lexer_tokenize_all`, `duo_lexer_step`,
`duo_lexer_text_fingerprint`) become callable **unchanged** — the host ABI is
not affected by the workaround.

Measured, each a C host linking the artifact and calling in:

| artifact built from | result |
| --- | --- |
| `lexer.duo` directly | no answer (139 SIGSEGV, or 124 hang) |
| `host.duo` (lexer as dependency) | `n=15`, agrees token-for-token with in-process |

## The fix

Emit the primary module's file-scope initialization into the lib constructor,
instead of only into `main`. The constructor already exists and already runs;
it needs one more block. Closing this should turn `host.duo` from load-bearing
into a convenience, and the table above is the regression test.
