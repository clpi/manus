# GAP-057 — the FP register allocator has no liveness and no caller-save

**Status:** PARTIALLY FIXED 2026-08-08 (a3ad3ec) · steps 1 done, 2-3 open
**Blocks:** `examples/mandelbrot.duo` (DNB003), still correctly refused

## What I tried, and why it was wrong

`allocFpReg` allocates only d0-d7 and then raises `RegisterExhausted`, which
refuses `examples/mandelbrot.duo` with DNB003. ARM64 has d16-d31 sitting unused
as the other caller-saved half of the FP file, so widening the pool from 8 to 24
looked like a one-loop fix with no downside. I wrote a comment arguing there was
"no new hazard across calls" because `emitSaveCallerRegs` already saves no FP
registers, so d16-d31 would merely inherit an existing limitation.

That reasoning was wrong, and the measurement caught it:

    mandelbrot, --backend=c        exits 0, 3280 lines of output
    mandelbrot, --backend=direct   HANGS. zero output. killed at 10 minutes

A clean refusal became an infinite loop. Reverted.

## The actual defects, both structural

```zig
fn releaseFpReg(self: *Arm64Compiler, reg: u5) void {
    _ = self;
    _ = reg;
}
```

1. **No liveness.** `releaseFpReg` is a no-op, so `used_fp_regs` only ever fills
   up. FP allocation is not allocation, it is a monotonic counter. With 8
   registers a float-heavy function exhausts them quickly and gets refused;
   widening the pool does not fix the allocator, it just postpones the refusal
   until after the program has become wrong.

2. **No caller-save.** `emitSaveCallerRegs` saves x9-x28 and x30 and no FP
   register at all. Every d register is caller-saved on AAPCS64, so **no float
   value survives a call**. mandelbrot prints from inside its loop; its float
   loop state is destroyed by the printf and the loop never terminates.

The two compound. With d0-d7 only, mandelbrot never compiled, so defect 2 was
invisible. Widening the pool made it compile and hang.

## Why the refusal is currently load-bearing

DNB003 on mandelbrot is not really "register pressure". It is the only thing
standing between a float program with a call in it and a wrong answer. Anyone
widening the pool must fix caller-save FIRST, or they will convert refusals into
hangs exactly as I did.

## Order of work

1. **Caller-save for FP.** Extend `SaveSet`/`emitSaveCallerRegs` to spill live d
   registers around calls. This is the correctness prerequisite and is worth
   doing on its own — it fixes float-across-call for the existing d0-d7 pool.
2. **Real liveness.** Give `releaseFpReg` a body, so a register can be reused.
3. **Only then widen** to d16-d31. Skip d8-d15: they are callee-saved (low 64
   bits must be preserved), so using one without a prologue/epilogue save is a
   silent ABI violation rather than a refusal.

## Test that must exist before step 3

A float value that is live ACROSS a call, verified by value:

```duo
side(n: i64): i64
    return n
end

acc(x: f64): f64
    t: f64 = x * 2.0
    side(1)
    return t + 1.0
end
```

`acc(3.0)` is 7.0 on both backends or the caller-save is not done. Note the call
must sit BETWEEN the definition and the use of `t`; a call before or after
proves nothing.

## Update 2026-08-08 — a3ad3ec does step 1 only, and the reason matters

Two of the three items above are done:

* **Values are out of the argument range.** `allocFpReg` allocates d16+ instead
  of d0+, and f64 parameters are copied out of d0-d7 on entry when the body can
  call — the same move, on the same condition (`dnirFunctionHasCall`), that the
  integer path makes out of x0-x7. This retired `requireSafeFpStaging` in
  dnir_lower.zig, which had been REFUSING programs to avoid the collision.
* **Caller-save exists.** `SaveSet` has an FP block; live d16+ registers survive
  a call. d0-d7 stay unsaved, matching x0-x8, because saving the result register
  would clobber what the call produced.

**Step 2 (liveness) and step 3 (capacity) are NOT done, and I attempted step 3
anyway.** Widening to 15 value registers made `mandelbrot` compile and then
HANG with no output — the identical failure this gap was filed for, reproduced
hours later with caller-save now in place. Reverted to eight registers.

That is the finding worth keeping: **caller-save was not what mandelbrot needed.**
The hang survived it. So the remaining defect is something else — most likely
that `releaseFpReg` is still a no-op, making this a monotonic cursor rather than
an allocator, but that is a hypothesis and not measured. A simple float loop
(`x = x + 1.5` in a `while`, with and without a call inside) still refuses, so
mandelbrot's shape is not yet isolated and the next person should start by
finding a SMALLER hanging program than mandelbrot.

Capacity has now been grabbed before correctness twice in this allocator. The
ordering in this file was right; I did not follow it.
