# GAP-196 — constraint-domain polymorphism

**Status:** OPEN · **Filed:** !2026-08-18T16:35:00Z
**Priority:** P1 · **Kind:** research_gap
**Filed by:** devin-semantic-20260818
**Files:** docs/spec/constitution.md, docs/spec/law.md, src/semantic_graph.zig, src/sema.zig

A semantic constraint should select its solver by demand and available facts,
not by language subsystem. The same relation may realize as forward arithmetic,
interval propagation, linear programming, SMT, SAT, finite-domain search,
symbolic simplification, or compile-time proof depending on which variables are
known and what the demand is. Solver is representation.

## Current measured boundary

SMT and abstract interpretation are separate tools. There is no general
constraint-domain fact family that routes obligations to solvers.

**Crossed:**

- Abstract domains exist for range, shape, alias, effect.
- SMT and e-graphs are available as provers.

**Still missing:**

- `constraint(domain, variables, relations)` as a graph fact.
- Solver selection by domain and demand.
- Unified `solve` interface for arithmetic, intervals, booleans, finite domains,
  arrays, bitvectors, linear constraints.
- Fallback to simpler solver when facts permit (e.g., interval instead of SMT).
- User constraints as ordinary relations over a constraint domain.

## Required order

1. Define `constraint domain` as a semantic fact in C0.
2. Project applicable solver realizations from relation, domain, determinacy, and demand facts — a physical index may accelerate the projection; NO semantic solver registry exists (`delta.registries = 0`).
3. Implement dispatch: given constraints and knowns, choose the cheapest sound
   solver.
4. Unify type inference, bounds proof, layout, scheduling, user constraints,
  symbolic execution under the substrate.
5. Demonstrate one relation solved by different solvers in different contexts.

## Closure acceptance

Close when a single constraint substrate routes semantic obligations to the
appropriate solver and the same relation can be solved by different means as
context changes.

## C0 alignment

Instance of the schema in `gaps/RESEARCH-SPINE.md`; `tools/node/dev/gapc0` fails
closed without it.

- **constitutional owners:** obligation (the constraint) · relation · descriptor (domain facts) · witness (solver applicability/proof) · realization (a solver IS a realization)
- **kind delta:** 0
- **registry delta:** 0
- **source syntax delta:** 0
- **semantic invariant:** a constraint is an obligation; a solver is a realization of discharging it; solver choice is representation, never law — legality and profitability stay separate.
- **physical mechanism:** cheapest-sound-solver dispatch over projected applicability; fallback down the solver ladder (interval before SMT) when facts permit. Proof strategy itself is a realization with compile-time economics.
- **prerequisites:** GAP-195.
- **foreign implication:** foreign solvers are witness producers under their own trust level.
- **world implication:** solver availability is a world fact.
- **projection implication:** applicable solvers are projected from relation/domain/witness facts — an `index`/`cache` physical role may accelerate it.
- **demand implication:** the demanded determinacy and precision of a solution bound which solvers are admissible.
- **realization implication:** one relation realized as interval propagation, SAT, SMT, finite-domain search, LP, or direct arithmetic in different contexts; type inference, bounds proof, layout, scheduling, symbolic execution, and user constraints on one substrate.
- **evidence:** one relation solved by two different solvers in two contexts, each choice derived from facts, costs recorded.
- **deletion witness:** solver registries, per-solver glue, solver-shaped language subsystems.
