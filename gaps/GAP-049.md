# GAP-049 — tree-sitter's grammar is authored JavaScript, and the descriptor surface it should be projected from does not exist

**Filed** 2026-08-08. **Status** open. **Cost** 804 lines of hand-written
JavaScript that Pass 100 §19 names as output, plus a census that could not see
it.

## The rule being violated

Pass 100 §19, on the toolchain host:

> LSP = queries (hover=why, references=dependents, diagnostics=the audit),
> MCP = the same queries + the `add` family, **tree-sitter = a generated
> grammar projection (output, never authored)**, fmt = the canonicalizer's
> face, Ward = the in-repo proof application.

`ext/tree-sitter-duo/grammar.js` is 804 lines and 90 `rules:` productions,
written by hand in the tree-sitter JavaScript DSL. It is authored.

## Why it was not converted in this pass

**Because there is nothing to generate it from.** Every candidate was checked:

| candidate | what it actually is | why it cannot project a grammar |
|---|---|---|
| `lib/std/compiler/parser.duo` | a hand-written recursive-descent parser (L1 chars → L2 tokens → L3 statements) | **imperative, not declarative** — there is no production table to walk. Its own header documents a *bounded subset*: about twelve productions, no `for`, no `local`/`global`, no `match`, no `enum`, no method-call syntax, against grammar.js's 90 rules. |
| `docs/GRAMMAR_SPEC.md` | 213 lines of prose: a `GR-001`…-style status ledger (preferred / accepted / deprecated / removed) | **prose, machine-unreadable.** Each rule is a paragraph and a `.duo` snippet, not a production. Nothing parses it. |
| `duo token-tables emit` → `lib/std/token/classify.duo` | a generated **lexical** classifier | tokens only. It says nothing about how tokens combine, which is the whole content of a grammar. |
| `duo graph` | semantic facts lifted **after** parsing | downstream of the grammar; it presupposes it. |

So the honest statement is: the projection Pass 100 requires has no source. The
missing pieces, precisely:

1. **A declarative production registry in Duo** that is either what
   `src/parser.zig` is driven by, or is differentially proven against it. Today
   the grammar exists three times over — `src/parser.zig`, `parser.duo`'s
   bounded subset, and `grammar.js` — with nothing tying them together.
2. **An emitter** rendering those productions into the tree-sitter DSL
   (`seq` / `choice` / `repeat` / `optional` / `prec.left` / `token` / `field` /
   `supertypes` / `extras`), the same shape as the existing
   `token-tables emit`.
3. **A differential** proving the projection accepts exactly the corpus
   `src/parser.zig` accepts, and rejects `examples/compile_fail/`. Without it a
   generated grammar is a second unverified opinion instead of one authority.

## A second reason this is not a mechanical port

`grammar.js` is pinned to a **pre-Pass-100 surface**. Its rule list includes
`match_statement`, `match_arm`, `enum_definition`, `try_statement`,
`catch_clause`, `concept_definition`, `optional_type`, `local_declaration`,
`const_declaration` and `function_declaration` — and `CLAUDE.md` §1 denies
`match`, `switch`, `enum`, `try`, `catch`, `class`, `impl`, `trait`,
`interface`, `local`, `const`, `fn`, `function`, `?:` and `T?` by name.

Generating this file from Pass 100 descriptors would therefore **change which
programs the editor tooling recognises**, on a surface that GAP-025 records as
not implemented yet. That is a language decision, not a build-system one, and
it has to follow the descriptor work rather than lead it.

## A third fact, found while checking the first two: it does not build

`tree-sitter generate`, run in `ext/tree-sitter-duo/` with the CLI already on
this machine, **exits 1**:

```
Unresolved conflict for symbol sequence:
  'return'  •  '('  …
Possible interpretations:
  1:  (return_statement  'return'  •  expression  local_declaration_repeat2)
  2:  (return_statement  'return'  •  expression)
  3:  (return_statement  'return')  •  '('  …
```

Verified against the pristine `HEAD` copy of `grammar.js` as well as the
working tree, so this is not something a comment edit introduced. The tracked
`ext/tree-sitter-duo/src/grammar.json` still lists the same 90 rule names, so
it is structurally in step with the `.js` — it is output from a tree-sitter
that resolved this conflict, and the one installed here does not.

`scripts/setup-nvim.duo` runs the generator with `>/dev/null 2>&1` and prints
`-- tree-sitter generate failed` on non-zero. It does check the status, but the
line reads like a skipped optional step, which is how a grammar that has not
built in some time stayed unremarked.

The consequence for this gap: `grammar.js` is not merely un-generated, it is
**not currently buildable**, so "we can regenerate it later" is not a fallback
anyone should be relying on. Whoever lands the projection gets to fix the
`return_statement` ambiguity as part of the work — and a grammar emitted from a
production registry would not have it, because the registry states precedence
rather than leaving it to be inferred.

**Do not delete the file.** The tracked `grammar.json` beside it is the only
syntax front-end the editors have, and deleting the `.js` orphans it.

## How it is accounted for until then

Three separate ledgers touch it, and none of them said "authored JavaScript":

- `docs/spec/corpus.md` classifies `.duo` files only — `audit100` lists the
  corpus with `git ls-files '*.duo'`, so a rule naming a `.js` path would be
  dead data in that manifest, not an accounting.
- `audit100`'s `nonduo` row counts it as **1 of 536** tracked non-`.duo`,
  non-`.md` files, indistinguishable from a `.wast` fixture.
- `scripts/language_census.duo` (G11) counted `.duo`, `.zig`, `.lua`, `.c/.h`
  and `.sh/.py`. **`.js` matched no pattern**, so three tracked JavaScript
  files — `ext/tree-sitter-duo/grammar.js` (804), `docs/theme/custom.js` (97),
  `ext/vscode-duo/extension.js` (81), 982 lines — were invisible to the census
  whose headline is "no language but Duo", and `docs/RELEASE_STATUS.md` could
  call the census "otherwise clean" without either claim being checked.

Closed in this pass: G11 now counts `.js` as a second **DEBT** line, ratcheted
at its current count of 3 (`CENSUS_JS_FLOOR`). It is debt rather than
sanctioned because a sanctioned generated artifact has to name its generator,
and none of the three has one.

## Repair sequence

1. Land the production registry (item 1) as descriptors, proven against
   `src/parser.zig` on the existing corpus — this is the same work
   AUTHORITY.md's "offside parsing + canonicalizer" P0 needs.
2. Emit `grammar.js` from it (item 2).
3. Stand up the differential (item 3), and only then untrack `grammar.js` +
   `src/grammar.json`, gitignore both, and lower `CENSUS_JS_FLOOR` 3 → 2 in the
   same commit.

Step 3 is the point: untracking the file before the differential exists trades
a visible violation for an invisible one.
