# GAP-049 — tree-sitter's grammar is authored JavaScript, and the descriptor surface it should be projected from does not exist

**Filed** 2026-08-08. **Status** open. **Cost** 804 lines of hand-written
JavaScript that Pass 100 §19 names as output, plus a census that could not see
it.

## The rule being violated

Pass 100 §19, on the toolchain host:

> LSP = queries (hover=why, references=dependents, diagnostics=the audit),
> MCP = the same queries + the `add` family, **tree-sitter = a generated
> grammar projection (output, never authored)**, fmt = the canonicalizer's
> face, Ward = the in-repo proof application.

`ext/tree-sitter-duo/grammar.js` is 804 lines and 90 `rules:` productions,
written by hand in the tree-sitter JavaScript DSL. It is authored.

## Why it was not converted in this pass

**Because there is nothing to generate it from.** Every candidate was checked:

| candidate | what it actually is | why it cannot project a grammar |
|---|---|---|
| `lib/std/compiler/parser.duo` | a hand-written recursive-descent parser (L1 chars → L2 tokens → L3 statements) | **imperative, not declarative** — there is no production table to walk. Its own header documents a *bounded subset*: about twelve productions, no `for`, no `local`/`global`, no `match`, no `enum`, no method-call syntax, against grammar.js's 90 rules. |
| `docs/GRAMMAR_SPEC.md` | 213 lines of prose: a `GR-001`…-style status ledger (preferred / accepted / deprecated / removed) | **prose, machine-unreadable.** Each rule is a paragraph and a `.duo` snippet, not a production. Nothing parses it. |
| `duo token-tables emit` → `lib/std/token/classify.duo` | a generated **lexical** classifier | tokens only. It says nothing about how tokens combine, which is the whole content of a grammar. |
| `duo graph` | semantic facts lifted **after** parsing | downstream of the grammar; it presupposes it. |

So the honest statement is: the projection Pass 100 requires has no source. The
missing pieces, precisely:

1. **A declarative production registry in Duo** that is either what
   `src/parser.zig` is driven by, or is differentially proven against it. Today
   the grammar exists three times over — `src/parser.zig`, `parser.duo`'s
   bounded subset, and `grammar.js` — with nothing tying them together.
2. **An emitter** rendering those productions into the tree-sitter DSL
   (`seq` / `choice` / `repeat` / `optional` / `prec.left` / `token` / `field` /
   `supertypes` / `extras`), the same shape as the existing
   `token-tables emit`.
3. **A differential** proving the projection accepts exactly the corpus
   `src/parser.zig` accepts, and rejects `examples/compile_fail/`. Without it a
   generated grammar is a second unverified opinion instead of one authority.

## A second reason this is not a mechanical port

`grammar.js` is pinned to a **pre-Pass-100 surface**. Its rule list includes
`match_statement`, `match_arm`, `enum_definition`, `try_statement`,
`catch_clause`, `concept_definition`, `optional_type`, `local_declaration`,
`const_declaration` and `function_declaration` — and `CLAUDE.md` §1 denies
`match`, `switch`, `enum`, `try`, `catch`, `class`, `impl`, `trait`,
`interface`, `local`, `const`, `fn`, `function`, `?:` and `T?` by name.

Generating this file from Pass 100 descriptors would therefore **change which
programs the editor tooling recognises**, on a surface that GAP-025 records as
not implemented yet. That is a language decision, not a build-system one, and
it has to follow the descriptor work rather than lead it.

## The build, repaired — 2026-08-08

**`grammar.json` was not a fallback.** The paragraph above treats the tracked
`src/grammar.json` as "the live artifact", output from a tree-sitter that had
resolved the conflict. It is not. `tree-sitter generate src/grammar.json` on
the pristine `HEAD` copy fails with the **identical** `'return' • '('`
conflict, and `parser.c` is not tracked — so nothing on this tree could produce
a parser by any route. Every editor front-end named in Pass 100 §19 was dead,
not degraded.

The fix is two parts, both in `grammar.js`:

1. `return_statement` is wrapped in `prec.right`. The reported ambiguity is
   whether `return` continues into an expression list or ends and lets a
   parenthesised statement follow — right associativity says continue, which is
   what Lua and Duo both mean.
2. A `conflicts:` block of **36 entries**, grouped by cause in the file. They
   are not guesses: a script drops each one and re-runs the generator, and all
   36 are still required for it to exit 0. Four causes account for all of them
   — statement-head versus expression-statement, unterminated statement lists,
   pattern position overlapping expression position, and prefix operators that
   bind before the LR item is decided. Duo has no statement terminator and an
   expression is a statement, so these are genuine LR(1) ambiguities that GLR
   resolves at parse time rather than defects in the rules.

Proof: `tree-sitter generate` exits 0; `parser.c` compiles to a loadable
library (`xcrun clang -shared`, 808 KB); `tree-sitter parse` returns a correct
tree for a hand-checked file.

### Step 1 — the rule, and the exclusion that makes it safe

`fib(n: any)` and `_env_or(n: str, d: str): str`, with no `fun` and no
`function`. It is split into two arms, and the split is **by the parameters,
not by the return type**, because that is what keeps it LR(1): both arms open
on the same unannotated-parameter symbol, so nothing forks at `(`, and they
separate one token later at the first `:` inside the list.

- arm (a) — no parameter is annotated, so a **return type is required**.
- arm (b) — some parameter is annotated, so the return type is optional.

`main()` followed by statements and an `end` is therefore NOT a declaration,
which is GR-001's own rule and is load-bearing here. Statement-initial heads
over the 748 files: **4645** carry a return type, **230** an annotated
parameter and no return type, **48** are `main()`-shaped with neither, and
**791** are ordinary calls like `print(out)`. Accepting the 48 would make a
declaration candidate out of every one of the 791.

Adding it needed **`prec.dynamic(3)`** on the rule plus four `conflicts:`
entries. A first attempt used static `prec(1)` instead: `tree-sitter generate`
accepted it, reported two conflicts as newly unnecessary, and recognition fell
from 56.4 % to **24.7 %** — static precedence resolved the `f(` fork at the
paren, killing the call reading before the `:` that decides it could arrive.
That is why the number is re-measured after every change and not only at the
end.

### Steps 2–9, and what each was actually fixing

- **The operator table did not match the lexer.** `src/lexer.zig` lexes `!=`
  to the same `.neq` as `~=`, and `!=` is the spelling **271** tracked files
  use; without it `a != nil` lexed as an unwrap `a!` followed by `= nil`. `&`
  (amp), binary `~` (xor) and `|>` (pipe_gt) were likewise absent while `|`
  was present, and the six compound assignments `plus_assign`…`caret_assign`
  had no rule at all, so `sub -= 1` parsed as `sub -` then `= 1`.
- **`@` was capped at two path segments** (`@comp.define.derive` had no rule)
  and its argument list was the raw regex `/[^)]*/`, which stops at the first
  `)` — so `@comp.assert(@comp.satisfies(P, "H"), "…")` ended mid-argument.
  Arguments are ordinary expressions now, and a directive argument may also be
  a whole function, which is what 22 files write as
  `@comp.define.derive("Name", generate(meta) -> str … end)`.
- **`@{ … }` had no rule in either position**, though CLAUDE.md §0.4 names it
  as the descriptor form.
- **Long strings could not contain a `]`.** The body pattern was `/[^]]*/`, so
  `@c.emit([[ … a[i] … ]])` ended at the first index expression and took the
  rest of the file with it. A `]` is body text unless the next character is
  also `]`; stated as an alternation, not a lookahead, because tree-sitter's
  token DFA has none. Controlled against the greedy failure mode: two long
  strings in one file still lex as two, because `]]` can never be consumed as
  body.
- **`.field` in value position** — `has(.err)(r)`, `map(users, .name)`,
  `t:sort(.key)` — 35 files. It is given the LOWEST precedence of anything that
  can consume a `.`, so a dot that could extend a dotted name or attach to the
  expression on its left still does.
- **A bodyless declaration** (`@ffi("llabs")` then `llabs(n: i64): i64`, 43
  files) requires an attribute list, and that requirement is what keeps it
  safe: a bare signature with no body is otherwise indistinguishable from one
  whose body follows.

### The method that made the decisions decidable

The previous pass stopped at 93.8 % saying the remaining files needed
ambiguity DECISIONS rather than rules. They did — but the decisions were not
judgement calls, because **`duo check` is an oracle and it was not consulted.**

Running the compiler over all 53 failing files, and comparing the line of its
FIRST error against the line of tree-sitter's first error, partitions them
exactly:

- **45 GAP** — the compiler parses past the point tree-sitter fails at, so the
  grammar is missing something real.
- **3 BADSRC** — both fail on the same line. The file is broken; refusing it is
  correct.
- **4 EARLIER** — the compiler fails before tree-sitter does, so the file was
  already broken upstream of the construct in question.
- **2 lexer rejects** — `duo check` dies with `UnexpectedChar` and no line at
  all.

Every rule added below was then probed against the compiler in isolation before
it was written. That is what kept three plausible clusters out, and each of
those is a decision this pass is making explicitly.

### The clusters, and the reading each one got

**Expression-body lambda — §5 is law, and it stops at the expression.**
Pass 100 §5 writes `connect = (host: str, port: u16 = 443, tls: bool = true)`
and states "A one-expression body IS one line (mandatory)", so `less = (a, b) a < b`
is the canonical spelling of a one-expression function and `… end` is the
variant. Added.

`(v) return v * 2` is NOT added, and that is the same decision rather than an
exception to it. `duo check` rejects it — `expected ')', got 'return'` — and
§15 graveyards the trailing `return expr`. Three tracked files
(`stdlib_smoke`, `stdlib_expanded_test`, `stdlib_comprehensive_test`) write it
and therefore do not compile; recognising it would have made the editor accept
programs the compiler refuses. The corpus was NOT the tiebreaker here, and if
it had been, the wrong rule would have landed.

`prec.dynamic(-1)` is what makes the lambda safe. `(a) - 1` is a subtraction
and `(f)(x)` is a call — both readings are structurally valid, so the lambda
has to LOSE by default and win only where nothing else parses: `(a, b) …`,
`() …`, `(x: T) …`, none of which can be a parenthesized expression. Static
`prec` cannot express this; it resolves at the `(`, which is the same trap that
cost the previous pass 56.4 % → 24.7 %.

**`type` — graveyarded as a keyword, so the function name is the reading.**
Not "mutually exclusive spellings": `duo check` accepts BOTH `type X = i64` and
`type(o: any): any`. The exclusion was this grammar's lexer, because a
tree-sitter keyword token beats `identifier` in every state that admits both.
Measured over the tracked corpus:

| spelling | uses |
|---|---:|
| `type X = T`, statement-initial | **0** |
| `type(` as a call or declaration head | **231** |

CLAUDE.md §1 denies `type X = type(` by name and Pass 100 §15 lists `type`
among the retiring keywords, so the count and both authorities agree.
`type_definition` is removed — the only rule this pass retired, and measured
before removal per the standing rule. `queries/highlights.scm` dropped `"type"`
from its keyword list in the same change, because highlighting it as a keyword
would now contradict the tree.

**`#` and `//` comment openers — the files are wrong, not the grammar.**
`src/lexer.zig` recognises `#` only as `#!` at index 0 and lexes `//` as
`slashslash`; neither is a comment. `duo check` confirms it, rejecting both
`examples/pass15_vertical_proof.duo` (`#`) and `examples/pass7/explain_smoke.duo`
(`//`) with `error: UnexpectedChar`. §15 does graveyard `//`, but as an
OPERATOR — and it has 0 corpus uses in that role either. Deliberately left
unrecognised: a syntax front-end that accepts what the compiler cannot lex is
worse than one that agrees with it.

**`macro … \`do` — graveyarded, and the cost is on the other 756 files.**
Pass 100 §15 graveyards "function/class/import/match/try/trait/**macro**/
ternary syntax". Three tracked files use it and `duo check` accepts all three,
which is the same argument that keeps `match` and `enum` in this grammar — so
this one is a genuine cost decision rather than a spec reading. The unquote
these files need (`,x` inside a quoted body, `\`(,x + ,x)`) has to live in
`expression`, where it makes EVERY comma-separated argument list in the corpus
ambiguous. Three files against that is not worth it. Left unrecognised.

**Newline as the separator — §7 X8, and the corpus cites it.**
`examples/spec100/x8.duo` opens by quoting the rule: ">=2 named fields -> one
per line, always", which makes the comma the optional element and the newline
the canonical one. Applied to record types, table constructors and descriptor
constructors alike, since `duo check` accepts all three. The same change makes
the EMPTY record legal (`alias M = {}`, `type Empty = {}`), which it is.

**Binding conditions — §6, with one honest limitation.**
`if v, err = parse(s) …` and `while b = cursor:next() …` are §6 law and were
unparseable. Added. What the grammar does NOT express is the guard chain's
split: §6 says `while b = pull() and small(b)` binds `b` to `pull()` alone and
treats the `and` as a correlated guard, but `expression` already owns `and` at
`prec.left(10)` and excluding it needs a parallel expression hierarchy. The
files are recognised and the trees are well formed; the binding EXTENT is a
semantic fact this grammar does not carry, which `guard.duo` itself says has to
be checked by value.

### The one defect the percentage still hides

**Three or more stacked bodyless declarations degrade after the second.**
`@ffi("a")\nf1(): i64` repeated five times yields two `foreign_declaration`
nodes and then loose `expression_statement`s. It is not a missing rule: the
reading "a declaration whose body has not started yet" cannot be discarded
until an `end` or EOF arrives, so one GLR stack version is spent per
declaration and tree-sitter's budget (~6) runs out. **The pristine `HEAD`
grammar produces exactly the same 2-of-5**, so this is pre-existing and was
simply never looked at. It is what keeps `lib/std/fs_watch.duo` (12 stacked
`@ffi` declarations) and `examples/benchmark.duo` unrecognised, and both were
failing before this pass too.

Three repairs were tried and rejected with evidence: raising
`foreign_declaration`'s dynamic precedence above the bare declaration's fixes
the stacking and breaks the ordinary `@export f(): i64 … end` case; lowering it
fixes nothing; merging the two rules into one with an optional body does not
generate. Recorded rather than papered over.

  `parser.c` fails on `stdlib.h` and every file reports unparseable, a 0/N that
  reads as catastrophic regression and is a missing environment variable;
- fails if `tree-sitter` is absent rather than skipping;
- runs `tree-sitter generate` and fails on a non-zero exit — the thing
  `scripts/setup-nvim.duo` used to swallow — **and** on an "unnecessary
  conflicts" warning, so the conflict list cannot silently rot;
- parses every tracked `.duo` file and reports recognised/total/percentage;
- ratchets on a CEILING of unrecognised files (15), not a floor of recognised
  ones, so deleting a `.duo` file cannot redden it while a grammar regression
  or a new unreadable file does;
- **positive-controls its own detector on every run**, writing one valid file
  and one with a deliberate syntax error and refusing to trust its count unless
  the valid one is recognised AND the broken one is not.

That control caught two real defects in the gate while it was being written.
`SDKROOT='…' cd dir && tree-sitter …` binds the variable to the `cd` alone, so
every command returned empty and `to(i64)("")` made it a confident **0**; and a
`$PWD/` prefix on an already-absolute temp path made tree-sitter print nothing,
which the counter also read as "recognised". Both would have produced a green
gate measuring nothing.

Proof it can redden, both directions:

- a tracked file with a deliberate syntax error → `recognised 744 / 760
  (97.8 %), unrecognised 16, ceiling 15`, `FAIL`, exit 1, and it names the file;
- one `conflicts:` entry deleted → `FAIL — tree-sitter generate exited 1`,
  the conflict text printed, exit 1.

### The proofs, re-run at the end

- `tree-sitter generate` **exits 0** with no warnings, and is **idempotent**:
  `src/grammar.json` byte-identical on a second run.
- `src/parser.c` compiles — `xcrun clang -shared -fPIC -Isrc`, 2.3 MB dylib.
- **All 94 `conflicts:` entries are necessary.** A script drops each in turn and
  re-runs the generator; an entry counts drop-safe only if the run exits 0 AND
  prints no "unnecessary conflicts" warning. 94 necessary, 0 drop-safe. Entries
  that became unnecessary as broader ones landed were removed, not left.
- **All four `queries/*.scm` compile.** `highlights.scm` needed two repairs
  that the grammar change forced: `"type"` is no longer a node type, and a
  table's entries are `table_entry` nodes now, so the key is matched with an
  anchor (`(table_entry . (identifier) @property)`) — which is strictly better
  than the old `(table_constructor (identifier))`, since that also highlighted
  values.
- Trees spot-checked BY SHAPE, not just for absence of errors: `req "std.os"`
  is one `call_expression`; `less = (a, b) a < b` is a `lambda_expression` with
  a `body` field; `while b = pull()` carries a `binding_condition`; `type(o)`
  is a `call_expression`; newline-separated record fields are separate
  `record_field` nodes.

## How it is accounted for until then

Three separate ledgers touch it, and none of them said "authored JavaScript":

- `docs/spec/corpus.md` classifies `.duo` files only — `audit100` lists the
  corpus with `git ls-files '*.duo'`, so a rule naming a `.js` path would be
  dead data in that manifest, not an accounting.
- `audit100`'s `nonduo` row counts it as **1 of 536** tracked non-`.duo`,
  non-`.md` files, indistinguishable from a `.wast` fixture.
- `scripts/language_census.duo` (G11) counted `.duo`, `.zig`, `.lua`, `.c/.h`
  and `.sh/.py`. **`.js` matched no pattern**, so three tracked JavaScript
  files — `ext/tree-sitter-duo/grammar.js` (804), `docs/theme/custom.js` (97),
  `ext/vscode-duo/extension.js` (81), 982 lines — were invisible to the census
  whose headline is "no language but Duo", and `docs/RELEASE_STATUS.md` could
  call the census "otherwise clean" without either claim being checked.

Closed in this pass: G11 now counts `.js` as a second **DEBT** line, ratcheted
at its current count of 3 (`CENSUS_JS_FLOOR`). It is debt rather than
sanctioned because a sanctioned generated artifact has to name its generator,
and none of the three has one.
