# GAP-121 — Native module initialization blocks real Idol compiler modules

**Status:** OPEN · **Filed:** !2026-08-09T20:08:52Z
**Priority:** P0 · **Kind:** native_lowering_gap
**Filed by:** codex_shc_priority
**Files:** lib/compiler/parser.id,examples/pass16_parser_corpus_proof.id,src/codegen.zig

## Filed counterexample

At filing, the SH-04 proof compiled
`std.compiler.parser.proj_program` through the normal generated-C path and then
exited 139 before any comparison. Generated C called the static function while
module globals were initialized only by `duo_mod_std_compiler_parser`; direct
static dispatch had no dependency edge to that initializer.

The required repair is a module dependency and initialization contract. A
`req` or `lua_Value` fallback is not a repair: semantic module identities and
their demanded initialization must reach realization directly.

## Partial scalar bridge

Commit `cb2d22d` recorded each scalar identity actually emitted by an embedded
module and allowed cross-module projection only for that exact identity. The C
bootstrap parser proof then moved from exit 139 to exit 0, with boxed token
field reads falling from 220 to zero. This is a useful bootstrap bridge, but it
does not make module initialization authoritative in Idol and does not close
this gap. The implementation remains in `src/codegen.zig` and is deleted with
that bootstrap owner.

## Current dependency order

Forced-direct SH-04 now fails earlier at `keyed-table-export`: the real parser
corpus requires a demanded immutable module table and iteration before the
initializer edge can be exercised again. GAP-127 records that ordering. Do not
shrink the parser proof, hide the corpus in generated constants, or count the
passing generated-C bridge as direct compiler-B authority.

After native immutable-table realization lands, retest the original boundary.
Closure requires a graph-owned module application/dependency identity, an
explicit initialization demand, direct execution without boxed module state,
and a negative control proving a static consumer cannot run before its demanded
module initialization.

## 2026-09-05 the defect is live, quieter, and now measured

The filed counterexample cannot be rerun: `examples/pass16_parser_corpus_proof.id`
is not in the tree, and on a Linux aarch64 host the direct backend refuses
`DNB004` before lowering, so neither the exit 139 nor the `keyed-table-export`
refusal GAP-127 recorded is reachable here. What IS reachable is the same defect
class, reproduced in six lines and executed:

```text
declared.id   global base = 40 ; pick(n) = base + n
use.id        main = declared.pick(2)

idol dump-c use.id | cc      exit 2      # 40 was never placed
```

The consumer is emitted, the storage is emitted, and the INITIALIZER is not:
`static int64_t duo_g_declared_base;` — a `__DATA,__bss` zero the caller cannot
tell from a computed value. This is worse than the filed exit 139, because a
crash names itself and this answers.

The measurement that identifies the cause is an AGREEMENT across three spellings
of one module fact. `base = 40` — the Lua-compatibility assign — exited 42.
`global base = 40` and file-scope `local base = 40` — the canonical declaration
faces — exited 2. `embedded_module_scalar_const_assign` and its `str` companion
read only `.assign`, while `module_top_level_assigns` beside them had already
been widened to read all three as one module-scope fact. So a source SPELLING
selected the realization after resolution had agreed on the value, and the
canonical face is the one that lost.

`src/codegen.zig` now reads the declaration face for the initializer question
too, and the non-constant class fails closed instead of emitting the zero word:
a module global whose initializer is not a load-time constant, in a module that
emits no `duo_mod_*` thunk, is refused by name rather than realized as zero
(`law.fallback.zero`).

`gate/gap-121-module-init.sh` executes all five arms and PASSES with
`same=42 declared=42 scoped=42 assigned=42 computed=refused`. The same-file arm
is the positive control; `computed=refused` is the negative control this gap's
closure paragraph asks for, in the only form the C bridge can supply.

Blast radius, measured over `examples/*.id` + `lib/compiler/*.id` at `1bfbca1f`:
182 files emit C before and after, the same 182, and exactly two emissions
change. Both move toward the value the source declares —
`duo_g_contracts_contract_count = 0` (no behaviour change) and, in
`lib/compiler/comptime.id`, `duo_g_compiler_comptime__pos = 1` and
`__src = ""` where the tree had 0 and NULL. The compiler's own comptime cursor
was starting off by one and its source pointer was the `strcmp` NULL this file's
existing comment already describes.

## What this does NOT close

The bridge repair is bootstrap-scoped and dies with `src/codegen.zig`. Direct
realization is unchanged and still has no module initialization contract:

- `helper.add(40, 2)` refuses `call_direct/call-target-unknown` (wasm) and
  `call-target-not-in-module` (C99 realizer). The graph is COMPLETE for it —
  `idol graph` publishes the `helper` module node, its `add` relation, the
  application with `target: {card: one}`, and the `idol_helper__add` linkage —
  but `countModuleFunctions` in `dnir_lower.zig` enumerates the local
  `ast.Module` only, so the callee is not in the DNIR module the backends read.
- `global base: i64 = seed()` refuses `global-init-not-constant:base`, and the
  graph publishes that application with `caller: 0` — the module home itself.
  The initialization demand is a graph fact ALREADY; DNIR has no relation to
  carry it.

So the two facts closure needs are both published and neither is consumed. The
consuming edge is owned by `src/dnir_lower.zig` (GAP-221) and the cross-partition
link closure by `src/main.zig` (GAP-232); do not duplicate either from here.
Retest this gap's original boundary after a DNIR module-initialization relation
exists, and do not count the passing generated-C bridge as direct compiler-B
authority.
