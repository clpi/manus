# GAP-066 — a file-scope global is DECLARED `duo_g_g` and ASSIGNED `duo_g__g`

**Status:** CLOSED 2026-08-09 · **Filed:** 2026-08-08
**Severity:** hard C-compiler error — `--backend=c` cannot build the program at
all. Loud, not silent, but it blocks the bootstrap/oracle path.

## CLOSURE 2026-08-09 — fixed, and it was hiding a SILENT WRONG ANSWER

**The C mangling is fixed.** `src/codegen.zig` now has ONE mangler,
`global_c_symbol` (plus `p_global_c_symbol`, the write-to-stream form), and the
four promoted-local assignment emitters that spelled
`duo_g_{cname}_{name}` unconditionally now route through it. The declaration
emitter already guarded on an empty module prefix; the assignment emitters did
not, which is the two-rules-for-one-symbol defect this file named. The gap's own
prescription — "One mangling function, called by both emitters" — is what landed.

`native_dense_c_symbol` was the same guarded rule under a specialized name and is
now a one-line forward to `global_c_symbol`, so there is no second copy to drift.

**By value, both backends, name varied per this file's own note** (the defect was
never about the one-character name `g`):

```
g: i64 = 0        · for i = 1,3 / g = g + i · print(g)   c: 6      (was: would not build)
total / count     · same shape, longer names            c: 6 5    (was: would not build)
ratio/name/flag   · f64 · str · bool file-scope globals c: 1.5 hi true
```

## The second defect, found BECAUSE the first was fixed

With the C oracle finally able to build the program, the columns could be
compared for the first time — and `--backend=direct` was **wrong**:

```
for i = 1, 3 / g = g + i    c 6    direct 3      exit 0 both, no diagnostic
for i = 1, 3 / g = g + 1    c 3    direct 0      exit 0 both, no diagnostic
while i <= 3 / g = g + i    c 6    direct 3      NOT a `for` defect
```

This file recorded `--backend=direct` as running that program *"correctly (prints
`3`)"*. **3 is not correct — 1+2+3 is 6.** The misreading survived because no
gate compared the value against an oracle; gap[067] is the same lesson from the
other side.

Root cause: the native-scalar profile gives a file-scope binding no storage, so
each function body treats the name as its own register-resident local — the write
lands nowhere the next read can see, and the read folds to the initializer. The
`while` row proves it is not a loop-lowering defect at all.

Repair: the native-scalar precheck now refuses a module whose file-scope binding
is ASSIGNED by any function (`mod-global-written:<name>`), so the program takes
the honest DNB001 path to the C backend instead of answering confidently wrong. A
READ-ONLY file-scope binding still lowers natively — folding its initializer is
correct when nothing can change it — so the refusal is scoped to the written case
and `zig build native-census` is unchanged at **127**.

Fixtures: `examples/native_differential/unsupported/g066_written_file_scope_global.id`
(C column asserts `6 5`; promote it out of `unsupported/` when the native profile
gives written globals real storage). Caught by the stdout comparison landed for
gap[067] — status alone reads `0 == 0` on every row above.

## The defect

```duo
g: i64 = 0
main = (): i64
    for i = 1, 3
        g = g + i
    print(g)
    0
```

`--backend=c`:

```
/tmp/duo_p.c:107:5: error: use of undeclared identifier 'duo_g__g';
                    did you mean 'duo_g_g'?
  107 |     duo_g__g = 0;
      |     ^~~~~~~~
/tmp/duo_p.c:91:16: note: 'duo_g_g' declared here
   91 | static int64_t duo_g_g;
```

The **declaration** emitter and the **initializer-assignment** emitter mangle the
same name by two different rules. Prefix `duo_g_` + `g` gives `duo_g_g` at the
declaration; the assignment adds a separator that the declaration does not,
giving `duo_g__g`.

`--backend=direct` compiles and runs the same program correctly (prints `3`), so
this is the C emitter alone.

## Note on the name

The reproducer's global is spelled `g`, one character. Whether the defect is
general or needs a short/particular name is **not yet narrowed** — vary the name
before concluding, per `duo-identifiers-collide-with-libc`: a failing probe may
be the NAME, not the form.

Also relevant: `codegen.zig:20852` drops `_`-prefixed names from module exports
(`duo-underscore-is-export-control`). If either mangling path routes through
that logic, the extra `_` may be a *stripped-prefix* artifact rather than a
separator, and the fix belongs there rather than in the mangler.

## How it was found

Observed in passing by the G-D3 ISA agent and not filed; independently
reproduced while narrowing gap[067], where it appeared as the `c` column of the
"for body writes global" row.

## Fix

One mangling function, called by both emitters. Fixture: a file-scope typed
global, initialized and mutated, asserting its printed VALUE on **both**
backends.
