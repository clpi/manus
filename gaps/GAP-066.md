# GAP-066 — a file-scope global is DECLARED `duo_g_g` and ASSIGNED `duo_g__g`

**Status:** OPEN · **Filed:** 2026-08-08
**Severity:** hard C-compiler error — `--backend=c` cannot build the program at
all. Loud, not silent, but it blocks the bootstrap/oracle path.

## The defect

```duo
g: i64 = 0
main = (): i64
    for i = 1, 3
        g = g + i
    print(g)
    0
```

`--backend=c`:

```
/tmp/duo_p.c:107:5: error: use of undeclared identifier 'duo_g__g';
                    did you mean 'duo_g_g'?
  107 |     duo_g__g = 0;
      |     ^~~~~~~~
/tmp/duo_p.c:91:16: note: 'duo_g_g' declared here
   91 | static int64_t duo_g_g;
```

The **declaration** emitter and the **initializer-assignment** emitter mangle the
same name by two different rules. Prefix `duo_g_` + `g` gives `duo_g_g` at the
declaration; the assignment adds a separator that the declaration does not,
giving `duo_g__g`.

`--backend=direct` compiles and runs the same program correctly (prints `3`), so
this is the C emitter alone.

## Note on the name

The reproducer's global is spelled `g`, one character. Whether the defect is
general or needs a short/particular name is **not yet narrowed** — vary the name
before concluding, per `duo-identifiers-collide-with-libc`: a failing probe may
be the NAME, not the form.

Also relevant: `codegen.zig:20852` drops `_`-prefixed names from module exports
(`duo-underscore-is-export-control`). If either mangling path routes through
that logic, the extra `_` may be a *stripped-prefix* artifact rather than a
separator, and the fix belongs there rather than in the mangler.

## How it was found

Observed in passing by the G-D3 ISA agent and not filed; independently
reproduced while narrowing gap[067], where it appeared as the `c` column of the
"for body writes global" row.

## Fix

One mangling function, called by both emitters. Fixture: a file-scope typed
global, initialized and mutated, asserting its printed VALUE on **both**
backends.
