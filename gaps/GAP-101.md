# GAP-101 — indexed WRITE does not lower; it is 8 of the 10 benchmark losses and the idiom migration will not fix it

**Status:** OPEN · **Filed:** 2026-08-09
**Law:** `law.perf.floor` · `law.c.floor` (§47) · §3 MEASUREMENT HONESTY
**Answers:** *"address every possible performance gap"* — the gaps are not many.
They are mostly ONE, and it is small enough to name in a sentence.

## The finding, isolated to two programs

```duo
-- READS a table, indexed by a loop variable
s = s + xs[i]                     -> ok compile   ARM64 native, answer 15

-- WRITES a table, same shape
xs[i] = i                         -> bail site: lowerIndexAssignTarget()
```

**Indexed read lowers. Indexed write does not.** Same table, same index
expression, same loop. The asymmetry is the whole gap.

## Why it costs almost every loss

The benchmark suite, measured 2026-08-09: **25 measured wins, 10 losses.** The
losses are not scattered — 8 of 10 are table-shaped, and a table-shaped kernel
must write:

```
Table max · Table lookup · Table churn · Ring buffer · Fenwick tree ·
Sparse dot · Game of Life                          7 rows, all indexed writes
Levenshtein                                        2D array
Ackermann                                          deep recursion (different)
Cond swap                                          0.000239s (near the floor)
```

So the loss column is not a list of ten independent optimisation problems. It is
**one missing lowering** plus two rows that need their own answers.

## No typed sequence reaches it either

Every spelling of a typed sequence was tried, and none is a way around:

| spelling | result |
|---|---|
| `xs = {}` untyped | `bail: lowerIndexAssignTarget()` |
| `xs: seq(i64) = {}` | `error: direct backend: DNB001: program construct` |
| `xs: [i64] = {}` | `error: expected 'name'` — no such syntax |
| `xs: array(i64) = {}` | `error: direct backend: DNB001` |

The native-array machinery exists (`alloc_slots`, pointer params, scaled indexed
load/store landed under SH-04). **It is not reachable from any source spelling**,
because the one construct that would feed it — the indexed store — bails before
reaching it. Nothing downstream can be measured until this is wired.

## The idiom migration is NOT a performance win, and that needs saying first

The natural assumption — that 227 files of `string.*` are costing native
coverage — is half true and misleading in the expensive direction.

`runtime-global:*` IS the largest first-reported native-scalar bail class,
**11 of 24** (`string` 7, `mem` 2, `os` 1, `io` 1). So the Lua module idiom does
block lowering. But the canonical replacement does not lower either:

```
string.sub(s, 1, 3)   -> bail: native-scalar precheck — runtime-global:string
s:sub(1, 3)           -> bail: method-unresolved:sub   (in situ)
                      -> bail: patchCalls()            (minimal case)
```

Both answer correctly. **Neither lowers.** The precheck RECOGNISES `string.sub`
and refuses it; it does not understand `s:sub` at all.

**Therefore: migrating the 227 files to canonical idiom yields ZERO native
coverage by itself.** Anyone who does that migration expecting a performance
result will have spent the migration and gotten style. The migration is still
right — it is the law, and it is the precondition — but the win only arrives
once `:sub` / `:byte` resolve as value edges in the native-scalar precheck.
**Sequence the value-edge lowering BEFORE the corpus migration**, or the
migration cannot be measured and will be blamed.

This is the GAP-098 peel rule doing its job: the first reported cause was
`runtime-global:string`, and underneath it was `method-unresolved`.

## The worklist, ordered by measured value

1. **`lowerIndexAssignTarget()` — the indexed store.** 8 of 10 losses sit behind
   it, and the read side already lowers, so the shape and the addressing are
   proven. Highest value in the tree by a wide margin.
2. **Value-edge resolution for `:sub` / `:byte` / `:len`** in the native-scalar
   precheck. Unlocks 11 of 24 bails AND makes the idiom migration measurable.
   Must land before the corpus migration, not after.
3. **A typed sequence spelling that reaches the native array.** Blocked on (1);
   worthless before it.
4. `ret-type:any` / `param-type:any` (4 of 24) — gap[099] holds the analysis:
   the guard is already hoisted and nothing specialises under it.
5. `keyed-table-export` (3), `assign-value:nil` (2) — separate, smaller.

Native coverage today: **123 of 191 reachable (64%)**, 68 bails.

## Do not

**Do not raise benchmark bounds to move these rows.** They are not folded, they
are LOSSES — measured, at real durations, with C faster. A bound raise scales
both columns and changes nothing except the appearance of effort.

**Do not report the idiom migration as a performance change** until item 2
lands. Measured today it is zero, and a commit claiming otherwise would be the
§3 failure mode with a new coat of paint.

## CORRECTION 2026-08-09 — indexed write DOES lower. The gap is GROWABLE tables.

The headline above is too broad and is corrected here. Measured:

```duo
xs = { 0, 0, 0, 0 }        xs[i] = i * 2   ->  ok compile, ARM64 native, answer 10
xs = {}                    xs[i] = i       ->  bail: lowerIndexAssignTarget()
```

**A fixed-size table takes an indexed store natively today.** What bails is a
table with no compile-time length — the `{}`-then-append shape every real
kernel uses.

`src/dnir_lower.zig:1735` has three paths and the shape misses all three:

1. **memory-backed** — `ptrSlotOf(ctx, obj)` gives a real scaled `store_index`.
   This is the SH-04 machinery and it is the RIGHT path. `{}` does not reach it.
2. **integer-literal key** — resolves a `name.N` slot directly. Needs a constant
   index, so a loop variable misses.
3. **select-chain** — unrolls one compare-and-store per slot, guarded by
   `if (len == 0 or len > 32) return bail(@src())`.

For `xs = {}` the `name.len` slot is **0**, so path 3 refuses at its first
condition. That single `len == 0` is the whole distance between the benchmark's
table kernels and native code.

## Why this changes the work

The fix is **not** "implement an indexed store" — three implementations exist
and one of them is a real scaled store. It is **routing**: make `{}` followed by
indexed writes allocate a memory-backed table so `ptrSlotOf` succeeds, instead
of falling through to a select-chain that requires a length `{}` cannot have.

That is a bounded change against machinery already landed, not new backend work.
It also has a natural correctness gate: the select-chain path already emits
`emitIndexBoundsTrap`, so the memory-backed path must trap identically — the
comparison is against a lowering that already answers correctly for len<=32.

## What is still true from the original filing

8 of 10 losses are table-shaped, and every one of them builds its table
dynamically, so the loss column does not move until the growable shape lowers.
The typed-sequence spellings (`seq(i64)`, `array(i64)`) remain DNB001 and are
blocked behind the same routing, not behind a missing syntax.

**Method note against myself:** I filed "indexed write does not lower" from one
failing program and did not vary the table's construction. Varying it took one
minute and moved the finding from a whole missing feature to a single `len == 0`
condition. A bail is a property of the PROGRAM SHAPE, not of the operator in it.

## SECOND CORRECTION — "bounded routing change" was too optimistic

The paragraph above says the fix is routing `{}` to the memory-backed path.
Reading the machinery, that is wrong, and the optimism should not stand.

`ptr_slots` — the set `ptrSlotOf` tests — is populated in exactly two places:

```
src/dnir_lower.zig:767    typeIsPtr(par.typ)          a `ptr`-typed PARAMETER
src/dnir_lower.zig:1458   inside materializeTableSlots
```

and `materializeTableSlots` allocates with a **compile-time immediate**:

```
src/dnir_lower.zig:1444   .op = .alloc_slots, .lhs = .{ .i64 = len }
```

So every existing route to a memory-backed table needs a length known at
compile time — the same thing `{}` cannot supply. There is no path to route to.

**The real work is a runtime-sized allocation plus growth**: `alloc_slots` (or a
sibling) taking a computed operand, a capacity/length distinction, and a growth
policy when an index passes capacity. That is new backend capability, not
rewiring. It is still the highest-value item in the tree — 8 of 10 losses — but
it should be sized as a feature, not an afternoon.

**Method, twice in one gap:** first I over-broadened ("indexed write does not
lower"), then I over-narrowed ("just routing"). Both came from reading one layer
and stopping. The peel rule in gap[098] is about bail causes; it applies just as
well to a fix estimate — *read to the allocation, not to the branch that
refused.*

## THIRD AND FINAL READ — memory-backed tables are STACK regions at fixed offsets

Read to the bottom so this is not re-litigated a fourth time.

`alloc_slots` is not an allocator. It is a **compile-time stack reservation**:

```
native_backend.zig:1446   for every alloc_slots instruction, at frame setup
              :1448-1450  n := ins.lhs as .i64, else refuse(@src())
                          refuse unless 0 < n <= 4096
              :1452       bytes := align16(n * 8)
              :1453       refuse if the running total exceeds 32752
              :1454       slot_bases[result] = running offset
              :2153       lowering is emitAddSpImm(dst, off) — sp + a constant
```

Every element of that is compile-time. The size is an immediate (`else =>
return refuse`), the offset is assigned by walking the function before codegen,
and the instruction lowers to *add a constant to the stack pointer*. A runtime
length has nowhere to go: there is no allocation call, no base register to
compute, and the frame is already sized.

**So the ceiling is not `len == 0`, and not `len > 32` either.** It is that
duon's only memory-backed table lives in the FRAME, capped at 32752 bytes —
**4094 slots for the whole function, shared across every table in it.**

### What this rules out, and what it leaves

Raising the select-chain's `len > 32` to hand off to `alloc_slots` was the
obvious next idea. It is worth ~4094 elements and no more, which does not reach
the benchmark's kernels. It would move small cases and leave the loss column
where it is.

The honest requirement is a **heap-backed table**: an allocation whose size is a
computed operand, a base held in a register rather than derived from `sp`, a
capacity/length distinction, and growth when an index passes capacity. And
because it is heap, it lands directly on §0c's memory tiers — a table is exactly
the shape tier 2 (region, bulk free) and tier 3 (RC, Perceus reuse) exist for.

**That is a foundational feature and it is on the critical path to `law.c.floor`.**
C's answer to every one of these ten rows is `malloc` plus a pointer; duon does
not yet have that answer at all, and no amount of routing produces it. Sizing it
as anything smaller has now been wrong three times in this file.

### Standing recommendation

Do not attempt this incrementally under a session budget. It wants a design
pass against §0c first — where the allocation comes from, who frees it, and
what `why(free)(xs)` answers — because the wrong choice here is one that has to
be unmade across every table in the language.

# FOURTH CORRECTION — AND IT INVALIDATES THIS GAP'S HEADLINE

**The benchmark does not use the direct backend.** Its own manifest says so:

```
BENCH_MANIFEST backend=c-specialized ... intermediate=generated-c external_compiler=clang
```

`lowerIndexAssignTarget` is a `--backend=direct` bail. **It cannot be causing a
single benchmark loss.** Everything above that attributes the 10 losses to it
conflates two separate things:

| | measured by | blocked by |
|---|---|---|
| **native coverage** 123/191 | `--backend=direct` | `lowerIndexAssignTarget`, stack-only `alloc_slots` |
| **benchmark losses** 10 | the C backend | *not this — see below* |

Both are real. Neither is the other, and this file spent four sections treating
them as one.

## And duon DOES have a heap-backed growable table

The previous section concluded "duon has no heap-backed table at all". That is
false for the backend the benchmark actually uses. The generated C contains
**zero** `lua_table_set` and instead uses the dense-table runtime:

```c
static inline void duo_dt_set_##sfx(ty** p, int64_t* cap, int64_t i, ty x) {
    if (__builtin_expect((uint64_t)i >= (uint64_t)*cap, 0)) {
        if (i < 0) return;
        duo_dt_grow_##sfx(p, cap, i + 1);
        if ((uint64_t)i >= (uint64_t)*cap) return;
    }
    (*p)[i] = x;
}
static inline ty duo_dt_get_##sfx(ty* p, int64_t cap, int64_t i) {
    return __builtin_expect((uint64_t)i < (uint64_t)cap, 1) ? p[i] : (ty)0;
}
```

A real malloc'd array, geometric growth, a branch-predicted guard, then a raw
`(*p)[i] = x`. That is the answer I said did not exist.

## So what the losses actually are

The overhead against hand-written C is **one predictable compare and a pointer
reload per access**, not a representation gap. The margins agree:

```
Table lookup   duo 0.000425   c 0.000401     1.06x
Table max      duo 0.000597   c 0.000331     1.80x
```

Those are guard-and-indirection numbers. A boxed-table gap would be 10-50x.

## Where the work actually is

Immediately after `duo_dt_get_` in the emitted prelude:

```c
/* Loop versioning guard. An index that is affine in the loop counter takes ... */
```

**The optimization that removes this overhead already exists** — it is the same
`duo_dt_hi_num` machinery gap[099] found hoisted-but-unused. So the question for
every losing row is not "how do we build an array" but:

> **does loop versioning fire on this kernel, and if not, which precondition
> declines?**

That is a measurement against existing machinery, one row at a time, and it is
the correct next step. `zig build bench` plus reading the emitted C for one
losing kernel answers it.

## Method — the failure that produced three wrong answers in one file

I measured a bail with `--backend=direct`, read the loss table from a C-backend
run, and never checked that they were the same pipeline. Every conclusion after
that inherited the error, and each "correction" refined a claim whose premise
was already broken — missing operator, then routing, then a missing allocator,
each more confident and none of them checked against the manifest printed in the
same log I was reading the losses from.

**Check that your cause and your effect were produced by the same pipeline
BEFORE refining the cause.** A correction that does not re-examine the premise
is just a more detailed way to be wrong.
