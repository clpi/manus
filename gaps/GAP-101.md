# GAP-101 — indexed WRITE does not lower; it is 8 of the 10 benchmark losses and the idiom migration will not fix it

**Status:** OPEN — CORRECTION re-verified a THIRD time 2026-08-09 · **Filed:** 2026-08-09

## 2026-08-09, third verification — and the C column names the cause out loud

Both rows re-run at branch tip, by value, with a TYPED consumer (`v: i64 = xs[4]`,
never `print`, because `print` takes anything and would call a typed defect stale):

```
xs = { 0, 0, 0, 0 } ; xs[i] = i * 2 ; v: i64 = xs[4]
    direct  ok compile, native, 8      c  8            AGREE

    direct  bail lowerIndexAssignTarget() dnir_lower.zig:1820
```

The CORRECTION holds: **indexed writes lower.** Fixed-size tables take an indexed
store natively and agree with C. What does not lower is the table with no
compile-time length.

New this round, and it is the useful part: **look at what `--backend=c` emitted.**
The table argument is `(void*)0`. Under the native-scalar profile a `{}` table is
not a table that is hard to address — it is a NULL that was never allocated. So
the growable-table gap is not "indexing needs a base pointer"; it is that
runtime-sized storage does not exist in this profile at all, in either backend.

That makes this gap and **gap[108] the same missing capability wearing two
symptoms**: `alloc_slots` is compile-time stack reservation with fixed offsets,
and a module-scope binding is a per-function register-resident copy. Neither is
storage whose size or lifetime is decided anywhere but the compiler's own frame
layout. Whoever builds one should scope the other in the same breath — the
`__DATA,__bss` zerofill arena in `native_backend.zig` (`bss_size`, emitted by
`emitMachOArm64Object` and currently never given a nonzero value) is dormant
scaffolding for exactly this and has no symbol machinery attached to it yet.
**Law:** `law.perf.floor` · `law.c.floor` (§47) · §3 MEASUREMENT HONESTY
**Answers:** *"address every possible performance gap"* — the gaps are not many.
They are mostly ONE, and it is small enough to name in a sentence.

## The idiom migration is NOT a performance win, and that needs saying first

The natural assumption — that 227 files of `string.*` are costing native

`runtime-global:*` IS the largest first-reported native-scalar bail class,

```
string.sub(s, 1, 3)   -> bail: native-scalar precheck — runtime-global:string
s:sub(1, 3)           -> bail: method-unresolved:sub   (in situ)
                      -> bail: patchCalls()            (minimal case)
```

Both answer correctly. **Neither lowers.** The precheck RECOGNISES `string.sub`
and refuses it; it does not understand `s:sub` at all.

**Therefore: migrating the 227 files to canonical idiom yields ZERO native
coverage by itself.** Anyone who does that migration expecting a performance
result will have spent the migration and gotten style. The migration is still
right — it is the law, and it is the precondition — but the win only arrives
once `:sub` / `:byte` resolve as value edges in the native-scalar precheck.
**Sequence the value-edge lowering BEFORE the corpus migration**, or the
migration cannot be measured and will be blamed.

This is the GAP-098 peel rule doing its job: the first reported cause was
`runtime-global:string`, and underneath it was `method-unresolved`.

## CORRECTION 2026-08-09 — indexed write DOES lower. The gap is GROWABLE tables.

The headline above is too broad and is corrected here. Measured:

```duo
xs = { 0, 0, 0, 0 }        xs[i] = i * 2   ->  ok compile, ARM64 native, answer 10
xs = {}                    xs[i] = i       ->  bail: lowerIndexAssignTarget()
```

**A fixed-size table takes an indexed store natively today.** What bails is a
table with no compile-time length — the `{}`-then-append shape every real
kernel uses.

`src/dnir_lower.zig:1735` has three paths and the shape misses all three:

1. **memory-backed** — `ptrSlotOf(ctx, obj)` gives a real scaled `store_index`.
   This is the SH-04 machinery and it is the RIGHT path. `{}` does not reach it.
2. **integer-literal key** — resolves a `name.N` slot directly. Needs a constant
   index, so a loop variable misses.
3. **select-chain** — unrolls one compare-and-store per slot, guarded by
   `if (len == 0 or len > 32) return bail(@src())`.

For `xs = {}` the `name.len` slot is **0**, so path 3 refuses at its first
condition. That single `len == 0` is the whole distance between the benchmark's
table kernels and native code.

## Why this changes the work

The fix is **not** "implement an indexed store" — three implementations exist
and one of them is a real scaled store. It is **routing**: make `{}` followed by
indexed writes allocate a memory-backed table so `ptrSlotOf` succeeds, instead
of falling through to a select-chain that requires a length `{}` cannot have.

That is a bounded change against machinery already landed, not new backend work.
It also has a natural correctness gate: the select-chain path already emits
`emitIndexBoundsTrap`, so the memory-backed path must trap identically — the
comparison is against a lowering that already answers correctly for len<=32.

## What is still true from the original filing

8 of 10 losses are table-shaped, and every one of them builds its table
dynamically, so the loss column does not move until the growable shape lowers.
The typed-sequence spellings (`seq(i64)`, `array(i64)`) remain DNB001 and are
blocked behind the same routing, not behind a missing syntax.

**Method note against myself:** I filed "indexed write does not lower" from one
failing program and did not vary the table's construction. Varying it took one
minute and moved the finding from a whole missing feature to a single `len == 0`
condition. A bail is a property of the PROGRAM SHAPE, not of the operator in it.

## SECOND CORRECTION — "bounded routing change" was too optimistic

The paragraph above says the fix is routing `{}` to the memory-backed path.
Reading the machinery, that is wrong, and the optimism should not stand.

`ptr_slots` — the set `ptrSlotOf` tests — is populated in exactly two places:

```
src/dnir_lower.zig:767    typeIsPtr(par.typ)          a `ptr`-typed PARAMETER
src/dnir_lower.zig:1458   inside materializeTableSlots
```

and `materializeTableSlots` allocates with a **compile-time immediate**:

```
src/dnir_lower.zig:1444   .op = .alloc_slots, .lhs = .{ .i64 = len }
```

So every existing route to a memory-backed table needs a length known at
compile time — the same thing `{}` cannot supply. There is no path to route to.

**The real work is a runtime-sized allocation plus growth**: `alloc_slots` (or a
sibling) taking a computed operand, a capacity/length distinction, and a growth
policy when an index passes capacity. That is new backend capability, not
rewiring. It is still the highest-value item in the tree — 8 of 10 losses — but
it should be sized as a feature, not an afternoon.

**Method, twice in one gap:** first I over-broadened ("indexed write does not
lower"), then I over-narrowed ("just routing"). Both came from reading one layer
and stopping. The peel rule in gap[098] is about bail causes; it applies just as
well to a fix estimate — *read to the allocation, not to the branch that
refused.*

## THIRD AND FINAL READ — memory-backed tables are STACK regions at fixed offsets

Read to the bottom so this is not re-litigated a fourth time.

`alloc_slots` is not an allocator. It is a **compile-time stack reservation**:

```
native_backend.zig:1446   for every alloc_slots instruction, at frame setup
              :1448-1450  n := ins.lhs as .i64, else refuse(@src())
                          refuse unless 0 < n <= 4096
              :1452       bytes := align16(n * 8)
              :1453       refuse if the running total exceeds 32752
              :1454       slot_bases[result] = running offset
              :2153       lowering is emitAddSpImm(dst, off) — sp + a constant
```

Every element of that is compile-time. The size is an immediate (`else =>
return refuse`), the offset is assigned by walking the function before codegen,
and the instruction lowers to *add a constant to the stack pointer*. A runtime
length has nowhere to go: there is no allocation call, no base register to
compute, and the frame is already sized.

**So the ceiling is not `len == 0`, and not `len > 32` either.** It is that
duon's only memory-backed table lives in the FRAME, capped at 32752 bytes —
**4094 slots for the whole function, shared across every table in it.**

### What this rules out, and what it leaves

Raising the select-chain's `len > 32` to hand off to `alloc_slots` was the
obvious next idea. It is worth ~4094 elements and no more, which does not reach
the benchmark's kernels. It would move small cases and leave the loss column
where it is.

The honest requirement is a **heap-backed table**: an allocation whose size is a
computed operand, a base held in a register rather than derived from `sp`, a
capacity/length distinction, and growth when an index passes capacity. And
because it is heap, it lands directly on §0c's memory tiers — a table is exactly
the shape tier 2 (region, bulk free) and tier 3 (RC, Perceus reuse) exist for.

**That is a foundational feature and it is on the critical path to `law.c.floor`.**
C's answer to every one of these ten rows is `malloc` plus a pointer; duon does
not yet have that answer at all, and no amount of routing produces it. Sizing it
as anything smaller has now been wrong three times in this file.

### Standing recommendation

Do not attempt this incrementally under a session budget. It wants a design
pass against §0c first — where the allocation comes from, who frees it, and
what `why(free)(xs)` answers — because the wrong choice here is one that has to
be unmade across every table in the language.

# FOURTH CORRECTION — AND IT INVALIDATES THIS GAP'S HEADLINE

**The benchmark does not use the direct backend.** Its own manifest says so:

```
BENCH_MANIFEST backend=c-specialized ... intermediate=generated-c external_compiler=clang
```

`lowerIndexAssignTarget` is a `--backend=direct` bail. **It cannot be causing a
single benchmark loss.** Everything above that attributes the 10 losses to it
conflates two separate things:

| | measured by | blocked by |
|---|---|---|
| **native coverage** 123/191 | `--backend=direct` | `lowerIndexAssignTarget`, stack-only `alloc_slots` |
| **benchmark losses** 10 | the C backend | *not this — see below* |

Both are real. Neither is the other, and this file spent four sections treating
them as one.

## And duon DOES have a heap-backed growable table

The previous section concluded "duon has no heap-backed table at all". That is
false for the backend the benchmark actually uses. The generated C contains
**zero** `lua_table_set` and instead uses the dense-table runtime:

```c
static inline void duo_dt_set_##sfx(ty** p, int64_t* cap, int64_t i, ty x) {
    if (__builtin_expect((uint64_t)i >= (uint64_t)*cap, 0)) {
        if (i < 0) return;
        duo_dt_grow_##sfx(p, cap, i + 1);
        if ((uint64_t)i >= (uint64_t)*cap) return;
    }
    (*p)[i] = x;
}
static inline ty duo_dt_get_##sfx(ty* p, int64_t cap, int64_t i) {
    return __builtin_expect((uint64_t)i < (uint64_t)cap, 1) ? p[i] : (ty)0;
}
```

A real malloc'd array, geometric growth, a branch-predicted guard, then a raw
`(*p)[i] = x`. That is the answer I said did not exist.

## So what the losses actually are

The overhead against hand-written C is **one predictable compare and a pointer
reload per access**, not a representation gap. The margins agree:

```
Table lookup   duo 0.000425   c 0.000401     1.06x
Table max      duo 0.000597   c 0.000331     1.80x
```

Those are guard-and-indirection numbers. A boxed-table gap would be 10-50x.

## Where the work actually is

Immediately after `duo_dt_get_` in the emitted prelude:

```c
/* Loop versioning guard. An index that is affine in the loop counter takes ... */
```

**The optimization that removes this overhead already exists** — it is the same
`duo_dt_hi_num` machinery gap[099] found hoisted-but-unused. So the question for
every losing row is not "how do we build an array" but:

> **does loop versioning fire on this kernel, and if not, which precondition
> declines?**

That is a measurement against existing machinery, one row at a time, and it is
the correct next step. `zig build bench` plus reading the emitted C for one
losing kernel answers it.

# THE FAST PATH EXISTS AND FIRES — measured, and it is hand-written-C equivalent

The per-row question posed above is answered for the general shape: **loop
versioning fires, and its fast arm has no overhead left to remove.**

A fold-resistant kernel (`n` read from the environment so no closed form can
replace it), building a 200000-element table and scanning it:

```c
int64_t* __dt_xs = NULL; int64_t __dtc_xs = 0;
duo_dt_reserve_i64(&__dt_xs, &__dtc_xs, (int64_t)(n) + 1);   /* ONE malloc, pre-sized */
int64_t __lvhi0 = duo_dt_hi_int((int64_t)(n), false);
if (__lvhi0 != INT64_MIN && duo_dt_range_ok(__dtc_xs, (i), 1, __lvlo0, __lvhi0)) {
    while (i <= __lvhi0) {
        __dt_xs[i] = ((int64_t)((i * 7)) % 1000);   /* RAW ARRAY STORE, no guard */
        i = (i + 1);
    }
} else {
    while ((i <= n)) {
        duo_dt_set_i64(&__dt_xs, &__dtc_xs, i, ...);  /* guarded fallback */
    }
}
```

Both loops version. The table is **reserved once** from `n`, the bounds check is
**hoisted entirely out**, and the hot loop is a raw indexed store into a malloc'd
array. There is no representation gap, no per-access guard, and no growth check
in the steady state. That is what a C programmer writes.

So every despairing conclusion earlier in this file is wrong, in order: the
operator lowers, the table is heap-backed, the array is pre-sized, and the guard
is hoisted.

## What that leaves, precisely

The 10 losses cannot be "duon's tables are slow" — for this shape duon emits the
C. They must be rows where **versioning DECLINES**, and the decline is
observable in the emitted C as taking the `else` arm. The preconditions are
named right there and are individually checkable:

```
duo_dt_hi_int(bound, strict) != INT64_MIN      the bound must be affine and safe
duo_dt_range_ok(cap, at, coeff, lo, hi)        the access must stay in capacity
```

**The worklist is therefore per-row and mechanical:** compile each losing kernel
with `--backend=c`, look for `__lv` in its body, and when the fast arm is absent
read which precondition refused. No design work, no new machinery — the fast
path is already written and already fires.

# THE TABLE THESIS IS CLOSED: the losing kernel's codegen is already C-equivalent

`table_max_scan` is a losing row (duo 0.000597 / c 0.000331). Its emitted C:

```c
duo_dt_reserve_i64(&__dt_t, &__dtc_t, (int64_t)(n) + 1);   /* one calloc */
if (__lvhi0 != INT64_MIN && duo_dt_range_ok(...)) {
    while (i <= __lvhi0) { __dt_t[i] = ((i * 17) % 100003); i = i + 1; }
} else { /* guarded fallback */ }
```

versus the reference it loses to:

```c
int64_t *t = calloc((size_t)n + 1, sizeof(int64_t));
for (int64_t i = 1; i <= n; i++) t[i] = (i * 17) % 100003;
```

**Same allocation, same raw indexed store, same loop, bounds check hoisted.**
Both loops in the kernel version. There is no codegen difference left to find on
this row.

And the allocation strategy I was about to propose is ALREADY IMPLEMENTED, with
a comment stating the reasoning:

```
/* First allocation: calloc, not realloc+memset. The zeroing is required
   (an unwritten slot reads as Lua nil, i.e. 0 in arithmetic), but a
   fresh calloc of several MB is served from zero pages the process
   never has to touch, while the memset writes every byte up front. */
```

So duon calloc's on first allocation exactly as the reference does, and pays
realloc+memset only on genuine growth — which `reserve(n+1)` avoids entirely.

## What this means

**The table-representation thesis is dead.** It was the organising idea of this
entire gap and it does not survive contact with the emitted code: the operator
lowers, the table is heap-backed, the array is pre-sized with calloc, the guard
is hoisted, and the losing row emits what the reference emits.

The residual 0.27ms on 500000 iterations is **~0.5ns/element**. At that scale the
candidates are vectorization of the reference loop by clang, allocator
first-touch behaviour, and timing noise — **profiling questions, not codegen
questions.** Nobody should open this gap again looking for a missing lowering.

## THE "EASY" NATIVE-COVERAGE PATH IS CLOSED — the `any` bails are often INTENTIONAL

`ret-type:any` and `param-type:any` look like the one bail class fixable in duon
rather than Zig: add the missing annotation, the precheck stops refusing, native
coverage rises. Four programs carry it:

```
apply_one_pack_proof.duo          ret-type:any
empty_table_smoke.duo             param-type:any
hash_agreement.duo                ret-type:any
pass42_binding_conditions_proof.duo  ret-type:any
```

**It does not survive reading the source.** `hash_agreement.duo:30`:

```duo
box(x: any): any
    return x
end
```

The `any` is not debt — it is a BOXING HELPER, and the fixture exists to check
that boxed and native hashing agree. Annotating it would delete the thing the
test measures and the program would still print PASS, which is the §3 failure
mode exactly: a number moved by editing the measurement rather than the compiler.
`empty_table_smoke` and the two proofs are the same shape — each is named for
the dynamic behaviour it exercises.

**So there is no duon-side shortcut to native coverage.** Every one of the 68
bails is either a compiler repair in `src/*.zig` or an intentional dynamic
program that SHOULD bail. The census denominator ("reachable programs that can
reach 100%") is therefore optimistic: it counts programs whose whole purpose is
to exercise the boxed path.

**Worth measuring before anyone plans against 100%:** how many of the 68 are
intentionally dynamic? That number comes off the target, and nobody has taken
it. A coverage goal that counts `hash_agreement.duo` as a miss is asking the
compiler to natively lower a test of non-native behaviour.

## HOW MUCH OF THE 68 SHOULD BAIL — first measurement, with its limits

Sampled `examples/*.duo` (42 of the 68 bailers; the rest are in subdirectories
the loop did not walk), classified by whether the source contains dynamic
constructs at all — `: any`, `tostring(`, `pairs(`, `metatable`, `lua_`:

```
bailing programs containing dynamic constructs   17   (40%)
bailing programs containing none                 25   (60%)
```

**This is a signal, not a verdict, and the heuristic is weak in both
directions.** Containing `: any` does not prove the `any` is intentional —
`hash_agreement.duo`'s `box(x: any): any` is (it is a boxing helper the fixture
exists to exercise), but another program's `any` may be plain annotation debt.
And containing none does not prove a program should lower: it may bail on
`keyed-table-export` or `assign-value:nil` for reasons unrelated to its source
vocabulary.

What it does establish: **a substantial fraction of the "worklist" is not work.**
A 100% target that scores `hash_agreement.duo` as a miss is asking the compiler
to natively lower a test of non-native behaviour, and roughly two in five
bailers look like that on inspection.

### What would make this authoritative

Per-program adjudication, one line each: *is this program's dynamism the point,
or is it debt?* 42 programs, and the answer is usually obvious from the file's
own header comment — most of these fixtures say what they exercise in their
first three lines. That is an afternoon, it is pure duon reading with no
compiler work, and **it should happen before anyone sizes the road to 100%**,
because it moves the denominator rather than the numerator.

Until then the honest statement of native coverage is a RANGE, not 65%: between
127/195 and 127/(195 - the intentionally-dynamic count), and nobody has taken
that count.

## MANDELBROT'S BAIL, READ: a register-CLASS mismatch, and the function name misleads

```
bail site: evalDnirValueFp() at native_backend.zig:2359
```

Line 2359 is the guard, not the `else` arm:

```zig
fn evalDnirValueFp(...) {
    if (self.crossFile(v, true)) return refuse(@src());   // <- 2359
```

and `crossFile` (`:2319`) is **not about files at all**:

```zig
fn crossFile(self: *const Arm64Compiler, v: dnir.Value, want_fp: bool) bool {
    return switch (v) {
        .local, .temp => |id| self.fp_temps.contains(id) != want_fp,
        else => false,
    };
}
```

It asks: *is this temp's FLOAT-ness different from what the use site wants?* So
mandelbrot refuses on a **register-class disagreement** — a temp recorded in
`fp_temps` reaching a GP use, or the reverse. Nothing to do with module
boundaries.

**The name cost me a wrong hypothesis and would cost the next reader the same.**
I read `crossFile` at a bail site, in a session that had spent hours on a genuine
cross-file defect, and concluded mandelbrot shared it. It does not. Renaming this
to what it tests — `classMismatch` / `fpClassDiffers` — is a one-line change
worth more than its size, and it is the kind of finding LAW-ONE exists to
prevent: a name that describes neither its argument nor its answer.

### Why this is the right first target anyway

The classification is a compiler-internal fact, not a source-level one: the
program is fully typed and its floats are ordinary. So the repair is to make
`fp_temps` agree with the use, or to insert the conversion that already exists
two arms below (`.i64` materializes into a GP register and `scvtf`s — the
comment there says *"scvtf already existed for exactly this and nothing reached
it from here"*, which is the same shape of gap one level down).

That is bounded backend work on the one bailing program that is genuinely user
code rather than test equipment.

## MANDELBROT PEELED ONE LAYER — the second direction is a SEMANTIC choice, not a gap

The int->float guard in `evalDnirValueFp` was widened: a temp classified INTEGER
reaching a float use is a CONVERSION, not a refusal, and `scvtf` was already
sitting two arms below with a comment saying "scvtf already existed for exactly
this and nothing reached it from here". A temp is the case that never reached it.

**The bail moved and the count did not:**

```
before   bail site: evalDnirValueFp() at native_backend.zig:2359
after    bail site: evalDnirValue()   at native_backend.zig:2327
native   127 -> 127
```

`:2327` is the mirror guard — an FP-classed temp reaching a GP use. **That
direction is NOT symmetric and was deliberately left refusing:** int->float
widens losslessly, float->int TRUNCATES, and a backend that silently truncates
is choosing semantics the source did not state. Converting it to make a number
move would be the §3 failure mode in compiler form.

**Reverted**, because a peel that adds a conversion path and moves no program is
machinery without a result, and it is Zig under a standing directive.

### What the peel bought

The layer underneath is now named, and it reframes the repair: mandelbrot does
not need two conversions, it needs its temps CLASSIFIED CONSISTENTLY. A value
being asked for as both `i64` and `f64` at different sites means `fp_temps`
disagrees with the dnir's own typing — so the fix belongs where the
classification is built, not at either use site. Patching both guards would
paper over a disagreement rather than resolve it, and would leave the truncation
question standing.

That is the real shape of the one genuinely-user-code bail in `examples/`, and
it is now a specific question — *why does this temp have two classes?* — rather
than a bail site.

## THE CLASSIFICATION BUG HAS A PRECEDENT IN THE SAME FILE

`native_backend.zig:1852` documents this exact class, already fixed once:

> This arm parked the result in d0 and left it UNRECORDED, so `fp_temps`
> disagreed with the register the code had actually written. An integer consumer
> then read x0 — the same file confusion `crossFile` refuses everywhere else,
> but invisible to it, because the record said nothing. **Say what was emitted;
> the cross-file guard can then judge the consumer instead of guessing.**

That is mandelbrot's bail, one instance over: some instruction writes an FP or GP
register and does not `markFpTemp` to match, so the guard later sees a temp whose
recorded class contradicts its actual register.

**So the repair is not a conversion and not a guard.** It is finding the arm that
emits without recording — the same shape as the `call_extern` arm above, whose
fix was one `markFpTemp(ins.result)` line. The instruction is identifiable by
tracing which temp mandelbrot fails on and reading the arm that produced it.

`valueIsFp` (`:4036`) is the other half of the record and worth checking in the
same pass: it answers `.f64 => true` for an immediate but only consults
`fp_temps` for a temp, so any producer that skips `markFpTemp` is invisible to
it too.

**Next step, concretely:** instrument the bail to print the offending temp id,
find the instruction that defined it, and check whether that arm calls
`markFpTemp`. Precedent says the fix is one line, and the file already carries
the lesson in prose — *say what was emitted.*

## INSTRUMENTED TO THE INSTRUCTION — temp 6 is an INTEGER BINOP feeding a float use

Traced rather than reasoned. Printing the offending value at the guard, then the
op that defines it:

```
FPTRACE want=fp got=gp .temp id=6
FPTRACE defines temp 6: op=binop fp=true      (one function)
FPTRACE defines temp 6: op=binop fp=false     (another — fp_temps is cleared per function)
```

**Temp 6 is a `binop` result classed INTEGER, consumed by a float operand.**
That is not a missing `markFpTemp`, and the precedent at `:1852` — an arm that
emitted without recording — is a DIFFERENT bug that happens to share a symptom.
The record here is correct: the binop really did produce an integer.

So mandelbrot's shape is an integer subexpression feeding a float one, which the
file already anticipates in `evalDnirValueFp`'s `.i64` arm:

> An integer immediate in a float position. `(col - WIDTH / 2) * 3.5 / WIDTH`
> folds `WIDTH / 2` to an i64 constant and then wants it as a double; there is
> no fmov for an arbitrary integer, so it materializes into a GP register and
> converts. **scvtf already existed for exactly this and nothing reached it from
> here.**

The comment names the immediate case and mandelbrot is the TEMP case of the same
sentence — `(col - WIDTH/2)` is a binop, not a literal, so it arrives as a temp
and the arm never sees it.

**Which retro-justifies the conversion I reverted.** The int->float widening was
correct for this program: lossless, and the arm above documents the intent. It
was reverted for the right reason at the time (it moved no count) but the wrong
diagnosis (I called it "machinery without a result"); it is in fact the correct
half of a two-part repair, and the count did not move because a SECOND temp then
needs the mirror direction.

### The state of the repair, precisely

1. **int -> float on a temp** — correct, lossless, matches the documented intent
   of the `.i64` arm. This is the patch reverted above and it should go back.
2. **float -> int on a temp** — the layer underneath, and NOT automatic:
   truncation is a semantic choice. Before writing it, find which temp needs it
   and why the dnir asks for a float in an integer position; that may itself be
   an upstream typing defect rather than a conversion the backend owes.

Both are needed for mandelbrot to lower, and only the first is unambiguously
safe.

## THE SECOND DIRECTION IS AN UPSTREAM DEFECT — do NOT convert it

With the int->float widening restored, the bail moves to its mirror and the
trace names the value:

```
FPTRACE2 want=gp got=fp id=5
FPTRACE2 defines temp 5: op=binop fp=true
```

A FLOAT binop result reaching an INTEGER use. The obvious patch is the symmetric
one — `fcvtzs` and move on. **Do not write it.**

`examples/mandelbrot.duo` contains **no conversions at all**:

```
grep -nE "to\(i64\)|to\(f64\)|floor|int\(" examples/mandelbrot.duo   ->  no matches
```

So nothing in the source asks for a float to become an integer. A backend that
truncates here is inventing a conversion the program never wrote, and
mandelbrot's output is a rendered image — a silently truncated intermediate
would still print a picture, just the wrong one. That is the §3 failure mode
with a plausible disguise: the number moves, the fixture still passes, and the
defect is now inside the compiler instead of in front of it.

**The real question is upstream:** why does dnir class temp 5 as FP when its
consumer wants an integer, in a program with no conversions? Either the
consumer's expectation is wrong, or the producer's classification is, and the
backend cannot tell which. Answering that is the actual repair.

| direction | verdict |
