# GAP-091 — a declared contract was enforced only by the backend nobody uses

**Status:** `@noalloc` and `@pure` CLOSED; `@noreturn` OPEN · **Filed:** 2026-08-09
**Law:** Pass 103 §0b (`--backend=direct` IS the path) · H-8 output totality
**Branch:** `canonical-to-relation` · **Parent:** GAP-090 findings 2 and 3

## What was measured, not inherited

GAP-090 reported `@noalloc` as unenforced. The measurement was right and the
diagnosis was one level short. Re-measured at the parent commit:

| invocation | exit |
|---|---|
| `duo check   examples/pass7/noalloc_fail.id` | **0** |
| `duo compile examples/pass7/noalloc_fail.id` | **0** |
| `duo compile --backend=direct … noalloc_fail.id` | **0** |
| `duo compile --backend=c      … noalloc_fail.id` | **1** |
| `duo explain examples/pass7/noalloc_fail.id` | **0**, rejection printed as JSON |

The check was not missing. `codegen.zig`'s `guardNoAlloc` fires at five emit
sites and works. It only runs while the **C backend is writing the allocation**,
and the default backend is `direct`. So the contract held on the oracle path and
nowhere else — `--backend=c` was the only red in the table, and it is the path
Pass 103 §0b names as *not* the shipping one.

The deleted Zig test asserted `error.NoAllocViolation` out of
`explain_pipeline.runForProvenance`, which reaches `emit_module` and therefore
reached the guard. That is why it was green for its whole life while the product
was not: **the test entered through the one door that was locked.**

## The repair

A declared contract is a semantic fact about the graph, not a property of one
emitter. The scan moved to `parse_and_check` in `src/main.zig` — the single
funnel every verb shares — so `check`, `compile`, `run` and `explain` agree
without any of them knowing a backend exists.

What a user sees now, on `duo check examples/pass7/noalloc_fail.id`:

```
examples/pass7/noalloc_fail.id:3:25: error: @noalloc violated in function 'leak': heap allocation at mem.alloc
  |
3 |     raw: *u8 = mem.alloc(64)
  |                         ^
hint: Remove @noalloc from the function if heap allocation is required [preserve_dynamic]
hint: Use stack storage or a caller-provided buffer instead of mem.alloc [allocate_output_separately]
error: 1 contract violation(s)
```

The two hints are the **same `repair_candidate.catalog` rows** the explain JSON
renders as `repair_candidates`. One taxonomy, two projections — H-8 rather than
a second hand-written message.

`explain` is the one verb that still RENDERS. Its job is to project the graph,
and the rejection plus its repair set is part of that projection; the missing
piece was the exit, not the render. It diagnoses, finishes the JSON, exits 1.

**Deliberately NARROWER than `guardNoAlloc`.** The scan reports the four `mem.*`
intrinsics and not `closure.malloc` (codegen only allocates a closure that
captures upvalues; reproducing that decision would reject closures the backend
accepts) or `dense_table.alloc` (a sema-inferred representation choice, not a
written allocation). Strictly narrower means it can never reject a program the C
backend accepts, and the C path still catches the rest.

### `@pure` was not decorative — it was a wrong-answer generator

`codegen.zig` lowers `@pure` to `__attribute__((const))`, which promises the C
compiler the body reads nothing but its arguments. Nothing checked the promise.
Measured by VALUE, by running it:

```
seed: i64 = 7
@pure
peek(x: i64): i64   seed + x

a = peek(1)     -- 8
seed = 100
b = peek(1)     -- 8.  The right answer is 101.
```

The C compiler cashed the unchecked promise and reused the first result. This is
the §3 measurement-honesty failure mode in the compiler rather than in the
benchmark suite: an unverified `use_*`-shaped assertion handed straight to the
optimizer.

`@pure` is now diagnosed when the body reads or writes **mutable module state** —
bound at module scope *and* assigned somewhere in the module. Reading an
immutable module binding is not reported, because it cannot be observed through
`const`. Fixtures: `examples/pass7/pure_ok.id` (reads nothing, and additionally
reads `scale` at the *call site*, outside the contract) and
`examples/compile_fail/pure_module_state.id`.

`@pure` and `@noreturn` are used **0 times** across every tracked `.id` file
(`lib/ examples/ tools/ ext/ scripts/`), so the blast radius of the new rejection
is zero. `@noalloc` appears at 3 sites, two of them these fixtures.

### `sem.module_globals` is the wrong oracle, and this is worth recording

The first implementation used `sema.Sema.module_globals` as "module state". It is
filled from the Lua-mode *"unknown identifier is a dynamic global"* path, and in
duon mode it was measured wrong in **both** directions on one four-line fixture:
it held `mem` (the intrinsic namespace, not state) and it did **not** hold `seed`
from `seed: i64 = 7` at file scope, which duon binds as a module local. The set
is now derived from the module's own top-level binding statements. A check built
on that oracle would have shipped a false positive and a false negative together.

## `duo explain` printed a raw Zig error name (H-8)

GAP-090 finding 2. `duo_lexer_dispatch.route` returns a lexer REJECTION and sets
`lex.last_error_loc`; `parse_and_check` and `do_fmt` both consumed it with a bare
`try`, so it escaped as a Zig error. Before:

```
$ duo explain examples/pass7/explain_smoke.id     # the broken tracked state
error: UnexpectedChar
```

No file, no span, no repair — `law.output.total` says an emission is graph data
rendered through the role taxonomy, and a bare error name names no edge. After:

```
lex_slash_comment.id:1:20: error: '//' does not begin a comment in duon
  |
1 | // GAP-090 fixture — DENIED TEXT IS THE ASSERTION.
  |                    ^
hint: a duon comment starts with `--`; `//` is the floor-division operator, so the
      rest of this line lexed as code
```

The caret is where the lexer **stopped**; the message is the **cause**. Both are
true and they are different positions, which is the honest rendering.

The column is derived host-side, not plumbed: the Duo lexer publishes
`duo_lexer_error_line` and no column, and adding `duo_lexer_error_col` would mean
regenerating the tracked `src/duo_lexer_tokenize.c`. The derivation is exact for
the class of byte that produces this rejection — a byte no token can start with —
and when nothing on the line qualifies the caret stays at column 1 rather than
pointing somewhere invented. Four rejection classes carry their own repair:
`UnexpectedChar` (split into the `//` case and the non-ASCII case),
`UnterminatedString`, `UnterminatedLongString`, `InvalidEscape`.

## Two defects this gap did not fix

- **`--backend=c` cannot compile `mem.alloc` under ARC.**
  `duo compile --backend=c examples/pass7/noalloc_fail.id` with the attribute
  removed emits `duo_retain((void*)(raw));` / `duo_release(...)` with no
  declaration in scope, and clang refuses. Pre-existing, in `codegen.zig`, owned
  by another session this session. It is the reason the gate asserts text.
- **`@noreturn` is an unchecked promise.** It lowers to
  `__attribute__((noreturn))` on a body that may fall off its end — the same
  shape as `@pure`, and the same class of licence to miscompile. It is NOT fixed
  here because "can this body return" is a real dataflow analysis and half of one
  is worse than none. Zero uses in tree, so it is a latent hole rather than a
  live one.

## EXTENDED 2026-08-09 — "parses" was measured; LOWERING was not

This gap's table records `seq(i64)` as parsing in a descriptor field and a local
binding, and failing in parameter and return position. Measured again against
CODEGEN, the local-binding row does not survive:

| spelling | result |
|---|---|
| `t = {}` (control) | **7** — lowers and answers |
| `t: seq(i64) = {}` | **`error: use of undeclared identifier 't'`** |
| `t: [i64] = {}` | **`error: expected 'name'`** |

So there is **no spelling of a typed sequence local that lowers.** The untyped
table is the only form that works, and that is the form the benchmark's
table-shaped kernels use — `Table max`, `Table lookup`, `Table churn`, `Fenwick
tree`, `Sparse dot`, `Game of Life`, all currently losing to C.

## Why this matters for the losses

Retyping SCALAR parameters `any -> i64` moved the benchmark from 13 losses to
10, because the compiler could then emit an integer compare instead of a float
one. The table kernels cannot receive the same treatment: the annotation that
would carry the element type does not lower in any position.

That is the difference between the two loss clusters. The scalar handicap had a
duon-side repair available and it worked. **The table handicap has none** —
there is no way to write, today, that this table holds `i64`.

## The pattern, third instance

`parses` and `lowers` are different measurements and this tree keeps conflating
them:

- gap[087] — canonical bare case parses, does not resolve
- gap[088] — `@{…}` is in the grammar, does not lower
- gap[091] — `seq(i64)` as a local parses, does not lower

Each was recorded as available on the strength of a parse. **A form is available
when it LOWERS AND ANSWERS**, and every table in this gap should be re-read with
that column added.
