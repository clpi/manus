**Severity:** the wall §46 names, measured. A canonical form is rejected by sema;

**Law:** `law.nominal` (§46) · §1 DENY LIST · `law.canon.performance` · §3

## The measurement

`law.nominal`: *semantic descriptor identity is INDEPENDENT of physical
representation — a `feet` value may physically remain an `f64`.* Measured
against the tree, every canonical spelling of that is rejected:

| declaration | binding `d: feet = 3.0` |
|---|---|
| `feet: f64` — descriptor face | **`error: type mismatch: declared as 'feet', but initializer has type 'f64'`** |
| `feet = f64` — binding face | same error |
| `feet@f64` — anchor face | same error |
| `alias(f64)` | `error: parse failed` |
| **`type feet = f64`** — **DENIED by §1** | compiles |

All three canonical spellings **parse**. Sema rejects the binding in all three,
with the identical message. So the declaration face exists and the *binding*
face is the hole.

## And the denied spelling is silently wrong

`type` is on the §1 deny list. It is also the only spelling that reaches
codegen — and it diverges:

| | `--backend=c` | `--backend=direct` |
|---|---|---|
| `type feet = f64` · `print(d)` | **(nothing)** | `3.000000` |
| `type count = i64` · `print(d)` | **(nothing)** | `7` |
| `d: f64 = 3.0` (control) | `3` | `3.000000` |

Both report `ok compile`. The C path emits **no output at all** — not a wrong
number, no number. Both underlying representations behave the same way, so it is
the nominal wrapper and not a float defect.

**The control found a second defect.** Plain `f64` already disagrees between
backends — `3` versus `3.000000`. That is Pass 107's shortest-round-trip ruling
surfacing as a BACKEND DISAGREEMENT, and it means the differential cannot
convict any float-printing program until the two paths agree on what an `f64`
looks like.

## The shape of the finding

- nominal identity has **no canonical spelling that works**;
- the **denied** spelling is the only one that compiles;
- and it **loses the value** on half the backends.

That is why the conversion algebra stalled at SER 2.00 / N=4. gap[082] recorded
"a user descriptor cannot be attached to a value". The narrower truth: through a
canonical spelling it cannot be attached at all, and through the denied one it
attaches and then vanishes.

## Fix

**Sema accepts an initializer whose REPRESENTATION matches the nominal's
underlying descriptor**, for the canonical spellings. That is `law.nominal`
stated as a rule: `feet` and `f64` share a representation and differ in
identity, so `d: feet = 3.0` is well-typed and `d: feet = m` where `m: meters`
is NOT.

NNS: no new surface. `feet: f64` already parses; only the binding rule is
missing.

Fixture asserts BY VALUE on BOTH backends that:

```
d: feet = 3.0        prints
feet and meters      remain DISTINCT — assigning one to the other DIAGNOSES
```

The second half is what makes it nominal rather than a rename, and a fixture
that only checks the first would pass against a compiler that erased the
identity entirely.

## Do not

**Do not repair this by lowering the nominal to its underlying type at the
binding.** That erases the identity `law.nominal` exists to establish and leaves
the conversion algebra unable to tell `feet` from `meters` — which is the whole
reason for having them.

**Do not use `type`.** It is on the §1 deny list; that it is the only spelling
which compiles is a finding about the tree, not a licence.

## Where the repair lives — and it is not duon

The binding rule is in **sema**, which is `src/*.zig`. The standing directive is
NO ZIG, stated four times, so this gap is RECORDED AND NOT REPAIRED — the fourth
tonight to terminate in the bootstrap:

| gap | repair lives in | duon-expressible? |
|---|---|---|
| 083 name mangling | `src/codegen.zig` | no |
| 087 bare-identity resolution | sema | no |
| 088 rung (a) lowering | `src/codegen.zig` | **YES, once the parser fed it** — done |
| 093 nominal binding rule | sema | no |

gap[088] is the one that got out, and how it got out is the pattern worth
copying: the duon-side piece was the PARSER (`proj_postfix` gaining a brace
arm), and once the tree carried an application node, `lower.id` and
`record.id` — both duon — could finish the job without touching the bootstrap.

So the question for 083, 087 and 093 is not "may we write Zig". It is **what is
the duon-side piece that makes the bootstrap unnecessary here**, and for a
binding rule the answer is a duon-native sema — which does not exist. That is
the honest next capability, and it is larger than any of the three gaps it would
close.
