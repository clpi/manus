# GAP-202 — scalar multiplication authority prototype is not production-safe

**Status:** OPEN · **Filed:** 2026-08-21
**Priority:** P0 · **Kind:** architecture_gap

## Exact preserved work

Commit `3dc68a458ce082c3a10cbe3db5e1d84c830041d2` preserved a rejected
scalar-i64 multiplication prototype; `2953bd7f2de016190cb7b20404f76edb3140e05a`
removed it from production. The prototype established useful controls for:

- one application identity with known-absent subject;
- ordered operand and result packs;
- overflow, may-trap, completion, and observable-identity facts;
- application → DNIR → machine lineage;
- refusal when any required law fact is unknown; and
- damage controls for relation-id or machine-operation corruption.

Git ancestry is the executable archive. Do not reapply the reverted patch.

## Why the prototype was rejected

It introduced a scalar-specific semantic subsystem:

- `Sema.scalar_multiplications` and `scalar_multiplication_rows` were a second
  application registry;
- `SemanticGraph.scalar_multiply_relation` was a dedicated relation slot rather
  than an ordinary relation entity selected through the one application algebra;
- DNIR selected the path by consulting that dedicated slot; and
- operand realization still called `lowerExpr` on `ast_ref` provenance, so
  changing or deleting AST after graph publication could change machine output.

That violates `law.application.one`, `law.fact.producer.one`,
`law.graph.sovereignty`, and `law.ast.backedge` even though the emitted multiply
and its validation controls were individually useful.

## Required producer-to-consumer chain

1. The grammar owner projects the operator token role to one resolved relation
   identity; this remains blocked on GAP-134.
2. Resolver publishes an ordinary `ApplicationFact`: relation, known-absent
   subject, ordered operands, result, demand, world, and provenance.
3. General sparse relation/application law columns publish overflow, trap,
   completion, effect/order, and observable identity. No scalar-specific table.
4. Graph value realization maps exact operand value ids to constants, parameter
   bindings, prior results, or places. DNIR must not recover operands through
   `valueExpression` / `ast_ref`.
5. The realization engine chooses an inline integer-multiply candidate from the
   relation id and law facts. `native_ir.BinOpTag.mul` remains a physical encoding,
   never relation identity.
6. Existing corruption and missing-law controls from `3dc68a45` are ported to the
   general machinery unchanged in substance.

## Acceptance

- no `scalar_multiplication*` registry or dedicated scalar relation field;
- one ordinary graph application survives source → graph → demand → realization
  → machine range;
- poisoning/removing AST provenance after graph publication leaves machine bytes
  unchanged;
- unknown overflow, trap, completion, effect, or identity facts refuse;
- relation-id and machine-op corruption controls fail;
- same-algorithm machine output is compared against optimized C; and
- compile work, memory, startup, artifact bytes, and runtime counters are recorded
  separately. Until exact-head measurements exist, performance is `UNMEASURED`.

## C0 alignment

Instance of the schema in `gaps/RESEARCH-SPINE.md`; this gap requires the one
application/relation/value algebra to become complete rather than adding a
scalar-operation subsystem beside it.

- **constitutional owners:** id · application · relation · value · pack · demand · effect · witness · realization
- **kind delta:** 0
- **registry delta:** 0
- **source syntax delta:** 0
- **semantic invariant:** scalar multiplication is one ordinary application whose exact relation, absent subject, operands, result, laws, demand, provenance, and witnesses are graph facts; neither a scalar-specific registry nor AST provenance may select downstream meaning.
- **physical mechanism:** the realization engine selects an inline target multiply from the ordinary application and admitted law facts; the machine operation tag remains only a checked physical encoding.
- **prerequisites:** GAP-134 and GAP-201.
- **foreign implication:** imported multiplication consumes the same relation and law facts; an ABI symbol or foreign opcode never becomes relation identity.
- **world implication:** the application carries its exact world/effect facts; numeric spelling or target lowering cannot grant authority.
- **projection implication:** none; ordinary `()` application and computed `[]` projection remain distinct.
- **demand implication:** exact result demand may erase or retain the application only after effect, trap, completion, ordering, and observable-identity obligations are known.
- **realization implication:** one application may realize as an inline multiply, fold, call, or refusal while preserving explicit application/value-to-machine lineage.
- **evidence:** AST-provenance poison, missing-law, relation-corruption, machine-operation-corruption, exact pack, machine-lineage, optimized-C comparison, and compiler/runtime/resource measurements.
- **deletion witness:** `scalar_multiplication*`, a dedicated scalar relation field, scalar-only application maps, and downstream AST-operand recovery.
