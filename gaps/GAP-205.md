# GAP-205 — measured native performance baseline: C leads on every kernel

**Status:** OPEN · **Filed:** !2026-08-21T19:10:00Z
**Priority:** P0 · **Kind:** performance_gap
**Filed by:** claude-gap145
**Files:** src/native_backend.zig,src/dnir_lower.zig,scripts/run_benchmark.id

`zig build bench` cannot run (GAP-204: the harness uses `print`, `tostring`,
`tonumber` and `type`, all bare-name runtime globals the native-scalar precheck
refuses). So the project has had NO current performance measurement at all, and
`evidence/HEAD.txt` records `Performance_admission: denied`.

These four kernels run on the direct backend TODAY. They are written in the
admitted subset, each verified to produce output identical to a C translation
BEFORE any timing, and they are the first multi-kernel measurement of this tree.

## Measured 2026-08-21, subject e2a3bdc6, aarch64 Apple Silicon

Median of five runs each, `clang -O3` opposite `idol compile` at its default:

| kernel | idol | C -O3 | C leads by |
| --- | --- | --- | --- |
| collatz, 300k seeds | 0.0503s | 0.0351s | 1.43x |
| gcd reduce, 2M pairs | 0.0828s | 0.0595s | 1.39x |
| integer mix, 200M iterations | 0.1664s | 0.0674s | 2.47x |
| fibonacci iterative, 3M x 30 | 0.0335s | 0.0067s | **5.00x** |

Agreement checked first, every kernel: 35669725, 13800284, 772400126426,
2496120000000 — identical from both implementations.

**C leads on all four. Idol is not faster on any of them.** The spread matters
more than the average: 1.39x on modulo-bound loops, 5.00x on the tightest
integer recurrence, which is where a C compiler's loop optimizer has the most
room and Idol's has the least.

## What this is and is not

It is a floor, not an indictment. Four kernels are not a benchmark suite, all
four are scalar integer loops, and none exercises the graph facts, demand or
realization search the architecture is actually built around.

It is also not comparable to any historical FTCFTW number, because those were
produced by a harness that does not run at this subject.

## What it is for

A measured baseline that exists, is reproducible, and can be regressed against.
Any future performance claim should move these four numbers, and any claim that
Idol beats C should name which of these kernels it beats and by how much.

## One named opportunity, from the fibonacci kernel's own assembly

The 5.00x row is the one with something visible behind it. `idol compile
--emit asm` on that kernel shows the inner loop is register-only — no spills —
but every arithmetic result lands in a scratch register and is then moved to its
destination:

```
add x13, x21, x22     # t = a + b
mov x24, x13          #   copy out of scratch
mov x21, x22          # a = b
mov x22, x24          # b = t
add x13, x23, #1      # i + 1
mov x23, x13          #   copy out of scratch
```

Two moves in that sequence exist only because the `add` wrote `x13` instead of
writing its destination directly. Across the file the mix is 19 `mov` against 9
`add`; the C translation is 2 `mov` against 3 `add`.

That is copy-coalescing: allocate the arithmetic result into the destination
register when the destination is dead at that point, instead of emitting
`op -> scratch` followed by `mov dest, scratch`.

STATED CAREFULLY, because the first reading of this was wrong. The whole-file
counts (69 instructions against 14, 27 loads and stores against 1) are NOT a
hot-loop comparison: every one of those loads and stores is a callee-saved
prologue or epilogue spill at `[sp, #0..48]`, and the inner loop touches no
memory at all. The defensible finding is the move redundancy in the loop body,
not a memory-traffic difference. Whether coalescing accounts for the whole 5x is
unmeasured — it is a lead, not a diagnosis.

## REFUTED: copy-coalescing measures 1.00x on the kernel it was named from

The opportunity named above is wrong, and the reasoning that produced it was
wrong in a way worth recording, because it is the natural way to read an
assembly listing and it points the wrong direction.

Replicating idol's fib inner loop instruction-for-instruction in inline asm and
walking the ladder, best of 5, 3M x 30:

| variant | instr/step | time | speedup |
| --- | --- | --- | --- |
| idol-exact | 9 | 0.0265 | — |
| copy-coalesced | 7 | 0.0265 | **1.00x** |
| + counted latch | 5 | 0.0256 | 1.03x |
| fully unrolled | 1 | 0.0046 | **5.77x** |

Deleting the moves is worth NOTHING. Apple's rename-time move elimination makes
them latency-free, and the loop already retires ~9 instructions in ~1.3 cycles.
The `19 mov : 9 add` count is real and not load-bearing. On collatz the same
change measures 1.05x.

**The rule these four kernels actually obey:** they are bound by taken
back-edges, branch mispredicts and `sdiv` latency — NOT by instruction count.
Every optimization that removes an instruction without removing a branch or a
divide measures at or near 1.00x. Every one that removes a back-edge, a
mispredict or a divide measures large. Counting instructions in a listing reads
the wrong axis.

## The real causes, per kernel, measured

- **fib** — unrolling, essentially all of it. C emits a fully unrolled 30-add
  chain with register rotation, no counter, no branch.
- **collatz** — two-sided if-conversion. C emits `tst`+`csinc` branchless where
  idol takes a ~50%-unpredictable branch. Worth 1.48x. Idol already
  strength-reduces `% 2` to `and #1`, `// 2` to `asr #1`, and fuses `3*n+1` to
  `madd` — the branch is the whole gap.
- **gcd** — a 6-instruction floored-remainder fixup that is provably dead when
  both operands are non-negative (1.28x), plus a divide-by-zero trap block laid
  out INLINE in the middle of the hot loop that a block-placement pass would sink.
- **mix** — two hardware `sdiv` per iteration for COMPILE-TIME constant divisors.
  `constBinopRealization` (`native_backend.zig:4944`) admits `.idiv`/`.mod` only
  for `k == 1` or powers of two. Its own doc comment at `:4943` says
  "`emitBinopFlooredConstDivisor` carries it instead" — and that function does
  not exist anywhere in the tree. Magic-multiply strength reduction is worth
  ~1.55x here before vectorization.

## Ranked by measured value x breadth

1. **Unroll counted loops with a static trip count** — 5.77x on fib. The only
   lever that touches the outlier, and the only one that reduces the SPREAD.
2. **Two-sided if-conversion to `csel`/`csinc`** — 1.48x on collatz, universal
   in branchy scalar code, and the recognizer machinery already exists.
3. **Magic-multiply for non-power-of-two constant divisors** — ~1.55x on mix.
   The function is already named in a comment and was never written.
4. **Drop the floor fixup when operand signs are known** — 1.28x gcd, 1.15x mix.
5. Sink the div-by-zero trap out of line.
6. **Copy-coalescing** — 1.00x. Breadth without value.

## Caveat on two rows of the table above

The gcd and mix sources were not recorded with the original measurement, so the
re-measurement used same-shape kernels; their ratios land close but their output
values differ. collatz and fib reproduce the exact recorded values and are the
same kernels.

The fib ratio also does not reproduce as 5.00x on a newer clang, which
constant-folds the entire kernel to one immediate. With only the fold blocked, C
measures 0.0071s against the recorded 0.0067s — so the original C was
unrolled-not-folded, and the honest ratio there is 4.03x.

## Reproduction

Each kernel is a single `.id` file in the admitted subset plus a C translation;
the Idol side uses only `while`, `if/else`, `i64` arithmetic, `//`, `%` and one
`stdout:write` of the result. Build with `idol compile k.id -o k.out` and
`clang -O3 -o kc.out k.c`, check the two outputs match, then time.

The fibonacci kernel is the one to look at first: same shape, same arithmetic,
five-fold difference.
