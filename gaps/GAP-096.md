# GAP-096 — 16 of 40 benchmark rows are below measurement resolution, so "faster than C" is unprovable

**Status:** OPEN · **Filed:** 2026-08-09
**Law:** §3 MEASUREMENT HONESTY · `law.c.floor` (§47) · `law.perf.floor`
**Blocks:** any claim of C-dominance, in either direction

## The measurement

`duo run scripts/run_benchmark.duo`, 2026-08-09:

```
All 40 benchmark results match reference C for .lua and .duo.

smallest positive Duo duration in this table: 1.5e-05s
rows with AT LEAST ONE Duo build folded: 16 of 40
negative control on real data: the rule fires on 0 rows when the C column
  is classified against itself

FAIL: Duo .lua and .duo must beat or tie reference C on every test, and the
      beating must be MEASURED. Folded rows count against this verdict.
```

**Correctness is total: 40 of 40.** The failure is entirely about
measurability.

## What "folded" means and why the FAIL is right

The fold rule: a row folds when the Duo time is at or below `1e-05s` — ten
times the `1e-06s` reporting resolution — or when C is at least 100x the Duo
time while C is itself above that floor.

The smallest positive Duo duration in the whole table is **1.5e-05s**. That is
roughly fifteen ticks of signal. A "win" measured with fifteen ticks is not a
win, it is noise with a favourable sign, and the harness refuses to credit it.

**That refusal is the suite working as designed.** This is the same file that
once reported "Duo beats C" on ten fabricated kernels — three returning frozen
literals — and §3 was written from that. A harness that counted these 16 as wins
would be repeating the exact failure it was rebuilt to prevent.

## The classifier is not the problem

Separately controlled, 11 of 11 synthetic rows agree, including the two that
matter:

```
genuine win, 2x      duo=0.005   c=0.01     folded=no
slower than C        duo=0.02    c=0.01     folded=no
```

So it distinguishes a real win from an unmeasurable one. And the negative
control fires on **0 rows** when C is classified against itself, so the rule is
not spuriously folding. **The 16 folds are a property of the workloads, not of
the threshold.**

## The repair, and why it must be done carefully

The workloads finish too fast to resolve. The repair is to raise the loop bounds
in `examples/benchmark.duo` until every row clears the floor by a comfortable
margin.

**This is the single most measurement-sensitive file in the repository**, and
editing it to make a verdict change is exactly what benchmark manipulation looks
like from outside. So it must be done as a deliberate, documented change:

1. **Raise bounds only. Change no kernel, no expected value, no row name.** The
   fold classifier already takes none of those as input, and the correctness
   comparison against reference C must stay byte-identical.
2. **Publish before and after for every row**, including the ones that were
   already measurable, so a reader can see that nothing was tuned selectively.
3. **Re-run the 11 classifier controls and the negative control.** A bound
   change that also moved the classifier would be indistinguishable from a
   rigged one.
4. **The C side runs the same bounds.** Raising Duo's work and not C's is the
   obvious way to fake this and the reason step 2 exists.
5. If a row still folds after a bound raise, that row is genuinely too cheap to
   benchmark and should be REMOVED with a reason, not left folding.

## What this does not license

It does not license claiming C-dominance once the folds clear. §47 makes the
claim conditional on the C-equivalent realization being a *candidate the
compiler costs and can choose*, which is architecture the tree does not have —
`law.c.floor` names it and nothing implements it. Clearing the folds makes the
comparison MEASURABLE. It does not make it monotone.

## Related

`law.perf.floor` and §47's twelve cost dimensions: wall time alone was never the
claim, and a suite that reports one number per row cannot express dominance.
Whoever raises the bounds should consider whether the table wants a second
column before it wants longer rows.
