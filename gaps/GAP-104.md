# GAP-104 — `law.c.floor` exists as architecture and holds ZERO cost facts; the twelve dimensions are empty

**Status:** OPEN · **Filed:** 2026-08-09
**Law:** constitution §47 (`law.c.floor`, `law.perf.floor`, `law.perf.dominance`) · §49 `cost.objective` · §3 MEASUREMENT HONESTY
**Follows:** `gaps/GAP-096` — which said the comparison was measurable but not monotone
**Gate:** `zig build c-floor` (`scripts/cfloor.duo`)

## What landed

§47's three laws are no longer text with nothing behind them. For every
module-scope callable the compiler now builds a `.lowering` realization variable
holding **two** candidates:

| candidate | what it is | status |
|---|---|---|
| `lower.cequiv` | the C-equivalent lowering | **baseline, unconditional** |
| `lower.native` | the direct machine-code lowering | legal iff every declared descriptor lowers native |

`duo explain` renders it under `c_floor`. `selectAgainstFloor` starts at the
baseline and moves off it only for a candidate that dominates on the §47
frontier **and** covers the active objective's relevance set **and** carries
`proven` or `measured` evidence. `monotoneAgainst` checks a candidate set never
shrinks when a fact is added.

`zig build c-floor`, measured 2026-08-09, all rows green:

```

  ok C2 law.c.floor        typed callable keeps both: total=2 viable=2
  ok F1 law.perf.floor     floor retained; why(skip): relation=insufficient
                           compared=0 missing=12 of 12 · unseats=false
  ok D1 law.perf.dominance candidate set across the fact: 2 -> 2
  ok D2 control            the fact was not inert: viable 1 -> 2

  ok M1 compile            direct=90ms  c-equivalent=120ms
  ok M2 size               direct=33608B  c-equivalent=33432B
  ok M3 latency            direct=510..620ms  c-equivalent=390..490ms
     verdict               the C-EQUIVALENT lowering is resolvably faster
```

## The gap, stated as the number it is

**Cost facts attached to either candidate: 0 of 12.**

`src/realization.zig` carries `LOWERING_COST_FACTS_ATTACHED = 0` so this is a
constant a test asserts, not a claim in prose. Nothing in the semantic graph
tells the builder what the two lowerings cost in latency, throughput, code size,
compile time, peak memory, allocations, cache footprint, branch misses, energy,
startup, binary size or tail latency — so it asserts nothing about any of them,
`why(skip)` answers `insufficient · compared 0 · missing 12`, and the C floor is
retained for want of evidence rather than on merit.

That is the whole distance between the architecture and the goal. The selector,
the frontier, the evidence ladder and the monotonicity check are all real and
tested; **the vector they read is empty.**

## Two things the measurement killed, recorded so they are not re-derived

**1. `compile_time` is NOT proven from the process-spawn fact.** The first draft
attached `compile_time` as `proven`: the C-equivalent path spawns an external C
compiler and the direct path does not, so the ordering looked structural. The
gate measured it and the ordering was **backwards** — 220ms direct vs 110ms
c-equivalent on the first run. Later runs put it the other way (100 vs 180),
because clang's invocation is cache-sensitive. So the dimension is not merely
mislabelled, it is **not stably ordered at all** on this workload.

The fact was **deleted, not demoted to `estimated`**. An estimate pointing the
wrong way is still a wrong number, and an estimate can never unseat a baseline
anyway — it would have been decoration on the render with no effect on
selection. This is §3's second rule ("a detector must verify every constant its
emitter assumes, and decline to the general path otherwise") applied to a cost
model instead of a kernel recognizer.

**2. The direct lowering LOSES to its own C-equivalent on the fixture.** On
`examples/cfloor/fact.duo` — 100M iterations of an integer recurrence, answer
independently verified by awk — five runs each measured:

```
direct         510..620ms
c-equivalent   390..490ms
```

The 120ms gap clears the 110ms spread, so the gate resolves it: **the
C-equivalent lowering is faster.** On a noisier run the same fixture came back
610-710 against 430-660 and the gate declined to resolve it at all. Both
outcomes pass — the row is published, not gated — and neither is a big result on
one kernel on one machine. What it does establish is that `law.c.floor` is not
a formality here: on the one workload anybody has measured, the floor is the
better realization, and a compiler that shipped native "because it is native"
would be shipping the slower code. That is the failure §47's `fails` clause
names in as many words.

**No claim of C-dominance is made or supported by any of this**, in either
direction. The comparison is duon's direct lowering against duon's own
C-equivalent lowering; awk is the answer oracle only. Clearing the architecture
makes a claim possible to state; it does not make one true.

## What the empty vector needs, in order

1. **A latency fact with a witness.** The gate can measure whole-program wall
   time; the plan needs a per-candidate number. That is a profile-feedback edge,
   and it is the one dimension the goal is actually about.
2. **`code_size` from the emitters.** Both backends know how many bytes they
   emitted for a callable. This is the cheapest honest row on the board and it
   needs no measurement harness — it is a fact each lowering already has and
   throws away.
3. **`allocations` from the effect algebra.** `semantic_algebra.EffectSet`
   already tracks allocation effects; wiring it into the vector is a projection
   of a fact that exists.
4. **An objective that is not `balanced`.** Under `balanced` all twelve are
   relevant, so nothing will ever unseat the floor. §49 makes the objective an
   ordinary target/world fact; nothing reads one yet, so `C_FLOOR_OBJECTIVE` is
   a constant.

## A SEPARATE DEFECT found while writing this, and it is worse than the gap

**An `if` whose condition is a compile-time-known local silently DROPS ITS
BODY.** Found while rewriting the fixtures away from `end` for the idiom gate;
it has nothing to do with §47 and it is recorded here because it needs to be
somewhere today.

```duo
main = (): i64
    n = 42
    if n > 10
        print("big")
    print("done")
    0
```

prints `done`. Only `done`. The true branch is discarded. It is **not** an
offside-layout artifact — the identical program with `end` on both blocks
behaves the same way — and it is **not** a parse error: the program compiles
clean and answers wrongly, which is the worst available shape.

Narrowed by control: replace `n = 42` with `n = std.script.status("true")` and
the same program takes the branch correctly and declines the false one. So the
trigger is the CONSTANT, and the family is the file-scope scalar fold already
recorded in this repository's memory as having produced confident wrong numbers
once before.

Every gate in `scripts/` that writes `if <literal-derived local>` is exposed to
this. `scripts/cfloor.duo` is not: every condition in it comes from a shell
capture or a function parameter, and rows P0/D2/M4 are positive controls that
would fail loudly if a branch vanished.

## What is stubbed, named as stubs

- **Selection is a PLAN, not a decision.** Nothing consults the `.lowering`
  variable to choose a backend. `duo compile --backend=…` still decides, and the
  native backend's own precheck still decides bail-vs-native inside the backend
  — which is the `law.stack.direction` violation §47's mechanism is supposed to
  retire. Row D3 measures that the plan's legality verdict and the backend's
  actual behaviour AGREE, which is the strongest statement available while the
  two are separate mechanisms.
- **Legality is per-callable, the backend refuses per-module.** `funcLowersNative`
  reads one callable's declared descriptors. `--backend=direct` refuses the whole
  program when any part of it is outside the subset. D3 passes because the
  fixtures have a single interesting callable each; a mixed module would show the
  two disagreeing, and that disagreement is real, not a harness artifact.
- **`ModuleRealizations.lowering` is a second list** rather than more rows in
  `variables`, because `variables.len` is a gated number (`scripts/realize.duo`
  asserts `"variable_count":1`) and `region_graph` sums legal candidates over it
  into a pending-decision count. Merging is right once both read a dimension
  filter instead of a length.
- **The twelve dimensions extend an existing enum** (`CostDimension` went 11 →
  16) rather than replacing it, so §47's twelve are a named subset and
  `transform_engine`'s four extra dimensions survive. `CostDimension.constitutional`
  is the §47 list and a test asserts it has twelve distinct rows.
- **Every JSON key this change introduces is one lowercase word** — `viable`,
  `total`, `unseats`, `retained`, `choice`, `decided`, `lowerings`, `missing`,
  `compared`. The older keys beside them (`selected_id`, `subject_entity`,
  `static_cost`, `optionality_retained`, `hard_constraints`) are not, and were
  left alone because `scripts/realize.duo` and `scripts/explain.duo` read them.
  H-8 makes an emission graph data rendered through the taxonomy and LAW-ONE
  governs the taxonomy, so the old keys are migration debt on this schema and
  the new ones are not added to it.

## SHARPENED 2026-08-09 — it is not the local, it is the TRUE constant, and `else` dies too

Reproduced independently and narrowed. The filed repro blamed a compile-time
constant LOCAL. The local is incidental — a bare literal comparison does it too,
and an `if/else` loses **both** arms.

| program | prints | verdict |
|---|---|---|
| `n = 42` · `if n > 10 print("BIG")` | *nothing* | WRONG |
| `if 42 > 10 print("BIG")` | *nothing* | WRONG — no local involved |
| `if 42 < 10 print("X")` · `print("done")` | `done` | correct — a FALSE constant skips properly |
| `if 42 > 10 print("T") else print("F")` | *nothing at all* | WRONG — **neither arm runs** |
| `print(42)` | `42` | control — printing and constants both fine |

**The rule: a constant condition that evaluates TRUE drops the branch it should
take.** False conditions are correct, so the folder is deciding and then
discarding the arm it decided on — an inversion of the emission, not of the test.
The `else` case is the sharpest: a two-armed `if` where control reaches neither
arm cannot be explained by a mis-taken branch.

Every one exits 0 with `ok compile`. Nothing warns.

## Why this is worse than a wrong answer

`if <true constant>` is the shape of every feature flag, every debug guard, every
`if DEBUG`, and every specialization written by hand. It is also the shape a
CONSTANT-FOLDING OPTIMIZER CREATES: propagate a constant into any conditional and
this defect activates on code the author never wrote that way. So the blast
radius is not "programs containing a literal condition" — it is "programs the
optimizer folds a condition in", which is far larger and impossible to grep for.

It is the same family as the file-scope scalar fold and gap[063]'s table
fill+sum: the fold is right, the emission after it is not.

## Controls run

`print(42)` alone answers 42, so neither printing nor constant handling is
broken in general. The FALSE row is the positive control for the classifier —
if constants were simply not evaluated, that row would print `X`.

## CORRECTED AGAIN 2026-08-09 — it is not constants and it is not the branch. `print` inside an `if` is dropped on the NATIVE backend.

Two diagnoses were wrong, including my own sharpening directly above. Both were
wrong the same way: inferring the mechanism from what the program printed,
without asking whether the branch ran.

The test that settles it uses the EXIT CODE instead of stdout, so the branch
reports itself without going through `print`:

```duo
main(): i64
    if 42 > 10
        return 7
    end
    return 3
end
```

```
--backend=direct   rc=7          the branch IS taken
--backend=c        rc=7
```

So nothing is dropping the branch. The claim "a true constant condition drops
its taken arm", and the earlier "an `if` on a compile-time-constant local
silently drops its body", are both **withdrawn**.

It is also not about constants. A value produced by a loop behaves identically:

```duo
n: i64 = 0
while n < 1
    n += 42
end
if n > 10
    print("RUNTIME")     -- not printed
end
print("after")           -- printed
```

| program | backend | prints |
|---|---|---|
| `if 42 > 10 print("BIG")` | direct | *nothing* |
| same | **c** | **BIG** |
| `if <runtime n> > 10 print("RUNTIME")` | direct | *nothing* |
| `print` outside any `if` | direct | prints |
| `if 42 > 10 return 7` | direct | **rc=7** |

**THE DEFECT: on the native/direct backend, a `print` call inside an `if` body
emits nothing. The branch executes; the call does not.** The C backend is
correct throughout, which is why `--backend=c` masked it.

## Why three readings missed it

Every earlier probe used `print` as its instrument, and the instrument was the
thing that was broken. The dnir `if_stmt` lowering and the `br_if_not` emission
both read correct on inspection — and they ARE correct; the branch is taken. An
audit of the branch machinery would have found nothing wrong, forever.

The rule this earns: **when a program produces no output, do not test the
control flow with output.** Use the exit code, which the earlier gap note itself
warned about from the other direction ("exit codes are 8-bit").

## Blast radius

Far larger than the constant-condition reading suggested. Every `print` guarded
by a condition — every error path, every debug branch, every conditional
diagnostic — is silent under the default backend. `duo run` uses `direct`.

## What closes it

Find why a `call_extern` to `print` inside a branch body is not emitted or not
reached in `src/native_backend.zig`, given the branch demonstrably executes.
Positive control: the same `print` outside the `if` works, so the call lowering
is fine in isolation — it is the interaction with the branch.

## LOCALIZED — it is the TAIL statement of the branch, and only that one

```duo
if 42 > 10
    print("FIRST")     -- prints
    print("LAST")      -- DOES NOT PRINT
end
```

One `print` in the body vanishes; two, and only the last one does. So this is
tail-slot handling, not `print` and not branching.

The machinery, all in `src/dnir_lower.zig`:

- `lowerBlockReturns` walks the statements, marking one with
  `stmtIsTailSlot(block, i)`, and only afterwards calls
  `tryEmitTailDemandReturn` — and only `if (allow_return)`.
- `tryEmitTailDemandReturn:967` special-cases a void tail call:
  `if (isVoidTailCall(r.expr)) { _ = try lowerExprCons(ctx, r.expr, .discard); return false; }`
  Its comment cites gap[033]: emitting `ret` there made `if c print(" ") end`
  compile to `return print(" ")`, exit 59.
- `isVoidTailCall` matches the callee spelled exactly `print` — the one builtin
  whose voidness is unconditional.

**The suspected shape: the tail statement is skipped by the statement walk on
the understanding that `tryEmitTailDemandReturn` will lower it, and for a branch
body reached with `allow_return == false` that call never happens — so nothing
lowers it.** Two paths, each correct alone, with a gap between them. That is
consistent with every observation: the branch runs (rc=7), non-tail prints
survive, and the C backend — which has no such split — is correct.

Not yet fixed: confirm which of the two paths drops it before editing. `print`
is dispatched in `lowerExprCons` BEFORE the `discard` branch
(`if (eql(callee,"print")) return lowerPrint(...)`), so `.discard` is not
eliding the call and the gap[033] special case is likely innocent.

Fix must keep gap[033] green: `if c print(" ") end` must not become
`return print(" ")`. That fixture is the regression test.
