# GAP-032 — a receiver face on an `any` receiver silently returns nil

**Status:** CLOSED 2026-08-08 · **Filed:** 2026-08-07 · **Frequency:** 1
**Cited at:** `lib/std/json.duo` · **Measured blast radius: 273 sites in 37 lib/std modules**

## Repro (fails before the fix, passes after)

```duo
cur = { s = "hello", i = 2 }

string.byte(cur.s, cur.i)   -- 101   correct
cur.s:byte(cur.i)           -- nil   WRONG, no diagnostic  ->  101 after the fix

string.sub(cur.s, 2, 3)     -- "el"  correct
cur.s:sub(2, 3)             -- nil   WRONG, no diagnostic  ->  "el" after the fix

#cur.s                      -- 5     the len face was always FINE
```

A table field is `any`. In `src/codegen.zig`'s `.method_call` arm the `any`
receiver fell straight through to the table-member dispatch at the bottom of the
branch — `lua_table_get_str_lit(__self, "byte", ...)` then `lua_invoke`. A string
carries no members, so the lookup found nil, `lua_invoke` invoked nil, and the
call produced nil. No diagnostic, because nothing on that path knows the
receiver was supposed to be a string. `#` is unaffected, which is why the
`string.len` -> `#` sweep was safe and the other two were not.

A bare local did not help (`a = cur.s; a:byte(i)` -> nil) — it is `any` too. A
**typed** local did (`b: str = cur.s`), but adding the annotation broke other
uses of the same binding: doing it in json.duo produced 10 C errors,
`invalid operands to binary expression ('lua_Value' and 'int')`.

## The fix

`try_emit_guarded_string_face` in `src/codegen.zig`, called from the `ot == .any`
arm before the file/str-buf faces. It emits the **runtime-guarded dispatch**
gap[014] named as the only correct shape:

```c
({ lua_Value __self = <recv>; lua_Value __a0 = <arg>;
   __self.type == VAL_STRING ? lua_str_sub(__self, __a0, lua_val_nil())
                             : ({ /* member lookup + lua_invoke, unchanged */ }); })
```

Data still wins the name **by construction**: a string cannot carry a member, so
a table with its own `sub` is never hijacked. That is exactly what sank the
unconditional projection tried for gap[014] and reverted on 2026-08-07 — the
guard is what makes the same idea safe. Verified: `t = { sub = mysub }; t:sub(1,2)`
returns `"MEMBER-SUB"`, and a nested `holder.inner:sub(1,2)` does too. Receiver
and arguments are bound to temporaries first, so each is evaluated exactly once
whichever arm runs (measured: one call to a counting function, same as the
operation-first form).

Covers `sub byte rep gsub gmatch find match split starts_with ends_with lower
upper reverse`. Names already claimed on `any` by the file and str-buf faces
(`get set read write len close flush seek`) are deliberately excluded.

## Census

The register's original grep, `\b[a-z]+\.[a-z]+:(sub|byte)\(`, counted 92 sites
and **undercounted by a factor of three**: it only matches a `a.b:` receiver, so
it missed every bare `any` local (`remaining:sub(r.pos)`, `line:sub(1, n)`,
`part_body:sub(...)`, `key:byte(i)`).

The honest census compiles each module and counts the emitted guard, attributed
to functions the module itself declares:

* **273 sites in 37 `lib/std` modules** went through the broken path.
* **0 in `examples/`, 0 in `scripts/`.**
* Of the 92 grep sites, **76 were genuinely broken** and **16 were never broken**
  — `lib/std/cursor.duo` (2), `lib/std/compiler/lexer.duo` (10),
  `lib/std/compiler/source.duo` (3), `lib/std/compiler/parser.duo` (1) declare
  their receivers as record types with `str` fields (`c: ByteCursor`,
  `self: Lexer`, `t: Tok`), so those faces lowered natively all along
  (`c->data[c->pos - 1]`, `duo_str_sub_cstr`) and emit no guard.

Top affected: `ml/tokenizer` 23, `encoding/json` 23, `zip` 22, `text/scanner` 20,
`string` 20, `ffi_gen` 18, `bufio` 17, `uuid` 11, `mime/multipart` 10,
`math/prng` 10, `encoding/pem` 10, `bytes` 10, `crypto/signature` 9, `flag` 8,
`argparse` 7.

## Consequence for the interim

The interim spelling is retired. `lib/std/json.duo` and `lib/std/wasm/decode.duo`
were hand-reverted to `string.byte(recv, i)` on 2026-08-07 and are back on the
canonical face form; the four json sites are the direct proof, since a binary
built without the fix now fails that file and one built with it decodes exactly.
No other site needed a source edit — the compiler repairs all 273.

## Adjacent defects found while measuring, NOT part of this gap

* `tonumber(s, 16)` **ignores the base**: `tonumber("0041", 16)` -> 41,
  `tonumber("ff", 16)` -> 0. Identical before and after the fix. It is why
  `std.encoding.json` decodes `"A"` as `)` and `std.net.url.unescape`
  turns `%20` into a control character rather than a space.
* `string.char(n)` for **n >= 128 returns the empty string**, so
  `string.char(0xE5) .. string.char(0x8E)` is `""`. Use `"\xE5\x8E"` escapes,
  which do work.
* `print(string.byte(s, i))` on a native `str` emits `lua_to_display_str(int64_t)`
  and fails the C compile; assigning to an `i64` local first is the workaround.
