# GAP-094 - single-hole interpolation preserves an unnecessary concat realization

**Status:** CLOSED · **Filed:** 2026-08-09 · **Reopened:** 2026-08-10 · **Closed:** 2026-08-25
**Priority:** P1
**Owner:** realization and generated-C projection

## Current boundary

Single-hole interpolation now preserves text semantics, but the parser represents
the conversion as concatenation with an empty text value. That source-shaped
realization is not the semantic relation and must not force physical concat work.

At `335af08` with the existing shared dirty tree, a temporary canonical `.id`
probe returned the same value on both backends. Machine inspection did not agree
on work:

| Path | Result | Physical work for one integer hole |
| --- | --- | --- |
| direct native | `7` | one `malloc`; no `strlen` or `memcpy` in `main` |
| generated C | `7` | two `malloc` calls plus `strlen` and `memcpy` in `main` |

`dump-c` exposes the second allocation directly: the integer-to-text result is
passed through an empty-text concat. The optimized C executable retains both
allocations, so this is not only an intermediate C artifact.

## Required closure

Preserve interpolation as one semantic conversion/application with exact source
provenance. Realization may concatenate when literal or additional dynamic
segments demand it. A single dynamic segment must not materialize an empty
segment or a concat operation.

Closure requires:

- equal output on direct-native and generated-C paths;
- one conversion allocation or a cheaper lawful realization on both paths;
- no empty concat in the generated C or direct machine lineage;
- the original interpolation application and value lineage remain queryable;
- no parser-local special case becomes semantic authority.

The parser and codegen files are concurrently owned. Do not reconstruct the
missing semantic conversion in another backend. The owner boundary is the
source-recognition to graph/application projection; realization must consume that
exact fact.

## Closure (2026-08-25, tree `fc48acea` + this change)

Reproduced live at `fc48acea` before the change: `i = 7 ; a: str = "{i}" ;
print(a)` through `dump-c` emitted
`const char* a = duo_str_concat("", duo_str_from_i64((int64_t)(i)));`, and the
`cc -O2` executable's `main` carried two `malloc` calls plus `strlen` — the
filed measurement exactly.

The repair lives at the C-projection owner named above, in `src/codegen.zig`
(`concat_operand_is_empty_text` beside the two concat emission arms). The
parser's single-hole seed (`"" .. i`) is a SOURCE-shaped realization; the C
projection now consumes the exact graph fact — a text-literal operand of length
zero — and elides the concat, realizing the value as the hole's display
conversion alone. This is `law.observation.minimum` / INTERMEDIATE-ZERO: the
empty text is the identity operand of `..` on the one observation the value
makes; the witness (no effect dropped, no evaluation-order change, byte-identical
result through the same display conversion, allocation identity not a semantic
observation for immutable text) is written on the helper. The BYTE face `''` is
excluded — the witness speaks only for text — and the boxed `lua_concat` path
is excluded because under Lua law `"" .. x` errors on nil/table and stringifies,
so the equivalence is witnessed only on the full-native arm. The parser is
untouched: no parser-local special case, and the interpolation application and
its value lineage in the AST/graph are unchanged — the elision is emission-only.

Measured after the change, same probe, same tree:

- generated C: `const char* a = duo_str_from_i64((int64_t)(i));` — no
  `duo_str_concat(""` anywhere in the artifact; `cc -O2` executable prints
  exactly bytes `37 0a` (`7\n`), exit 0, and `main` carries ONE `malloc`, no
  `strlen`, no `memcpy`.
- positive control `b: str = "x{i}"`: emits
  `duo_str_concat("x", duo_str_from_i64((int64_t)(i)))` and prints exactly
  bytes `78 37 0a` (`x7\n`), exit 0 — a genuine two-part interpolation still
  concatenates and answers right.
- pinned by the unit test
  `codegen: gap[094] single-hole interpolation realizes as the conversion, not
  an empty concat` in `src/codegen.zig`: value line, artifact-shape assertion
  that no empty-seeded concat survives, and the two-part positive control.

The direct-native leg cannot be re-measured on this host: the direct backend
refuses x86_64-linux with DNB004, so the 335af08 direct measurement (one
`malloc`, no empty concat in the direct lineage) stands as the direct-path
evidence — the direct lineage never carried the empty concat, which is why this
gap's owner is the generated-C projection. The repair does not touch admission,
`dnir_lower.zig`, or the direct backend, so the separately recorded DNB001
`concat` face (which blocks `gate/idiom.id` direct execution) is unaffected in
both directions.
