# GAP-094 - single-hole interpolation preserves an unnecessary concat realization

**Status:** OPEN
**Priority:** P1
**Owner:** realization and generated-C projection
**Filed:** 2026-08-09
**Reopened:** 2026-08-10

## Current boundary

Single-hole interpolation now preserves text semantics, but the parser represents
the conversion as concatenation with an empty text value. That source-shaped
realization is not the semantic relation and must not force physical concat work.

At `335af08` with the existing shared dirty tree, a temporary canonical `.id`
probe returned the same value on both backends. Machine inspection did not agree
on work:

| Path | Result | Physical work for one integer hole |
| --- | --- | --- |
| direct native | `7` | one `malloc`; no `strlen` or `memcpy` in `main` |
| generated C | `7` | two `malloc` calls plus `strlen` and `memcpy` in `main` |

`dump-c` exposes the second allocation directly: the integer-to-text result is
passed through an empty-text concat. The optimized C executable retains both
allocations, so this is not only an intermediate C artifact.

## Required closure

Preserve interpolation as one semantic conversion/application with exact source
provenance. Realization may concatenate when literal or additional dynamic
segments demand it. A single dynamic segment must not materialize an empty
segment or a concat operation.

Closure requires:

- equal output on direct-native and generated-C paths;
- one conversion allocation or a cheaper lawful realization on both paths;
- no empty concat in the generated C or direct machine lineage;
- the original interpolation application and value lineage remain queryable;
- no parser-local special case becomes semantic authority.

The parser and codegen files are concurrently owned. Do not reconstruct the
missing semantic conversion in another backend. The owner boundary is the
source-recognition to graph/application projection; realization must consume that
exact fact.

## Evidence

Focused runs, serialized through the repository lock:

- C execution: exit 0, output `7`.
- direct-native execution: exit 0, output `7`.
- direct-native compile trace: `direct-proof-artifact`, native link, exit 0.
- generated C: two allocation sites survive optimization.
- direct-native disassembly: one allocation site in `main`.

This evidence exercises native direct and generated-C paths only. It is not Wasm
evidence, an aggregate pass, or compiler-B ownership evidence.
