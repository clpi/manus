# GAP-094 — a single-hole interpolation is not a `str`, and the native backend crashes on it

**Status:** CLOSED 2026-08-09 — parser half repaired; the paired requirement was
already closed · **Filed:** 2026-08-09

## 2026-08-09 — the parser half is FIXED, by value on both backends

`desugar_string_interpolation` (`src/parser.zig`) builds a list of parts and
folds them with `concat`. With one literal byte anywhere in the string there are
at least TWO parts, so the fold runs and produces a string. With no literal text
at all there is exactly ONE part, **the fold body never executes, and the
function returns the hole expression itself** — the desugar of a string
literal handed back an `i64`.

That is the whole defect. It is four lines from the end of the function, and it
explains every row in this file including why the control fired: the control
differs from the failing row by exactly the thing that makes `parts.len` two.

**Repair:** seed the fold with an empty literal when the first part is not one,
so the single-hole case takes the SAME shape as every other — `"" .. i` beside
`"x" .. i`. It reuses the concat lowering that already works rather than
introducing a conversion the multi-part path does not use, and an all-literal
string cannot reach it (`parts.len == 0` returns earlier).

## The rule that is broken

`"{x}"` must be a `str`. Interpolation is the ONLY sanctioned way to render a
value into text (§0.8 forbids `..` + `to(str)` chains), so a hole is a
CONVERSION EDGE — never an identity.

## What it actually does

`desugar_string_interpolation` (`src/parser.zig:4828`) splits the literal into
parts, then folds them with `.concat`:

```zig
var expr = parts.items[0];
for (parts.items[1..]) |part| { expr = ... .concat ... }   // parser.zig:4923
```

When the literal is **exactly one hole and no surrounding text**, `parts.len ==
1`, the fold body never runs, and the function returns **the bare hole
expression**. `"{i}"` IS `i`. The str conversion is not deferred, it is gone.

## Three measurements, one control

```
$ cat /tmp/hole.duo
main = (): i64
    i = 7
    a: str = "{i}"
    print(a)
    0
end
$ duo compile --backend=c /tmp/hole.duo
error: type mismatch: variable 'a' declared as 'str', but initializer has type 'i64'
```

**CONTROL (fires, and localizes the bug):** add one literal byte and it is a
`str` again — `b: str = "x{i}"` compiles and prints `x7`. So this is not "holes
are untyped"; it is specifically the no-literal-text case falling out of the
fold.

**The divergence, in six lines.** `--backend=direct` ACCEPTS this program and
the binary segfaults; `--backend=c` correctly refuses it:

```
main = (): i64
    out: str = "a"
    i = 7
    word = "{i}"
    out = word
    print(out)
    0
end
```

```
--backend=direct   ok compile   → SIGSEGV (rc 139)
--backend=c        1 error: incompatible integer to pointer conversion
```

An i64 flows into a `const char*` place. C's type system catches it; the native
precheck has no such check, admits the module, and emits a load through 7.

## Why there is no duon-side repair

- `word: str = "{i}"` — rejected, that IS the diagnostic above.
- `word = i:to(str)` — type-correct, but bails native at
  `lowerExprCons() dnir_lower.zig:2127 — str`, so it trades one hole for
  another and violates §0.8 besides.
- Annotating only `out: str = ""` makes fizzbuzz LOWER NATIVELY and SEGFAULT.
  That is strictly worse than the bail and must not be landed.

## The repair, when someone is licensed to write it

Return the single part wrapped in the same conversion the concat fold applies,
rather than returning it bare. The fold is already the conversion site; the
one-part case must not be a shortcut past it. Paired requirement: the
native-scalar precheck must stop admitting an i64 into a `str` place —
`--backend=direct` accepting what `--backend=c` rejects is the failure mode
§3 exists for, and `zig build native-differential` compares stdout, so the
six-line program above belongs in it as a regression row.
