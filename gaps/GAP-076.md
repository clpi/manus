# GAP-076 — the gap allocator is atomic across PROCESSES, blind across BRANCHES

**Status:** OPEN · **Filed:** 2026-08-08
**Severity:** the collision it was built to prevent, one level up

## What was built and what it fixed

`duo_agent_gaps_update(action="open")` now ALLOCATES the number instead of
accepting one. Allocation is a `mkdir(2)` on a reservation directory; POSIX
makes that atomic, so winning the mkdir IS the allocation and there is no lock
to race. Measured: **12 concurrent processes, 12 distinct numbers.**

That is a real fix for a real failure — three collisions happened tonight when
agents chose their own numbers, and one of them (GAP-065) had to be recovered
from git after another session overwrote it.

## The defect

The allocator scans `gaps/` **on the current branch**. It cannot see a number
already filed on a branch that has not merged.

Reproduced immediately, by using it:

- I asked it for a number. It answered **GAP-074** and created the file.
- `gaps/GAP-074.md` did not exist on `canonical-to-relation` — correct.
- But `pass104-evaluator`, pushed and unmerged, already carries
  **GAP-074 — "a module-level table is never equal to itself across a
  parameter"**, and GAP-073 for a second compiler bug.
- On main, GAP-073 is a *different* finding again ("the role taxonomy is not
  implementable as written").

So the first real use of the allocator produced the exact collision class it
exists to prevent. I removed the stub and filed at 075 by hand after scanning
every branch:

```
for b in $(git branch --format='%(refname:short)'); do
    git ls-tree -r --name-only "$b" gaps/ | grep -oE 'GAP-[0-9]+'
done | sort -u | tail -1
```

## Why this is the harder half

`mkdir(2)` gives atomicity within **one filesystem view**. Parallel agents in
this repo do not share one view — they work in `git worktree`s on separate
branches by design, because that is the mitigation for the *other* recurring
failure (a bare `git commit` sweeping another session's staged work). The two
mitigations are in tension: worktrees make commits safe and allocation blind.

This is the same shape as tonight's other measurement findings — a shared mutable
surface (`zig-out/bin/duo`, a fixed `/tmp` path, one build cache) makes a number
somebody else's. Here the surface is not shared *enough*.

## Fix directions, none obviously right

1. **Scan all refs, not the worktree.** The loop above, run inside the
   allocator. Cheap, and catches unmerged branches — but not a branch that
   exists only in another worktree and has never been pushed.
2. **Reserve in a location outside the branch** — a single reservation directory
   in the repo's common git dir, which every worktree shares. Restores one
   filesystem view without giving up worktrees. Probably correct.
3. **Make the number not matter** — content-addressed gap ids, with the numeric
   name a rendering. Largest change; removes the class rather than guarding it.

Whichever lands, the acceptance test is the reproduction above: allocate from
two worktrees on two branches and get two distinct numbers.

## Note for whoever fixes it

Do not weaken the process-level atomicity to get branch-level coverage. The
12-process measurement is a real property and the positive control behind it —
a hand-made reservation with no gap file is SKIPPED, proving the ledger gates
rather than the scan — is worth preserving as-is.
