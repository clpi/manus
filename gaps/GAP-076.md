# GAP-076 — the gap allocator is atomic across PROCESSES, blind across BRANCHES

**Status:** **CLOSED 2026-08-09** — fix direction 2 landed, acceptance test
passes · **Filed:** 2026-08-08
**Severity:** the collision it was built to prevent, one level up
**Gate:** `zig build gapalloc` (`scripts/gapalloc.duo`)

## CLOSED 2026-08-09 — and the diagnosis below understated it

The gap says the allocator "scans `gaps/` on the current branch". True, and
**not the worst of it.** The reservation ledger was `root/.agents/session/
gapalloc`, which is *gitignored* — so it was not merely branch-local, it was
**worktree-local**. Two agents in two worktrees mkdir'd two DIFFERENT
directories. Both won. The POSIX guarantee held perfectly and protected
nothing, which is why 12-processes-12-numbers and four real collisions were
both true at once.

Measured at the time of the fix: this worktree had **no ledger directory at
all**, while the main checkout's held `GAP-074`. Both would have been handed
the same next number.

### What landed

**Fix direction 2, as the gap predicted ("probably correct").** Reservations
moved to `git rev-parse --path-format=absolute --git-common-dir`, the one
directory every worktree of a repository shares — `/Users/clp/x/duo/.git/
duon-gapalloc`. The primitive is unchanged and **only its LOCATION moves**, so
the note's instruction to preserve the process-level atomicity is satisfied by
construction rather than by re-argument.

**Fix direction 1 as well, because neither source subsumes the other.**
`gaphigh()` is now SEEDED from every ref (`git log --all … -- gaps/`, 0.06s)
instead of starting at 0. A seed rather than a fourth loop, so the two
existing scans can only RAISE it and a failed pipeline degrades to the old
behaviour instead of handing out a low number.

| source | covers | misses |
|---|---|---|
| shared ledger | a number reserved before its file is written | one filed by hand, or before the allocator existed |
| all refs | a gap COMMITTED on an unmerged branch | one written but not yet committed |

### The acceptance test the gap asked for

> *"allocate from two worktrees on two branches and get two distinct numbers"*

```
worktree A (gaps-measurement-a866)  ->  112
worktree B (detached, /private/tmp) ->  111
```

Run concurrently, both backgrounded, one shared ledger. Two worktrees, two
numbers. The second worktree's probe was renamed `gapallocb.duo` first —
`duo run` writes `/tmp/duo_<basename>.c` with no run identity, so two
concurrent runs of the same basename corrupt each other's C.

### Controls, because "it returned two numbers" is not proof

| control | result |
|---|---|
| OLD topology: `mkdir GAP-999` in two worktree-local ledgers | **both exit 0** — no mutual exclusion at all |
| NEW topology: `mkdir GAP-999` twice in the shared ledger | exit 0 then **exit 1** — exclusion restored |
| after the concurrent run, shared ledger holds | `GAP-111` **and** `GAP-112` |
| after the concurrent run, this worktree's `.agents/session/gapalloc` | **still absent** — proves the fallback never fired |

That last row is the one that matters: a silent fallback to the worktree-local
ledger would keep colliding *while reporting success*. It is also why the gate
prints the **resolved ledger path** rather than a verdict.

### Caught live while testing — a fifth collision, prevented

`GAP-109` and `GAP-110` exist on other refs and **not** in this worktree's
`gaps/`. The old allocator would have handed out **109**. The new one answered
**111**. The defect reproduced itself during its own repair.

### Two silent traps, recorded in the source because neither errors

- **`std.proc.capture` re-appends `"\n"` per line**, so its result always
  carries a trailing newline even against `printf %s`. Untrimmed it builds a
  path with `\n` in the MIDDLE — which every worktree agrees on, so the
  allocator keeps working and stays wrong. Visible only by dumping bytes; a
  line-oriented grep over the gate's own output hides it perfectly, and did.
- **The `: str` annotation on the capture binding is load-bearing.**
  Unannotated the value stays boxed, codegen emits `lua_str_buf_len_i64`
  against the box, which answers **0**; `:len() - 1` is then `-1`, and
  `sub(1, -1)` is Lua for *the whole string*. The trim silently returns its
  input with no error anywhere. Filed separately as **gap[111]**.

### Numbers consumed

111 and 112 were allocated by the acceptance test and are NOT reclaimed —
"leaking a number costs nothing; reusing one is the bug this exists to
prevent." 111 carries the codegen finding above; 112 stays a deliberate hole.

### What is still not covered

A branch in a **different clone**. Out of scope for a repository-shared
reservation directory, and there is no evidence of that failure mode here.

*Original filing follows.*

## What was built and what it fixed

`duo_agent_gaps_update(action="open")` now ALLOCATES the number instead of
accepting one. Allocation is a `mkdir(2)` on a reservation directory; POSIX
makes that atomic, so winning the mkdir IS the allocation and there is no lock
to race. Measured: **12 concurrent processes, 12 distinct numbers.**

That is a real fix for a real failure — three collisions happened tonight when
agents chose their own numbers, and one of them (GAP-065) had to be recovered
from git after another session overwrote it.

## The defect

The allocator scans `gaps/` **on the current branch**. It cannot see a number
already filed on a branch that has not merged.

Reproduced immediately, by using it:

- I asked it for a number. It answered **GAP-074** and created the file.
- `gaps/GAP-074.md` did not exist on `canonical-to-relation` — correct.
- But `pass104-evaluator`, pushed and unmerged, already carries
  **GAP-074 — "a module-level table is never equal to itself across a
  parameter"**, and GAP-073 for a second compiler bug.
- On main, GAP-073 is a *different* finding again ("the role taxonomy is not
  implementable as written").

So the first real use of the allocator produced the exact collision class it
exists to prevent. I removed the stub and filed at 075 by hand after scanning
every branch:

```
for b in $(git branch --format='%(refname:short)'); do
    git ls-tree -r --name-only "$b" gaps/ | grep -oE 'GAP-[0-9]+'
done | sort -u | tail -1
```

## Why this is the harder half

`mkdir(2)` gives atomicity within **one filesystem view**. Parallel agents in
this repo do not share one view — they work in `git worktree`s on separate
branches by design, because that is the mitigation for the *other* recurring
failure (a bare `git commit` sweeping another session's staged work). The two
mitigations are in tension: worktrees make commits safe and allocation blind.

This is the same shape as tonight's other measurement findings — a shared mutable
surface (`zig-out/bin/duo`, a fixed `/tmp` path, one build cache) makes a number
somebody else's. Here the surface is not shared *enough*.

## Fix directions, none obviously right

1. **Scan all refs, not the worktree.** The loop above, run inside the
   allocator. Cheap, and catches unmerged branches — but not a branch that
   exists only in another worktree and has never been pushed.
2. **Reserve in a location outside the branch** — a single reservation directory
   in the repo's common git dir, which every worktree shares. Restores one
   filesystem view without giving up worktrees. Probably correct.
3. **Make the number not matter** — content-addressed gap ids, with the numeric
   name a rendering. Largest change; removes the class rather than guarding it.

Whichever lands, the acceptance test is the reproduction above: allocate from
two worktrees on two branches and get two distinct numbers.

## Note for whoever fixes it

Do not weaken the process-level atomicity to get branch-level coverage. The
12-process measurement is a real property and the positive control behind it —
a hand-made reservation with no gap file is SKIPPED, proving the ledger gates
rather than the scan — is worth preserving as-is.
