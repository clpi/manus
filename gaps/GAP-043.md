# GAP-043 — `std.script`'s ergonomic aliases are all nil at runtime

**Filed** 2026-08-08. **Status** open. **Cited at** `scripts/init_build_smoke.id`
(`_present`), `lib/std/script.id` (the "Ergonomic aliases" block).

## What happened

`lib/std/script.id` closes with an export table that re-exports thirteen
filesystem functions under shorter names:

```
    exists = fs_exists,
    is_file = fs_is_file,
    is_dir = fs_is_dir,
    read = fs_read,
    ...
```

Every one of those alias names returns **nil** when called through the module.
The original name works. Measured, same binary, same process:

| call | result |
|---|---|
| `std.script.fs_exists("/etc/hosts")` | `true` |
| `std.script.exists("/etc/hosts")` | `nil` |
| `std.script.fs_is_file("/etc/hosts")` | `true` |
| `std.script.is_file("/etc/hosts")` | `nil` |
| `std.script.fs_read("/etc/hosts")` | file contents |
| `std.script.read("/etc/hosts")` | `nil` |

## Why it is worse than a missing function

`nil` is falsy, so `if not std.script.exists(p)` is taken for EVERY path —
present or absent alike. A gate written against the ergonomic name to assert a
build artifact into existence reports the artifact missing whether or not it was
built, and reports it with total confidence. That is the "confident zero" shape:
no error, no diagnostic, a plausible answer, and it is wrong on every input.

This cost real time on the `duo init` work: the first draft of
`scripts/init_build_smoke.id` used `std.script.exists(bin)` and reported
"no duo binary at …/zig-out/bin/duo" for a 7.3 MB binary sitting at exactly that
path. The gate looked like it had caught something.

## Mechanism

It is the named-function-as-value gap, not a table bug. A function declared at
module scope and then placed in a table under a DIFFERENT key does not survive
lowering. Reduced to the smallest case the failure is not even silent — it is a
hard C error, which is what shows the shape:

```
truth: bool = ()
    true
end
{ truth = truth, other = truth }
```

```
/tmp/duo_main.c:5636:9: error: passing 'bool ()' to parameter of
    incompatible type 'lua_Value'
```

The compiler is passing the function DESIGNATOR where a boxed value is expected.
In `script.id` the same construct does not reach the C compiler as an error; it
degrades to nil instead. Two different outcomes for one cause is itself worth
noting — the loud form is the one that found the mechanism.

## What to do

Two options, in preference order:

1. Fix the lowering so a module-scope function can be exported under a second
   name. This is the same root as the closure-capture gap and fixes the class.
2. If (1) stays out of reach, replace the alias block with real forwarding
   functions (`exists(p: str): bool` → `fs_exists(p)`). That is a Duo-source
   repair and needs no compiler change.

Do NOT simply delete the aliases: the names are ergonomic and the next author
will re-add them the same broken way.

## Positive control for any fix

Nothing in the tree calls the alias names today — `grep -rn` over
`scripts/ tools/ lib/ examples/ ext/` for `script.exists(`, `script.read(`, … is
0. So a fix cannot be validated by "the gates still pass"; it needs a fixture
that calls an alias and asserts the VALUE, and a negative control showing that
fixture fails against a binary without the fix.
