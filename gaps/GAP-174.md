# GAP-174 — a multi-statement `if`/`else` branch loses its value in every non-direct realization

**Status:** OPEN · **Filed:** !2026-08-15
**Priority:** P0 · **Kind:** correctness
**Found by:** GAP-173 re-measurement, `direct`-vs-`c` then `direct`-vs-`wasm` corpus differential
**Files:** src/wasm_backend.zig,src/codegen.zig,density/sieve.id (idol-native),density/perf/sieve.id (idol-native)

## Obligation

An `if`/`else` used as a VALUE loses that value whenever the branch that decides
the answer holds MORE THAN ONE STATEMENT. It compiles, it runs, it prints
`ok compile`, and the function answers `0` — or, worse, the OTHER branch's
constant. No diagnostic. `law.fallback.zero`.

**The direct backend is CORRECT. Every other realization measured is wrong**, and
the two wrong ones are wrong identically, row for row, which is what says the
defect is upstream of both emitters rather than a coincidence in either.

    --backend direct    CORRECT   (and this is what plain `idol run` selects)
    --backend wasm      WRONG     LIVE at idol 24b6c21c
    --backend c         WRONG     measured live at idol 9b5d54d5; the spelling
                                  was RETIRED mid-measurement (docs/rulings.md,
                                  "NO C BACKEND, PERIOD"), so this column is now
                                  unreachable from the CLI — the defect was
                                  DELETED OUT OF REACH, never fixed

## Minimal reproduction (a three-line function body)

```
f: i64 = (n: i64)
    if n < 2
        0
    else
        answer = 7
        answer

main: i64 = ()
    f(11)
```

    idol run --backend direct                        -> exit 7   CORRECT
    idol compile --backend wasm --target wasm32-wasi ; wasmtime -> exit 0   WRONG
    idol run --backend c        (at 9b5d54d5)        -> exit 0   WRONG

`idol check` is clean. Measured on the vendored `idol-native/bin/idol` at HEAD
`24b6c21c` and on a clean isolated build of `9b5d54d5`, with a fresh build-cache
key both times.

## The boundary, measured

`direct` is the CORRECT column throughout; `wasm` is the current wrong one and
answered identically to the retired `c` on every row.

| body of the branch that decides the answer | direct | wasm | |
| --- | ---: | ---: | --- |
| `7` — one expression | 7 | 7 | ok |
| `7 + 0` — one expression, compound | 7 | 7 | ok |
| `answer = 7` then `answer` | 7 | **0** | WRONG |
| `answer = 7` then `answer + 0` | 7 | **0** | WRONG |
| `a = 1`, `b = 6`, then `a + b` | 7 | **0** | WRONG |
| the multi-statement arm is the `if`, not the `else` | 7 | **0** | WRONG |
| `answer = 7` then `return answer` | 7 | 7 | ok |
| early `return` then a fall-through tail, no `else` | 7 | 7 | ok |

So it is not about `else`, not about the tail being a bare name, and not about
how many bindings precede it: **one statement before the tail is enough, in
either arm.** An explicit `return` inside the branch avoids it entirely, which
is why so much of the corpus never met it.

**The failure is not uniformly zero, and anyone grepping for `0` will miss half
of it.** With the other branch taken, the same function returns the value of the
branch that was NOT taken:

```
f: i64 = (n: i64)
    if n > 0
        7
    else
        answer = 9
        answer
```

    f(-1)   direct -> 9   CORRECT
    f(-1)   wasm   -> 7   WRONG — the arm that did not run

## Blast radius as measured

Differenced `--backend direct` against `--backend wasm` (run under `wasmtime`)
over every `.id` under `idol-native` (maxdepth 2) and `idol/examples`
(maxdepth 2) — 526 files, `examples/boring/roman.id` excluded as
nondeterministic by a separate defect. 179 files were accepted by BOTH
realizations; **34 of those 179 disagree**, 13 of them on stdout.

The headline is a benchmark row, and its truth was computed outside both
compilers:

    idol-native/density/sieve.id     wasm: count=2     last=3
                                   direct: count=2262  last=19997
                                    truth: count=2262  last=19997

2262 is π(20000) and 19997 is the largest prime below it, recomputed in Python
from the file's own algorithm. `prime`'s deciding arm is multi-statement, so
`answer` never leaves the branch. Under the retired C backend the same file said
`count=9998` — at `limit = 30` it printed `p 9  p 15  p 21  p 25  p 27` beside
the real primes, i.e. **it called every odd number prime**; under wasm the same
defect lands on the other side and it finds two. Same cause, opposite direction,
both silent. `density/perf/sieve.id` is the same program at `limit = 200000`.

**A density/perf benchmark row has been measurable through a realization that
computes the wrong answer.** `HPLS.md` §68 in its sharpest form: a workload
whose verification observer never ran.

The other 11 stdout divergences are NOT this defect and are listed so nobody
re-derives them: 2 are the `known_divergent/` residents already recorded there;
4 are `examples/shc/*` world access (`cwd`, `env`, `arg`, `path`) which WASI
does not have and which should refuse rather than answer `nil`;
`native_differential/io_read_path.id` and `seed_test.id` trap under wasm (exit
134); and `examples/table/div/sign.id`, `examples/table/divsign.id` and
`examples/cbackend/modsign.id` are the floored-modulo ruling, which has landed
in `direct` — it now matches those files' `# expect:` lines — and has NOT landed
in wasm. That last group belongs to the modulo lane, not here, but it is the
same shape of finding: **one law, two realizations, and only one of them was
migrated.**

Of the 21 exit-status-only divergences, 6 are the file-scope-tail convention,
3 are gates whose count is lower under wasm (`gate/numeric.id` 53 vs 32,
`gate/width.id` 90 vs 89, `gate/match.id` 17 vs 15 — the same
one-law-two-realizations shape), and the remaining 12 exit 1 under
`wasmtime`, which is a WASI entry-point question and not evidence of a
miscompile.

## Why nothing saw it

- `--backend auto`, which is what plain `idol run` means, resolves to the direct
  backend and REFUSES rather than falling back. Measured on
  `examples/anchor/bare.id`: `auto` and `direct` emit the identical `DNB011`, and
  at 9b5d54d5 only an explicit `--backend c` compiled it. So the everyday path
  never reaches the broken lowering, and `density/sieve.id` is correct under
  `idol run`. **The defect is only reachable by asking for a second
  realization — which is exactly what nobody does except a differential.**
- The direct backend refused 339 of 521 corpus files at 9b5d54d5 and 339 of 526 at HEAD (187
  accepted; the wasm backend accepts 343, so each realization compiles a
  DIFFERENT subset and the intersection where a differential is even possible is
  179 files). For those there is no second column at all, so this defect could be
  live in one of them with nothing to detect it. That number is UNKNOWN and
  nothing in this tree measures it.
- The retirement of `--backend c` removed one of the only two instruments that
  could see this class. **`gate/expect.sh`'s entire design — "the one detector in
  the tree that can convict BOTH backends at once" — was built on a two-backend
  differential that no longer has two backends.** It still shells out to
  `compile --backend=c` for one of its two columns, so at HEAD that column is
  uniformly `dead`. MEASURED on `idol-native`, same command, same day:

        before the re-vendor    expect gate: 11 verdict(s) moved over 120 file(s)
        after  the re-vendor    expect gate: 109 verdict(s) moved over 123 file(s)

  **108 of the 109 are `[c]` rows**, and not one of them is about a program.
  A gate that is 90% red for a reason unrelated to a program's correctness is
  a gate that will be ignored, which is the state a defect needs to survive in.
  Repointing that column at `--backend wasm` restores the instrument, re-pins the
  ledger against something that exists, and would have caught this defect with
  nobody looking for it — the two sieves are already in that corpus.
  (The three GAP-173 fixtures are pinned `pass pass`, measured on a compiler that
  still had both realizations, deliberately: pinning them `dead` would have made
  them the only three rows re-pinned and hidden them inside the wave of 105.)

## Acceptance

- The reproduction above answers 7 under `--backend wasm`, and all five WRONG
  rows of the table agree with their `direct` column.
- `density/sieve.id` prints `count=2262 / last=19997` under `--backend wasm`.
- Root-caused in the lowering the wasm and C emitters SHARE — the identical
  row-for-row signature says it is not in either emitter — and not by rewriting
  the corpus to add `return`: "the current compiler cannot do X" must never
  become "Idol should not permit X".
- A fixture with an `# expect:` line graded under every surviving realization, so
  a re-regression is a moved verdict and not a silent one.

## Open face at `832c089a`

Commit `9e59d168` did not preserve the branch value. In the
`saved_answering`/`!allow_return` path, `lowerBlockReturns` calls
`lowerExprCons(ctx, tail, .single)` and discards the returned operand. This
preserves evaluation of the tail, but no fact carries its value through the
branch join to the enclosing result demand. GAP-174 therefore remains open
until shared lowering preserves that operand and the surviving realization
observes the five boundary rows above.

The executable check is currently blocked before lowering at `832c089a`:
`zig build unit-test` reaches the claimed parser frontier, where repository
fixtures are rejected and `tools/node/dev/parser/artifact` fails. That parser
work is separately owned; it is not a GAP-174 repair and must not be bypassed
by marking this obligation closed.

## Open face beyond `08fb1d5c6`

The first repair carries the five originally measured scalar tails into the
answer.  The next bounded face is composition: a multi-statement deciding arm
whose own tail is another value `if`.  The outer arm must preserve the inner
arm's selected value through both joins; observing only the outer scalar-tail
rows does not establish that.

The Wasm execution fixture now includes that nested-tail shape and requires an
answer of 7 through shared DNIR lowering and the surviving non-direct
realization under Wasmtime.  The direct column remains the oracle recorded in
`idol-native/gate/nest.id`; this land does not remeasure the five rows already
established by `08fb1d5c6`.

At this revision the fixture compiles into the Zig test binary, but its run is
blocked before lowering by the same separately owned parser frontier above:
the five existing rows and the new row all stop at their first declaration.
That is not evidence against the branch-value repair, and it is not permission
to close GAP-174.  The nested observation stays executable and red until the
parser owner restores fixture ingress; no parser bypass is part of this land.

## Open face beyond `8353391c4`

The nested-tail row above reaches the deciding arm through a plain `else`.  It
does not cross an `elseif` chain join.  The next bounded composition face is a
multi-statement deciding `elseif` arm whose own tail is another value `if`: the
selected value must survive the inner join and the chain join before it reaches
the enclosing answer demand.

The Wasm execution fixture now includes that shape and requires an answer of 7.
The earlier scalar rows and plain-`else` nested row remain unchanged; this row
adds one distinct control composition rather than remeasuring them.  GAP-174
remains open until the surviving non-direct realization executes this observer
and preserves the selected value.
