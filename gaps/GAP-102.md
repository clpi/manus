# GAP-102 — a descriptor-application binding is taken as the tail, so DEMAND-RETURN returns the wrong statement

**Status:** CLOSED 2026-08-09 · **Filed:** 2026-08-09
**Law:** §0.7 DEMAND-RETURN · `law.apply.one` · `law.construct.zero`
**Fixture:** `examples/tail_demand_call_proof.id` · **Gate:** `zig build semantics-gate` (tier-0)

## CLOSED — and the diagnosis was one layer past where the gap pointed

The gap named `blockTailResultWithDemand`'s transparent-trailer stripping. The
stripping was innocent. The DISCRIMINATOR was: `isDiscardCall` called EVERY
call a discard, so the walk-back fired on any body whose final expression was a
call — and the parser promotes *any* trailing call into `blk.tail_expr`. There
was no shape in the AST separating `print value` (an effect) from `d2(p)` (the
answer), so the resolver preferred the preceding statement in both cases.

### The gap understated the harm: it is also a SILENT WRONG ANSWER

Reducing the repro past the descriptor — `p = 5` instead of `p = Point{…}` —
takes the types out of it, and the program then COMPILES and answers wrong:

```duo
t(): i64
    p = 5
    d2(p)          -- 25
```

| | before | after |
|---|---|---|
| `--backend=direct` | **`5`** | `25` |
| `--backend=c` (oracle) | `25` | `25` |

The type error the gap recorded was the visible half. `dnir_lower`'s
`tryEmitTailDemandReturn` reads the same resolution and *returned the binding*,
so the default backend disagreed with its own oracle. Nothing had run the pair.

### Both acceptance criteria, verbatim from "What closes it"

```
main(): i64 · p = Point { x = 3, y = 4 } · d2(p)
  → exact.id:9:7: error: return type mismatch: expected 'i64', got 'f64'
    — the TAIL is named, at line 9, as f64. It was line 8, as 'Point'.
main(): f64 · p = Point { x = 3, y = 4 } · d2(p)
  → compiles, exits 25
```

The second is the positive control the gap asked for, and it passes, so the
error did not merely move.

### The repair

`src/tail_result_demand.zig` — the discriminator is VOID-NESS, not call-ness.
Only a callee known to yield nothing is transparent; everything else is the
body's value, per §0.7. `print` is the built-in floor and `installVoidOracle`
lets a caller holding declared return types widen it. The walk-back the effect
case is owed (`value = x * 2` then `print value` yields `value`) is preserved
and is a row in the fixture.

### The FIXTURE was also wrong, and this is not the forbidden repair

`examples/pass7/explain_smoke.id` declared `main(): i64` over a body whose
value is `distance2(p)`, an `f64`. That is the gap's OWN first row — the one it
says "must be diagnosed AS f64". The fixture is now `main(): f64`, which is the
gap's own positive control. **No `return 0` was added**; §0.7 still deletes the
trailing return. The declared contract was made true, not the body made silent.

## Repro

```duo
Point: @{ x: f64, y: f64 }

d2(p: Point): f64
    p.x * p.x + p.y * p.y
end

main(): i64
    p = Point { x = 3, y = 4 }
    d2(p)
end
```

```
exact.id:8:15: error: return type mismatch: expected 'i64', got 'Point'
```

**Line 8 is the BINDING. Line 9 is the tail.** The body's value is its final
expression's (§0.7), so the return under test is `d2(p)` — and the diagnostic
never mentions it. The compiler is treating the descriptor application on line 8
as the returned value.

## What it is NOT — each ruled out by measurement, not by reading

| hypothesis | test | result |
|---|---|---|
| the space in `Point { … }` splits the application | same program with `Point{ … }` | **both answer 25.** Space is irrelevant |
| integer literals into `f64` fields | `x = 3` vs `x = 3.0` | **identical error.** Not a coercion |
| `d2` returning `f64` against `main(): i64` | add `print(d2(p))` + `return 0` | **compiles and runs, prints 25.** Not the mismatch it names |

The last row is the decisive one: with an EXPLICIT `return 0` the same program is
fine. The defect only appears when the tail is implicit — so it is in tail
selection, not in construction, not in typing.

## Why it appeared now

`point{ … }` began CONSTRUCTING today (gap[092], `a5ab68d` + `31819a2`). Before
that, a descriptor application did not produce a descriptor-typed value, so a
binding of one could not be mistaken for a typed return. The feature is correct;
it exposed a tail-selection bug that was unreachable before it.

This is the third instance today of the same shape — a repair landing correctly
and revealing the next defect behind it (`global-decl-module-path` → the native
precheck; the three owed gap[092] sites → the fourth site the measurement found).
Worth naming as a pattern: **a correct fix that turns a gate red is usually
uncovering, not breaking.**

**Do not repair this by adding `return 0` to the fixture.** The fixture is

here, not the corpus.

## What closes it

Tail selection must pick the body's FINAL expression when the preceding
statement is a binding whose value happens to be descriptor-typed. Check both:

```duo
main(): i64
    p = Point { x = 3, y = 4 }
    d2(p)              -- tail is d2(p), f64, and must be diagnosed AS f64
main(): f64
    p = Point { x = 3, y = 4 }
    d2(p)              -- must compile
```

The second is the positive control: if only the first is fixed, the tail is
still not being read — the error just moved.
