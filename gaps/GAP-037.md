# GAP-037 — the branch tip did not build; `DUO_ROOT` does not govern `std.*`

**Status:** RESOLVED for the build; open for the resolution rule
**Filed:** 2026-08-07 · **Sites:** `scripts/census/probe.duo`

> **UPDATE — obstruction 2 is fixed and obstruction 1 was overstated.** The
> branch tip now builds (one enum tag declared, see below), and building a
> binary *from the worktree* makes that worktree's `lib/` live: the binary
> resolves the stdlib **relative to itself**, not from `DUO_ROOT`. So stdlib
> work IS testable from a worktree — you need your own binary, not a different
> checkout. With that, the GAP-035 parser fix landed and
> `scripts/census/selfhost.duo` went **6/8 → 8/8** with the 256-file corpus walk
> unchanged at 256/256.
>
> What remains open is only the ergonomic half: `DUO_ROOT` is accepted and
> ignored for `std.*` resolution, which is a silent trap — a run that should
> fail to resolve instead reports the *installed* stdlib's behaviour. Either
> honour it or reject it.

## Two independent obstructions, both hard

### 1. `DUO_ROOT` does not control `std.*` resolution

The binary loads the standard library from **its own installation path**, not from
`DUO_ROOT`. Proof — the same program, same output, with the variable pointed at
nothing:

```
DUO_ROOT=/nonexistent/path duo run scripts/census/probe.duo
plain:   (program (descriptor p (desc x i64)))
default: (program (descriptor p (desc x i64 (item (error)) (item 42))))
```

A run that should have failed to resolve `std.compiler.parser` instead produced
byte-identical output. So **an edit to `lib/std/**` inside a worktree is invisible
to the binary**, and any measurement of it silently reports the *installed*
stdlib's behaviour. This also explains an earlier oddity: `req "privlib"` failed
with `DUO_ROOT` set to the directory containing `privlib.duo`.

Every census in `scripts/census/` is unaffected — they measure the installed
stdlib deliberately, which is the live one. What is affected is *changing* it.

### 2. The live branch's committed state does not compile

The obvious workaround — build a binary from the worktree so it resolves the
worktree's `lib/` — fails:

```
src/native_backend.zig:1539:14: error: enum 'duo_native_ir.Op' has no member
                                       named 'print_value'
```

`native_backend.zig` references `print_value`; `duo_native_ir.zig` does not
declare it. Measured across trees:

| tree | `print_value` in `duo_native_ir.zig` |
| --- | --- |
| `canonical-to-relation` (committed) | **0** |
| the shared checkout's working tree | **2** |

The declaration exists only as an **uncommitted edit in another session's working
tree**. So the branch tip is not buildable by anyone who does not already have
that session's unsaved state, and a fresh worktree cannot produce a compiler.

## Consequence for GAP-035

The GAP-035 repair is Duo work — the self-hosted parser already accepts 6 of 8
forms — but it cannot be **verified** from here, so it is not shipped. An
unverified parser change is exactly the class of edit that breaks a corpus
silently, and the honest move is to leave it out and hand over the diagnosis.

## The diagnosis, so the fix is one edit for whoever can build

`scripts/census/probe.duo` prints the projection rather than a pass/fail, which
localises the failure precisely:

```
p: { x: i64 = 42 }
  → (desc x i64 (item (error)) (item 42))
```

In `proj_desc_body`, the `keyed` arm consumes `x` and `:`, projects the shape,
and returns to the loop — which finds `=` where it expects a comma or `}`, takes
the `else` arm, and stalls into `(error)`. The `=` is never claimed by the arm
that owns the slot. The proposed patch, immediately after the keyed arm's value
projection:

```duo
            -- `x: i64 = 42` — a slot carrying BOTH its shape and a default.
            if lexer.peek(lx).kind == token.KIND_ASSIGN
                d = lexer.next(lx)
                s = s .. " (default " .. proj_expr(lx) .. ")"
            end
```

Untested, for the reasons above. The sibling case (`next = () :peek()`) projects
`(ret peek) (lambda (params) (error))` — the leading `:` is read as a return of
the name `peek` rather than a sibling call, so that one needs a production in the
expression parser, not a patch to this loop.

## The fix, in order

1. Commit whatever declares `Op.print_value` so the branch tip builds.
2. Give `DUO_ROOT` (or an explicit flag) authority over `std.*` resolution, so a
   worktree can test its own stdlib. Without this, `lib/std` is effectively a
   single-writer file set no matter how many worktrees exist.
3. Then the GAP-035 patch above is verifiable in one run of
   `scripts/census/selfhost.duo` (currently 6/8; it should reach 7/8).
