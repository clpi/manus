# GAP-113 — an unknown relation on a subject silently answers nil; the same mistake in the denied spelling diagnoses

**Status:** OPEN (P0, silent wrong answer) · **Filed:** 2026-08-09
**Law:** B-12 (structural nil is UNWRITTEN) · B-14 (an unconsumed failure
DIAGNOSES; silent loss is unexpressible) · FACE-CALL (§0.5) · H-8
**Found by:** the standard-basis lane, verified independently here.

## Measured

```duo
s = "abcd"
r = s:zzznotarelation()     -- ok compile, runs, r is nil, NO DIAGNOSTIC
print("survived")           -- prints
```

and the control, one character of syntax away:

```duo
r = zzznosuchfn(1)
  -> error: 'zzznosuchfn' is neither a descriptor nor a callable
```

**The compiler HAS this diagnostic. It is wired to the operation-first spelling
and missing from the subject-first one** — which is the spelling FACE-CALL
mandates and the deny list requires.

`s:len()` answers 4, so relations that exist do resolve. It is only the *absent*
case that goes quiet.

## Why this is P0 and not an ergonomics complaint

**Every typo in a method call silently becomes nil.** `xs:lenght()`,
`p:normalise()`, `t:instert(v)` all compile, run, and answer nil — and nil then
propagates into arithmetic as 0 or into a comparison as false. The program does
not stop; it produces a different answer.

That is precisely what the law forbids twice over:

- **B-12**: structural nil is UNWRITTEN. A relation that does not exist should
  not be able to hand back a nil the source never wrote.
- **B-14**: an unconsumed failure position DIAGNOSES — bind, route, or drop BY
  NAME. **Silent loss is unexpressible.** An unknown relation is the purest
  possible failure position and it is being lost silently.

## It also invalidates a class of measurement

The basis lane's first probe pass read all sixteen candidate relations as PRESENT
because each call compiled. They were not present; the calls were nil. The pass
had to be rebuilt to assert a VALUE with the negative control checked first.

**Any probe in this repo that tests for a relation's existence by compiling a
call to it is measuring nothing.** That is worth stating plainly because this
session has already found four instruments that produced their own answers.

## The fifth instance of one pattern

| | works / checked | canonical form |
|---|---|---|
| ambient sigil (gap[107]) | legacy `@c.emit` | `@{…}`, `x@rel` |
| application (gap[110]) | `point{x,y}` | `p: point = {x,y}` |
| ambient fields (gap[107]) | `.x` | bare `x` in a descriptor home |
| pipeline (gap[111]) | `std.iter.map(xs,f)` | `xs:map(f)` |
| **unknown-name diagnostic (here)** | `f(x)` diagnoses | `x:f()` is silent |

The first four are canonical forms that do not work. **This one is worse: the
canonical form works and is unprotected.** A user writing the mandated spelling
gets less safety than one writing the denied spelling.

## Repair

The resolution site for `subject:relation(args)` must diagnose when no relation
of that name is applicable to the subject's descriptor — the same answer
`zzznosuchfn` already gets, in the same words where possible.

**The check is not "does the name exist somewhere".** FACE-CALL means the
relation is selected by subject, so the diagnostic must say what was searched:
the subject's descriptor, its representation edges, and the ambient graph. That
is also what makes it a repair edge rather than a rejection — the message can
name near relations that DO apply.

**Do not fix this by making an unknown relation trap at runtime.** It must be a
compile-time diagnostic; a runtime trap turns a silent wrong answer into a late
crash and still ships the typo.
