# GAP-075 — `std.fs.remove` reports success AND leaves the file on disk

**Status:** OPEN · **Filed:** 2026-08-08
**Severity:** SILENT WRONG ANSWER, and the failing direction is the dangerous
one — every caller believes cleanup happened.

## The defect

```duo
main = (): i64
    ok = std.fs.remove("/nonexistent/path/that/cannot/exist.txt")
    print("remove missing -> {ok}")
    ok2 = std.fs.remove("<a real file>")
    print("remove real    -> {ok2}")
    0
```

```
remove missing -> true
remove real    -> true
```

…and the real file is **still on disk afterward**, still readable, still its old
contents. Verified with `ls` immediately after.

So there are TWO defects stacked, and either alone would be bad:

1. **The return is unconditionally `true`.** The body is
   `os.remove(p) ~= nil`, and `false ~= nil` is **TRUE** — so the failure value
   and the success value both report success. There is no input that makes this
   function answer `false`.
2. **The removal does not happen** for a path that exists.

Defect 1 is what hides defect 2. A caller that checks the return gets `true`,
concludes the file is gone, and never looks.

## Why `false ~= nil` is the whole of defect 1

This is the `~=`-against-`nil` idiom used as a success test. It works when the
callee returns a value-or-nil. It is silently wrong when the callee returns a
BOOLEAN, because `false` is a value and `false ~= nil` is true. The predicate
tests *presence*, and the author read it as *truth*.

Grep the tree for the same shape before assuming this site is unique — the
idiom is not rare and the failure is invisible at every one of them.

## Blast radius

Anything that cleans up after itself and believes it did. Note the interaction
with **gap[070]**: a trailing shell call at the end of `main` overwrites the
process exit status, and it "hit both gates that `mktemp` and clean up — i.e. it
targets exactly the files written to prevent false greens." This is the same
population. A gate that removes its scratch directory, is told `true`, and exits
on a status it never set is wrong twice for two unrelated reasons.

## How it was found

The MCP revival needed a claim-release path and declined to use `std.fs.remove`
after testing it by value. Independently reproduced here, which is how the
second defect surfaced — the original report was "returns true unconditionally";
checking the filesystem afterward showed the file had not been removed at all.

That is the lesson: **verifying the return value was not enough.** The return
was a lie about an operation that also did not happen, and only looking at the
filesystem separated the two.

## Fix

`remove` returns `t | error` per §0.6 (B-12: the structural nil is UNWRITTEN),
and the removal is verified by the syscall's own result, not by `~= nil` over a
boolean. Fixture asserts BOTH directions by value — a missing path must answer
the failure side, and a real file must be **absent from the filesystem**
afterward. A fixture that only checks the return would pass against the current
code for the missing-path case and prove nothing.
