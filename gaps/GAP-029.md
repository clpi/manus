# GAP-029 — `tonumber` returns 0 on non-numbers instead of nil

**Status:** open · **Filed:** 2026-08-07 · **Frequency:** 1
**Cited at:** `scripts/run_benchmark.duo` (`extract_times`)

## Repro

```
tonumber("Fibonacci(40)")   -- 0    expected nil
tonumber("Time")            -- 0    expected nil
tonumber("0.017439")        -- 0.017439   correct
```

## Why it mattered

Every "parse it and check whether it failed" idiom silently accepts garbage:

```
for word in words
    num = tonumber(word)
    if num != nil          -- ALWAYS true
        use(num)           -- uses 0 for "Fibonacci(40)"
        break
    end
end
```

In the benchmark harness this meant the first word of every timing line was
accepted as its time, recording 0. Combined with gap[028] it produced a suite
that declared C the winner of all 40 benchmarks.

This is the same family as the recorded `to(f64) never fails` behaviour: Duo's
string-to-number conversions do not signal failure, so the nil check that every
Lua-shaped program writes is dead code.

## Interim

Check the shape before converting; `string.match` is exact:

```
if string.match(s, "^%-?%d+$") != nil  -- integer
if string.match(s, "^[0-9%.eE%+%-]+$") != nil  -- numeric-ish
```

## Relation to the canon

Epoch 2 denies `tonumber(` outright; the canonical form is
`if n = s:to(i64)` — a binding condition whose failure is *observable*. That
form is the real fix: it makes the failure a value the caller must consume
(B-14 OBLIGATION) rather than a sentinel that reads as data. Until `s:to(i64)`
lands with failure semantics, the shape check above is the interim.
