# GAP-029 — the Duo parser rejects a receiver face in a return pack

**Status:** FIXED 2026-08-08 · **Filed:** 2026-08-07
**Scope:** `lib/std/compiler/parser.id` (SH-04 coverage) — the HOST parser
accepts the construct

## The defect

A receiver face as the first element of a comma-separated pack does not parse:

```duo
f: str = (b: str, n: i64)
    b:sub(1, n), nil        -- parse_status 1
```

Everything adjacent parses:

```duo
    string.sub(b, 1, n), nil    -- 0   namespace form, same pack
    b:sub(1, n)                 -- 0   face alone
    b:sub(n)                    -- 0   face, one argument
```

So it is the pair: **receiver face + pack position**. The host compiler accepts
all four, so this is Duo-parser coverage, exactly like gap[028].

## Narrowed: it is the BARE pack, not packs generally

    return b:sub(1, n), nil     0   explicit return handles it
    b:sub(1, n), nil            1   BARE pack — the implicit-return form
    string.sub(b, 1, n), nil    0   bare pack, namespace form
    b, nil                      0   bare pack, plain name

So `proj_return`'s comma loop is fine, and the bare-expression-statement path
has a comma loop too — the namespace and plain-name rows prove it. What breaks
is specifically a **receiver face as the first element of a bare pack**.

That points at the statement-level expression path: after parsing `b:sub(1, n)`
as an expression statement it does not continue into the comma, while it does
for `string.sub(...)` and for a bare name. The method-call parse is leaving the
cursor somewhere the comma continuation does not expect.

`proj_return` (lib/std/compiler/parser.id) is the working reference — its loop
is three lines and handles exactly this.

## FIXED 2026-08-08 — the rewind path was the one NAME arm without `tail_pack`

Not `is_lambda_head`, and not a face problem at all. `proj_stmt`'s NAME
dispatch has four arms, and three of them offer the comma continuation:

    NAME `(`   ->  tail_pack(lx, proj_expr(lx))
    NAME `.` / `[` / `,`  ->  proj_target_or_expr(lx)   (has its own comma loop)
    default    ->  tail_pack(lx, proj_expr(lx))
    NAME `:`   ->  proj_expr(lx)                        <- the gap

The `NAME :` arm is SPECULATIVE: `n: i64 = 5` and `obj:m(1, 2)` start
identically, so it consumes NAME and `:`, reads a type, and rewinds when no `=`
follows. The rewind then returned a bare `proj_expr`. That parsed
`b:sub(1, n)` correctly and returned with the comma still unread, and the block
loop rejected the statement it could not continue.

That is why every adjacent probe passed. `string.sub(b, 1, n), nil` and `b, nil`
never enter this arm (`.` and `,` route to `proj_target_or_expr`); `b:sub(1, n)`
alone has no comma to lose; `return b:sub(1, n), nil` goes through `proj_return`.
The face was incidental — it is only the thing that makes a statement start
`NAME :`.

Fix: `lib/std/compiler/parser.id` — the rewind returns
`tail_pack(lx, proj_expr(lx))`, the same continuation the other three arms use.

## Cited site — retired

`lib/std/crypto/tls.id:156` now reads `buf:sub(1, n), nil`, the last of the 370
`string.sub` sites to take the receiver face. Both parsers accept it: `duo
check` on the file is clean, and the corpus walk stays 256/256 with it
converted.


## Cited site (historical)

`lib/std/crypto/tls.id:156` is the only occurrence in lib/std. It is left as
`string.sub(buf, 1, n), nil` with a `-- gap[029]` citation while the other 369
`string.sub` sites converted to the receiver face.

## How it was found

The corpus-wide `sub` sweep dropped parser coverage to 255/256. The coverage
tool named the file (`REJECT .../crypto/tls.id`), two `:sub(` sites were
visible in it, and four probes separated the pack position from the face.

That is the bisect order gap[025] records as the cheap one — file, then site,
then reduce — and it cost one gate run plus four probes instead of the three
full regen-and-gate cycles the earlier attempts spent.

## Fix

Whatever handles the comma-continuation of an expression list in
`parser.id` needs to accept a `:`-invocation as an element. The host parser's
handling of the same position is the reference.
