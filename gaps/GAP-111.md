# GAP-111 — CHAIN-PREFER has nothing to chain: the canonical call form fails where the denied one works

**Status:** OPEN (measured) · **Filed:** 2026-08-09
**Law:** CHAIN-PREFER · CHAIN-BREAK (owner ruling 2026-08-09) · FACE-CALL (§0.5)
· §1 DENY LIST

## The ruling

> **CHAIN-PREFER**: when a value is produced only to become the semantic subject
> of exactly one following relation, canonical source forms a postfix `:` chain
> and removes the temporary binding.
>
> Postfix `:` is the only chain operator. Leading `:` is ambient-subject
> invocation, not implicit pipeline continuation.

with the canonical example:

```duo
users
    :map(.score)
    :take(n)
    :filter(positive)
```

## What works — the mechanism

```duo
r = n:double():bump()          -> 11
r = n                          -> 11
    :double()
    :bump()
```

**Postfix chaining works, one-line and multiline offside.** The chain operator
is implemented and the layout rule holds. That is the good half.

## What fails — everything it would chain

```
std.iter.map(xs, twice)     operation-first, on the §1 DENY LIST     ->  2
xs:map(twice)               subject-first, CANONICAL                 ->  type error
xs:take(2)                                                           ->  type error
xs:map(.s)                  field shorthand                          ->  no output
```

`map`, `filter` and `take` DO exist — in `lib/std/iter.id`, declared
operation-first with every parameter `any`:

```duo
map(list: any, fn_ref: any): any
filter(list: any, fn_ref: any): any
take(list: any, n: i64): any
```

So the pipeline vocabulary is reachable only through the spelling FACE-CALL
denies (`std.iter.map(xs, f)`), and unreachable through the spelling FACE-CALL
requires (`xs:map(f)`).

**CHAIN-PREFER cannot be canonical because the chain has nothing chainable.**
The canonical example in the ruling does not compile.

## This is the fourth instance of one pattern

| consolidation | works | canonical form | state |
|---|---|---|---|
| ambient sigil (gap[107]) | legacy prefix `@c.emit` | `@{…}`, `x@rel` | unparsed / a synonym for `.` |
| application (gap[110]) | `point{ x, y }` | `p: point = { x, y }` | breaks on read |
| ambient fields (gap[107]) | `.x` | bare `x` in a descriptor home | undeclared identifier |
| **pipeline (here)** | `std.iter.map(xs, f)` | `xs:map(f)` | type error |

**Across every consolidation the law asks for, the explicit or denied form works
and the canonical or inferred form does not.** That is not four bugs; it is one
shape, and it says the rulings describe the language's target rather than its
present.

Worth stating because it changes how the rulings should be read by anyone
implementing them: each is a specification of work, not a description of
behaviour, and a doc or website example written from the ruling will not run.

## Order

1. **`xs:map(f)` before CHAIN-PREFER.** A canonicalizer that rewrites temporaries
   into chains would produce source that does not compile. The subject-first
   reach must work first.
2. **The `any` parameters are the same blocker one level down.** `map(list: any,
   fn_ref: any)` forfeits every descriptor fact, so even when the call form
   works, fusion has nothing to fuse on and `xs:map(f):take(n)` cannot stream —
   which is the whole point of preferring the chain.
3. **Then CHAIN-PREFER as a canonicalizer rule**, with CHAIN-BREAK's four
   exceptions (multiple consumers, semantic name, effect/world boundary,
   operations targeting the original ambient subject) as its guard.

## Do not

**Do not implement CHAIN-PREFER as a formatter rewrite first.** It would delete
temporaries and produce chains that fail to compile, and the failure would look
like a formatter bug rather than a missing relation surface.

**Do not add `map`/`filter`/`take` as new native primitives on `str` or table.**
gap[106] records why: they belong to a SEQUENCE basis
(`at`/`iter`/`put`/`len`) and hand-writing them per descriptor is the thing the
basis measurement exists to delete.

## Note on a collision found in passing

`double = (v) …` fails with *"cannot combine with previous 'type-name'
declaration"* — `double` is a C type name. Same family as `read`/`write`/`open`
being unbuildable as identifiers. Not this gap's subject, but it cost a probe and
will cost the next person one too.
