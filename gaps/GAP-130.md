## Exact value-flow source of the loop moves

The `kernel` body is:

```text
local.get 0; const A; add; local.tee 0
local.get 1; local.tee 3; const B; mul; add; local.set 1
local.get 2; const -9; add; local.tee 2; br_if 0
```

`jit_compile` tracks only `ali_slot` and `ali2_slot`. Before `local.tee 3`, its
generic pre-materialization writes both pending aliases into fixed operand-stack
registers, then the `local.tee` arm copies the top stack register into local 3.
At loop termination, `local.tee 2` creates another alias but `br_if` cannot read
it; pre-materialization emits a move and the branch reads the stack register.
These are the observed loop-carried copies.

Adding a third alias channel would preserve the defect. The required fact is:

```text
semantic value -> current register(s) -> live uses
```

for every operand-stack value and local. `local.get` projects an existing value,
`local.tee` adds a binding/use without changing that value, and `br_if` consumes
the value in its current register. Materialization happens only where liveness
requires distinct storage; local 3 genuinely needs the old local-1 value after
local 1 is overwritten, while the temporary stack copies do not.

The same value graph exposes `add(mul(old-local-1, B), new-local-0)` as one
`MADD`, and preserves the signed value of `-9` long enough to select `SUB #9`
instead of materializing `0xfffffff7`. Implement this as ordinary Duon
value/control/realization facts shared with SHC. Do not extend the two-slot
cache, add a `hot_big` recognizer, or create a Wasm-only opcode/allocator.

The instruction budget is consequently concrete. Keep the one required copy
that preserves old local 1 in local 3; remove two alias flushes and the final
branch-feed move; replace `MUL; ADD` with `MADD`; replace constant materialize
plus `ADD` for -9 with `SUB #9`. The 15-instruction loop becomes approximately
9 instructions, matching the inspected Wasmtime loop. This is a falsifiable
closure target for the shared value/liveness realization, not a benchmark
timing guess.

## 2026-08-10 rejected signed-immediate prototype

An engine-local prototype correctly selected the unshifted AArch64 immediate
forms for `i32.add` and `i32.sub` with signed constants through 4095. A durable
Duon harness generated the four neighboring `-4095` and `-4096` modules; the
interpreter, JIT, and wasmtime agreed, fitted cases emitted 25 words, fallback
cases emitted 27, and deliberately wrong value and word-count controls failed.
The full matrix remained 126 `PASS` plus four `OK(void)` across 130 rows.

The prototype was nevertheless rejected and reverted. The decoder exposes raw
wire bytes and generated `OP_*` constants, not the production relation and
descriptor identity declared by the SHC application schema. Raw numbers,
diagnostic-name strings, table positions, ARM64 words, and local aliases would
all reconstruct or disguise meaning. The exact diff gate therefore correctly
blocked the two new generated-constant references under LAW-ONE.

The required order is now explicit: the Duon application owner must mint the
production relation and descriptor identity; the Duon Wasm boundary must decode
the wire byte into those application facts while retaining the byte only as
origin/provenance; then the JIT may select the realization from that identity.
Until that seam exists, the generic materialization path remains the correct
implementation.
