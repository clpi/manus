# GAP-130 — Duon WASM hot loop remains 18 percent behind wasmtime in generated code

**Status:** OPEN · **Filed:** !2026-08-09T21:08:48Z
**Priority:** P0 · **Kind:** perf
**Filed by:** codex-root
**Files:** tools/wasm/src/engine.duo,tools/wasm/bench/six.duo,benchmarks/wasm_rt/hot_big.wasm,docs/performance.md,gaps/GAP-072.md

Fresh value-checked six-runtime measurement on benchmarks/wasm_rt/hot_big.wasm with the actual `zig-out/bin/wasm-conform` and DUO_WASM_* contract: Duon 130 ms, wasmtime 110 ms, wasmer 121 ms, wart 131 ms, wasm3 735 ms, iwasm 713 ms (min of 5 interleaved; answers verified before timing). DUO_WASM_PHASES shows read ~22 us, walks ~2 us, executable allocation ~1 us, JIT compile ~110 us, while engine execution is ~128-134 ms: the 20 ms loss is generated-code execution, not startup or compilation. Machine dump shows the 900M-iteration kernel loop is about 15 ARM64 instructions: two-word materialization for add constant, three alias/local MOVs, two-word multiplier materialization, MUL+ADD, two-word -9 materialization, ADD, MOV, CBNZ. Wasmtime's explored kernel loop is about 9 instructions and uses MADD plus fewer moves. General opportunities are signed-negative add/sub immediate factoring, multiplication-add fusion, and authoritative value liveness/register allocation across local.tee and the loop back dependency. Do not add benchmark-name recognizers or another Ward-only opcode ontology. The durable workstream is graph/DNIR value identities and realization facts feeding the shared allocator; a narrowly proven general Duon JIT peephole is acceptable only with full 130-row conformance and adversarial neighboring kernels. Current engine source remains migration debt under canonical source law.

## Independent fixed-artifact reproduction

A second value-checked min-of-3 run used a private engine artifact rather than
the mutable shared output:

```text
engine source sha256  fa151f7c8cdb20cd0471fd71bdf5c3cb85bbd70cd15438193cb19a7f92e17d92
artifact             /tmp/duowasm-audit, 262800 bytes
hash2b run           Duon 3763 ms, wasmtime 3754 ms
hot_big _start       Duon 131 ms, wasmtime 112 ms, wasmer 120 ms, wart 131 ms
```

Answers were compared with wasmtime before timing. This independently confirms
the tie-scale `hash2b` result and a roughly 17 percent `hot_big` loss. It does
not establish trustworthy compiler-build timing: the shared compiler SHA-256
changed from
`23cf9eb6c66806c2f582c5a939f2fe23ebf3d56bb6d670d0c0427e59bd4087f5`
to
`04763304f862d85e0f30048ff70c138ad8a72ec216fb6257e3bda2fd67ee5a7d`
during the build/measurement window. The runtime comparison remains attributable
to the fixed engine artifact; the compile duration and compiler provenance do
not. Release evidence must isolate or content-address the compiler, output,
cache, and run before it can claim reproducibility.
