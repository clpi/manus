## Boundary

The current engine has not reached this boundary. Its tracked project-owned
`.id` implementation is still a standalone interpreter/JIT with private opcode
and stack machinery, standard-root dependencies, and runtime fallback. Those
are SOURCE-ZERO and convergence debt. The sections below state the shared-graph
admission target, not ownership already achieved by the live engine.

WebAssembly enters Idol as an exact foreign lawset. Decode and import produce
graph identities and facts carrying foreign origin, module identity, operation
semantics, descriptors, ABI, ownership, effects, failures, worlds, trust, and
provenance. Demand selects the needed work; realization selects interpreter,
native, foreign, target-specialized, or other lawful physical candidates.

There is one graph, demand system, realization system, provenance chain, and
machine architecture. WebAssembly does not create a permanent virtual-machine
ontology, second optimizer, opcode semantic kingdom, or private type system.
Compact opcode tables, dispatch ranges, stacks, decoders, register allocation,
and code caches may exist as physical implementation when demanded; none owns
semantic identity.

A foreign operation may satisfy a native relation only when equivalence is
witnessed for the demanded domain. Until then, preserve the exact foreign
lawset and symbol as provenance. Never flatten incompatible traps, numeric
behavior, memory rules, imports, failures, or host effects to gain a shared
name.

## Authority and distribution

Module access, files, clocks, random input, devices, network, process activity,
and imported host services require their admitted worlds. A package, source
path, import, or implementation location grants no authority.

ROOT-ZERO applies here as everywhere else. The standard distribution may
contribute implementations, laws, origin, trust, and evidence, but its package
tree supplies no native relation identity. Do not extend `std`, replace it with
another root, or expose an implementation strategy as the public semantic
operation when one relation and law suffice.

FACE-ZERO applies to migrated canonical source. Subject-held operations are
subject-first; static identities use named projection; square brackets mean a
genuinely computed key. Source shape never forces a table, linear-memory
access, branch, allocation, box, interpreter dispatch, or JIT strategy.

PREDICATE-ZERO preserves foreign and native law. Validation, capability,
presence, trap, and refinement states remain semantic facts or cases rather
than `is`, `has`, `can`, `exists`, sentinel, or unknown-as-false helpers.
Predicate-shaped foreign imports retain foreign provenance until an exact
mapping to native facts is witnessed.

## Source and migration

Canonical project-owned implementation uses `.id`. Existing project-owned
`.id` sources in this directory are SOURCE-ZERO debt and behavioral evidence,
not Idol idiom sources. For each retained behavior, identify the relation,
subject, foreign law, worlds, effects, outcome, demand, and realization;
migrate it semantically into `.id`, prove it, and delete the old source. Delete
obsolete or duplicate implementations rather than archive them in-tree.

Compiler-forced monoliths, manual opcode ladders, sentinel outcomes, silent
fallback, foreign-call wrappers, and implementation-qualified APIs are debt,
not patterns. Record a removal gap when compiler capability blocks the canonical
form. Do not add a host-language subsystem to improve a boundary Idol must own.

Physical tool, environment, or artifact names containing `duo` are bootstrap
aliases and deletion targets only. Foreign `.wasm` and `.wat` files are test or
interchange inputs, not canonical Idol source.

## Evidence

Obtain current state from the checkout, `docs/bootstrap.md`, live gaps, and
fresh serialized runs. The focused correctness proof is the repository
`wasm-test` build step under the shared build lock. It must compare semantic
results by value with an identified external oracle, cover each demanded entry
and realization shape, and include positive and negative controls. Transport
completion, process exit, non-sentinel output, or one successful realization is
not conformance evidence.

Performance evidence is admitted only after correctness for the same workload.
It records the exact revision, dirty state, machine, target, oracle, input,
selected realization, fallback/refusal reason, repetitions, and known
unsupported or divergent cases. Report decode/import, compile, instantiate,
startup, steady execution, memory, runtime footprint, artifact size, and
end-to-end latency separately. A throughput gain may not hide cold-start,
compiler, memory, or artifact regressions.

Every zero needs a positive control and every oracle needs a negative control.
Every run uses private mutable artifacts. A silent fallback or evidence another
run can overwrite is a failed proof.
